# Sample requests: shipment exceptions

This agent receives business events rather than chat prompts. The .NET, Python and Node.js implementations accept the same requests on port `5168`, so the PowerShell HTTP examples below work with any stack. We also use the same contract for the local simulation and the Entra-authenticated path, changing only how we obtain the bearer token.

## Submit one event

Start the service and acquire a caller token using [Phase 0](3.Runbook.md#phase-0-run-the-starting-point) or [Phase 1](3.Runbook.md#phase-1-protect-the-webhook-with-entra). In the caller terminal:

```powershell
$body = @{
    sourceEventId = "SAP-SHIPMENT-20260907-001"
    orderId = "ORDER-1042"
    delayHours = 12
} | ConvertTo-Json
$headers = @{
    Authorization = "Bearer $env:S2S_CALLER_TOKEN"
    "X-Correlation-ID" = "shipment-1042"
}
$response = Invoke-RestMethod -Method Post -Uri "http://localhost:5168/api/shipments" `
    -Headers $headers -ContentType "application/json" -Body $body
$response
```

We should get `replayed=false`, a run ID, the supplied correlation ID, an operations summary, and two identifiers prefixed with `stub-`. Those identifiers don't represent real channel messages or ITSM tickets. In default mode, the summary also says it is a local simulation.

## Retry without creating another notification

```powershell
$retry = Invoke-RestMethod -Method Post -Uri "http://localhost:5168/api/shipments" `
    -Headers $headers -ContentType "application/json" -Body $body
$retry.replayed
$retry.result.runId -eq $response.result.runId
```

Both expressions should be `True`. The second request returns the saved result without invoking the model or any tool again. Removing the correlation header from a later retry generates a new attempt label, but its body still contains the original run's correlation ID.

## Reject a changed event

```powershell
$changed = @{
    sourceEventId = "SAP-SHIPMENT-20260907-001"
    orderId = "ORDER-1042"
    delayHours = 24
} | ConvertTo-Json
Invoke-WebRequest -Method Post -Uri "http://localhost:5168/api/shipments" `
    -Headers $headers -ContentType "application/json" -Body $changed -SkipHttpErrorCheck |
    Select-Object StatusCode, Content
```

We should get `409` with `payload_conflict`. The same source event cannot silently replace the payload of a completed run. A genuine new shipment update needs its own source event ID.

## Exercise caller rejection

```powershell
Invoke-WebRequest -Method Post -Uri "http://localhost:5168/api/shipments" `
    -ContentType "application/json" -Body $body -SkipHttpErrorCheck |
    Select-Object StatusCode, Content
```

This request omits the token and should return `401` with a correlation ID. The rejection log should identify the reason and use `unknown` for the caller. The [local checks for each stack](3.Runbook.md#step-0-2-run-a-batch-and-inspect-the-boundary-cases) also exercise wrong signatures, audiences, issuers and roles, plus tokens carrying delegated claims. An accepted token identifies the calling application, not a human user behind it.

For a real tenant exercise, use a separate test caller without the application-role assignment, or a token obtained through an approved delegated flow. Don't remove a production caller's permission just to generate a failure sample.

## Replay a machine-sized batch

Use the command for the stack running in our project, with `S2S_CALLER_TOKEN` set in the caller terminal.

### .NET

```powershell
.\Invoke-Replay.ps1 -Count 400 -BatchId "supplychain-night-01"
.\Invoke-Replay.ps1 -Count 400 -BatchId "supplychain-night-01"
```

The PowerShell harness sends 400 events, then repeats those same event IDs against the .NET host.

### Python

```powershell
uv run python -m app.replay --count 400 --batch-id supplychain-night-01
uv run python -m app.replay --count 400 --batch-id supplychain-night-01
```

The Python module sends the same event IDs and payloads, with the bearer token read from the environment.

### Node.js

```powershell
npm run --silent replay -- --count 400 --batch-id supplychain-night-01
npm run --silent replay -- --count 400 --batch-id supplychain-night-01
```

The Node.js script uses the same batch contract. Every harness refuses redirects and permits unencrypted HTTP only for loopback addresses.

In every stack, we expect 400 new runs followed by 400 replays. Before instrumentation, inspect `run.started`, `tool.ended` and `ingress.replay` logs. After onboarding, inspect the corresponding agent and tool traces. If we also added the runbook's optional business-event attributes and metrics, find the trace for `supplychain-night-01-1` and compare the run, attempt and replay counters with the harness output.

## Wrapping up
