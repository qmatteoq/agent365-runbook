# Service-to-service agent: supply-chain exceptions

A shipment slips overnight, and the integration middleware sends an event while nobody is signed in. We want the agent to read the order, check stock, write an operations summary, notify a channel, and open a ticket. When we review the run the next morning, we need to know which service called it, which business event started the work, and what the agent accessed under its own permissions.

This is the service-to-service, or S2S, path. We're going to start with a webhook in .NET, Python or Node.js and onboard it as a blueprint-derived Agent 365 agent, without adding Teams hosting or an agent user account.

## What we're starting with

We can choose any of these starting points. They expose the same HTTP contract on port `5168`, follow the same workflow and apply the same authorization and replay rules.

| Stack | HTTP host | Optional Azure OpenAI reasoning |
| --- | --- | --- |
| [.NET](0.Resources/Starting-point/dotnet/) | ASP.NET Core on .NET 10 | Microsoft Agent Framework |
| [Python](0.Resources/Starting-point/python/) | FastAPI on Python 3.12 or later | LangChain |
| [Node.js](0.Resources/Starting-point/nodejs/) | Express and TypeScript on Node.js 22 or later | LangChain |

None of the starting points includes Agent 365 packages, a blueprint token exchange, OpenTelemetry exporters or custom meters. Their structured JSON logs let us inspect the workflow before adding that instrumentation.

We can run the whole request path without a tenant. Local mode validates locally signed JWTs, checks an application role and caller allowlist, and uses deterministic substitutes for reasoning and all four tools. The response calls this mode `Stub`, because it isn't an LLM invocation. When we configure Azure OpenAI, the reasoning step uses a real model; the ERP, inventory, channel, and ticket tools remain stubs.

| Piece | Included in the starting point | Added while following the runbook |
| --- | --- | --- |
| Ingress | `POST /api/shipments`, bearer validation, app-only policy, caller allowlist | Separate webhook API and middleware registrations in Entra |
| Workflow | Four typed tool interfaces and stub implementations; optional model reasoning | Agent identity tokens when we replace a stub with an authenticated API |
| Retry handling | Bounded, process-local event ledger | Durable storage and downstream idempotency before deployment |
| Attribution | Caller, source event, correlation and run IDs in structured logs | Blueprint and agent identity attributes on logs and spans |
| Telemetry | JSON application logs | Agent 365 traces, with console or OTLP options and an optional custom metrics exercise |
| Replay | A 400-event harness in each stack | Comparison of new runs and duplicates; optional counters for operational reporting |

The shipped code is the starting point, not the result of onboarding. The [runbook](3.Runbook.md) uses shared skill prompts and identity steps, with parallel .NET, Python and Node.js sections for the commands and code that differ. Tenant registration, live model access and Agent 365 ingestion require our own resources and credentials.

For the same onboarding without a coding assistant, use the [manual runbook](3.Runbook-Manual.md). We run the CLI and add the token service and instrumentation ourselves, using the same starting points.

We can also follow the onboarding steps with our own supported agent. The skills inspect its code and ask for the identity choices they need; we don't need to reproduce this sample's workflow or describe SDK internals in the prompt. Shipment attributes and machine-rate counters are an optional extension after standard observability is working.

## The identities we're going to use

We're separating the webhook's API registration from the identity that performs the work. The middleware receives `Shipment.Invoke` on that API, while the agent receives application permissions on the downstream resources it needs. An inbound token never becomes an outbound credential.

Webhook authentication proves which application submitted the event and whether it may trigger work. It doesn't identify a person who might have initiated an upstream process. We record the verified service caller alongside the agent run without inventing a human user's identity or permissions.

The agent identity comes from an Entra agent identity blueprint. Its client ID identifies the agent in the observability route and `gen_ai.agent.id`; its directory object ID identifies the service principal when we assign permissions. Credentials belong to the blueprint, not to the child identity.

This corrects two assumptions in the original scenario brief. The objects involved aren't a fixed count of two service principals, and an agent identity doesn't store its own credentials. The [architecture](2.Architecture.md) explains the separation and links to the current Microsoft documentation.

## Scope of this version

All three stacks cover the same webhook scenario. Real SAP or ITSM adapters, deployment manifests and the optional agent-to-agent variant aren't included. The tools model API contracts, not actual SAP, Microsoft Graph or ServiceNow integrations, and no local run posts to Teams or creates an external ticket.

> Keep this sample on a development machine until we replace the event ledger with durable storage. It remembers completed and failed events only while the process lives, and it cannot guarantee exactly-once effects after a crash or across multiple instances.

We also don't use Work IQ as a substitute for an application-permission API. Each downstream service must support the S2S operation we want, with a permission grant appropriate to that resource.
