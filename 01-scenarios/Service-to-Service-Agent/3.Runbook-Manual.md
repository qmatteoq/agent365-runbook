# Manual runbook: service-to-service agent

## Introduction

We're going to onboard the supply-chain webhook without a coding assistant. We'll run the Agent 365 CLI ourselves, configure the identities, and add the token service and instrumentation in our editor. The [skill-led runbook](3.Runbook.md) covers the same scenario for teams that want the skills to make those changes.

The webhook receives an event from an application, with no signed-in user. That application gets permission to submit events; the agent gets its own identity and permission to export telemetry. We keep those two credentials separate throughout the guide.

Choose .NET, Python or Node.js and follow that stack's instructions. All three starting points use port `5168`, execute the same four stub tools and remember completed events in a process-local ledger. We can use our own agent instead: keep its existing authentication and business logic, then apply the registration and instrumentation steps to its execution boundaries. The shipment payload and replay harness are examples, not Agent 365 requirements.

| Phase | What we're doing |
| --- | --- |
| [0: Run the starting point](#phase-0-run-the-starting-point) | Make a working copy and submit a local event |
| [1: Protect the webhook](#phase-1-protect-the-webhook-with-entra) | Create an API role and authorize the middleware application |
| [2: Register the agent](#phase-2-register-the-agent) | Create the blueprint and child identity, then complete application grants |
| [3: Add observability](#phase-3-add-observability) | Add the exporter, refreshable S2S token service and semantic scopes |
| [4: Review the evidence](#phase-4-review-the-evidence) | Inspect local traces, try real inference and check tenant activity |

The code we add is a local-development example using a blueprint client secret. It doesn't deploy an Azure host or implement managed identity federation. The four tools remain stubs, including after we enable real model reasoning.

### Step 0-2. Start the webhook and submit an event

The local issuer signs a caller token with a random key. The webhook still checks its signature, application role and caller allowlist, but uses fictional directory IDs so we can run without Entra.

```

The `http` launch profile selects Development and binds to loopback on port `5168`. The Development configuration selects Local ingress and Stub reasoning. Generate the key once, then reuse it when restarting this copy.

In a second terminal, change to the same project directory:

```powershell
$env:ASPNETCORE_ENVIRONMENT = "Development"
$env:S2S_CALLER_TOKEN = (dotnet run --no-build --no-launch-profile -- --issue-local-token).Trim()
.\Invoke-Replay.ps1 -Count 1 -BatchId "first-shipment"
.\Invoke-Replay.ps1 -Count 1 -BatchId "first-shipment"
```

The token command exits without starting another host. The first request creates a run; the second returns its stored result. We capture the bearer token into the environment instead of printing it.

### Step 0-3. Understand what we're instrumenting

Each newly reserved event reads an order, reads inventory, produces a summary, sends a stub notification and creates a stub ticket. The host controls that sequence. Stub reasoning produces fixed text and makes no inference call.

The ledger keys events by verified caller client ID and source event ID. An identical completed replay returns the original result. A changed payload, an active reservation or a retained failure returns `409`; a new event at capacity returns `503`. The first execution failure returns `500` and retains the reservation because some downstream operations may already have completed.

> Keep one process for this exercise. The ledger has no durable storage or expiry, and restarting clears it. We need durable idempotency and authenticated downstream adapters before deploying this as a production integration.

## Phase 1: Protect the webhook with Entra

Local JWTs let us exercise the application, but a real middleware needs an Entra application permission. We'll put that permission on a separate API registration. It authorizes the calling application to trigger work without turning it into a human caller or lending its permissions to the agent.

### Step 1-1. Create the webhook API

1. Open the [Microsoft Entra admin center](https://entra.microsoft.com), then **Entra ID**, **App registrations**, **New registration**.
2. Enter **Name** `SupplyChain Webhook API`, select **Accounts in this organizational directory only**, leave **Redirect URI** empty, and select **Register**.
3. Record **Application (client) ID** and **Directory (tenant) ID**. Add an accountable owner under **Owners**.
4. Open **Expose an API**, select **Add** beside **Application ID URI**, and save `api://<webhook-api-client-id>`.
5. Open **App roles**, select **Create app role**, and enter **Display name** `Invoke shipment workflow`, **Allowed member types** `Applications`, **Value** `Shipment.Invoke`, and **Description** `Submit shipment exceptions to the supply-chain webhook`. Enable the role and select **Apply**.
6. Open **Manifest**. Within the existing `api` object, set `requestedAccessTokenVersion` to `2`, preserving the other properties, then save.
7. Open **Token configuration**, select **Add optional claim**, choose **Access**, select **idtyp**, and select **Add**.

The API issues v2 access tokens with an application role and the [`idtyp` claim](https://learn.microsoft.com/entra/identity-platform/optional-claims-reference). Our policy requires `idtyp=app`; the absence of a username isn't sufficient evidence that a token is app-only.

### Step 1-2. Create the middleware caller

1. Under **App registrations**, select **New registration**, enter **Name** `SupplyChain Middleware`, select the same single-tenant account option, leave **Redirect URI** empty, and select **Register**.
2. Record its **Application (client) ID** and add an owner under **Owners**.
3. Open **API permissions**, select **Add a permission**, then **My APIs**, and select `SupplyChain Webhook API`.
4. Choose **Application permissions**, select `Shipment.Invoke`, and select **Add permissions**.
5. Have an authorized administrator select **Grant admin consent for \<tenant\>** and confirm.
6. For this local exercise, open **Certificates & secrets**, select **New client secret**, enter **Description** `Local S2S exercise`, and choose a short permitted lifetime. Store the secret **Value** in our approved secret store.

The grant allows event submission. It doesn't give the middleware or agent access to an ERP, a model or Agent 365 telemetry. A deployed middleware should use a certificate or workload identity federation.

### Step 1-3. Replace the local ingress settings

Stop the host before editing its configuration. The API audience is the webhook application's client ID, and the allowed caller is the middleware's client ID. Neither field is the Agent 365 identity we'll create in Phase 2.

#### .NET

Merge this `Ingress` section into `appsettings.json`, preserving the rest of the file:

```json
{
  "Ingress": {
    "Mode": "Entra",
    "TenantId": "<tenant-id>",
    "Audience": "<webhook-api-client-id>",
    "RequiredRole": "Shipment.Invoke",
    "AllowedCallers": {
      "<middleware-client-id>": "SupplyChain Middleware"
    }
  }
}
```

The allowlist supplies our trusted display name and adds a restriction beyond the API role. Leave `Agent:ReasoningMode` set to `Stub`.

Restart without the Development profile:

```powershell
$env:ASPNETCORE_ENVIRONMENT = "Production"
dotnet run --no-launch-profile --urls "http://localhost:5168"
```

Production avoids loading the fictional Development identities. It also doesn't load user-secrets; Phase 3 explains how to supply the blueprint credential to this process.

#### Python and Node.js

Replace the corresponding entries in the ignored `.env`:

```dotenv
APP_ENVIRONMENT=Production
INGRESS_MODE=Entra
INGRESS_TENANT_ID=<tenant-id>
INGRESS_AUDIENCE=<webhook-api-client-id>

Remove the unused local signing key and clear any shell variables that override these entries. Restart with `uv run python -m app` or `npm start`. Production rejects Local ingress.

### Step 1-4. Submit an event as the middleware

In the caller terminal, acquire a token addressed to the webhook API:

```powershell
$tenantId = "<tenant-id>"
$callerId = "<middleware-client-id>"
$apiId = "<webhook-api-client-id>"
$credential = Get-Credential -UserName $callerId -Message "Enter the middleware client secret as the password"
$response = Invoke-RestMethod -Method Post `
    -Uri "https://login.microsoftonline.com/$tenantId/oauth2/v2.0/token" `
    -Body @{
        grant_type = "client_credentials"
        client_id = $callerId
        client_secret = $credential.GetNetworkCredential().Password
        scope = "api://$apiId/.default"
    }
if ([string]::IsNullOrWhiteSpace($response.access_token)) { throw "The token response has no access token." }
$env:S2S_CALLER_TOKEN = $response.access_token
Remove-Variable credential, response
```

The credential dialog collects an application secret, not a user's password. This is a client-credentials request, and the resulting token belongs to the middleware application. A deployed caller must refresh it before expiry.

Run the command for our stack in that terminal:

| Stack | Command |
| --- | --- |
| .NET | `.\Invoke-Replay.ps1 -Count 1 -BatchId "entra-shipment"` |
| Python | `uv run python -m app.replay --count 1 --batch-id entra-shipment` |
| Node.js | `npm run --silent replay -- --count 1 --batch-id entra-shipment` |

Expect one new run, with the middleware client ID in the application logs. Repeating the command returns a replay. A successful token request alone doesn't prove authorization; the webhook also checks the role, tenant and caller.

> Use HTTP only on loopback for this exercise. A remote listener needs HTTPS before we send it a real bearer token. Never paste tokens or client secrets into an online token decoder.

## Phase 2: Register the agent

### Step 2-1. Install and inspect the CLI

Agent 365 registration uses the same CLI regardless of our application's language. Install the [.NET tool](https://learn.microsoft.com/microsoft-agent-365/developer/agent-365-cli) through the configured NuGet source:

```powershell
dotnet tool install --global Microsoft.Agents.A365.DevTools.Cli
a365 --version
a365 setup all --help
```

If the tool is already installed, use `dotnet tool update --global Microsoft.Agents.A365.DevTools.Cli` when an update is needed. The commands in this guide match CLI `1.1.221`. Its .NET runtime dependency also applies to Python and Node.js users; follow the installation page for the tool runtime.

### Step 2-2. Create the blueprint and child identity

From our copied project, sign in as the operator and inspect the proposed registration:

```powershell
az login --tenant "<tenant-id>" --allow-no-subscriptions
a365 setup all --agent-name "SupplyChainExceptionAgent" --tenant-id "<tenant-id>" --authmode s2s --dry-run
```

Operator sign-in authorizes directory setup; the running agent will never borrow that login. Check the tenant, display names and requested permissions in the dry run. With a new folder and `--agent-name`, [config-free setup](https://learn.microsoft.com/microsoft-agent-365/developer/reference/cli/setup#config-free-setup-with---agent-name) assumes external hosting and skips infrastructure creation and project configuration sync. If we're adapting an existing project, inspect any `a365.config.json` before running setup.

Run the registration after reviewing that output:

```powershell
a365 setup all --agent-name "SupplyChainExceptionAgent" --tenant-id "<tenant-id>" --authmode s2s
```

We pass `s2s` because the default is OBO. Omit `--aiteammate` and `--m365`; this webhook needs neither an agent user nor a Teams messaging endpoint. Complete the CLI's prompts or give its **Action Required** instructions to the authorized administrator. If it offers to provision a missing resource service principal, have the administrator review and complete that step too.

> Some versions of the setup reference describe the generated identity name as `<name> Agent`; CLI `1.1.221` help says `<name> Identity`. Use the generated IDs when locating objects, rather than relying on the display-name suffix.

### Step 2-3. Record IDs and complete the observability grant

Open `a365.generated.config.json` locally. Record only the identifiers, and keep the generated file out of source control.

| Value | Meaning | Where we use it |
| --- | --- | --- |
| Tenant ID | The agent's tenant | Token authority, trusted baggage and export route |
| `agentBlueprintId` | Blueprint application/client ID | First token exchange and blueprint metadata |
| `agentIdentityClientId` | Child agent application/client ID | `fmi_path`, second token exchange, `gen_ai.agent.id` and export route |
| Child service principal object ID | Directory object for the child | Looking up and assigning application roles |

The inbound API and middleware IDs from Phase 1 remain separate. The blueprint owns the credential; we don't create a secret on the child identity.

The S2S observability recipe uses resource application ID `9b975845-388f-4429-889e-eab1ef63949c` and the **Application** permission `Agent365.Observability.OtelWrite`. Declaring a permission on the blueprint doesn't prove that the child service principal has its application-role assignment. Complete the CLI's administrator handoff, then inspect that assignment:

```powershell
$agentClientId = "<agentIdentityClientId>"
$agentObjectId = az ad sp show --id $agentClientId --query id -o tsv
if ($LASTEXITCODE -ne 0 -or [string]::IsNullOrWhiteSpace($agentObjectId)) { throw "Cannot resolve the child service principal." }
$resourceJson = az ad sp show --id "9b975845-388f-4429-889e-eab1ef63949c" -o json
if ($LASTEXITCODE -ne 0) { throw "Cannot resolve the observability resource service principal." }
$resource = $resourceJson | ConvertFrom-Json
$role = @($resource.appRoles | Where-Object {
    $_.value -eq "Agent365.Observability.OtelWrite" -and
    $_.isEnabled -and $_.allowedMemberTypes -contains "Application"
})
if ($role.Count -ne 1) { throw "Expected one enabled observability application role." }
$grantsJson = az rest --method GET `
    --url "https://graph.microsoft.com/v1.0/servicePrincipals/$agentObjectId/appRoleAssignments" -o json
if ($LASTEXITCODE -ne 0) { throw "Cannot read the child's role assignments." }
$grants = $grantsJson | ConvertFrom-Json
while ($true) {
    $match = @($grants.value | Where-Object { $_.resourceId -eq $resource.id -and $_.appRoleId -eq $role[0].id })
    if ($match.Count -gt 0) { break }
    if (-not $grants.'@odata.nextLink') { throw "The child has no observability role assignment. Complete the administrator handoff." }
    $grantsJson = az rest --method GET --url $grants.'@odata.nextLink' -o json
    if ($LASTEXITCODE -ne 0) { throw "Cannot read the next page of role assignments." }
    $grants = $grantsJson | ConvertFrom-Json
}
$match | Select-Object principalId, resourceId, appRoleId
```

This read-only check resolves the role ID from the resource instead of assuming a fixed GUID. `principalId` must be the child object's directory ID. It doesn't grant anything; if the lookup fails or the role is missing, use the setup handoff with our administrator. The [application-role assignment documentation](https://learn.microsoft.com/entra/identity/enterprise-apps/assign-agent-identities-to-applications#assigning-an-agent-identity-to-an-application-role) describes the underlying directory operation.

## Phase 3: Add observability

We need a runtime identity, a token resolver that still works when a background exporter flushes, and spans that describe agent work. Ordinary HTTP tracing alone doesn't supply the semantic invocation and output that Agent 365 expects.

The token service performs two client-credentials exchanges. First, the blueprint requests `api://AzureADTokenExchange/.default` with `fmi_path` set to the child client ID. Then the child presents that returned token as its client assertion and requests `api://9b975845-388f-4429-889e-eab1ef63949c/.default`. Neither request uses the inbound middleware token.

We'll start with Console export. Agent365 export is an explicit choice that enables the S2S route and our refreshable resolver. Otlp is an alternative for an existing collector. The public-cloud scope here follows the [S2S observability authentication guide](https://learn.microsoft.com/microsoft-agent-365/developer/observability-authentication-setup#agent-365-enabled-using-s2s); don't substitute a Bot Framework, delegated or Power Platform audience from a different recipe.

Each stack's helper leaves telemetry disabled when its export setting is absent, so the original local test commands can run without tenant configuration. Once we set the export target, invalid configuration fails instead of silently falling back to an uninstrumented run.

Follow just one implementation: [.NET](#net-implementation), [Python](#python-implementation) or [Node.js](#nodejs-implementation). Each includes its package commands, new helper files and edits to the existing entry point and workflow.

### .NET implementation

We're going to keep the existing authentication, event ledger and shipment workflow, then wrap the work that runs after the ledger accepts an event. Console export lets us check those boundaries without contacting Entra. Agent365 export will use a separate blueprint credential and the registered child identity; the webhook caller's bearer token never enters that token exchange.

#### Add the package and configuration

In the .NET working copy created in Phase 0, add the tested package:

```powershell

```

This version contains the Agent 365 scope types as well as the exporters. We don't add a separate `Microsoft.Agents.A365.Observability.Runtime` reference, which would duplicate those types. The command uses the machine's existing NuGet configuration; if its managed source cannot restore this version, stop and resolve that feed issue without adding a public source.

Merge this top-level section into `appsettings.json`, alongside the existing `Ingress` section, and fill in the registration values before starting the host:

```json

  "Agent365Observability": {
    "TenantId": "<tenant-id>",
    "AgentBlueprintId": "<agentBlueprintId>",
    "AgentId": "<agentIdentityClientId>",
    "AgentName": "SupplyChainExceptionAgent",
    "ResourceScope": "api://9b975845-388f-4429-889e-eab1ef63949c/.default",
    "ExportTarget": "Console",
    "OtlpEndpoint": null
  }

```

Use the tenant from Phase 2, copy `agentBlueprintId` from `a365.generated.config.json` into `AgentBlueprintId`, and copy `agentIdentityClientId` into `AgentId`. Config-free CLI setup doesn't write these project settings for us. `AgentId` is neither the blueprint ID nor the child's service-principal object ID. Keep `BlueprintClientSecret` out of this file. Console uses the configured IDs as metadata but makes no token request.

The helper below stays disabled when `Agent365Observability:ExportTarget` is absent, so the unconfigured starter's tests still run. Once the key exists, it accepts only `Console`, `Agent365` or `Otlp` and rejects invalid configuration at startup. Console is our guide's default, not a fallback after an export or authentication failure.

#### Add the blueprint token service

The [autonomous-agent authentication protocol](https://learn.microsoft.com/en-us/entra/agent-id/autonomous-agent-authentication-authorization-flow) uses two token requests. The first authenticates the blueprint and supplies the child's client ID as `fmi_path`; the second authenticates that child with the returned T1 assertion and requests the observability resource's application permissions.

Create `BlueprintTokens.cs`:

```csharp
using System.Text.Json;

namespace SupplyChainAgent;

public sealed class BlueprintTokens : IDisposable
{
    private readonly string tenant, blueprint, agent, secret, resource;
    private readonly HttpClient http;
    private readonly SemaphoreSlim refresh = new(1, 1);
    private string? cached;
    private DateTimeOffset expires;

    public BlueprintTokens(string tenant, string blueprint, string agent, string secret, string resource,
        HttpMessageHandler? handler = null)
    {
        this.tenant = tenant; this.blueprint = blueprint; this.agent = agent;
        this.secret = secret; this.resource = resource;
        http = new(handler ?? new HttpClientHandler { AllowAutoRedirect = false })
        { Timeout = TimeSpan.FromSeconds(20) };
    }

    public async Task<string> GetAsync(string agentId, string tenantId)
    {
        if (!string.Equals(agent, agentId, StringComparison.OrdinalIgnoreCase) ||
            !string.Equals(tenant, tenantId, StringComparison.OrdinalIgnoreCase))
            throw new InvalidOperationException("Observability identity is not configured for this resolver.");
        await refresh.WaitAsync();
        try
        {
            if (cached is not null && expires > DateTimeOffset.UtcNow.AddSeconds(60)) return cached;
            var (assertion, _) = await PostAsync(new()
            {
                ["client_id"] = blueprint, ["client_secret"] = secret,
                ["grant_type"] = "client_credentials",
                ["scope"] = "api://AzureADTokenExchange/.default", ["fmi_path"] = agent
            });
            var token = await PostAsync(new()
            {
                ["client_id"] = agent, ["client_assertion"] = assertion,
                ["client_assertion_type"] = "urn:ietf:params:oauth:client-assertion-type:jwt-bearer",
                ["grant_type"] = "client_credentials", ["scope"] = resource
            });
            if (token.Expires <= DateTimeOffset.UtcNow.AddSeconds(60))
                throw new InvalidOperationException("Observability token lifetime is too short.");
            (cached, expires) = token;
            return cached;
        }
        finally { refresh.Release(); }
    }

    private async Task<(string Token, DateTimeOffset Expires)> PostAsync(Dictionary<string, string> fields)
    {
        var started = DateTimeOffset.UtcNow;
        using var form = new FormUrlEncodedContent(fields);
        try
        {
            using var response = await http.PostAsync(
                $"https://login.microsoftonline.com/{tenant}/oauth2/v2.0/token", form);
            if (!response.IsSuccessStatusCode)
                throw new InvalidOperationException($"Observability token endpoint returned HTTP {(int)response.StatusCode}.");
            using var json = JsonDocument.Parse(await response.Content.ReadAsStringAsync());
            var root = json.RootElement;
            if (root.ValueKind != JsonValueKind.Object ||
                !root.TryGetProperty("access_token", out var access) || access.ValueKind != JsonValueKind.String ||
                string.IsNullOrWhiteSpace(access.GetString()) ||
                !root.TryGetProperty("token_type", out var type) || type.ValueKind != JsonValueKind.String ||
                !string.Equals(type.GetString(), "Bearer", StringComparison.OrdinalIgnoreCase) ||
                !root.TryGetProperty("expires_in", out var lifetime) || lifetime.ValueKind != JsonValueKind.Number ||
                !lifetime.TryGetInt32(out var seconds) || seconds <= 60)
                throw new InvalidOperationException("Observability token response is malformed.");
            return (access.GetString()!, started.AddSeconds(seconds));
        }
        catch (JsonException) { throw new InvalidOperationException("Observability token response is malformed."); }
        catch (HttpRequestException) { throw new InvalidOperationException("Observability token request failed."); }
        catch (TaskCanceledException) { throw new InvalidOperationException("Observability token request timed out."); }
    }

    public void Dispose() { http.Dispose(); refresh.Dispose(); }
}
```

The cache refreshes within 60 seconds of expiry and serializes concurrent lookups, including lookups from the exporter's background worker. It only serves the configured child and tenant, refuses malformed responses and reports failures without response bodies, tokens or secrets. The optional HTTP handler supports local protocol tests; normal execution uses the fixed Entra endpoint with redirects disabled.

> Use this small protocol implementation for the local blueprint-secret exercise. It does not implement production managed-identity federation. For deployment, follow the same [authentication guide's Microsoft.Identity.Web recipe](https://learn.microsoft.com/en-us/entra/agent-id/autonomous-agent-authentication-authorization-flow#configure-your-client-credentials) and use a certificate or a managed identity with the required federated trust. class TokenService:
    def __init__(self, settings, post=httpx.post, clock=time.monotonic):
        self.settings, self.post, self.clock = settings, post, clock
        self.lock = threading.Lock()
        self.token, self.expires = None, 0.0

    def _request(self, form):
        url = f"https://login.microsoftonline.com/{self.settings.tenant_id}/oauth2/v2.0/token"
        try:
            response = self.post(url, data=form, timeout=20, follow_redirects=False)
            if not 200 <= response.status_code < 300:
                raise ValueError()
            payload = response.json()
            token = payload["access_token"]
            lifetime = float(payload["expires_in"])
            if (not isinstance(token, str) or not token.strip()
                    or not math.isfinite(lifetime) or lifetime <= 60
                    or str(payload.get("token_type", "")).lower() != "bearer"):
                raise ValueError()
            return token, lifetime
        except (httpx.HTTPError, ValueError, TypeError, KeyError, OverflowError):
            raise RuntimeError("Agent365 token acquisition failed; check credentials and permissions.") from None

    def resolve(self, agent_id, tenant_id):
        s = self.settings
        if agent_id != s.agent_client_id or tenant_id != s.tenant_id:
            raise ValueError("Agent365 exporter requested an unexpected identity.")
        with self.lock:
            if self.token and self.clock() < self.expires - 60:
                return self.token
            t1, _ = self._request({
                "client_id": s.blueprint_client_id,
                "client_secret": s.blueprint_client_secret.get_secret_value(),
                "grant_type": "client_credentials",
                "scope": "api://AzureADTokenExchange/.default",
                "fmi_path": s.agent_client_id,
            })
            started = self.clock()
            token, lifetime = self._request({
                "client_id": s.agent_client_id,
                "grant_type": "client_credentials",
                "client_assertion_type": "urn:ietf:params:oauth:client-assertion-type:jwt-bearer",
                "client_assertion": t1,
                "scope": s.resource_scope,
            })
            if self.clock() >= started + lifetime - 60:
                raise RuntimeError("Agent365 returned an access token too close to expiry.")
            self.token, self.expires = token, started + lifetime
            return token

        yield
    finally:
        if token is not None:

@contextmanager
def observed(kind, name, correlation=None):

        yield
        return
    from microsoft.opentelemetry.a365.core import (
        BaggageBuilder, ExecuteToolScope, InferenceCallDetails, InferenceOperationType,
        InferenceScope, InvokeAgentScope, InvokeAgentScopeDetails, Request, ToolCallDetails,
    )
    if correlation is not None and re.fullmatch(r"[A-Za-z0-9_.-]{1,64}", correlation) is None:
        raise ValueError("Telemetry correlation must be the validated request correlation.")
    s = _settings
    builder = BaggageBuilder().tenant_id(s.tenant_id).agent_id(s.agent_client_id)
    if correlation is not None:
        builder.conversation_id(correlation)
    with isolated_root(kind), builder.build():
        request = Request(content="Shipment exception operation.", conversation_id=correlation)
        if kind == "agent":
            scope = InvokeAgentScope.start(request, InvokeAgentScopeDetails(), _agent)
        elif kind == "tool":
            scope = ExecuteToolScope.start(request, ToolCallDetails(tool_name=name), _agent)
        elif kind == "model":
            scope = InferenceScope.start(request, InferenceCallDetails(
                operationName=InferenceOperationType.CHAT, model=name, providerName="azure.ai.openai"), _agent)
        else:
            raise ValueError("Unknown telemetry operation.")
        scope.__enter__()
        if kind == "model":
            # Distro 1.3.8's CHAT enum serializes as "Chat"; OTel uses lowercase.
            from opentelemetry import trace
            trace.get_current_span().update_name(f"chat {name}")
            scope.set_tag_maybe("gen_ai.operation.name", "chat")
        try:
            yield
        except BaseException:
            scope.record_error(RuntimeError("Operation failed."))
            raise
        else:
            if kind == "tool":
                scope.record_response("Tool completed.")
            else:
                scope.record_output_messages("Operation completed.")
        finally:
            # Passing no exception prevents the SDK from recording the original business error.
            scope.__exit__(None, None, None)

#### Add the local token service

The [autonomous agent token protocol](https://learn.microsoft.com/en-us/entra/agent-id/autonomous-agent-authentication-authorization-flow) has two token-endpoint requests for our local client-secret case. The blueprint first obtains T1 with `fmi_path` set to the child client ID. The child then uses T1 as its client assertion to request the observability resource. We implement those form POSTs directly, so there isn't an assumed `fmiPath` option hidden inside an authentication library.

Create `src\observability-token.ts`:

```typescript
export interface ObservabilityIdentity {
    tenantId: string;
    blueprintId: string;
    agentId: string;
    resourceScope: string;
}

export class ObservabilityTokenService {
    private cached?: { token: string; expiresAt: number };
    private refreshing?: Promise<string>;

    constructor(
        private readonly identity: ObservabilityIdentity,
        private readonly secret: string,
        private readonly send: typeof fetch = fetch,
        private readonly now: () => number = Date.now,
    ) {}

    readonly resolve = async (agentId: string, tenantId: string, scopes?: string[]): Promise<string> => {
        if (agentId.toLowerCase() !== this.identity.agentId ||
            tenantId.toLowerCase() !== this.identity.tenantId ||
            (scopes && (scopes.length !== 1 || scopes[0] !== this.identity.resourceScope))) {
            throw new Error("Observability identity or resource scope mismatch.");
        }
        if (this.cached && this.cached.expiresAt - this.now() > 60_000) return this.cached.token;
        if (!this.refreshing) {
            this.refreshing = this.refresh().finally(() => { this.refreshing = undefined; });
        }
        return this.refreshing;
    };

    private async post(fields: Record<string, string>): Promise<{ token: string; expiresAt: number }> {
        const startedAt = this.now();
        let response: Response;
        try {
            response = await this.send(
                `https://login.microsoftonline.com/${this.identity.tenantId}/oauth2/v2.0/token`,
                {
                    method: "POST", redirect: "error", signal: AbortSignal.timeout(15_000),
                    headers: { "Content-Type": "application/x-www-form-urlencoded" },
                    body: new URLSearchParams({ grant_type: "client_credentials", ...fields }),
                },
            );
        } catch {
            throw new Error("Observability token request failed or timed out.");
        }
        if (!response.ok) {
            await response.body?.cancel();
            throw new Error(`Observability token endpoint returned HTTP ${response.status}.`);
        }
        let value: Record<string, unknown>;
        try {
            value = await response.json() as Record<string, unknown>;
        } catch {
            throw new Error("Observability token endpoint returned invalid JSON.");
        }
        if (!value || typeof value.access_token !== "string" || !value.access_token.trim() ||
            typeof value.expires_in !== "number" || !Number.isFinite(value.expires_in) ||
            value.expires_in <= 60 || value.token_type?.toString().toLowerCase() !== "bearer") {
            throw new Error("Observability token endpoint returned an invalid token or lifetime.");
        }
        const expiresAt = startedAt + value.expires_in * 1000;
        if (expiresAt - this.now() <= 60_000) throw new Error("Observability token expires too soon.");
        return { token: value.access_token, expiresAt };
    }

    private async refresh(): Promise<string> {
        const t1 = await this.post({
            client_id: this.identity.blueprintId,
            client_secret: this.secret,
            scope: "api://AzureADTokenExchange/.default",
            fmi_path: this.identity.agentId,
        });
        this.cached = await this.post({
            client_id: this.identity.agentId,
            client_assertion: t1.token,
            client_assertion_type: "urn:ietf:params:oauth:client-assertion-type:jwt-bearer",
            scope: this.identity.resourceScope,
        });
        return this.cached.token;
    }
}
```

We cache the resource token using its returned lifetime, subtract a 60-second safety margin and share one refresh promise across concurrent exports. The resolver rejects another agent, tenant or resource scope. Failed HTTP responses produce a status-only error; neither response bodies nor tokens reach logs, and a failure never becomes an empty-token fallback. The service stays alive outside the request context, so a batch can obtain or refresh its token after the webhook response has completed.

async function within<T>(scope: OpenTelemetryScope, action: () => Promise<T>): Promise<T> {
    try {
        const request = requests.getStore();
        scope.recordAttributes({
            "microsoft.session.id": request?.sessionId ?? "",
            "supplychain.run.id": request?.sessionId ?? "",
            "supplychain.correlation.id": request?.conversationId ?? "",
        });
        return await scope.withActiveSpanAsync(action);
    } catch (error) {
        scope.recordError(new Error("Operation failed; inspect the application run log."));
        throw error;
    } finally {
        scope.dispose();
    }
}

export async function observeRun(
    shipment: ShipmentEvent, run: RunContext, action: () => Promise<RunResult>,
): Promise<RunResult> {
    if (!runtime) return action();
    const { sdk, api, agent } = runtime;
    const request: A365Request = {
        content: "Process a shipment exception; business data omitted.",
        sessionId: run.runId, conversationId: run.correlationId,
        channel: { name: "webhook", role: sdk.InvocationRole.Event },
    };
    return await api.context.with(api.ROOT_CONTEXT, async () => {
        const baggage = new sdk.BaggageBuilder()
            .tenantId(agent.tenantId).agentId(agent.agentId).agentBlueprintId(agent.agentBlueprintId)
            .agentName(agent.agentName).sessionId(run.runId).conversationId(run.correlationId)
            .channelName("webhook").setPairs({ "supplychain.run.id": run.runId,
                "supplychain.correlation.id": run.correlationId }).build();

            const scope = sdk.InvokeAgentScope.start(request, {}, agent);
            return within(scope, async () => {
                const result = await action();
                scope.recordOutputMessages(["Shipment exception processed; summary and tool results omitted."]);
                return result;
            });
        }));
    });
}

Its resolver already has a resource token before the listener opens. Console and Otlp don't create the token service.

The helper clears inherited OTLP endpoint, header and protocol overrides before selecting our destination, disables Azure Monitor and the distro's SDK statistics exporter, and sets full trace sampling for the exercise. These are process-local telemetry settings, not changes to npm or machine configuration. Otlp uses the supported `OTEL_EXPORTER_OTLP_ENDPOINT` route; it doesn't redirect Agent 365's authenticated exporter to a collector.

We enter `context.with(ROOT_CONTEXT, ...)` before building baggage, then enter `baggage.run` before creating any scope. This removes inherited baggage and parent span identity rather than merely replacing the agent and tenant while leaving spoofed user fields behind. Both callbacks return their asynchronous promises, and the context manager restores the previous context afterward. The HTTP auto-instrumentation is also disabled, and our Express code doesn't extract incoming baggage headers.

The session ID is the run GUID, the conversation ID carries the request correlation ID, and the channel is `webhook`. The SDK's baggage processor copies a fixed list of attributes, so `within` also writes our run and correlation attributes explicitly. The blueprint is a separate attribute from the child identity. We start a new trace for each reserved invocation; an inbound `traceparent` doesn't select the telemetry parent.

Version `1.3.0` has an API mismatch we need to account for: `InferenceOperationType.CHAT` contains `"Chat"`, while the exporter recognizes lowercase `"chat"`. We still create an `InferenceScope` through its typed API, then normalize that semantic attribute through the public `recordAttributes` method. The visible inference span name remains `Chat <deployment>`.

We record generic input and output messages, not shipment IDs, model prompts, summaries or tool payloads. Successful output is recorded before disposal. A failing scope receives a sanitized error, and the original exception continues to the existing error handler. The inbound caller remains in the application's authenticated logging context; we don't turn that middleware into a user, an Agent 365 caller agent or a sponsor identity. `CallerDetails` and `UserDetails` are optional in the installed API and aren't supplied here.

#### Load configuration before the application

ESM evaluates static imports before the body of an entry point. We need to load `.env` and initialize the SDK before importing Express, LangChain or the model implementation, so replace `src\main.ts` with:

```typescript
import { ConfigurationError, loadEnvironment, readSettings } from "./config.js";
import { Logger } from "./logging.js";

const logger = new Logger();
let stopTelemetry: () => Promise<void> = async () => {};
const flush = async () => {
    try { await stopTelemetry(); }
    catch {
        logger.event("host.failed", { Reason: "telemetry_shutdown_failed" }, "Error");
        process.exitCode = 1;
    }
};
try {
    loadEnvironment();
    const settings = readSettings();
    const telemetry = await import("./observability.js");
    stopTelemetry = telemetry.stopObservability;
    await telemetry.startObservability(settings);
    const { createApp } = await import("./app.js");
    const app = createApp(settings);
    const server = app.listen(settings.port, settings.host, () => {
        logger.event("host.started", {
            Host: settings.host, Port: settings.port, IdentityMode: settings.ingress.mode,
            ReasoningMode: settings.reasoningMode, ToolMode: "Stub",
        });
    });
    server.on("error", () => {
        logger.event("host.failed", { Reason: "listener_failed" }, "Error");
        process.exitCode = 1;
        void flush();
    });
    let closing = false;
    const shutdown = () => {
        if (closing) return;
        closing = true;
        server.close(() => { void flush(); });
        server.closeIdleConnections();
    };
    process.once("SIGINT", shutdown);
    process.once("SIGTERM", shutdown);
} catch (error) {
    logger.event("host.failed", {
        Reason: error instanceof ConfigurationError ? error.message : "startup_failed",
    }, "Error");
    process.exitCode = 1;
    await flush();
}
```

We load `.env` once in this process, preserving the starting point's environment-variable precedence. Graceful shutdown waits for active HTTP work before flushing the provider; repeated shutdown calls share one promise. The token and replay CLIs keep their original entry points and don't import observability startup. We don't need an automatic instrumentation loader because the code above disables automatic instrumentations and uses manual scopes.

### Step 4-6. Diagnose the failing boundary

The [cross-scenario troubleshooting guide](../../03-references/Troubleshooting.md#an-s2s-webhook-works-but-the-expected-trace-is-missing) separates ingress, model and exporter credentials, and explains why replays and stub reasoning produce different evidence from new model-backed runs.

| Symptom | What we inspect |
| --- | --- |
| Host won't start | Port `5168` is free, enabled telemetry configuration is complete, and the chosen stack's dependencies are restored |
| Local mode is rejected | Development is required, with a random signing key and a loopback socket peer |
| Webhook returns `401` | Caller token signature, issuer, expiry and webhook API audience |
| Webhook returns `403` | `idtyp=app`, application role, configured tenant and middleware allowlist |
| Event returns `409` | Payload conflict, a run already in progress, or a retained failed reservation |
| New event returns `503` | The process-local ledger reached capacity |
| Token exchange fails | Blueprint credential, `fmi_path`, child client ID, resource scope and tenant policy |
| Export returns `401` or `403` | S2S route, final token audience, child application-role assignment and permission propagation |
| Console works but tenant export doesn't start | Export target, exporter activation and refreshable token resolver registration |
| Export succeeds but Activity is empty | Child identity, tenant eligibility, `invoke_agent` semantics and output messages |
| A replay creates another invocation | The invocation scope was placed before reservation or the host restarted |
| Stub reasoning has a model span | Inference instrumentation surrounds the generic reasoner rather than the real model branch |

The [architecture](2.Architecture.md) contains the identity and token diagrams. The [sample requests](4.Sample-prompts.md) cover payload conflicts and authorization failures without needing a conversational interface.
