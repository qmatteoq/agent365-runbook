# Step-by-step guide: service-to-service agent

## Introduction

Our integration middleware has detected a delayed shipment and submitted an event. There is no signed-in user whose token we can exchange, and nobody is waiting in a chat window. We're going to let a supply-chain agent process that event under its own identity, then give the operations team enough telemetry to reconstruct what happened.

The .NET, Python and Node.js starting points already handle machine authentication, correlation and retries. Their four downstream tools are stubs, so we can exercise the workflow without an ERP tenant, a Teams channel or an ITSM account. Each also has an optional Azure OpenAI reasoning step. We're going to ask our coding assistant to add Agent 365 using the dedicated skills: `a365-setup` for registration, then `instrument-observability` for the token service, packages and telemetry code.

**The skills do the implementation work. We supply the prompts, answer their questions and approve the changes.** The CLI commands, configuration examples and code snippets in this guide explain what the assistant does behind the scenes. They aren't a second set of steps to perform after the skill finishes, and we don't need to paste them into our project.

If we're onboarding without a coding assistant, follow the [manual runbook](3.Runbook-Manual.md). It covers the same .NET, Python and Node.js scenario with commands to run and files to edit ourselves.

| Phase | What we have at the end |
| --- | --- |
| 0: Run the starting point | A local webhook, stub workflow and repeatable 400-event exercise |
| 1: Protect the webhook | Real Entra app-only caller authentication and an assigned API role |
| 2: Register the agent | A blueprint-derived identity with the S2S observability permission |
| 3: Add observability | Semantic agent spans and S2S export, with an optional sample-specific telemetry exercise |
| 4: Review the evidence | Queries that distinguish callers, events, new runs and retries |

We choose ASP.NET Core, FastAPI or Express for the host, but use the same separate inbound API registration and blueprint-derived agent identity in every stack. Console is our first telemetry destination; OTLP is an alternative when we have a collector. We don't provision Azure hosting or choose a production telemetry vendor in this guide.

## How to follow this guide

In Phases 2 and 3, start with **What we ask the assistant**. The skill runs the setup commands or edits the project, then we use the explanations and checkpoints to review its work.

| Label | What we do |
| --- | --- |
| What we ask the assistant | Send the prompt from our chosen stack's project workspace |
| What the skill does | Review the work the skill is about to perform and approve it |
| Behind the scenes | Read the commands and code as reference; don't run or paste them again |
| What we verify | Review the result with the assistant and complete any required tenant-side checks |

Phases 0 and 1 prepare the application before Agent 365 onboarding. The assistant can run the local commands and update configuration for us, but these are ordinary development tasks, not Agent 365 skill features. The numbered portal steps, sign-in, secure credential entry and administrator consent still require us or an authorized administrator. Phase 4 uses the assistant to exercise the result and help us inspect the evidence.

Choose one stack and follow its subsections; the portal steps and skill prompts are shared. Each starting point uses `http://localhost:5168`, so run one at a time unless we configure another port. The reference terminal commands use PowerShell 7, while Python and Node.js also have native replay commands.

### Bringing our own agent

The supply-chain webhook gives us something concrete to run, but the onboarding prompts also work with our own supported agent. Open that agent's project in the coding assistant and describe what we want to add. The skills inspect the code, identify the framework and ask for the identity and authentication choices they need.

If our agent already runs and has an appropriate inbound authorization boundary, we can use Phases 0 and 1 as background and begin at Phase 2. If it is already registered with Agent 365, continue at Phase 3. We don't need the sample's class names, shipment payload, replay harness or custom metric names in our application.

The business-event attributes and volume metrics later in this guide are an optional extension for the supply-chain demo. They aren't prerequisites for Agent 365 observability.

## Prerequisites

For Phase 0, choose the runtime for our starting point and install [PowerShell 7](https://learn.microsoft.com/powershell/scripting/install/installing-powershell) to follow the terminal examples. We don't need Azure, Entra or an LLM subscription for the local stub path.

The Python and Node.js agents use LangChain; the .NET agent uses Microsoft Agent Framework. This changes the model integration, not the workflow or S2S identity choices.

For the tenant phases, we need an Agent 365-enabled Microsoft 365 tenant and the applicable licenses, the Azure CLI, and the Agent 365 CLI. Blueprint creation needs an account with Agent ID Developer or a higher role. Creating inbound applications and granting their application permissions needs the corresponding application administrator permissions; Agent 365 setup may also require a Global Administrator handoff. Check the [setup reference](https://learn.microsoft.com/microsoft-agent-365/developer/reference/cli/setup) against the roles available in our tenant.

Install the Agent 365 skills using [Installing the skills](../../00-overview/Installing-the-Skills.md). Open the chosen starting-point folder, or our standalone copy of it, as the assistant's workspace. We can ask the assistant to check the local prerequisites; `a365-setup` checks and installs the Agent 365 CLI when we reach registration. The CLI is a .NET tool even when our agent is Python or Node.js, so its runtime prerequisite still applies.

## Phase 0: Run the starting point

### Step 0-1. Start the local service

**What we ask the assistant**

> Run this starting point locally with stub reasoning, then submit one shipment event and retry it. Don't add Agent 365 yet.

The assistant reads the selected stack's README, generates a random local signing key and stores it in .NET user-secrets or the ignored `.env` file for Python and Node.js. It acquires the local caller token without displaying it. We don't need an Agent 365 skill for this step.

**Behind the scenes**

When starting from the repository root, the equivalent commands are:

#### .NET

```powershell
Set-Location .\01-scenarios\Service-to-Service-Agent\0.Resources\Starting-point\dotnet
dotnet build
$key = [Convert]::ToBase64String([Security.Cryptography.RandomNumberGenerator]::GetBytes(48))
dotnet user-secrets set "Ingress:LocalSigningKey" $key
Remove-Variable key
dotnet run --no-build --launch-profile http
```

The launch profile sets Development and binds to `http://localhost:5168`. `appsettings.Development.json` supplies fictional directory IDs and selects the local JWT issuer. We still validate a signed token and check the role and caller; local mode isn't an anonymous bypass.

The caller uses a second terminal or process in the same folder. These are the equivalent token and request commands:

```powershell
$env:ASPNETCORE_ENVIRONMENT = "Development"
$env:S2S_CALLER_TOKEN = (dotnet run --no-build --no-launch-profile -- --issue-local-token).Trim()
.\Invoke-Replay.ps1 -Count 1 -BatchId "first-shipment"
```

The CLI flag prints a one-hour local access token and exits. We capture it directly into an environment variable, and the harness sends it to `/api/shipments`. We should see one new run, with stub notification and ticket identifiers.

#### Python

```powershell
Set-Location .\01-scenarios\Service-to-Service-Agent\0.Resources\Starting-point\python
uv sync
Copy-Item .env.example .env
$key = [Convert]::ToBase64String([Security.Cryptography.RandomNumberGenerator]::GetBytes(48))
Add-Content .env "`nINGRESS_LOCAL_SIGNING_KEY=$key"
Remove-Variable key
uv run python -m app
```

The `.env` file selects Development, Local ingress and Stub reasoning with the same fictional IDs as .NET. The appended key replaces the blank template value when the configuration loads. These initialization commands assume a fresh copy; preserve an existing `.env` and its key when restarting. Uvicorn starts one worker on the configured loopback address and port `5168`.

In a second terminal in the Python folder:

```powershell
$env:S2S_CALLER_TOKEN = (uv run python -m app --issue-local-token).Trim()
uv run python -m app.replay --count 1 --batch-id first-shipment
```

The token command reads the same `.env`, issues a one-hour token and exits without starting a server. The replay module sends the same shipment payload as the .NET harness.

#### Node.js

```powershell
Set-Location .\01-scenarios\Service-to-Service-Agent\0.Resources\Starting-point\nodejs
npm ci
Copy-Item .env.example .env
$key = [Convert]::ToBase64String([Security.Cryptography.RandomNumberGenerator]::GetBytes(48))
Add-Content .env "`nINGRESS_LOCAL_SIGNING_KEY=$key"
Remove-Variable key
npm start
```

Express uses the same local settings and port as the other hosts. As with Python, the file-copy and key-generation commands are for a fresh copy, not every restart. `npm start` runs the TypeScript entry point; `npm run build` produces compiled JavaScript.

In a second terminal in the Node.js folder:

```powershell
$env:S2S_CALLER_TOKEN = (npm run --silent token).Trim()
npm run --silent replay -- --count 1 --batch-id first-shipment
```

The silent npm option keeps script banners out of the captured token. The replay command reads `S2S_CALLER_TOKEN` from the environment instead of accepting it as a command-line argument.

**What we verify**

The assistant's second submission should report one replay rather than another run. The original response is stored under the verified caller and source event ID.

### Step 0-2. Run a batch and inspect the boundary cases

**What we ask the assistant**

> With stub reasoning, run the `nightly-demo` batch twice and run the local checks for this stack. Report the new-run and replay counts and any failures. Keep credentials out of the output.

**Behind the scenes**

#### .NET

```powershell
.\Invoke-Replay.ps1 -BatchId "nightly-demo"
.\Invoke-Replay.ps1 -BatchId "nightly-demo"
.\Test-Local.ps1
```

The two replay commands submit 400 events each: the first creates runs and the second returns stored results. The test script starts a separate stub host with an ephemeral key and stops its own process.

#### Python

```powershell
uv run python -m app.replay --count 400 --batch-id nightly-demo
uv run python -m app.replay --count 400 --batch-id nightly-demo
uv run python -m unittest discover -s tests
```

The replay module exercises the running host. The tests use isolated application instances and their own settings, so they don't consume reservations in that host's ledger.

#### Node.js

```powershell
npm run --silent replay -- --count 400 --batch-id nightly-demo
npm run --silent replay -- --count 400 --batch-id nightly-demo
npm run build
npm test
```

The replay script exercises Express, while the build and tests cover the TypeScript implementation. In every stack, the local checks cover token validation, delegated-token rejection, input validation and replay behavior, including concurrent duplicates and a full ledger.

> Keep `ReasoningMode=Stub` for this first batch. A 400-event run with Azure OpenAI enabled makes 400 model calls and consumes quota. The burst also differs from 400 events distributed across a night, so we shouldn't use its wall-clock throughput as a production baseline.

When we're comparing implementations in this repository, `0.Resources\Starting-point\Test-Parity.ps1` runs the same HTTP checks against all three stacks. It needs the .NET build, Python environment and Node.js dependencies prepared first, and starts isolated hosts with fresh keys. This is a repository maintenance check, not another prerequisite for onboarding our own agent.

### Step 0-3. Add real model reasoning when needed

The model is optional for learning the ingress and identity flow, but we need it before claiming to observe real inference. Creating the Azure resource is separate from the Agent 365 skills. If we don't already have one, we or our Azure administrator follow these portal steps:

1. Open the [Azure portal](https://portal.azure.com), select **Create a resource**, search for **Azure OpenAI**, and select **Create**.
2. Select the subscription we can use, choose **Create new** under **Resource group**, and enter `rg-s2s-supplychain-demo`.
3. Choose a region with quota for the model, enter a globally unique resource name, and select the available pricing tier. Select **Review + create**, then **Create**.
4. Open the resource in Microsoft Foundry. Under **Deployments**, select **Deploy model**, then **Deploy base model**.
5. Choose `gpt-4.1` if available in that region and subscription, set **Deployment name** to `gpt-4.1`, and create the deployment. If we use another model, retain its actual deployment name in the configuration.
6. Back on the resource, open **Keys and Endpoint** and copy the endpoint. For a local key-auth trial, retrieve a key only if our organization permits local authentication.

After creating the resource, ask the assistant to configure the existing Azure OpenAI reasoning component with the endpoint, deployment name and approved authentication method, then restart the local service. Supply secrets through the local secret store or another approved secure mechanism, not in the prompt.

**Behind the scenes**

For the local API-key variant, the configuration and restart commands look like this:

#### .NET

```powershell
dotnet user-secrets set "AzureOpenAI:Endpoint" "https://<resource>.openai.azure.com/"
dotnet user-secrets set "AzureOpenAI:Deployment" "gpt-4.1"
dotnet user-secrets set "AzureOpenAI:Authentication" "ApiKey"
dotnet user-secrets set "AzureOpenAI:ApiKey" "<resource-key>"
dotnet user-secrets set "Agent:ReasoningMode" "AzureOpenAI"
dotnet run --launch-profile http
```

The reasoning component now invokes `AIAgent.RunAsync` with the event, order and inventory facts. The host still performs the four operations in a fixed order.

#### Python and Node.js

The assistant updates these settings in the ignored `.env` file, using the key supplied through our approved secure mechanism:

```dotenv
AGENT_REASONING_MODE=AzureOpenAI
AZURE_OPENAI_ENDPOINT=https://<resource>.openai.azure.com/
AZURE_OPENAI_DEPLOYMENT=gpt-4.1
AZURE_OPENAI_API_VERSION=2024-12-01-preview
AZURE_OPENAI_AUTHENTICATION=ApiKey
AZURE_OPENAI_API_KEY=<resource-key>
```

Restart with `uv run python -m app` for Python or `npm start` for Node.js. Both use LangChain's `AzureChatOpenAI` to summarize the same event, order and inventory facts. The configuration names are shared across these two stacks; environment variables override `.env` values.

Generated text never decides which external resource to call, and an empty or failed model response fails the run instead of silently substituting stub text. Use a fresh source event ID to get a new run rather than replaying an earlier stub result.

For a hosted connection, use managed identity and assign **Cognitive Services OpenAI User** at the Azure OpenAI resource. For a local noninteractive Entra connection, create an approved service principal, assign the same role and select `ClientSecret`. The [.NET](0.Resources/Starting-point/dotnet/README.md#configuration), [Python](0.Resources/Starting-point/python/README.md#configuration) and [Node.js](0.Resources/Starting-point/nodejs/README.md#configuration) READMEs list the required settings. No stack invokes interactive login at runtime. This model credential is independent of the Agent 365 identity we create later.

When switching Node.js to a token-based model credential, clear any previously configured `AZURE_OPENAI_API_KEY`; its underlying SDK rejects a simultaneous key and token provider. Python rejects an ambient `AZURE_OPENAI_AD_TOKEN` so it cannot override the configured workload credential. These are SDK configuration differences, not changes to the S2S identity path.

## Phase 1: Protect the webhook with Entra

This phase creates the middleware and API registrations, not the Agent 365 blueprint. We or our tenant administrator perform the portal steps below; afterward, the assistant can wire their identifiers into the existing authentication code. The Agent 365 registration skill runs in Phase 2.

### Step 1-1. Create the inbound API registration

We need an application permission that authorizes submission of a shipment event. We're putting it on a separate webhook API registration, so this permission won't be confused with permission to read inventory or export telemetry.

We authenticate the calling application to decide whether it may trigger work and to record a verified service caller. This doesn't identify a human who might have triggered the middleware upstream. The workflow executes under the agent's own identity, without a user's delegated permissions.

1. In the [Microsoft Entra admin center](https://entra.microsoft.com), open **Entra ID**, **App registrations**, then **New registration**.
2. Set **Name** to `SupplyChain Webhook API`, select **Accounts in this organizational directory only**, leave **Redirect URI** empty, and select **Register**.
3. Record **Application (client) ID** and **Directory (tenant) ID**. The application ID becomes `Ingress:Audience` in .NET or `INGRESS_AUDIENCE` in Python and Node.js, not the agent ID.
4. Open **Owners** and assign an accountable owner. Open **Expose an API**, select **Add** beside **Application ID URI**, and save `api://<webhook-api-client-id>`.
5. Open **App roles**, select **Create app role**, and enter **Display name** `Invoke shipment workflow`, **Allowed member types** `Applications`, **Value** `Shipment.Invoke`, and **Description** `Submit shipment exceptions to the supply-chain webhook`. Enable the role and select **Apply**.
6. Open **Manifest**. Within the existing `api` object, set `requestedAccessTokenVersion` to `2`, preserving its other fields, then save.
7. Open **Token configuration**, select **Add optional claim**, choose **Access**, select **idtyp**, and select **Add**.

The [app-role guide](https://learn.microsoft.com/entra/identity-platform/howto-add-app-roles-in-apps) describes the role assignment model. The [`idtyp` optional claim](https://learn.microsoft.com/entra/identity-platform/optional-claims-reference) is `app` for app-only tokens. Our policy requires it as well as `roles`; the absence of a user name by itself isn't enough.

### Step 1-2. Create and authorize the middleware caller

1. Under **App registrations**, select **New registration**, name it `SupplyChain Middleware`, use the same single-tenant setting, and leave **Redirect URI** empty.
2. Record its **Application (client) ID** and add an owner under **Owners**.
3. Open **API permissions**, select **Add a permission**, then **My APIs**, and choose `SupplyChain Webhook API`.
4. Select **Application permissions**, choose `Shipment.Invoke`, and select **Add permissions**.
5. Have an authorized administrator select **Grant admin consent for \<tenant\>** and confirm the grant.
6. For the local tenant exercise, open **Certificates & secrets**, select **New client secret**, enter `Local S2S exercise`, and choose a short permitted lifetime. Copy the secret **Value** into our secret store, not into a tracked file.

This grant lets the middleware call the webhook. It grants nothing to the agent on an ERP, a model or the observability service. A deployed caller should use a certificate or workload identity federation rather than a copied development secret.

### Step 1-3. Configure and exercise real token validation

**What we ask the assistant**

> Configure Entra ingress using the tenant, webhook API and middleware client IDs I provide. Allow the middleware to invoke the agent with `Shipment.Invoke`, keep stub reasoning, and help me send one authenticated event. Don't print tokens or put secrets in tracked files.

Provide the three identifiers with the prompt. The assistant edits the configuration; we enter the caller credential through a secure local prompt or secret store when needed.

**Behind the scenes**

#### .NET

The resulting `Ingress` section looks like this:

```json
{
  "Ingress": {
    "Mode": "Entra",
    "TenantId": "<tenant-id>",
    "Audience": "<webhook-api-client-id>",
    "RequiredRole": "Shipment.Invoke",
    "AllowedCallers": {
      "<middleware-client-id>": "SupplyChain Middleware"
    }
  }
}
```

The assistant merges these values into the existing file. These are identifiers, not secrets. The allowlist is an additional boundary: the caller needs both a valid role assignment and an entry here. The display name is our configured label, not an untrusted request header.

After stopping the local host, the assistant restarts it without the Development launch profile. The equivalent commands are:

```powershell
$env:ASPNETCORE_ENVIRONMENT = "Production"
dotnet run --no-launch-profile --urls "http://localhost:5168"
```

Production avoids loading the fictional Development identity settings. It also doesn't read development user-secrets, so any optional model credentials must come from environment variables or a deployment secret provider. Keep `Agent:ReasoningMode=Stub` for this ingress exercise.

#### Python and Node.js

The assistant replaces the local identity settings in `.env` with the real registration values:

```dotenv
APP_ENVIRONMENT=Production
INGRESS_MODE=Entra
INGRESS_TENANT_ID=<tenant-id>
INGRESS_AUDIENCE=<webhook-api-client-id>
INGRESS_REQUIRED_ROLE=Shipment.Invoke
INGRESS_ALLOWED_CALLERS={"<middleware-client-id>":"SupplyChain Middleware"}
AGENT_REASONING_MODE=Stub
```

Restart with `uv run python -m app` or `npm start`. Remove the unused local signing key, and clear any shell variables that override these settings. Production refuses Local mode; Entra mode validates the JWT against the tenant's signing keys and v2 issuer.

#### Acquire the caller token

The following reference shows a caller token request using the middleware credentials. If the assistant runs this variant, the operator enters the development secret at the credential prompt:

```powershell
$tenantId = "<tenant-id>"
$callerId = "<middleware-client-id>"
$apiId = "<webhook-api-client-id>"
$credential = Get-Credential -UserName $callerId -Message "Enter the middleware client secret as the password"
$response = Invoke-RestMethod -Method Post `
    -Uri "https://login.microsoftonline.com/$tenantId/oauth2/v2.0/token" `
    -Body @{
        grant_type = "client_credentials"
        client_id = $callerId
        client_secret = $credential.GetNetworkCredential().Password
        scope = "api://$apiId/.default"
    }
$env:S2S_CALLER_TOKEN = $response.access_token
Remove-Variable credential, response
```

The operator enters a development secret once; this is a client-credentials request, not a runtime user login. A middleware deployment acquires and refreshes the token with its configured workload credential. The token is addressed to the webhook API and must contain `idtyp=app`, `roles=["Shipment.Invoke"]`, the configured tenant, and the middleware's client ID.

With `S2S_CALLER_TOKEN` set in that terminal, the assistant submits one event using the chosen stack's command:

| Stack | Command |
| --- | --- |
| .NET | `.\Invoke-Replay.ps1 -Count 1 -BatchId "entra-shipment"` |
| Python | `uv run python -m app.replay --count 1 --batch-id entra-shipment` |
| Node.js | `npm run --silent replay -- --count 1 --batch-id entra-shipment` |

**What we verify**

The authenticated request should create one run, and its logs should identify the middleware client ID. We use HTTP only over loopback here. Don't publish this listener directly or send real bearer tokens to an unencrypted remote address.

## Phase 2: Register the agent

### Step 2-1. Run Agent 365 setup for S2S

We now have an authorized event coming in, but the workflow hasn't become a governed agent yet. This is where the dedicated Agent 365 skills take over.

**What we ask the assistant**

> Register this agent with Agent 365. It runs without a signed-in user.

This request uses `a365-setup`. For this scenario, choose **Agent (Non AI Teammate)** and **S2S** when asked. If setup offers observability immediately afterward, we can continue into Phase 3 in the same conversation; there is no need to register again. We don't need Teams hosting or Work IQ for this example.

**What the skill does**

`a365-setup` checks the CLI and prerequisites, then routes to `make-a365-agent` for registration. The assistant runs the setup commands and writes the resulting configuration. We confirm the tenant, approve resource creation and complete any sign-in or administrator handoff it requests.

**Behind the scenes**

The following commands show the setup operation the skill drives. Don't run them again after the skill has completed registration:

```powershell
az login --tenant "<tenant-id>"
a365 setup all --agent-name "SupplyChainExceptionAgent" --tenant-id "<tenant-id>" --authmode s2s
```

This is operator setup, so interactive sign-in here doesn't introduce a human into the runtime flow. The default non-teammate path creates the blueprint and child service principal without an agent user. The command omits `--aiteammate` and `--m365` because this is a webhook.

**What we verify**

If setup prints an administrator handoff, complete it before proceeding. A permission declaration on a blueprint is not an application-role assignment. We need the effective observability permission on the acting agent identity.

> Inspect the generated diff before committing it. Setup can write credential values into generated configuration. Ask the assistant to move secrets to .NET user-secrets, an ignored local `.env`, or a deployment secret provider. A generated `TokenValidation:Enabled=false` setting belongs to Agents SDK hosting and must not remove or disable the webhook's independent ingress checks in any stack.

### Step 2-2. Record the identity mapping

Ask the assistant to report the blueprint client ID, child agent client ID and child service principal object ID separately, confirming the child against Entra. We review that mapping rather than relying on a generated field named just `AgentId`.

**Behind the scenes**

This is the lookup the assistant can use:

```powershell
az ad sp show --id "<agent-identity-client-id>" `
    --query "{clientId:appId,objectId:id,displayName:displayName}" --output json
```

The result distinguishes `appId` from `id`. Use `appId` for `gen_ai.agent.id`, token acquisition and the exporter; use `id` for service-principal grants and audit metadata. If our account cannot read the identity, ask the tenant administrator to confirm these values.

The observability skill adds the configuration it needs in Phase 3. The following example groups the identity and scope values used in this guide, including an object ID for the optional audit attributes. The generated key names can differ; we don't need to create this exact section by hand:

```json
{
  "Agent365Observability": {
    "TenantId": "<tenant-id>",
    "AgentBlueprintId": "<blueprint-client-id>",
    "AgentId": "<agent-identity-client-id>",
    "AgentObjectId": "<agent-identity-object-id>",
    "ResourceScope": "api://9b975845-388f-4429-889e-eab1ef63949c/.default"
  }
}
```

The starting points don't read this section. It is a .NET-shaped example of the identity mapping, not a required configuration format for Python or Node.js. The assistant uses the registration details available in our project and adds the runtime settings its implementation needs. When reviewing them, check that credentials stay outside tracked files and that the agent client ID isn't confused with the blueprint or object ID. We don't need user-specific identifiers for this S2S agent.

### Step 2-3. Confirm the permission and credential boundary

Review the setup output with the assistant and confirm the administrator's grant. The acting agent needs the **application** role `Agent365.Observability.OtelWrite` on the observability resource. A delegated permission with the same display name is not sufficient.

For a later hosted deployment, the blueprint needs a federated identity credential that trusts the host's managed identity. This deployment work is outside the local exercise. The [managed identity federation guide](https://learn.microsoft.com/entra/workload-id/workload-identity-federation-config-app-trust-managed-identity) covers creation of the managed identity and the trust. The managed identity authenticates the blueprint; it doesn't replace the child identity in exported activity.

We're keeping ERP, inventory, channel and ITSM as stubs, so there are no grants for them yet. When we replace one, the API owner must expose an application permission, an administrator must assign it to the agent identity, and our adapter must request that resource's `/.default` token. A Teams-style stub doesn't imply that a normal Microsoft Graph channel-posting operation supports unrestricted app-only access.

## Phase 3: Add observability

We describe the capability we want and let `instrument-observability` inspect the agent and make the changes. Steps 3-2 through 3-4 explain the token service, exporter and spans for review. Step 3-5 is an optional extension for this sample's operational questions.

### Step 3-1. Instrument the existing execution boundary

### Step 3-2. Review token acquisition and refresh

**Behind the scenes**

The [architecture](2.Architecture.md#the-two-outbound-exchanges) gives the exact protocol shapes. The blueprint first requests T1 with `fmi_path` set to the child agent client ID. The child then uses T1 as its client assertion in a second client-credentials request for the observability resource.

The current [S2S authentication recipe](https://learn.microsoft.com/microsoft-agent-365/developer/observability-authentication-setup#agent-365-enabled-using-s2s) requests `api://9b975845-388f-4429-889e-eab1ef63949c/.default`. Follow that recipe as a pair with its exporter configuration. Some older scaffolds use a Power Platform scope; don't mix a token from one recipe with an endpoint from another. Confirm the final token audience and role locally without logging or uploading the token.

Ask the assistant to walk through the generated token service against these requirements and correct any gaps:

1. It uses a blueprint credential only to acquire an assertion for the configured child, and uses the child client ID in the resource exchange.
2. It caches resource tokens by tenant, agent client ID and resource scope, honors expiry with a refresh margin, and coordinates concurrent refresh.
3. It can refresh when the exporter runs after the HTTP request has finished. It doesn't retain an HTTP request object, the inbound bearer token or a request-scoped service.
4. It rejects an unexpected agent or tenant passed to the resolver and surfaces token acquisition failures without returning an empty token as success.
5. It uses managed identity federation or a certificate in deployment; a development blueprint secret stays outside tracked files.

The final token must identify the child agent in `azp` or `appid`, carry the configured tenant and observability audience, and contain the `Agent365.Observability.OtelWrite` application role. A token with `scp` and a user context belongs to a delegated recipe.

### Step 3-3. Select the exporter and operational destination

For this exercise, we can ask the assistant to show the traces locally before testing tenant export: "Show me the traces in the console first." It applies the exporter settings needed for that check. Console and OTLP are diagnostic choices, not extra information required in the initial onboarding prompt.

**Behind the scenes**

The skill adds the Microsoft OpenTelemetry distribution and any framework integration it needs. The package and initialization syntax differ by stack; the identity and refresh requirements stay the same.

#### .NET

```powershell
dotnet add package Microsoft.OpenTelemetry
```

The skill records the selected version in the project file and adapts the code to its API surface. The dependency is absent from the repository's starting point because the skill adds it during onboarding; there is no separate package-install step for us here.

The [distribution documentation](https://learn.microsoft.com/microsoft-agent-365/developer/microsoft-opentelemetry) shows the console configuration:

```csharp
builder.UseMicrosoftOpenTelemetry(options =>
{
    options.Exporters = ExportTarget.Console;
});
```

The extension comes from `Microsoft.OpenTelemetry`. This is an excerpt of the registration the skill adds before `builder.Build()`, not an additional registration to paste alongside another provider. Console output lets us inspect the spans before sending them to a tenant.

When we ask the assistant to enable Agent 365 export, it configures both a custom resolver and S2S routing. This excerpt shows those settings:

```csharp
options.Exporters = ExportTarget.Agent365 | ExportTarget.Console;
options.Agent365.UseS2SEndpoint = true;
options.Agent365.TokenResolver = (agentId, tenantId) =>
    s2sTokens.GetTokenAsync(agentId, tenantId);
```

Here `s2sTokens` and `GetTokenAsync` are illustrative names for the refreshable service and its token lookup method, not built-in SDK names or names we must request in the prompt. The official [authentication setup](https://learn.microsoft.com/microsoft-agent-365/developer/observability-authentication-setup) requires the custom resolver for S2S. The generated exporter must not resolve request-scoped services.

These flat properties match `Microsoft.OpenTelemetry` 1.0.7, used in the [manual implementation](3.Runbook-Manual.md#net-implementation). Some Learn examples show an older nested `.Exporter` property; the assistant needs to follow the API of the package it installs.

#### Python

```powershell
uv add microsoft-opentelemetry
```

The skill records the dependency in `pyproject.toml` and updates `uv.lock`. It initializes the distribution before the model and application components that need instrumentation. This excerpt shows the console-only choice:

```python
from microsoft.opentelemetry import use_microsoft_opentelemetry

use_microsoft_opentelemetry(
    enable_a365=True,
    a365_enable_observability_exporter=False,
    enable_console=True,
)
```

The Agent 365 exporter is disabled while we inspect spans locally. When we approve tenant export, the assistant changes that same registration to use the refreshable S2S resolver:

```python
use_microsoft_opentelemetry(
    enable_a365=True,
    a365_enable_observability_exporter=True,
    a365_use_s2s_endpoint=True,
    a365_token_resolver=s2s_tokens.get_token,
    enable_console=True,
)
```

`s2s_tokens.get_token` is an illustrative callback name, not a function shipped in the starting point. The skill must match its callable shape to the installed SDK and provide refresh that works outside a FastAPI request, including when export runs on a worker thread. A cache containing only the first token isn't sufficient.

#### Node.js

```powershell
npm install @microsoft/opentelemetry
```

The skill updates `package.json` and the lockfile. It initializes instrumentation before importing the application and LangChain components that need it. The console-only registration can look like this:

```typescript
import { useMicrosoftOpenTelemetry } from "@microsoft/opentelemetry";

process.env.ENABLE_A365_OBSERVABILITY_EXPORTER = "false";
useMicrosoftOpenTelemetry({ enableConsoleExporters: true });
```

The environment setting prevents tenant export during the local check. When we approve Agent 365 export, the assistant replaces that registration and removes the disabling setting:

```typescript
process.env.ENABLE_A365_OBSERVABILITY_EXPORTER = "true";
useMicrosoftOpenTelemetry({
  enableConsoleExporters: true,
  a365: {
    enabled: true,
    useS2SEndpoint: true,
    tokenResolver: (agentId, tenantId) =>
      s2sTokens.getToken(agentId, tenantId),
  },
});
```

`s2sTokens.getToken` is an illustrative name for the generated token service. It resolves tokens for the configured child identity even after the Express response completes. The [distribution documentation](https://learn.microsoft.com/microsoft-agent-365/developer/microsoft-opentelemetry) describes the activation flags; an environment variable alone doesn't enable Agent 365 without the corresponding code options.

These console and tenant examples are alternatives at a single initialization point, not registrations to stack on top of one another. The skill adapts them to the SDK version it installs, enables the relevant Agent Framework or LangChain integration, and arranges exporter shutdown so buffered spans can flush when the process exits.

For an existing OTLP collector, .NET uses `ExportTarget.Otlp` and `OtlpEndpoint`; Python and Node.js support `OTEL_EXPORTER_OTLP_ENDPOINT`. We give the assistant the collector settings and ask it to configure export, including TLS and authentication. If we don't have a collector and storage backend, we stay on console; this guide doesn't provision them.

The Agent 365 route is a trace destination. If we add the optional volume metrics in Step 3-5, they need an operational destination of their own; we don't expect Agent 365's trace endpoint to retain them as metrics.

### Step 3-4. Check the semantic spans and attribution

**Behind the scenes**

The instrumentation associates spans with the configured tenant and agent client ID. These excerpts show the baggage scope around our webhook's invocation and child scopes; another agent's generated code may use a hosting integration instead.

#### .NET

```csharp
using var baggageScope = new BaggageBuilder()
    .TenantId(tenantId)
    .AgentId(agentClientId)
    .ConversationId(run.CorrelationId)
    .Build();
```

`BaggageBuilder` comes from `Microsoft.Agents.A365.Observability.Runtime.Common`. The `using` scope must remain open through the awaited workflow.

#### Python

```python
from microsoft.opentelemetry.a365.core import BaggageBuilder

with (
    BaggageBuilder()
    .tenant_id(tenant_id)
    .agent_id(agent_client_id)
    .conversation_id(correlation_id)
    .build()
):
    # Create the invocation and its child scopes inside this context.
    ...
```

The context manager surrounds the awaited workflow, so its invocation, tool and real inference spans inherit the configured identity. It must not close before the asynchronous work completes.

#### Node.js

```typescript
import { BaggageBuilder } from "@microsoft/opentelemetry";

const baggageScope = new BaggageBuilder()
  .tenantId(tenantId)
  .agentId(agentClientId)
  .conversationId(correlationId)
  .build();

await baggageScope.run(async () => {
  // Create and await the invocation and its child scopes here.
});
```

The callback keeps the asynchronous workflow inside the baggage context. Merely calling `build()` doesn't put later operations inside it.

In all three examples, we're mapping the business correlation label into the SDK's conversation field for grouping. The label doesn't prove a caller's identity and doesn't replace the unique run or trace ID. Identity values come from trusted configuration, never incoming baggage.

The invocation request carries the execution context appropriate to the host. In our webhook example, that includes correlation/session context and a webhook channel value. `AgentDetails` uses the child client ID and blueprint client ID, with user-specific fields absent when there is no user.

| Signal | What we review |
| --- | --- |
| `invoke_agent` | Agent and tenant identity, execution context, outcome and sanitized output |
| `execute_tool` | The actual tool operation, its parent invocation, duration and outcome |
| `chat` | Actual model and deployment, inference outcome and available token usage; only for a real model call |

In the supply-chain code, inspect the workflow entry point and the helper that wraps its four tool calls. In .NET these are `ShipmentWorkflow.RunAsync` and `ExecuteToolAsync`; the Python and Node.js starting points have the equivalent boundaries in their workflow modules. These are places to inspect in the generated diff, not names a customer needs to put in a prompt. A replay should not create another agent invocation, and stub reasoning should not create a model span. For a real model call, avoid adding a second inference span if the framework integration already records that operation.

The generated code must record output messages before closing the invocation scope. A span named after a method, or an HTTP server span by itself, doesn't supply the semantic invocation that Agent 365 uses. Sensitive prompt capture should remain off by default: an order summary may contain business data.

**What we verify**

Ask the assistant to explain the generated token resolver and span placement, then review the build and existing behavior checks. In our own agent, those checks should exercise its normal invocation and tools. If the skill reports a framework limitation or misses a code path, address that finding with a focused follow-up.

### Step 3-5. Add machine-rate metrics (optional)

Agent 365 onboarding doesn't require the supply-chain demo's volume counters or shipment attributes. We can skip this step and verify agent activity in Phase 4.

For this example, we also want to investigate retries and rejected machine calls, including requests that never became agent invocations. That is application-specific telemetry. Once the standard instrumentation works, we can ask for it separately:

> Also help me track which service and business event triggered each run, how often requests are rejected or replayed, and how long the workflow and its tools take.

With our own agent, we would describe its operational questions instead. The following tables show one possible design for this supply-chain example, not a built-in output contract of `instrument-observability`.

**Behind the scenes**

The sample already has caller, event and correlation fields in its structured logs. An optional extension can carry these into traces and add the following counters:

| Instrument | Type | Useful bounded dimensions |
| --- | --- | --- |
| `s2s.ingress.attempts` | Counter | Caller or `unknown`, identity mode |
| `s2s.ingress.rejections` | Counter | Caller or `unknown`, bounded reason code |
| `s2s.runs` | Counter | Caller, outcome, reasoning mode |
| `s2s.replays` | Counter | Caller, replay decision |
| `s2s.run.duration` | Histogram, seconds | Outcome, reasoning mode |
| `s2s.tool.duration` | Histogram, seconds | Target, operation, outcome |

The generated code must increment ingress attempts before authentication can reject a call, and count a new run only after a successful event reservation. A duplicate contributes an attempt and a replay, not another run. Source event IDs, correlation IDs, run IDs and arbitrary submitted strings must not become metric labels.

For the custom audit attributes, keep the verified caller client ID and configured display name, source event ID, correlation ID and run ID. Add the agent object ID from trusted configuration if we need it for directory lookups. Rejections retain their reason code and use `unknown` when no caller has been authenticated; an unvalidated header must not become caller attribution.

When adding data-access attributes to tool records, distinguish permission type from scope. `application` says which authority was exercised, while `one_order`, `one_sku` or a channel identifier describes the data accessed. Until we replace the stubs, retain `ToolMode=Stub` and `PermissionMode=none`. Keep bearer tokens, secrets and raw credential responses out of every record.

The assistant must register the custom meter with the metrics provider and route these metrics and rejection logs to the operational destination. Step 4-2 provides example `s2s.*` names for the custom attributes; our own agent can use its existing naming conventions.

**What we verify**

If we add this extension, ask the assistant to show where it updates the counters and carries the audit fields, along with the build and local-check results. These checks are separate from confirming Agent 365 trace ingestion.

#### Query any stack's application logs

```powershell
$records = Get-Content "$env:TEMP\supply-chain-s2s.jsonl" | ForEach-Object { $_ | ConvertFrom-Json }
$rows = foreach ($record in $records) {
    if ($null -eq $record.State) {
        $record
        continue
    }
    $fields = @{}
    foreach ($scope in $record.Scopes) {
        foreach ($property in $scope.PSObject.Properties) { $fields[$property.Name] = $property.Value }
    }
    foreach ($property in $record.State.PSObject.Properties) { $fields[$property.Name] = $property.Value }
    $fields["Timestamp"] = $record.Timestamp
    [pscustomobject]$fields
}
$rows | Where-Object SourceEventId -eq "nightly-demo-1" |
    Select-Object EventName, CallerClientId, CorrelationId, RunId, TargetSystem, Operation, DataScope, Outcome
$rows | Where-Object EventName -eq "ingress.rejected" |
    Group-Object CallerClientId, Reason | Select-Object Name, Count
$rows | Where-Object { $_.EventName -eq "run.started" -and [datetimeoffset]$_.Timestamp -gt [datetimeoffset]::UtcNow.AddHours(-1) } |
    Group-Object CallerClientId | Select-Object Name, Count
```

The normalization block flattens .NET's `Scopes` and `State` properties; Python and Node.js already emit the application fields at the top level. The first query reconstructs one business event. The second groups rejected attempts by verified caller and reason; invalid tokens remain `unknown`. The third counts actual runs during the last hour. It doesn't claim that 400 is an hourly baseline: we must derive expected rates from the scheduler and normal production history.

If we chose the optional extension in Step 3-5, this is one possible custom attribute mapping alongside the standard agent attributes:

| Governance question | Attributes and signals to query |
| --- | --- |
| Which service invoked this run? | `s2s.caller.client_id`, `s2s.caller.display_name`, `s2s.run.id` |
| What did the agent touch, and how broadly? | `gen_ai.agent.id`, `s2s.agent.object_id`, `s2s.target.system`, `s2s.operation`, `s2s.data_scope`, `s2s.permission_mode` |
| Which business event started it? | `s2s.source_event.id`, `s2s.correlation.id` |
| Did the rate change? | `s2s.runs` and `s2s.ingress.attempts`, grouped into comparable time windows |
| Which attempts were rejected? | `s2s.ingress.rejections` and rejection logs with `s2s.rejection.reason` |

These `s2s.*` attributes belong to the optional sample extension. They aren't reserved Agent 365 field names or something the basic skill prompt promises to generate. If we adopt this mapping, ask the assistant to confirm it appears consistently on the relevant records and query it in our operational backend; the Microsoft 365 admin center doesn't necessarily display every custom attribute.

The optional original-initiator question for agent-to-agent calls remains outside this sample. We don't fill that gap with a copied `X-Original-Caller` header.

### Step 4-3. Recognize common failures

The [cross-scenario troubleshooting guide](../../03-references/Troubleshooting.md#an-s2s-webhook-works-but-the-expected-trace-is-missing) separates ingress, model and exporter credentials, and explains why replays and stub reasoning produce different evidence from new model-backed runs.

| Symptom | Check |
| --- | --- |
| Host refuses to start in Local mode | Development environment and a random local key of at least 32 bytes; Python and Node.js read `APP_ENVIRONMENT` and `INGRESS_LOCAL_SIGNING_KEY` |
| Another stack cannot bind the listener | All three default to port `5168`; stop the other host or configure another port and replay base URL |
| Webhook returns `401` | Signature, issuer, v2 API audience, expiry; don't confuse API ID with agent ID |
| Webhook returns `403 app_only_required` | `idtyp=app` is present and no delegated or user claims are carried |
| Webhook returns `403 missing_role` | Role assignment and admin consent on the webhook API |
| Webhook returns `403 caller_not_allowed` | Verified middleware client ID is in the configured allowlist |
| Same event returns `409` | Changed payload, active execution or a retained failed run |
| New event returns `503` | Process-local ledger capacity; don't clear it as a production retry strategy |
| Token exchange returns `AADSTS82001` | Blueprint was used directly against the resource instead of through the child exchange |
| Export returns `401` or `403` | Token audience, application role, tenant, child client ID and S2S route |
| Activity is absent despite export | Semantic `invoke_agent`, output, identity attributes and tenant eligibility |

## Wrapping up

We started with a locally runnable webhook in .NET, Python or Node.js, used `a365-setup` to register the agent, and asked `instrument-observability` to add the S2S token service and telemetry. The assistant performed the CLI and code work; we supplied the tenant decisions and approvals, then reviewed the result using the behind-the-scenes explanations.

The same short requests apply to our own supported agent: register it, then ask for Agent 365 observability and select S2S. The sample's shipment attributes and volume metrics are optional additions for its business workflow, while the token and SDK details remain reference material for reviewing the generated result.

Before deploying this beyond a single-process exercise, replace the ledger with durable storage, implement authenticated adapters for the real downstream systems, and configure the host's federated credential, HTTPS endpoint and operational telemetry destination. The [sample requests](4.Sample-prompts.md) remain useful after those changes because they exercise the same ingress contract.
