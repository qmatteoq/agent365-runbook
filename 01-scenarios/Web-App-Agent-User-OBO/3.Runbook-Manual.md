# Step-by-Step Guide: Web App Agent with User OBO (Manual Path)

> **Scenario**: Onboarding a user-driven web agent into Microsoft Agent 365, entirely by hand
> **Platform**: Microsoft Agent 365 · Microsoft Entra ID · OpenTelemetry
> **Stacks**: .NET Agent Framework (Blazor Server) · Python + LangChain (FastAPI) · Node.js + LangChain (Express)
> **Target Readers**: Agent developers, Entra administrators
> **Last Updated**: February 2026

## Introduction

We have an agent. It works: a user opens a web page, asks a question, the agent reasons over it, calls a few tools, and answers. From the outside it looks finished.

From the point of view of the organization it runs in, however, that agent doesn't exist. Nobody can see it in the tenant inventory. Nobody knows what it did yesterday, on whose behalf, or which data it touched. If a security analyst asks "which agents accessed customer mailboxes last week?", our agent won't be part of the answer, not because it behaved well, but because it never told anyone anything.

**Microsoft Agent 365** is what closes that gap. It gives the agent an identity in the tenant, a way to report its activity to Microsoft Defender, Microsoft Purview and the Microsoft 365 admin center, and a governed path to Microsoft 365 data.

This guide is the **manual path**. There is a sibling to it, [3.Runbook.md](3.Runbook.md), which does most of the same work by asking an AI coding assistant to edit the project for you through the [Agent 365 Skills](https://github.com/microsoft/agent365-skills). That route is faster when it applies. It also assumes you have GitHub Copilot, Claude Code or something comparable, that you are allowed to point it at this codebase, and that you are comfortable reviewing a large generated diff. Plenty of teams fail at least one of those tests, and a pipeline never passes any of them.

So here we type every command ourselves and write every line of code ourselves. There are no prompts anywhere in this guide, and nothing below assumes a coding assistant is running. Phases 0 to 3 land in the same place as the skill-driven guide, and you can move between the two: if you started with the skills and want to understand or repair what they produced, the code here is the reference to compare against. Phase 4 is the one place where the two diverge, for reasons we'll come to when we get there.

The onboarding path we're following is the **User On-Behalf-Of (OBO)** one. It's the right choice when a human drives the agent: the user signs in, and everything the agent does is attributed back to that person, including the granted permissions. There are other paths, a Teams-hosted agent or an agent acting under its own identity, and if you're not sure which one applies to you, [Choosing Your Onboarding Path](../../02-patterns/Choosing-Your-Onboarding-Path.md) walks through the decision.

The work is split into phases. Phase 1 is a setup phase that only pays off at the end of Phase 2, but from Phase 2 onwards every phase is a valid place to stop, with something real to show for it.

| Phase | What you get at the end of it | Rough time |
| --- | --- | --- |
| 0: Get it running | A working agent, and a machine that can run the tooling | 15 to 45 min |
| 1: Sign users in | An Entra app registration, and the sign-in configured and understood | 30 min |
| 2: Registration | The agent exists in your tenant as a governed identity, and users sign in to it | 30 min |
| 3: Observability | Activity flowing into Defender, Purview and the admin center | 90 to 120 min |
| 4: Work IQ | Work IQ servers chosen, and the tenant permissions granted | 30 min |
| 5: Verification | Proof that it all actually works end to end | 30 min |

Phase 3 is budgeted higher here than in the skill-driven guide, because there you review generated code and here you type it. Let's get started!

## Prerequisites

Let's get the boring part out of the way first. There are three kinds of prerequisites here: tools on your machine, licences in your tenant, and permissions on your account. Check all three now, because a gap in any of them surfaces partway through a later phase rather than at the point you'd expect.

### The tools you need on your machine

| Requirement | Minimum | Check it with | What needs it |
| --- | --- | --- | --- |
| .NET SDK | 8.0 for the CLI, 10.0 for the .NET agent | `dotnet --version` | The A365 CLI itself, and .NET agents |
| Agent 365 CLI | latest | `a365 --version` | Phases 2 and 4 |
| PowerShell | 7.0 | `pwsh --version` | The consent scripts |
| Azure CLI | latest | `az version` | Signing in to the tenant |
| Az PowerShell module | latest | `Get-Module -ListAvailable Az.Accounts` | Granting permissions |
| Git | any | `git --version` | Not applicable |
| Python | 3.12 | `python --version` | Python agents only |
| uv | latest | `uv --version` | Python agents only |
| Node.js | 20.10 | `node --version` | Node.js agents only |

> **You need the .NET 8 SDK even if your agent is written in Python or TypeScript.** This surprises people. The reason is simply that the Agent 365 CLI is distributed as a .NET global tool, so .NET has to be there to run it. It has nothing to do with the language your agent is written in. If you're following the .NET starting point, note that it targets `net10.0`, so you'll want the .NET 10 SDK for the agent itself even though the CLI is happy with 8.

The CLI is the one tool you almost certainly don't have yet, so let's install it:

```bash
dotnet tool install --global Microsoft.Agents.A365.DevTools.Cli
a365 --version
```

If the second command prints a version number, we're good. If `a365` isn't found afterwards, the global tools directory isn't on your `PATH`: add `%USERPROFILE%\.dotnet\tools` on Windows, or `$HOME/.dotnet/tools` on macOS and Linux, and open a new terminal.

The CLI moves quickly, so if you installed it a while ago, update it rather than assuming what you have is current:

```bash
dotnet tool update --global Microsoft.Agents.A365.DevTools.Cli
```

Finally, sign in to the tenant you're going to register the agent in:

```bash
az login --allow-no-subscriptions
az account show --query "{user:user.name, tenantId:tenantId}" -o json
```

Agent 365 registration is Entra work rather than Azure resource work, so it doesn't need a subscription at all, and without `--allow-no-subscriptions` a plain `az login` fails outright for accounts that don't have one. Read the output of the second command and confirm the tenant id is the one you meant, because everything from Phase 2 onwards is created wherever this session points.

### The licences your tenant needs

| Requirement | What to know |
| --- | --- |
| Microsoft 365 tenant | With Agent 365 enabled |
| Agent 365 licence | **At least one user in the tenant must hold one** |
| Azure subscription | For the Azure OpenAI resource the agent reasons wit |

### The permissions you need on your account

| Permission | Who needs it | What it's for |
| --- | --- | --- |
| Agent ID Developer | You | Creating the blueprint in Phase 2 |
| Application Developer (or higher) | You | Creating the sign-in app registration in Phase 1 |
| Global Administrator | You *or* a colleague | Tenant-wide consent: the blueprint's permissions, the `access_agent_as_user` grant, and the Work IQ grants in Phase 4 |
| Azure OpenAI access | You | The model the agent uses. For the Entra credential path you need the **Cognitive Services OpenAI User** role on the resource; for key auth, access to the resource keys |

> **You don't have to be a Global Administrator yourself, but somebody does.** The CLI does everything it's allowed to do, then prints a consent URL or a PowerShell snippet for an administrator to run. Line that person up before you reach Phase 2, otherwise you'll be blocked at the start of Phase 3 with a consent error that reads like a bug in your code.

### The agent we're onboarding

This scenario ships with three starting points, one per stack. They are the same agent three times over: a research assistant that grounds its answers in the Microsoft Learn MCP server. All three are complete and working, and none of them contains a single line of Agent 365 code:

| Stack | Framework and host | Where it lives |
| --- | --- | --- |
| .NET | Agent Framework on Blazor Server | [`0.Resources/Starting-point/dotnet/`](0.Resources/Starting-point/dotnet/) |

What all three starting points *do* already contain is the Microsoft Entra sign-in. Signing users in is ordinary web app work that doesn't require Agent 365. In Phase 1 you're going to register the application, fill the settings in and understand what the code does, so the piece your token chain will rest on is something you understand rather than a black box.

## Phase 0: Get the agent running first

Before we add anything, let's make sure the agent works as it is.
This phase is optional and you need to follow it only if you don't have an agent already, but you want to use one of the available starting points

### Step 0-1. Configure the Azure OpenAI connection

The agent reasons using a model deployed in Azure OpenAI, so the very first thing it needs to know is *which* resource to call and *which* deployment on it to use. You'll find both in the Azure portal, on the Azure OpenAI resource, under **Resource Management → Keys and Endpoint** and **Model deployments** respectively.

Every stack also wants the id of the tenant that owns that resource.

> **The tenant id is not optional if you work across more than one tenant.** Leave it out and the credential hands back a token from whichever tenant you last signed in to, which may not be the one that owns the Azure OpenAI resource, and the service answers with `HTTP 400`, `Tenant provided in token does not match resource token`. Pinning the tenant explicitly avoids an error that otherwise looks like a code problem.

#### .NET

Open `appsettings.json`. The blocks in this guide are always fragments to merge into that file rather than replacements for it, and this is the first of three that touch it, so merge rather than paste over:

```json
{
  "AzureOpenAI": {
    "Endpoint": "https://<your-resource>.openai.azure.com/",
    "Deployment": "<your-deployment-name>",
    "TenantId": "<tenant that owns the Azure OpenAI resource>"
  },
  "LearnMcp": { "Endpoint": "https://learn.microsoft.com/api/mcp" }
}
```

Those two sections are the whole of what Phase 0 needs. Phase 1 fills in `AzureAd`, and Step 3-2 extends `Agent365Observability`, and by the end all four sections sit side by side in the same file.

#### Python

Copy `.env.example` to `.env` (the example file is committed, `.env` is gitignored) and fill it in:

```bash
AZURE_OPENAI_ENDPOINT=https://<your-resource>.openai.azure.com/
AZURE_OPENAI_DEPLOYMENT=<your-deployment-name>
AZURE_OPENAI_API_VERSION=2024-10-21
AZURE_OPENAI_TENANT_ID=<tenant that owns the Azure OpenAI resource>
```

#### Node.js

The Node starting point uses the same `.env` convention as the Python one, read through `dotenv` in `src/config.ts`, so copy `.env.example` to `.env` and fill in the same four values:

```bash
AZURE_OPENAI_ENDPOINT=https://<your-resource>.openai.azure.com/
AZURE_OPENAI_DEPLOYMENT=<your-deployment-name>
AZURE_OPENAI_API_VERSION=2024-10-21
AZURE_OPENAI_TENANT_ID=<tenant that owns the Azure OpenAI resource>
```

Only the endpoint is genuinely required. `src/config.ts` falls back to `gpt-4.1` and to the `2024-10-21` API version if you leave those two out, and it throws a readable error at startup rather than a stack trace if the endpoint is missing.

### Step 0-2. Decide how the agent authenticates to Azure OpenAI

All three starting points support two ways of authenticating, and they choose between them automatically at startup with a very simple rule: *if an API key is configured, use key auth; if not, use Entra credentials.* There's no flag to flip; the presence or absence of the key is the switch.

Here's how the two compare:

|  | **Path A: Entra credentials** *(the default, and the recommended one)* | **Path B: API key** |
| --- | --- | --- |
| What it actually uses | `DefaultAzureCredential` on .NET, `AzureCliCredential` on Python and Node.js, so your `az login` session locally, and a managed identity once hosted on Azure | A resource key, sent as a bearer secret |
| What you have to configure | Nothing beyond Step 0-1; you just need to be signed in | The key itself, kept in a secret store |
| What you need access to | The **Cognitive Services OpenAI User** role on the resource | The resource keys |
| Why you'd pick it | No long-lived secret to leak or rotate, the call carries a real identity, and it's the *only* option in tenants where key auth is disabled by policy | Environments that still depend on keys. The key never expires and carries no identity of its own |

#### Path A: Entra credentials

There's nothing to add to the configuration. Just sign in to the tenant that owns the Azure OpenAI resource:

```bash
az login --tenant <tenant of the Azure OpenAI resource>
```

When you later deploy to Azure, this path keeps working with no code change. On .NET, `DefaultAzureCredential` picks up the managed identity assigned to the App Service automatically. On Python and Node.js you set one extra value, `AZURE_OPENAI_USE_MANAGED_IDENTITY=true`, which is what makes the code swap the Azure CLI credential for `DefaultAzureCredential`.

#### Path B: API key

If you do need key auth, the important thing is to keep the key out of files that get committed, and both `appsettings.json` and `.env.example` are committed. Where the key goes depends on your stack.

**.NET.** User secrets live outside the project folder entirely, so nothing you do can accidentally commit them:

```bash
dotnet user-secrets set "AzureOpenAI:ApiKey" "<your-key>"
```

You can also set the `AzureOpenAI__ApiKey` environment variable instead, which is what you'd do in a hosting environment where user secrets aren't available.

**Python.** The key goes in `.env`, which is gitignored:

```bash
AZURE_OPENAI_API_KEY=<your-key>
```

**Node.js.** Identical to Python, in the same gitignored `.env`:

```bash
AZURE_OPENAI_API_KEY=<your-key>
```

Take a second to confirm `.env` really is ignored before you paste a key into it. The repository has a single `.gitignore` at its root that covers all three starting points, and it ignores `.env` while explicitly keeping `.env.example`, but that's exactly the kind of thing worth checking rather than assuming.

### Step 0-3. Run it

Now we can start the agent.

#### .NET

```bash
cd 0.Resources/Starting-point/dotnet
dotnet run
```

The default `http` launch profile binds to `http://localhost:5140`, which is the address you'll be registering as a redirect URI in Phase 1.

#### Python

```bash
cd 0.Resources/Starting-point/python
uv sync
uv run uvicorn app.main:app --reload
```

`uv sync` creates the virtual environment and installs the dependencies from the lock file, so the first run takes a moment longer than the ones after it. The app listens on `http://localhost:8000`.

#### Node.js

```bash
cd 0.Resources/Starting-point/nodejs
npm install
npm run dev
```

`npm run dev` runs the TypeScript straight through `tsx` in watch mode, restarting the server on every change, which is the equivalent of `--reload` on the Python side. `npm start` does the same thing without the watcher, and `npm run build` compiles into `dist/` if you want a compiled artifact to deploy. Either way the app listens on `http://localhost:8000`, the same port as the Python one, so don't try to run both at once.

Open the app in a browser and ask it something it should be able to answer, for example:

```text
What is Microsoft Entra Conditional Access?
```

You should get a proper answer with links to Microsoft Learn at the end of it, because this agent grounds its answers in the Microsoft Learn MCP server rather than answering from the model's own memory.

✅ **Checkpoint.** The agent answers questions and cites its sources. There is still no trace of Agent 365 anywhere.

## Phase 1: Sign users in

Nothing in this phase is specific to Agent 365. We're going to register an ordinary Entra application, point the agent at it, and read through the sign-in code that already ships in the starting points. If you've built a web app that signs users in with Entra before, the work will be familiar.

We do it first, before touching Agent 365 at all, because the OBO path attributes everything the agent does back to the person who asked for it, and it can't do that until there's a signed-in person to attribute it to.

One value stays missing until Phase 2. The token this sign-in eventually produces has to be addressed to the agent's blueprint, and the blueprint doesn't exist yet. So this phase gets you a registered sign-in client, the settings filled in and a clear picture of the code, and then Phase 2 supplies the last value and switches the whole thing on in one short step.

### Step 1-1. Create the app registration that signs users in

Signing a user in means sending their browser to Entra and getting them back again, and Entra will only do that for an application it knows about. So the first thing we need is an app registration whose job is to authenticate the human.

Keep the values from this step somewhere handy, because you'll be pasting them into the app's configuration in Step 1-2.

#### 1-1a. Create the registration

1. Go to the [Entra admin center](https://entra.microsoft.com) and navigate to **Identity → Applications → App registrations**.
2. Click **New registration**.
3. Give it a name that makes its role obvious, something like **my-agent-web-signin**. Phase 2 adds two more identities for this one agent, so a vague name will cost you time later.
4. For **Supported account types**, choose **Accounts in this organizational directory only (Single tenant)**.
5. Under **Redirect URI**, select the **Web** platform and enter the callback address your app will actually listen on. That address depends on your stack:

| Stack | Redirect URI to register | Where the address comes from |
| --- | --- | --- |
| .NET | `http://localhost:5140/signin-oidc` | The default `http` profile in `Properties/launchSettings.json` |
| Python | `http://localhost:8000/signin-oidc` | The uvicorn defaults, and `AZURE_AD_REDIRECT_URI` in `.env.example` |
| Node.js | `http://localhost:8000/signin-oidc` | `HOST` and `PORT` in `.env.example`, and the same `AZURE_AD_REDIRECT_URI` |

6. Click **Register**.

You'll land on the **Overview** blade. Copy the **Application (client) ID** and the **Directory (tenant) ID** from there and keep them somewhere handy; we'll need both in a moment.

> **The redirect URI has to match what the browser sees, scheme included.** It's easy to register the `https` address and then run the app over plain `http`, and Entra answers that with `AADSTS50011`, which reads like a configuration mistake in the app rather than a mismatched string. If you'd rather run the .NET app over TLS, launch it with `dotnet run --launch-profile https` and register `https://localhost:7199/signin-oidc` instead. An app registration can hold several redirect URIs, so registering both now and picking later is perfectly reasonable.

> **`localhost` and `127.0.0.1` are not interchangeable here, even though they reach the same process.** The browser treats them as different origins and scopes the session cookie accordingly, so if you register the callback on `localhost` and then browse the app on `127.0.0.1`, the cookie set just before the redirect isn't sent back on the way in. The sign-in then fails in a way that looks like a lost session rather than a mismatched host. All three starting points default to `localhost` for exactly this reason, and the Python and Node ones say so in `.env.example`.

#### 1-1b. Create a client secret

1. In the same registration, go to **Certificates & secrets**.
2. On the **Client secrets** tab, click **New client secret**.
3. Give it a description and pick an expiry.
4. Click **Add**, then **copy the Value immediately**.

The value is shown once, and once you navigate away it's gone forever and you'll have to create another secret.

Store it somewhere the repository can't reach: `dotnet user-secrets` on .NET, the gitignored `.env` on Python and Node.js. Never in `appsettings.json`, which is committed.

#### 1-1c. Check the sign-in permissions

An OIDC sign-in needs `openid`, `profile` and `offline_access`, and Entra treats those as permissions any user can consent to for themselves. Go to **API permissions** and have a look at what's already there. A new registration usually arrives with **Microsoft Graph** → `User.Read` and nothing else, which is fine: the identity libraries add the OIDC scopes to the request themselves, and none of the starting points calls Graph.

So there's nothing to add here yet, and nothing that needs an administrator. This is a blade to get familiar with rather than one to change.

> **We will come back to it once.** In Step 2-3a we add a permission here that points this registration at the agent's blueprint, and that one does need admin consent. It has to wait, because the blueprint doesn't exist yet.

#### 1-1d. The same thing from the command line

If you'd rather not click through the portal, the registration and the secret can both be created from a terminal:

```bash
# Create the registration
az ad app create --display-name "my-agent-web-signin" \
  --sign-in-audience AzureADMyOrg \
  --web-redirect-uris "http://localhost:5140/signin-oidc"

# Add a secret
az ad app credential reset --id <sign-in client app id> --append
```

Swap the redirect URI for `http://localhost:8000/signin-oidc` if you're on the Python or the Node.js starting point. `az ad app create` prints the new registration as JSON, and the `appId` field in it is the client id you'll need next; `az ad app credential reset` prints the secret, and that output is the only time you'll see it.

### Step 1-2. Fill in the sign-in settings

Every stack needs the same three facts about your tenant: the tenant id, and the sign-in client's id and secret. The callback path and the authority are already filled in for you. There's a fourth value, the blueprint id, that stays blank until Phase 2, and leaving it blank now is the correct thing to do rather than an omission we'll be fixing later.

That blueprint id matters more than its one line suggests, because it's what the scope is built from. The scope is `api://<blueprint-id>/access_agent_as_user`, it has to be byte for byte identical in the sign-in request, in the token acquisition and in anything you paste into a debugger later, and a typo in any copy of it produces a token with the wrong audience rather than an error you can read. That's why all three starting points derive it in exactly one place from the blueprint id rather than letting you write the string out by hand.

#### .NET

The `AzureAd` and `Agent365Observability` sections are already in `appsettings.json`, sitting alongside the `AzureOpenAI` section you filled in during Step 0-1, with the tenant-specific values left blank:

```json
{
  "AzureAd": {
    "Instance": "https://login.microsoftonline.com/",
    "TenantId": "",
    "ClientId": "",
    "ClientSecret": "",
    "CallbackPath": "/signin-oidc"
  },
  "Agent365Observability": {
    "AgentBlueprintId": ""
  }
}
```

Fill in the tenant id and client id from the sign-in registration's **Overview** blade in Step 1-1a, and leave `AgentBlueprintId` alone for now. Leave `ClientSecret` empty in the file too, because the file is committed, and put the secret where it belongs instead:

```bash
dotnet user-secrets set "AzureAd:ClientSecret" "<sign-in client secret>"
```

`CallbackPath` has to line up with the redirect URI you registered in Step 1-1a, because `Microsoft.Identity.Web` builds the callback address from the app's own base URL plus this path. If the two disagree you'll get the `AADSTS50011` we warned about above.

The empty `Agent365Observability` section is the one Step 2-3 comes back to. It's named the way it is because that's the section the Agent 365 tooling and instrumentation look in, so filling it in later puts the blueprint id in the one place everything already expects to find it rather than introducing a second copy under a name of our own.

#### Python

The same values live in `.env`, and `.env.example` already lists them with the redirect URI filled in and the rest blank:

```bash
# Entra sign-in for the web app. Leave blank until the runbook creates the app registration.
AZURE_AD_TENANT_ID=
AZURE_AD_CLIENT_ID=
AZURE_AD_CLIENT_SECRET=
AZURE_AD_REDIRECT_URI=http://localhost:8000/signin-oidc

# Agent blueprint id. The runbook fills this in once the agent is registered, and the
# sign-in stays off until it is set.
AGENTS365OBSERVABILITY__AGENTBLUEPRINTID=
```

Fill in the first three and leave the blueprint id blank. `.env` is gitignored, which is why the secret can sit in it directly here while its .NET counterpart has to go into user-secrets.

The double underscore in `AGENTS365OBSERVABILITY__AGENTBLUEPRINTID` is a .NET configuration convention rather than a Python one. It's the name the Agent 365 tooling uses, so reading it directly means the same `.env` serves both the sign-in and everything the observability phase adds. Pydantic won't pick a name like that up on its own, so `app/config.py` maps it explicitly, and derives the scope from it in one place:

```python
agent_blueprint_id: str | None = Field(
    default=None,
    validation_alias="AGENTS365OBSERVABILITY__AGENTBLUEPRINTID",
)

@property
def agent_blueprint_scope(self) -> str:
    blueprint_id = (self.agent_blueprint_id or "").strip()
    if not blueprint_id:
        raise RuntimeError("The agent blueprint id is not configured.")

    return f"api://{blueprint_id}/access_agent_as_user"
```

You'll see `agent_blueprint_scope` again in the code we write in Phase 3. It's the scope the sign-in asks for, and Step 2-3 explains where the blueprint id in it comes from.

#### Node.js

The Node starting point reads the same variable names from the same kind of `.env` file, so `.env.example` looks almost identical to the Python one:

```bash
# Entra sign-in for the web app. Leave blank until the runbook creates the app registration.
AZURE_AD_TENANT_ID=
AZURE_AD_CLIENT_ID=
AZURE_AD_CLIENT_SECRET=
AZURE_AD_REDIRECT_URI=http://localhost:8000/signin-oidc

# Agent blueprint id. The runbook fills this in once the agent is registered, and the
# sign-in stays off until it is set.
AGENTS365OBSERVABILITY__AGENTBLUEPRINTID=

HOST=localhost
PORT=8000
```

Fill in the first three and leave the blueprint id blank, exactly as on Python. Keeping the variable names the same across the two stacks isn't an accident: the double-underscore name is the one the Agent 365 tooling writes, so honouring it here means the file the sign-in reads and the file the instrumentation reads are the same file.

`src/config.ts` reads that name straight out of `process.env` and derives the scope from it, which is the Node counterpart of the Pydantic property above:

```ts
agentBlueprintId: optional("AGENTS365OBSERVABILITY__AGENTBLUEPRINTID"),

get agentBlueprintScope(): string {
    const blueprintId = this.agentBlueprintId?.trim();

    if (!blueprintId) {
        throw new Error("The agent blueprint id is not configured.");
    }

    return `api://${blueprintId}/access_agent_as_user`;
},
```

It's a getter rather than a plain field for a concrete reason: a field would be evaluated when the settings object is built, which happens at import time, and the blueprint id is legitimately absent then. A getter is only evaluated when something actually asks for the scope, which is exactly the moment the value has to be there.

Note also the explicit `HOST=localhost`. That is the trap from Step 1-1a made concrete, and the Node app defaults to `localhost` rather than to the `127.0.0.1` that Express examples usually reach for.

### Step 1-3. Understand how the app decides whether to sign anybody in

All three starting points read the configuration at startup and ask one question: is every required sign-in value present? If anything is missing, they skip the whole authentication pipeline and behave exactly as they did in Phase 0. If everything is there, they wire it up.

Right now the app will still report the anonymous mode however carefully you filled Step 1-2 in, because the blueprint id is one of the values it looks for and that one is still empty. That's expected, and Step 2-3 is where it changes.

Phase 3 adds code on the far side of this gate, so here is how each stack decides.

#### .NET

The decision lives in `Agent365SignInOptions.FromConfiguration`, which is a little stricter than the other two: it also treats obvious placeholders as not configured, so a half-edited `appsettings.json` keeps the anonymous behaviour rather than failing against Entra.

```csharp
var requiredValues = new[] { instance, tenantId, clientId, clientSecret, callbackPath, agentBlueprintId };
var isEnabled = requiredValues.All(IsConfiguredValue);
var agentUserScope = isEnabled
    ? $"api://{agentBlueprintId}/access_agent_as_user"
    : string.Empty;
```

`IsConfiguredValue` rejects empty strings, anything containing angle brackets, anything starting with `your-`, and the all-zeroes guid. `Program.cs` then branches on `entraSignIn.IsEnabled` in four places: registering the authentication services, adding the middleware, mapping the controllers that `Microsoft.Identity.Web.UI` provides, and calling `RequireAuthorization()` on the Razor components.

#### Python

`app/config.py` exposes the same decision as a property, and `app/main.py` builds the `AuthService` only when it's true:

```python
@property
def entra_sign_in_enabled(self) -> bool:
    required_values = [
        self.azure_ad_tenant_id,
        self.azure_ad_client_id,
        self.azure_ad_client_secret,
        self.azure_ad_redirect_uri,
        self.agent_blueprint_id,
    ]
    return all(value is not None and value.strip() for value in required_values)
```

`app/main.py` then builds the service only when that property is true, which is the single place the decision is made:

```python
auth_service = AuthService(settings) if settings.entra_sign_in_enabled else None
```

#### Node.js

Identical in shape, as a getter on the settings object, with `src/main.ts` constructing the service conditionally:

```typescript
const authService = settings.entraSignInEnabled ? new AuthService(settings) : undefined;
```

#### A note on gating

The three stacks differ in how firmly they keep anonymous visitors out, and which one you're on changes what you see in Step 2-3c.

.NET gates hard: `RequireAuthorization()` on the Razor components means an anonymous browser is redirected to Entra before the chat page renders at all. Python and Node gate softly: the page loads for anyone, and it's the `/api/chat` handler that refuses to answer without a session, returning `401`. Both are legitimate choices for a sample. The soft version is the one to look at twice before production, because it means the page is public and only the API is protected.

## Phase 2: Register the agent

Now the agent stops being just code on your laptop and becomes an object in your tenant.

Two objects, actually, and the difference between them matters for everything that follows:

- The **blueprint** is the parent app registration. It holds the permissions, and it owns the agent. Think of it as the definition of the agent.
- The **agent identity** is a child principal of that blueprint. It's the thing that actually *acts*, the principal your telemetry will be attributed to.

The phase ends by going back to the sign-in from Phase 1 and giving it the piece it was missing.

Nothing in this phase depends on your stack. The CLI registers identities in Entra, and it doesn't care what language the agent is written in.

### Step 2-1. Register the blueprint and the agent identity

One command does the registration, and you should run it twice: once to see what it intends to do, and once to let it do it.

Run both from your agent's project folder, because the CLI writes its output file there.

```bash
a365 setup all --agent-name "my-agent" --authmode obo --dry-run
a365 setup all --agent-name "my-agent" --authmode obo
```

Read the dry run before you run the second line. It lists the objects it's about to create and the permissions it's about to ask for, and that summary is the cheapest opportunity you'll have to notice that you're pointed at the wrong tenant.

The two flags do different jobs:

`--agent-name` is the base name everything else is derived from. The CLI creates an app registration called `<name> Blueprint` and an identity called `<name> Identity`, which is a detail you'll want to remember in Step 2-3a when you go looking for the blueprint in a search box and type the bare name.

`--authmode obo` says that the agent acts on behalf of a signed-in user, so the agent identity gets principal-scoped delegated grants. It happens to be the default, and we pass it explicitly anyway, partly because the alternative (`s2s`, where the agent acts under its own identity and needs application permissions and a heavier consent) is a genuinely different shape, and partly because a command you can paste into a runbook or a pipeline should say what it means.

Here's what the command creates:

- an **agent blueprint** app registration, together with a client secret
- an **agent identity**, as a child of that blueprint
- the API permissions the agent needs, including `Agent365.Observability.OtelWrite`, which is the one that lets it write telemetry
- a file called `a365.generated.config.json`, holding all the generated identifiers

`a365 setup all` is idempotent, so re-running it after you fix a problem is safe.

> **On Windows the CLI may authenticate through the Windows Account Manager**, which puts a native sign-in dialog on your screen rather than printing anything in the terminal. If the command seems to hang, look for that dialog before assuming it's stuck. On a machine with no desktop it will wait for a dialog that can never appear, and the fix is to make sure `az login --allow-no-subscriptions` has already populated the token cache, so the CLI finds a cached token and skips the broker entirely.

**How to verify.** Open `a365.generated.config.json` in your editor. You're looking for two values that the rest of this guide keeps coming back to:

| Field | What it is | Where it's used later |
| --- | --- | --- |
| `agentBlueprintId` | The blueprint's app id | The sign-in scope, the baggage, hop 1 of the token chain |
| `agentIdentityClientId` | The agent identity's app id | Hop 2 of the token chain, and the id telemetry is attributed to |

Then go to the [Entra admin center](https://entra.microsoft.com) → **App registrations** and confirm that `my-agent Blueprint` is listed.

> ⚠️ **If you're not an administrator, read the CLI's closing summary carefully.** When it can't grant consent itself it prints a PowerShell snippet, under an "Action Required" heading, for an admin to run. Until somebody runs it the permissions exist but are not granted, and Phase 3 fails with a consent error that looks like a bug in your code. This is the handoff we mentioned in the prerequisites.

### Step 2-2. Store the blueprint secret somewhere safe

`a365 setup all` generated a client secret for the blueprint. That secret is what proves, when we build the token chain in Phase 3, that your code is allowed to act as this agent, so it must never end up in source control.

If you didn't catch it in the output, you don't have to re-register anything. You can read it back, on the same machine and signed in as the same user, with:

```bash
a365 setup blueprint --agent-name "my-agent" --show-secret
```

Where it goes depends on your stack, and it's the same choice you made for the Azure OpenAI key back in Step 0-2.

#### .NET

Put it in user secrets, which live outside the project folder entirely:

```bash
dotnet user-secrets set "Agent365Observability:BlueprintClientSecret" "<secret>"
```

#### Python

Put it in `.env`, and take a second to confirm that `.env` really is listed in `.gitignore`:

```bash
AGENT365_BLUEPRINT_CLIENT_SECRET=<secret>
```

#### Node.js

The same, in the same kind of gitignored `.env`:

```bash
AGENT365_BLUEPRINT_CLIENT_SECRET=<secret>
```

Nothing reads this value yet. It sits unused until Step 3-3 builds the token chain, and putting it away now simply means you handle the secret once, while the CLI output that produced it is still in front of you.

### Step 2-3. Connect the sign-in to the blueprint

Here is where the two halves meet. Phase 1 left us with an app that can authenticate a user, and Step 2-1 gave us a blueprint. What we don't have yet is a token that links them, and that link is what the OBO path runs on.

The obvious question at this point is why the blueprint can't just sign users in itself, given that it's an app registration like any other. The reason is that a blueprint is an **agentic application**, and Microsoft Entra bars agentic applications from interactive `/authorize` flows. A blueprint can never present a sign-in page. That's precisely why Phase 1 came first, and why what we registered there was a separate, completely ordinary application.

So this scenario has three identities in it, and keeping them straight in your head makes everything else easier:

| Identity | Who creates it | What it does |
| --- | --- | --- |
| **Sign-in client** | You, in Step 1-1 | Signs the user in, and requests the blueprint's scope |
| **Blueprint** | `a365 setup all`, in Step 2-1 | Owns the permissions, and authenticates hop 1 of the token chain |
| **Agent identity** | `a365 setup all`, in Step 2-1 | The principal the agent acts as, and that spans are exported as |

Keep `a365.generated.config.json` open, because you'll need the blueprint's app id twice below.

#### 2-3a. Give the sign-in app permission to call the blueprint

This is the step that makes the entire token chain possible. It's portal work, identical whatever your agent is written in.

1. Go back to the **sign-in registration** from Step 1-1, and open **API permissions**.
2. Click **Add a permission**.
3. Choose the **APIs my organization uses** tab.
4. Paste the **blueprint's app id** into the search box and select it from the results.
5. Choose **Delegated permissions**.
6. Tick **`access_agent_as_user`**.
7. Click **Add permissions**.

> **If the blueprint doesn't come up in the search**, search by its app id rather than its display name, because the CLI appends `" Blueprint"` to the name you chose and what you type may not match. And if you find the API but it exposes no scopes at all, open the **blueprint's** registration, go to **Expose an API → Add a scope**, create a scope named exactly `access_agent_as_user`, set **Who can consent?** to **Admins and users**, leave the state **Enabled**, and then come back here and repeat the steps above.

Then click **Grant admin consent for \<your tenant\>**. Consenting tenant-wide grants the permission once for everybody rather than prompting each user, which is what an agent reporting activity centrally needs. Whether the button is available to you depends on your role and on your tenant's user-consent policy. If it's greyed out, this is the second of the two admin handoffs in this guide, and a permission that's recorded but not consented to behaves exactly like one that was never added.

From the command line, the same two operations are:

```bash
# The scope id is on the blueprint's "Expose an API" blade
az ad app permission add --id <sign-in client app id> \
  --api <blueprint-app-id> --api-permissions <scope-id>=Scope

az ad app permission admin-consent --id <sign-in client app id>
```

Note that `az ad app permission add` only records the permission; the consent grant on the second line is what makes it usable.

> **Don't mix up the two secrets.** You now have a blueprint secret and a sign-in client secret, and they do completely different jobs. The blueprint secret authenticates hop 1 of the token chain; the sign-in client secret authenticates the web sign-in. Swapping them produces authentication errors that are genuinely hard to read.

#### 2-3b. Give the app the blueprint id

This is the value we left blank in Step 1-2, and it's the one that switches the sign-in on. Take `agentBlueprintId` from `a365.generated.config.json` and put it where the app expects it.

That single value does two things at once. It completes the set of settings the startup check looks for, so the authentication pipeline you read through in Phase 1 finally gets registered, and it supplies the resource half of `api://<blueprint-id>/access_agent_as_user`, which is the scope the sign-in asks for.

The scope determines who the token is *addressed to*, and hop 2 of the token chain will only accept an assertion addressed to the blueprint. Not `User.Read`, and not the blueprint's `.default`. An app can sign users in perfectly well and never ask for it, which leaves you with a working login and a token the next phase rejects.

#### .NET

In `appsettings.json`:

```json
"Agent365Observability": {
  "AgentBlueprintId": "<blueprint app id>"
}
```

#### Python

In `.env`:

```bash
AGENTS365OBSERVABILITY__AGENTBLUEPRINTID=<blueprint app id>
```

#### Node.js

In `.env`, with the same variable name as Python, since both samples read it through the same key:

```bash
AGENTS365OBSERVABILITY__AGENTBLUEPRINTID=<blueprint app id>
```

Restart the app afterwards, whichever stack you're on. On Python and Node.js the value is read once when the process starts, so a running app won't pick up the change.

#### 2-3c. Verify the token you get back

Open the app. The stacks announce themselves differently here, for the reason we covered in Step 1-3. On .NET you should be redirected to Entra before the chat page renders at all. On Python and Node.js the page still loads, and the line under the title changes from the anonymous message to a **Sign in** link. Either way, the first time on a tenant where an admin hasn't already consented, you'll be asked to approve the permissions.

Once you're back, we want to look at the token the app is holding:

- On **.NET**, set a breakpoint on the `return await tokenAcquisition.GetAccessTokenForUserAsync(...)` line in `Components/Pages/Home.razor` and reload the page. The first render probes for the token, so the breakpoint hits without you having to send a message. Copy the return value out of the debugger.
- On **Python**, set a breakpoint on the `return result["access_token"]` line in `app/auth.py` and send a message. `/api/chat` calls `acquire_user_assertion` before it does anything else, so the breakpoint hits on the first turn.
- On **Node.js**, set a breakpoint on the `return result.accessToken` line in `src/auth.ts` and send a message, for the same reason. The sample runs its TypeScript through `tsx` rather than compiling first, so point your editor's debugger at `npm run dev` and it will stop in the `.ts` file you're reading. If you'd rather use Chrome DevTools, `node --inspect node_modules/tsx/dist/cli.mjs src/main.ts` gets you the same thing.

Paste what you copied into [jwt.ms](https://jwt.ms), which decodes it in the browser without sending it anywhere, and look at four claims:

| Claim | What it should say |
| --- | --- |
| `aud` | The **blueprint's** app id, or `api://<blueprint-id>`, **not** the sign-in client's id |
| `scp` | It should contain `access_agent_as_user` |
| `oid` | The signed-in user's object id |
| `tid` | Your tenant id |

If `aud` is the sign-in client, or Microsoft Graph, then the scope wasn't requested correctly. The usual cause is a blueprint id that's present but wrong, a stale one from an earlier `a365 setup all` run, say, which builds a scope pointing at a resource that isn't your blueprint.

While you have the decoded token in front of you, make a note of the `oid` value, because Step 3-7 will reference it.

✅ **Checkpoint.** This is a perfectly good place to stop. The agent is registered and governed, it shows up in your tenant, and users sign in to it with a token addressed to the blueprint. It doesn't emit any telemetry yet; that's the next phase.

## Phase 3: Observability

This is the longest phase, and it's the one that delivers most of the value. By the end of it, every turn the agent takes will produce telemetry, attributed to the user who caused it, and visible in Defender, Purview and the Microsoft 365 admin center.

It's also the phase with the most moving parts. We install the telemetry distro, tell the app which identities it's working with, build the token the exporter needs, give the exporter somewhere to find that token, wire the distro into startup, and then instrument the turn itself.

Six things have to be true at the same time for a span to arrive. When something doesn't work in Step 3-7, the answer is nearly always that one of these is missing:

| Requirement | What happens when it's missing |
| --- | --- |
| The exporter is switched on, not merely registered | Spans are enriched and then dropped on the floor |
| A valid observability token is in the store when the batch flushes | The export goes out unauthenticated and is rejected |
| A baggage scope is open around the whole turn | `Partitioned into 0 identity groups` |
| The baggage agent id and the `AgentDetails` agent id agree | `Partitioned into 2 identity groups`, and half the spans vanish |
| A root `invoke_agent` span exists | Defender shows orphans; the admin center shows nothing |
| The caller id is a directory object id | Everything arrives, attributed to nobody |

### Step 3-1. Install the distro

The Agent 365 telemetry support ships as an OpenTelemetry distro: a wrapper around standard OTel that adds the Agent 365 exporter and the span processing the service expects. There's one for each of our three stacks, and they're close to each other in shape, which is why the steps that follow read so similarly.

#### .NET

```bash
dotnet add package Microsoft.OpenTelemetry
```

That package re-exports the Agent 365 observability types internally, so don't also add `Microsoft.Agents.A365.Observability.Runtime` or `.Hosting` as package references of their own: you'd get the same types twice and a wall of `CS0433` duplicate-type errors.

#### Python

```bash
uv add "microsoft-opentelemetry[langchain]"
uv add httpx
```

The `[langchain]` extra pulls in the LangChain instrumentation, which is what produces the `chat` spans for the model call. We add `httpx` explicitly because the token chain in Step 3-3 posts two forms to Entra. It's almost certainly already installed as a transitive dependency of the OpenAI client.

Here too, don't install the older `microsoft-agents-a365-observability-*` packages alongside it. They're the previous generation of the same code, and having both leads to imports that resolve to the wrong copy.

#### Node.js

```bash
npm install @microsoft/opentelemetry
```

The package brings its own copy of the OpenTelemetry SDK, so you don't need `@opentelemetry/sdk-node` as well. You already have `@azure/msal-node` from Phase 1, and we'll reuse nothing from it here, because the token chain uses `fetch`, which Node 20 provides globally.

### Step 3-2. Tell the app which identities it's working with

The instrumentation needs four facts, and right now the app only knows one of them. Let's get them all into configuration before we write any code, because every file in this phase reads from here.

| Value | Where it comes from | What it's for |
| --- | --- | --- |
| Tenant id | `az account show`, or the `tid` claim you decoded in Step 2-3c | Both hops of the token chain, and the baggage |
| Blueprint app id | `agentBlueprintId` in `a365.generated.config.json` | Hop 1, and the blueprint roll-up in reporting |
| Blueprint client secret | `a365 setup blueprint --show-secret`, stored in Step 2-2 | Hop 1 |
| Agent identity app id | `agentIdentityClientId` in `a365.generated.config.json` | Hop 2, and the id telemetry is attributed to |

That last row is the one people get wrong: **the agent identity, not the blueprint, is the principal your spans are attributed to.** The blueprint owns the agent and authenticates hop 1; the agent identity is what acts. Using the blueprint id where the agent identity belongs produces an export that fails with `HTTP 403`, because the id in the export route and the `azp` claim in the token no longer agree.

#### .NET

Extend the `Agent365Observability` section in `appsettings.json`. `AgentBlueprintId` is already there from Step 2-3b:

```json
"Agent365Observability": {
  "AgentBlueprintId": "<blueprint app id>",
  "AgentIdentityClientId": "<agent identity app id>",
  "TenantId": "<your tenant id>",
  "AgentName": "my-agent"
}
```

The secret stays out of that file, in user secrets, where you put it in Step 2-2:

```bash

```

Then give the app a typed view of the section, in a new file `Agent365RuntimeOptions.cs`. The name matters: the distro exports a type called `Agent365Options` of its own, so calling ours the same thing would give you two types with one name and a compiler error at the first line that mentions it.

```csharp
using Microsoft.Extensions.Configuration;

namespace LearnMcpAgent;

/// <summary>Everything the Agent 365 instrumentation needs to identify itself.</summary>
public sealed record Agent365RuntimeOptions(
    string TenantId,
    string BlueprintClientId,
    string BlueprintClientSecret,
    string AgentIdentityClientId,
    string AgentName)
{
    public static Agent365RuntimeOptions FromConfiguration(IConfiguration configuration)
    {
        var section = configuration.GetSection(Agent365SignInOptions.Agent365ObservabilitySectionName);

        return new Agent365RuntimeOptions(
            TenantId: Required(section, "TenantId"),
            BlueprintClientId: Required(section, "AgentBlueprintId"),
            BlueprintClientSecret: Required(section, "BlueprintClientSecret"),
            AgentIdentityClientId: Required(section, "AgentIdentityClientId"),
            AgentName: section["AgentName"] ?? "my-agent");
    }

    private static string Required(IConfigurationSection section, string key)
        => section[key] is { Length: > 0 } value
            ? value
            : throw new InvalidOperationException(
                $"Agent365Observability:{key} is not configured. Take it from a365.generated.config.json.");
}
```

The point of `Required` is to fail at startup with a sentence that tells you which key is missing and where to find it. The alternative is an empty string that travels all the way to Entra and comes back as an authentication error that names nothing.

### Step 3-3. Build the two-hop token chain

This is the most important part of the OBO path, and the part most nearly identical across the three stacks, because what's really going on is two HTTP requests to Entra, and the shape of those requests doesn't depend on your language.

The exporter needs a token to talk to the Agent 365 Observability API, and it has to be a specific one: a token issued to the agent identity, acting on behalf of the signed-in user. A plain delegated user token is rejected, because its principal is the human rather than the agent. Getting that token takes two hops, and both of them are form posts to `https://login.microsoftonline.com/<tenant>/oauth2/v2.0/token`.

**Hop 1** is the blueprint proving that it owns the agent identity:

```text
grant_type    = client_credentials
client_id     = <blueprint app id>
client_secret = <blueprint secret>
scope         = api://AzureADTokenExchange/.default
fmi_path      = <agent identity app id>
```

The `fmi_path` parameter is what turns this from an ordinary client-credentials call into an agent flow. It effectively says: *issue me an assertion I can use to act as this child identity*. What comes back is not an access token and cannot be used as one. It's only usable as a client assertion in the second hop.

**Hop 2** is the agent identity exchanging the user's token for the one we actually want:

```text
grant_type            = urn:ietf:params:oauth:grant-type:jwt-bearer
client_id             = <agent identity app id>
scope                 = api://9b975845-388f-4429-889e-eab1ef63949c/Agent365.Observability.OtelWrite
client_assertion_type = urn:ietf:params:oauth:client-assertion-type:jwt-bearer
client_assertion      = <the result of hop 1>
assertion             = <the user's blueprint-scoped token>
requested_token_use   = on_behalf_of
```

Look at the two assertions side by side, because that pairing is the whole idea: `client_assertion` says *which agent is asking*, and `assertion` says *who it's asking for*. That second one is the user token we so carefully addressed to the blueprint back in Step 2-3, and the app obtains it on every turn through `AcquireUserAssertionAsync()` on .NET, `acquire_user_assertion()` on Python and `acquireUserAssertion(req)` on Node.js.

The GUID in that scope is not your tenant or your agent. It's the fixed app id of the Agent 365 Observability API itself, so it's the same for everybody, and you can paste it verbatim.

> **Ask for the named scope, not `/.default`.** This is the single easiest mistake to make here, because `/.default` is what you reach for out of habit and it looks more correct. A delegated token carries scopes rather than roles, so `api://9b975845-.../.default` produces a token the export endpoint rejects with `401 InvalidAudience`. The Node distro's own built-in default happens to be the `/.default` form, which is right for the service-to-service path and wrong for ours, and it is one more reason we acquire the token ourselves rather than letting the distro do it.

One point applies to all three stacks: **watch the lifetime of the token you store.** The implementations below run both hops once per turn and keep only the result of hop 2, which is the simple arrangement and the right place to start: hop 1's assertion is used immediately and thrown away, and a chat turn is not a hot loop. What matters is that the stored token is treated as expired slightly before it really is, because a token that lapses between the turn and the exporter's next flush disables the export with no visible error at all. The agent keeps answering, and the telemetry quietly stops. The Python and Node stores below take `expires_in` off the response and subtract a five-minute margin; the .NET `ServiceTokenCache` is given the same lifetime and does its own expiry.

If your agent turns over fast enough that two Entra round trips per turn start to show, the obvious next step is to keep the hop 2 token until it's close to expiry and skip both hops while it's still good. The `needs_refresh` helpers on the Python and Node stores exist for exactly that, and nothing calls them yet, so the first version you read does the same thing every turn.

#### .NET

A new file, `ObservabilityTokenService.cs`:

```csharp
using System.Text.Json;

namespace LearnMcpAgent;

/// <summary>
/// The two-hop chain that turns a signed-in user's blueprint-scoped token into a token the
/// Agent 365 Observability API accepts, issued to the agent identity acting for that user.
/// </summary>
public sealed class ObservabilityTokenService(HttpClient http, Agent365RuntimeOptions options)
{
    /// <summary>The fixed app id of the Agent 365 Observability API. Named scope, not /.default.</summary>
    public const string ObservabilityScope =
        "api://9b975845-388f-4429-889e-eab1ef63949c/Agent365.Observability.OtelWrite";

    private const string TokenExchangeScope = "api://AzureADTokenExchange/.default";

    private string TokenEndpoint =>
        $"https://login.microsoftonline.com/{options.TenantId}/oauth2/v2.0/token";

    public async Task<(string Token, TimeSpan ExpiresIn)> GetAgentTokenAsync(
        string userAssertion,
        CancellationToken cancellationToken = default)
    {
        var exchangeAssertion = await AcquireExchangeAssertionAsync(cancellationToken);

        // Hop 2: the agent identity acts on behalf of the user. client_assertion proves which
        // agent is asking; assertion proves who it is asking for.
        var (token, expiresIn) = await PostFormAsync(new Dictionary<string, string>
        {
            ["grant_type"]            = "urn:ietf:params:oauth:grant-type:jwt-bearer",
            ["client_id"]             = options.AgentIdentityClientId,
            ["scope"]                 = ObservabilityScope,
            ["client_assertion_type"] = "urn:ietf:params:oauth:client-assertion-type:jwt-bearer",
            ["client_assertion"]      = exchangeAssertion,
            ["assertion"]             = userAssertion,
            ["requested_token_use"]   = "on_behalf_of",
        }, cancellationToken);

        return (token, expiresIn);
    }

    private async Task<string> AcquireExchangeAssertionAsync(CancellationToken cancellationToken)
    {
        // Hop 1: fmi_path is what makes this an agent flow rather than a plain
        // client-credentials call. The result is not an access token; it is only ever
        // usable as the client assertion in hop 2.
        var (assertion, _) = await PostFormAsync(new Dictionary<string, string>
        {
            ["grant_type"]    = "client_credentials",
            ["client_id"]     = options.BlueprintClientId,
            ["client_secret"] = options.BlueprintClientSecret,
            ["scope"]         = TokenExchangeScope,
            ["fmi_path"]      = options.AgentIdentityClientId,
        }, cancellationToken);

        return assertion;
    }

    private async Task<(string Token, TimeSpan ExpiresIn)> PostFormAsync(
        Dictionary<string, string> form,
        CancellationToken cancellationToken)
    {
        using var response = await http.PostAsync(
            TokenEndpoint, new FormUrlEncodedContent(form), cancellationToken);

        var body = await response.Content.ReadAsStringAsync(cancellationToken);

        if (!response.IsSuccessStatusCode)
        {
            // Entra's error body names the AADSTS code, which is the only useful thing to
            // put in front of whoever reads this log line.
            throw new InvalidOperationException(
                $"Entra returned {(int)response.StatusCode} for the token request: {body}");
        }

        using var json = JsonDocument.Parse(body);
        var token = json.RootElement.GetProperty("access_token").GetString()
            ?? throw new InvalidOperationException("The token response contained no access_token.");

        var seconds = json.RootElement.TryGetProperty("expires_in", out var expires)
            ? expires.GetInt32()
            : 3600;

        return (token, TimeSpan.FromSeconds(seconds));
    }
}
```

Both hops go through the same `PostFormAsync`, because they really are the same request with different bodies, and keeping them together means the error handling is written once. Note that hop 1 discards the expiry: the assertion is used immediately and never stored, so the only expiry we care about is the one on the token hop 2 returns.

### Step 3-4. Give the exporter somewhere to find the token

We can produce a token. Now the exporter has to be able to reach it.

The exporter doesn't flush spans on the request thread. It flushes them on a background loop, where there is no HTTP request, no signed-in user, and therefore nothing to exchange on behalf of. So the pattern is to acquire the token while we still have a user, park it somewhere both threads can see, and let the exporter read it from there.

The store is keyed on the agent id and the tenant id, because those are the two dimensions the exporter partitions spans by before it sends them.

> **Don't try to acquire the token inside the resolver itself.** It's a tempting simplification, and it cannot work on any of the three stacks: by the time the resolver runs, there is no user left to act on behalf of.

#### .NET

There's nothing to write here, because the distro ships a store that does exactly this. `ServiceTokenCache` holds a plain token string per agent and tenant, expires entries on its own, and exposes precisely the two methods we need:

```csharp
void RegisterObservability(string agentId, string tenantId, string token, string[] observabilityScopes, TimeSpan? expiresIn);
Task<string> GetObservabilityToken(string agentId, string tenantId);
```

`GetObservabilityToken` happens to match the exporter's `TokenResolver` delegate exactly, which means you can hand the method itself over in Step 3-5 rather than writing a lambda around it.

> **`ServiceTokenCache` is the one to use here, not `AgenticTokenCache`.** They sit in the same namespace and the names are close enough to grab the wrong one. `AgenticTokenCache` takes an `AgenticTokenStruct` built from a Teams turn context, which is the AI Teammate path and has no meaning in a web app. `ServiceTokenCache` takes a token you already hold, which is exactly our situation.

#### Python

A new file, `app/token_store.py`. It has to be its own module, importing nothing from the app, because Step 3-5 loads it before LangChain and anything it drags in would be loaded too early:

```python
"""Holds the observability token so the exporter's background thread can read it."""

from __future__ import annotations

import threading
import time

# Refresh this far ahead of the real expiry. A token that dies mid-turn stops the export
# with no visible error at all.
_SAFETY_MARGIN_SECONDS = 300


class ObservabilityTokenStore:
    def __init__(self) -> None:
        self._lock = threading.Lock()
        self._tokens: dict[tuple[str, str], tuple[str, float]] = {}

    def set(self, agent_id: str, tenant_id: str, token: str, expires_in: int) -> None:
        expires_at = time.monotonic() + max(expires_in - _SAFETY_MARGIN_SECONDS, 0)
        with self._lock:
            self._tokens[(agent_id, tenant_id)] = (token, expires_at)

    def get(self, agent_id: str, tenant_id: str) -> str | None:
        """The resolver the distro calls. Synchronous, on the exporter's worker thread."""
        with self._lock:
            entry = self._tokens.get((agent_id, tenant_id))

        if entry is None:
            return None

        token, expires_at = entry
        return token if time.monotonic() < expires_at else None

    def needs_refresh(self, agent_id: str, tenant_id: str) -> bool:
        return self.get(agent_id, tenant_id) is None


token_store = ObservabilityTokenStore()
```

`get` is called from the exporter's worker thread while `set` is called from the request thread, so this dictionary genuinely is touched from two threads at once and needs the lock.

`get` is synchronous because that is what the distro expects. It calls the resolver as `resolver(agent_id, tenant_id)` without awaiting it, from the batch processor's worker thread rather than from the event loop, so an `async def` here would hand the exporter a coroutine object instead of a token.

#### Node.js

A new file, `src/token-store.ts`, exporting a single shared instance for the same reason:

```typescript
/** Holds the observability token so the exporter's background flush can read it. */

// Refresh this far ahead of the real expiry. A token that dies mid-turn stops the export
// with no visible error at all.
const SAFETY_MARGIN_MS = 5 * 60 * 1000;

interface Entry {
    token: string;
    expiresAt: number;
}

class ObservabilityTokenStore {
    private readonly tokens = new Map<string, Entry>();

    private static key(agentId: string, tenantId: string): string {
        return `${agentId}:${tenantId}`;
    }

    set(agentId: string, tenantId: string, token: string, expiresInSeconds: number): void {
        const expiresAt = Date.now() + Math.max(expiresInSeconds * 1000 - SAFETY_MARGIN_MS, 0);
        this.tokens.set(ObservabilityTokenStore.key(agentId, tenantId), { token, expiresAt });
    }

    /** The resolver the distro calls. Returns null rather than a stale token. */
    get(agentId: string, tenantId: string): string | null {
        const entry = this.tokens.get(ObservabilityTokenStore.key(agentId, tenantId));

        if (!entry || Date.now() >= entry.expiresAt) {
            return null;
        }

        return entry.token;
    }

    needsRefresh(agentId: string, tenantId: string): boolean {
        return this.get(agentId, tenantId) === null;
    }
}

export const tokenStore = new ObservabilityTokenStore();
```

There's no lock here because Node is single-threaded, so the store is genuinely just a `Map`. What matters instead is that this module stays free of imports from the rest of the app, so `src/observability.ts` can pull it in without dragging `main.ts` along behind it. Step 3-5 explains why that would be fatal.

### Step 3-5. Wire the distro into the entry point

Now we initialise the distro when the app starts. All three stacks are doing the same two things: telling the distro to actually export rather than merely decorate spans, and handing it the store's read method so it can fetch a token later. Where they differ is in how fussy each one is about *when* that initialisation happens.

> **Two switches, not one, and this is the most common silent failure in the whole phase.** Enabling Agent 365 registers the span processor that enriches spans. Enabling the *exporter* is a second, separate flag, and it's the one that actually sends anything. Set only the first and your spans are beautifully enriched and then thrown away, with no error to tell you so.

### Step 3-6. Instrument the turn

Everything so far was setup. This step is where a turn actually produces telemetry, and there are four things to do in it, in this order:

1. **Acquire the token and park it in the store**, while we still have a signed-in user to act on behalf of.
2. **Resolve the caller**, which means the user's directory object id and nothing else.
3. **Open a baggage scope** around the whole turn.
4. **Open an `invoke_agent` scope** inside it, and run the agent within that.

Baggage and the semantic scopes are the two that need a word of explanation first.

**Baggage** is OpenTelemetry's mechanism for carrying contextual values alongside the current execution context, and Agent 365 uses it to carry the identity dimensions it partitions telemetry by: which tenant, which agent, which user, which conversation. Spans emitted outside an active baggage scope are dropped, and the exporter tells you so with `Partitioned into 0 identity groups`. Everything looks like it's working and nothing arrives. The scope has to be open for the *whole* turn rather than merely opened before it, which is why each stack below wraps the agent call rather than sitting next to it.

**The semantic scopes** exist because Agent 365 doesn't accept arbitrary spans. It only ingests spans whose `gen_ai.operation.name` is one of `invoke_agent`, `chat`, `execute_tool` or `output_messages`, and anything else is dropped span by span. The one that matters most is `invoke_agent`: it becomes the root span for the turn, and it is the only span the Microsoft 365 admin center ingests. Defender is happy to take everything; the admin center is not.

> **The agent id in baggage and the agent id in `AgentDetails` must be the same value.** If they disagree, the turn is split into two identity groups, only one of which has a token, and you get half your spans arriving and half disappearing with a cheerful `HTTP 200`. Read both from the same configuration value, as the code below does, rather than from two places that can drift apart.

> **Session, conversation and channel have to be on the request object, not only in baggage.** This one is subtle, because baggage *does* land on the span tags, so the information looks like it's there. But the exported `invoke_agent` payload is built from the request object you pass to the scope, so leaving them out gives you a span that is accepted and yet shows no run context at all.

One small thing that applies everywhere: the channel name is `"web"`. The exporter records whatever you give it verbatim, so a wrong value doesn't fail, it just quietly misreports where the activity came from. This isn't Teams, so don't copy `msteams` across from another sample.

```csharp

    if (string.IsNullOrWhiteSpace(_input) || _isThinking || _session is null) return;

    var userText = _input.Trim();
    _input = string.Empty;
    _messages.Add(new ChatEntry("user", userText));
    _isThinking = true;

    try
    {
        // 1. The token, while we still have a user to act on behalf of. Losing telemetry is
        // never a reason to fail the user's question, so this gets its own try/catch.
        var userAssertion = await AcquireUserAssertionAsync();

        try
        {
            var (agentToken, expiresIn) = await TokenService.GetAgentTokenAsync(userAssertion);

            ObservabilityTokens.RegisterObservability(
                Agent365.AgentIdentityClientId,
                Agent365.TenantId,
                agentToken,
                [ObservabilityTokenService.ObservabilityScope],
                expiresIn);
        }
        catch (Exception tokenError)
        {
            Logger.LogWarning(tokenError, "Could not acquire an observability token for this turn.");
        }

        // 2. The caller. GetObjectId() rather than a raw claim lookup; see the note below.
        var user = AuthenticationStateTask is null ? null : (await AuthenticationStateTask).User;
        var userId = user?.GetObjectId() ?? "unknown";
        var userName = user?.GetDisplayName() ?? "unknown";
        var userEmail = user?.Identity?.Name ?? string.Empty;

        var conversationId = _conversationId;

        var agentDetails = new AgentDetails(
            agentId: Agent365.AgentIdentityClientId,
            agentName: Agent365.AgentName,
            agentBlueprintId: Agent365.BlueprintClientId,
            tenantId: Agent365.TenantId);

        var callerDetails = new CallerDetails(
            userDetails: new UserDetails(
                userId: userId,
                userEmail: userEmail,
                userName: userName));

        // 3. The baggage scope, open for the whole turn.
        using var baggage = new BaggageBuilder()
            .TenantId(Agent365.TenantId)
            .AgentId(Agent365.AgentIdentityClientId)
            .AgentName(Agent365.AgentName)
            .AgentBlueprintId(Agent365.BlueprintClientId)
            .ConversationId(conversationId)
            .SessionId(conversationId)
            .UserId(userId)
            .UserName(userName)
            .UserEmail(userEmail)
            .ChannelName("web")
            .Build();

        // 4. The invoke_agent span, and the agent call inside it.
        var request = new Request(
            content: userText,
            sessionId: conversationId,
            conversationId: conversationId,
            channel: new Channel("web"));

        using var invokeScope = InvokeAgentScope.Start(
            request,
            new InvokeAgentScopeDetails(new Uri(Navigation.BaseUri)),
            agentDetails,
            callerDetails);

        invokeScope.RecordInputMessages([userText]);

        var response = await Agent.RunAsync(userText, _session);

        invokeScope.RecordOutputMessages([response.Text]);
        _messages.Add(new ChatEntry("assistant", response.Text));
    }
    catch (Exception ex)
    {
        _messages.Add(new ChatEntry("assistant", $"Error: {ex.Message}"));
    }
    finally
    {
        _isThinking = false;
    }
}
```

Both `using` declarations matter, and they matter for different reasons. The baggage scope stays open until the end of the enclosing block, which is why the agent call has to sit inside it. The invoke scope is a span, and a span that is never disposed is never ended, and a span that is never ended is never exported.

The nested `try` around the token acquisition is the .NET equivalent of the warning-and-continue that the Python and Node handlers do. Telemetry is not worth a failed answer, so a consent problem or an Entra outage should cost you the traces for that turn and nothing else.

`AgentDetails`, `CallerDetails` and `UserDetails` all take every parameter as optional, so name the arguments: `UserDetails` is declared as `(userId, userEmail, userName, userClientIP)`, with the email in the middle, so passing three positional strings in the order you'd expect silently swaps the name and the email.

#### Python

First, wire the pieces together near the top of `app/main.py`, after the settings import:

```python
from app.obo_tokens import OBSERVABILITY_SCOPE, ObservabilityTokenService
from app.token_store import token_store

obo_tokens = ObservabilityTokenService(settings) if settings.observability_enabled else None
```

Then replace the `/api/chat` handler:

```python
from microsoft.opentelemetry.a365.core import (
    AgentDetails,
    CallerDetails,
    Channel,
    InvokeAgentScope,
    InvokeAgentScopeDetails,
    Request as A365Request,
    ServiceEndpoint,
    UserDetails,
)
from microsoft.opentelemetry.a365.core.middleware.baggage_builder import BaggageBuilder


@app.post("/api/chat")
async def chat(request: ChatRequest, http_request: Request) -> ChatResponse:
    claims: dict[str, object] = {}

    if auth_service:
        try:
            user_assertion = auth_service.acquire_user_assertion(http_request)
        except AuthRequiredError as error:
            raise HTTPException(
                status_code=status.HTTP_401_UNAUTHORIZED,
                detail=str(error),
            ) from error

        session = auth_service._get_session(http_request)
        claims = (session or {}).get("claims") or {}

        # 1. The token, while we still have a user to act on behalf of.
        if obo_tokens:
            try:
                token, expires_in = await obo_tokens.get_agent_token(user_assertion)
                token_store.set(
                    settings.agent_identity_client_id,
                    settings.agent365_tenant_id,
                    token,
                    expires_in,
                )
            except Exception:
                # Losing telemetry is never a reason to fail the user's question.
                logger.exception("Could not acquire an observability token for this turn")

    if not obo_tokens:
        reply = await agent.ask(request.session_id, request.message)
        return ChatResponse(reply=reply)

    # 2. The caller. `oid` is the directory object id; nothing else resolves to a person.
    user_id = str(claims.get("oid") or "unknown")
    user_name = str(claims.get("name") or "unknown")
    user_email = str(claims.get("preferred_username") or claims.get("upn") or "")

    agent_details = AgentDetails(
        agent_id=settings.agent_identity_client_id,
        agent_name=settings.agent365_agent_name,
        agent_blueprint_id=settings.agent_blueprint_id,
        tenant_id=settings.agent365_tenant_id,
    )
    caller_details = CallerDetails(
        user_details=UserDetails(
            user_id=user_id,
            user_email=user_email,
            user_name=user_name,
        )
    )

    # 3. The baggage scope, open for the whole turn.
    with (
        BaggageBuilder()
        .tenant_id(settings.agent365_tenant_id)
        .agent_id(settings.agent_identity_client_id)
        .agent_name(settings.agent365_agent_name)
        .agent_blueprint_id(settings.agent_blueprint_id)
        .conversation_id(request.session_id)
        .session_id(request.session_id)
        .user_id(user_id)
        .user_name(user_name)
        .user_email(user_email)
        .channel_name("web")
        .build()
    ):
        # 4. The invoke_agent span, and the agent call inside it.
        with InvokeAgentScope.start(
            A365Request(
                content=request.message,
                session_id=request.session_id,
                conversation_id=request.session_id,
                channel=Channel(name="web"),
            ),
            InvokeAgentScopeDetails(
                endpoint=ServiceEndpoint(hostname=settings.host, port=settings.port)
            ),
            agent_details,
            caller_details,
        ) as scope:
            scope.record_input_messages([request.message])

            try:
                reply = await agent.ask(request.session_id, request.message)
            except Exception as error:
                scope.record_error(error)
                logger.exception("Chat turn failed")
                return ChatResponse(
                    reply="Sorry, something went wrong while researching that. Please try again."
                )

            scope.record_output_messages([reply])

    return ChatResponse(reply=reply)
```

Entering the scope is what makes its span the active one, so the agent call has to be inside the `with` rather than merely after `start()`. That's also why `record_input_messages` sits on the first line of the block: everything the turn produces should be parented by a span that is already active.

`ServiceEndpoint` wants a bare **hostname** rather than a URI, so `ServiceEndpoint(hostname="localhost", port=8000)` and not the address with a scheme in front of it. Passing a URI string fails later, from inside the scope, with `AttributeError: 'str' object has no attribute 'hostname'`.

`reply` is assigned inside the `with` and read after it, which is fine because `with` doesn't introduce a scope in Python. The only path that skips the assignment returns before the final line.

The starting point keeps the claims private on `AuthService`, since nothing needed them until now, so `auth_service._get_session` is the only way in without editing that class. In your own code, add a small public accessor for the claims and call that instead.

> **On Python, check that you actually get `chat` spans.** The LangChain instrumentation is what produces them, and it only attaches if `app.observability` really was imported before `app.agent`. Step 3-7 is where you confirm it. If they're missing, you can fall back to wrapping the model call in an `InferenceScope` by hand, but fix the import order first, because that's nearly always the real cause.

#### Node.js

Wire the pieces together near the top of `src/main.ts`:

```typescript
import { ObservabilityTokenService } from "./obo-tokens.js";
import { tokenStore } from "./token-store.js";

const oboTokens = settings.observabilityEnabled ? new ObservabilityTokenService(settings) : undefined;
```

Then replace the `/api/chat` handler:

```typescript
import {
    BaggageBuilder,
    InvokeAgentScope,
    type A365Request,
    type AgentDetails,
    type CallerDetails,
} from "@microsoft/opentelemetry";

app.post("/api/chat", async (req, res) => {
    const { session_id: sessionId, message } = req.body ?? {};

    if (typeof sessionId !== "string" || !sessionId || typeof message !== "string" || !message) {
        res.status(400).json({ reply: "Both session_id and message are required." });
        return;
    }

    let claims: Record<string, unknown> = {};

    if (authService) {
        let userAssertion: string;

        try {
            // The starting point already called this to reject anonymous callers, and threw
            // the result away. Now something needs it, so we keep it.
            userAssertion = await authService.acquireUserAssertion(req);
            claims = authService.claims(req) ?? {};
        } catch (error) {
            console.error("Could not acquire the user assertion", error);
            res.status(401).json({ reply: "Sign in before chatting with the agent." });
            return;
        }

        // 1. The token, while we still have a user to act on behalf of.
        if (oboTokens) {
            try {
                const { token, expiresInSeconds } = await oboTokens.getAgentToken(userAssertion);
                tokenStore.set(
                    settings.agentIdentityClientId!,
                    settings.agent365TenantId!,
                    token,
                    expiresInSeconds,
                );
            } catch (error) {
                // Losing telemetry is never a reason to fail the user's question.
                console.warn("Could not acquire an observability token for this turn", error);
            }
        }
    }

    if (!oboTokens) {
        res.json({ reply: await agent.ask(sessionId, message) });
        return;
    }

    // 2. The caller. `oid` is the directory object id; nothing else resolves to a person.
    const userId = readClaim(claims, "oid") ?? "unknown";
    const userName = readClaim(claims, "name") ?? "unknown";
    const userEmail = readClaim(claims, "preferred_username") ?? readClaim(claims, "upn") ?? "";

    const agentDetails: AgentDetails = {
        agentId: settings.agentIdentityClientId!,
        agentName: settings.agent365AgentName,
        agentBlueprintId: settings.agentBlueprintId,
        tenantId: settings.agent365TenantId,
    };

    const callerDetails: CallerDetails = {
        userDetails: { userId, userName, userEmail },
    };

    // 3. The baggage scope, open for the whole turn.
    const baggage = new BaggageBuilder()
        .tenantId(settings.agent365TenantId)
        .agentId(settings.agentIdentityClientId)
        .agentName(settings.agent365AgentName)
        .agentBlueprintId(settings.agentBlueprintId)
        .conversationId(sessionId)
        .sessionId(sessionId)
        .userId(userId)
        .userName(userName)
        .userEmail(userEmail)
        .channelName("web")
        .build();

    try {
        // 4. The invoke_agent span, and the agent call inside it.
        const reply = await baggage.run(async () => {
            const request: A365Request = {
                content: message,
                sessionId,
                conversationId: sessionId,
                channel: { name: "web" },
            };

            const invokeScope = InvokeAgentScope.start(
                request,
                { endpoint: { host: settings.host, port: settings.port, protocol: "http" } },
                agentDetails,
                callerDetails,
            );

            try {
                invokeScope.recordInputMessages([message]);
                const answer = await invokeScope.withActiveSpanAsync(() => agent.ask(sessionId, message));
                invokeScope.recordOutputMessages([answer]);
                return answer;
            } catch (error) {
                invokeScope.recordError(error as Error);
                throw error;
            } finally {
                // A scope that is never disposed is a span that never ends, and a span that
                // never ends is never exported.
                invokeScope.dispose();
            }
        });

        res.json({ reply });
    } catch (error) {
        console.error("Chat turn failed", error);
        res.json({ reply: "Sorry, something went wrong while researching that. Please try again." });
    }
});
```

`baggage.run()` is synchronous: it calls your function and returns whatever that function returned. Because our callback is `async`, what it returns is a promise, so the `await` in front of `baggage.run(...)` is awaiting the promise the callback produced. That works, and it's the reason the callback must *return* its promise rather than merely start it. Write `baggage.run(() => { agent.ask(...); })` with a forgotten `return` and `run()` completes immediately, the baggage is gone by the time the spans are created, and you're back to `Partitioned into 0 identity groups`.

`AuthService` doesn't expose the claims today, since `profile()` narrows them down to a name and a username for the chat page. Add a small accessor to `src/auth.ts` so the handler above compiles:

```typescript
/** The ID token claims for the current session, for telemetry attribution. */
claims(req: Request): Record<string, unknown> | undefined {
    return this.getSession(req)?.claims;
}
```

`getSession` is private, so this accessor has to live inside the class. The handler above also needs a small helper for reading claims, because `auth.ts` keeps its own `asString` to itself. Add this at the bottom of `src/main.ts`:

```typescript
function readClaim(claims: Record<string, unknown>, name: string): string | undefined {
    const value = claims[name];
    return typeof value === "string" && value ? value : undefined;
}
```

Take the `oid` from these ID token claims rather than from a decode of the access token you send to the observability API. They agree in this scenario, but relying on that means the day you change which resource you request, the caller identity changes with it for no visible reason.

#### A note on reading the caller's object id

The Microsoft 365 admin center needs the caller's **directory object id** to show you who did what. If you give it anything else, the export still returns `HTTP 200` and the row still arrives. It just never resolves to a person, and you get activity attributed to nobody.

The object id is the `oid` claim, the one you looked at in jwt.ms back in Step 2-3c. The trap in every stack is that there are several other claims sitting nearby that look like plausible identifiers and are not. `sub` is a pairwise identifier that differs per application, and the `nameidentifier` claim that some frameworks map `oid` onto can turn out to be a base64-looking hash instead.

On .NET this is why the code above calls `user.GetObjectId()` from `Microsoft.Identity.Web` rather than `user.FindFirst("oid")`. The OIDC handler renames inbound claims, so a raw lookup for `oid` misses, falls through to `ClaimTypes.NameIdentifier`, and hands you the pairwise hash. The export succeeds and the attribution is blank, which is the most common cause of "telemetry works but the admin center shows nothing".

### Step 3-7. Verify that the telemetry is actually leaving

Before we go looking in Defender, let's confirm from the app's own logs that spans are being exported. Turn on the exporter's logging:

```powershell
$env:OTEL_LOG_LEVEL="INFO"
$env:A365_OBSERVABILITY_LOG_LEVEL="debug"
```

Both variables matter, and this catches people out on Node in particular: `OTEL_LOG_LEVEL` controls the OpenTelemetry SDK's own diagnostics, while `A365_OBSERVABILITY_LOG_LEVEL` is what makes the Agent 365 components talk. Set only the first and you'll see the SDK start up and then apparent silence from the part you actually wanted to watch.

Restart the app, ask the agent a question, and read the output. There are five things to look for, and all five have to be right:

| What to look for | What it means if it's wrong |
| --- | --- |
| `Partitioned into 1 identity groups` | `0` means no baggage scope around the turn. `2` means baggage and `AgentDetails` disagree on the agent id. Step 3-6 |
| An `invoke_agent` span, and it's a **root** span | The invoke scope isn't wrapping the turn, or it was never disposed. Step 3-6 |
| `chat` spans for the model call | On .NET, the `UseOpenTelemetry()` call on the chat client is missing. On Python, the import order is wrong. Step 3-5 |
| `HTTP 200` on the export | `401` is the scope or the token, `403` means the agent id and the token's `azp` disagree. Steps 3-2 and 3-3 |
| The caller id is a **GUID** | A long base64-looking string means you're reading the wrong claim. Step 3-6 |

If nothing is exported at all and there's no error, check the two switches from Step 3-5 before anything else. Enriched-but-never-exported is the failure that looks most like success.

✅ **Checkpoint.** This is another good place to stop. The agent is registered, and it's observable.

## Phase 4: Work IQ

With observability in place, we can look at giving the agent access to Microsoft 365 data, Mail, Calendar and more, through the Work IQ MCP servers. The appeal is obvious: the agent reaches that data using the signed-in user's own permissions, so it can never see anything the person driving it couldn't already see.

This phase splits cleanly into two halves, and they are in very different states of readiness.

The **first half is the catalog and the permissions**. It's pure CLI work, it doesn't care what your agent is written in, and it works today. At the end of it your tenant has granted your agent the delegated scopes for the servers you picked, and your project has a `ToolingManifest.json` describing them.

The **second half is the runtime wiring**, and this is where a web app hits a wall. The published Work IQ extensions for .NET and Node.js both expect the Microsoft 365 Agents SDK: their entry points take an `Authorization` object and an `ITurnContext`, which exist in a Teams-hosted agent and simply do not exist in a Blazor Server page or an Express route. Python with LangChain has no extension package at all.

> **Read this before you plan a sprint around it.** For the scenario in this guide, a plain web app with a signed-in user, there is no supported turnkey runtime wiring for Work IQ on any of the three stacks. The CLI half is real and worth doing. The code half currently means either hosting your agent on the Microsoft 365 Agents SDK, which is the [Teams Agent scenario](../Teams-Agent-Custom-Engine-OBO/) rather than this one, or calling the MCP endpoints yourself with a token you mint through the same two-hop chain you built in Step 3-3. Work IQ is also unavailable to agents registered with `--authmode s2s`, because every Work IQ server requires delegated permissions, so the OBO path we're on is at least the right one.

So work through Step 4-1, and treat Step 4-2 as a decision rather than an instruction.

### Step 4-1. Choose the servers and get them granted

Start by looking at what's actually in the catalog, rather than guessing from a list in a document. The catalog changes, and the server names have to match exactly:

```bash
a365 develop list-available
```

You'll get a list of entries that look like this, each with the OAuth scope it needs and the audience it's addressed to:

```text
  mcp_MailTools
     URL: https://agent365.svc.cloud.microsoft/agents/servers/mcp_MailTools
     Required Scope: Tools.ListInvoke.All
     Audience: 16b1878d-62c7-4009-aa25-68989d63bbad

  mcp_CalendarTools
     URL: https://agent365.svc.cloud.microsoft/agents/servers/mcp_CalendarTools
     Required Scope: Tools.ListInvoke.All
     Audience: 910333d2-47e9-43ca-981f-6df2f4531ef4
```

Alongside Mail and Calendar you'll find Teams, SharePoint, OneDrive, Word, Excel, Planner, Microsoft 365 Copilot and a set of third-party connectors. Note the shape of the names, `mcp_MailTools` rather than `mail`, because the next command wants them verbatim.

Now add the ones you want. They're positional arguments, one per server, and the command writes `ToolingManifest.json` in the project directory:

```bash
a365 develop add-mcp-servers "mcp_MailTools" "mcp_CalendarTools"
```

If you're running from somewhere other than the project folder, point it at the right place with `--project-path`. And as with everything else in the CLI, `--dry-run` will show you what it intends to do first.

That command writes a manifest and nothing else. It grants no permissions at all, so the grant is a separate step:

```bash
a365 setup permissions mcp --agent-name "my-agent"
```

This one needs an administrator, because it creates the OAuth2 delegated grants for every server in the manifest. The `--agent-name` flag is there for the same reason we used it in Phase 2: it lets the command work without an `a365.config.json`, which our project doesn't have. Run it from the project directory so the CLI finds `ToolingManifest.json`. If you're not an administrator the CLI doesn't fail; it prints a single `/v2.0/adminconsent` URL for you to forward to a Global Administrator, which is a much easier handoff than a script.

**How to verify.** Ask the CLI what it thinks is configured, rather than reading the JSON yourself:

```bash
a365 develop list-configured
```

Every server you asked for should appear, and each should appear exactly once. Duplicate entries are a known failure mode and they cause the tools to be registered twice at runtime.

For local testing you'll also want a bearer token, which the CLI will fetch interactively using the scopes it finds in the manifest:

```bash
a365 develop get-token -o raw
```

Leave `--resource` off unless you also pass `--scopes`, since naming a resource explicitly turns off the manifest-driven scope resolution that makes this command convenient. These tokens expire, so expect to re-run that during a debugging session rather than once at the start of the day.

### Step 4-2. Decide how the tools reach your agent

At this point the tenant is ready and your agent is not, and how you close that gap is a design decision rather than a snippet.

The supported extensions, `Microsoft.Agents.A365.Tooling.Extensions.AgentFramework` on .NET and `@microsoft/agents-a365-tooling-extensions-langchain` on Node.js, expose a registration service whose method signatures tell you plainly what they expect:

```csharp
var a365Tools = await _toolService.GetMcpToolsAsync(agentId, UserAuthorization, handlerName, turnContext);
```

```typescript
agentWithTools = await toolService.addToolServersToAgent(
    agent, authorization, authHandlerName, turnContext, process.env.BEARER_TOKEN || "");
```

`UserAuthorization` and `turnContext` come from the Microsoft 365 Agents SDK. They carry the per-turn credentials that the service uses to perform the on-behalf-of exchange for each server's audience, and a Blazor circuit or an Express request has nothing to hand them. The code isn't hard to call; two of its four arguments simply don't exist in this hosting model.

That leaves three honest options, and which one is right depends on why you wanted Work IQ in the first place:

| Option | When it fits | What it costs |
| --- | --- | --- |
| Host the agent on the Microsoft 365 Agents SDK | You want the supported path, and Teams is an acceptable or desirable front end | A different scenario. Follow [Teams Agent: Custom Engine OBO](../Teams-Agent-Custom-Engine-OBO/) instead |
| Call the MCP servers directly from your own code | You need one or two servers from a web app you're keeping | You write the MCP client and the per-audience token exchange yourself |
| Wait | Work IQ is a nice-to-have rather than the point | Nothing, and the phase is genuinely optional |

The middle option reuses most of what you already have. Each catalog entry gives you a URL, a scope and an audience, and your `ObservabilityTokenService` from Step 3-3 is already a two-hop OBO exchange with the scope as a parameter in all but name. Point hop 2 at `<audience>/<scope>` instead of the observability scope and you get a token for that server, which you then use as the bearer token on an ordinary streamable-HTTP MCP client. The starting points all already speak MCP, since that's how they reach Microsoft Learn, so the transport is not new code either.

What you'd be signing up for is the part the extensions do for you: a token per audience rather than one token, cached and refreshed independently, plus the error handling for a server that's in your manifest but not yet consented. That's a real amount of work, and it's why this guide stops at describing it rather than pretending a dozen lines will do.

✅ **Checkpoint.** The manifest exists and the permissions are granted, so the tenant side of Work IQ is done. Whether the agent calls those servers is now your decision rather than one the tooling made for you.

## Phase 5: Verify it end to end

Everything so far proves the agent *emits* telemetry. This phase proves it *arrives*, which is not the same thing at all. As we've seen, there are several ways for a span to be accepted and then quietly discarded.

Nothing in this phase depends on your stack. You're looking at portals now, and by this point the three implementations are indistinguishable from the outside.

### Step 5-1. Produce some activity

Ask the agent three or four questions. There's a set of them in [4.Sample-prompts.md](4.Sample-prompts.md) if you want a starting point. Make sure at least one of them causes a tool call, so we have more than just inference spans to look at.

Do it as a user who holds an Agent 365 licence. Without one the telemetry is accepted and discarded.

### Step 5-2. Check Microsoft Defender

Go to [Advanced hunting](https://security.microsoft.com) in the Defender portal and query the `CloudAppEvents` table. Defender accepts every operation type, so this is where you should see the fullest picture: `InvokeAgent`, `InferenceCall` and `ExecuteToolByMCPServer` rows. Here's a query to start from:

```kusto
CloudAppEvents
| where ActionType in ("InvokeAgent", "InferenceCall", "ExecuteToolBySDK", "ExecuteToolByGateway", "ExecuteToolByMCPServer")
| where RawEventData.TargetAgentName == "my-agent" or RawEventData.AgentName == "my-agent"
| order by Timestamp desc
```

Defender has to index the events, so give it around five minutes before concluding something is wrong. If you get impatient, widen the query by dropping the name filter entirely and look for anything at all in the last hour; an empty table then is a different problem from a name that doesn't match.

### Step 5-3. Check the Microsoft 365 admin center

Now go to https://admin.cloud.microsoft, find your agent in the inventory, and open its activity.

This surface behaves differently from Defender, and understanding how saves a lot of debugging: the admin center ingests `invoke_agent` rows only, and it reads the caller identity off that one span. Which means the combination of what you see in each portal tells you precisely where a problem is:

| What you see | Where the problem is |
| --- | --- |
| Nothing anywhere | Export, token, or baggage scope. Go back to Step 3-7 |
| Defender ✅, admin center ❌ | Your `invoke_agent` span. Nine times out of ten it's the caller id. Step 3-6 |
| Both ✅, but no user shown | The caller resolved to something that isn't a directory object id. Step 3-6 |
| Both ✅, but no run context | Session, conversation or channel missing from the request object. Step 3-6 |

### Step 5-4. Read your own instrumentation back

There's no skill to check the code for you on this path, so here is the checklist it would have run, as something you can walk yourself. Each row is one of the six requirements from the top of Phase 3, turned into a question you can answer by looking at your own code:

| Question | Where to look |
| --- | --- |
| Is the exporter *enabled*, not merely registered? | Both flags in Step 3-5 |
| Is the token acquired on the request thread and stored, rather than fetched in the resolver? | Step 3-6, first block |
| Does hop 2 ask for the named scope rather than `/.default`? | Step 3-3 |
| Is the agent id the **agent identity**, not the blueprint? | Step 3-2 |
| Does the baggage scope wrap the agent call, rather than sitting before it? | Step 3-6 |
| Do the baggage agent id and `AgentDetails.agentId` come from one value? | Step 3-6 |
| Is the invoke scope disposed on every path, including the failing one? | Step 3-6 |
| Is the caller id `oid`, read through the framework's helper where one exists? | Step 3-6 |

If you'd rather have this checked mechanically and you do have a coding assistant available after all, the `a365-code-validator` skill from the [Agent 365 Skills](https://github.com/microsoft/agent365-skills) is read-only and understands all three stacks, so it's safe to point at a project you wrote by hand.

## Troubleshooting

For a diagnostic sequence from the running process through tenant reporting, use the [cross-scenario troubleshooting guide](../../03-references/Troubleshooting.md). The checks below point back to this runbook's manual implementation steps.

If something isn't working, this table covers the failures you're most likely to hit, and where each one comes from. The first group applies whatever you're writing in; the second group is stack-specific.

| Symptom | Likely cause |
| --- | --- |
| Spans are enriched but nothing is exported | Only one of the two exporter switches is on. Step 3-5 |
| `Partitioned into 0 identity groups` | No active baggage scope around the turn. Step 3-6 |
| `Partitioned into 2 identity groups` | Baggage and `AgentDetails` disagree on the agent id. Step 3-6 |
| `401 InvalidAudience` on the export | Hop 2 asked for `/.default` instead of the named scope. Step 3-3 |
| `HTTP 403` on the export | The agent id and the token's `azp` disagree, usually the blueprint id where the agent identity belongs. Step 3-2 |
| `HTTP 200`, but nothing lands anywhere | No user in the tenant holds an Agent 365 licence |
| `AADSTS500011` resource principal not found | Agent 365 isn't provisioned in this tenant |
| `AADSTS82001` | Client credentials were requested for an agentic app. Hop 1 needs `fmi_path` |
| Consent errors on the observability scope | The admin handoff from Step 2-1 was never run |
| `AADSTS50011` redirect URI mismatch | The registered redirect URI doesn't match the address the browser is on, scheme included. Step 1-1a |
| Hop 2 rejects the assertion | The sign-in asked for the wrong scope, so the user token isn't addressed to the blueprint. Step 2-3c |
| Telemetry stops after roughly an hour | The token expired and nothing refreshed it. Step 3-4 |
| The app starts in anonymous mode with a filled-in `.env` | The settings are read once at startup, so restart the process. Step 2-3b |
| Sign-in loops back to the sign-in page | The browser is on `127.0.0.1` and the app set its cookie on `localhost`, or the other way round. Step 1-1a |

And the ones that only affect one stack:

| Symptom | Stack | Likely cause |
| --- | --- | --- |
| `CS0433` duplicate type errors after adding the distro | .NET | The legacy `Observability.Runtime` or `.Hosting` packages are referenced directly as well. Step 3-1 |
| The caller never resolves to a person | .NET | `FindFirst("oid")` instead of `GetObjectId()`. The OIDC handler renames the claim. Step 3-6 |
| `MsalUiRequiredException` on the first turn after a restart | .NET | The auth cookie is encrypted at rest and survives the restart; the in-memory token cache doesn't. Sign out and back in |
| `AttributeError: 'str' object has no attribute 'hostname'` | Python | `ServiceEndpoint` was given a URI instead of a bare hostname. Step 3-6 |
| No `chat` spans | Python | The distro was initialised after LangChain was imported. Step 3-5 |
| A distro option seems to have no effect | Python | It's misspelled. `use_microsoft_opentelemetry` takes `**kwargs` and ignores what it doesn't recognise. Step 3-5 |
| No `chat` spans | Node.js | `./observability.js` isn't the first import in `main.ts`, so LangChain was loaded before the distro could patch it. Step 3-5 |
| Every span appears twice | Node.js | The LangChain instrumentation was registered by hand as well as by the distro, which enables it by default. Step 3-5 |
| Baggage is empty despite an open scope | Node.js | The callback passed to `run()` doesn't return its promise, so `run()` finished before the agent did. Step 3-6 |
| Everyone is signed out after a restart | Node.js | Sessions live in an in-process `Map`, which is fine for a sample and the first thing to replace for real |
| The last turn's spans never arrive | Node.js | The process exited before the exporter flushed. Add the shutdown handler from Step 3-5 |
| Breakpoints land in the wrong file | Node.js | You're debugging compiled output from `npm run build`. Run through `npm run dev`, which executes the TypeScript directly |

## Wrapping up

We started with an ordinary web agent that answered questions for anyone who opened the page and knew nothing about the tenant it ran in. We registered a separate sign-in app, because a blueprint is an agentic application and can never present a sign-in page. We registered the agent itself, which gave us a blueprint and an agent identity. We connected the two by pointing the sign-in at the blueprint's scope, so the user's token is addressed to the right resource. We built the two-hop chain by hand, watched it turn that user token into one issued to the agent acting for that person, and parked the result where a background exporter could find it. Then we wrapped every turn in the baggage and the spans that Agent 365 will actually ingest.

Every one of those steps was something you typed. That's slower than describing the outcome to a coding assistant, and it buys you two things worth having. The first is that you can now read a failure and know which of the six requirements at the top of Phase 3 it maps to, because you wrote all six. The second is that every command and every file in this guide runs in a pipeline, on a build agent, or on a colleague's machine, none of which have a coding assistant attached.

Whichever of the three stacks you followed, you ended up in the same place. The .NET version leans on `Microsoft.Identity.Web` and gets a lot of the sign-in handed to it, and the distro even ships the token cache. The Python version does more of the work by hand and is fussiest about import order. The Node version does more still, because MSAL's Node bindings leave PKCE and state to the caller, and because ES module hoisting makes the distro's placement a structural decision rather than a stylistic one. The registration, the token chain, the baggage and the spans are the same in all three, because those are properties of Agent 365 rather than of your language.

None of the work we have done changed what the agent *does*. It answers exactly the same questions it answered in Phase 0. What changed is that the organization can now see it, govern it, and hold it accountable, which is the difference between a demo and something you can actually put in front of users.
