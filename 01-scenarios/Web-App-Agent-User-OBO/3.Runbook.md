# Step-by-Step Guide — Web App Agent with User OBO

> **Scenario**: Onboarding a user-driven web agent into Microsoft Agent 365
> **Platform**: Microsoft Agent 365 · Microsoft Entra ID · OpenTelemetry
> **Stacks**: .NET Agent Framework (Blazor Server) · Python + LangChain (FastAPI)
> **Target Readers**: Agent developers, Entra administrators
> **Last Updated**: February 2026

## Overview

This runbook takes a working, un-instrumented web agent and onboards it into Microsoft Agent 365.
You do this by asking a **coding agent** — GitHub Copilot CLI, Claude Code, or VS Code Copilot
Chat — to run the Agent 365 Skills for you. Each step also shows what the skill does underneath,
so you can do it by hand, review what changed, or debug it when it goes wrong.

The work is split into phases. **Each phase is a valid stopping point** — you get real value from
Phase 1 alone, more from Phase 2, and so on.

| Phase | You get | Time |
| --- | --- | --- |
| 0 — Prerequisites | A machine that can run the tooling | 15–45 min |
| 1 — Registration | The agent exists in your tenant as a governed identity | 20 min |
| 2 — Observability | Activity in Defender, Purview and the admin center | 60–90 min |
| 3 — Work IQ | The agent can reach Microsoft 365 data | 30 min |
| 4 — Verify | Proof it actually works end to end | 30 min |

Where you'll be working:

| Location | URL | Task |
| --- | --- | --- |
| Your terminal | — | Skills, CLI, builds |
| Microsoft Entra admin center | https://entra.microsoft.com | Consent, app registrations |
| Microsoft 365 admin center | https://admin.cloud.microsoft | Agent inventory and activity |
| Microsoft Defender | https://security.microsoft.com | Advanced hunting over agent telemetry |

### How to read a step

Every step in Phases 1–3 has the same four parts:

1. **What you type** — the prompt you give your coding agent
2. **What the skill does** — what it will actually change, so nothing is a surprise
3. **Behind the scenes** — the CLI command or code it comes down to
4. **How to verify** — how to know it worked before moving on

If you'd rather not use a coding agent at all, read only parts 3 and 4. The runbook works
that way too.

## Phase 0: Get the agent running first

**Do not skip this.** Onboard an agent that already works. If you instrument a broken agent, you
won't know which layer is failing.

### Step 0-1. Run the starting point

**.NET**

```bash
cd 0.Resources/Starting-point/dotnet
dotnet user-secrets set "AzureOpenAI:ApiKey" "<your-key>"
dotnet run
```

**Python**

```bash
cd 0.Resources/Starting-point/python
cp .env.example .env      # then fill in your Azure OpenAI values
uv sync
uv run uvicorn app.main:app --reload
```

### Step 0-2. Verify

Open the app, ask *"What is Microsoft Entra Conditional Access?"*, and confirm you get an answer
that cites Microsoft Learn.

✅ **Checkpoint:** the agent answers questions and cites sources. Nothing Agent 365 exists yet.

## Phase 1: Register the agent

The agent becomes an object in your tenant: a **blueprint** (the parent registration that holds
permissions) and an **agent identity** (the child principal that acts).

### Step 1-1. Run the setup skill

**What you type**

```text
Set up Agent 365 for this agent. It's a web app where users sign in —
not a Teams agent and not an AI Teammate. Use the OBO auth mode.
```

**What the skill does**

`a365-setup` runs first. It checks every prerequisite above, walks you through installing anything
missing, and confirms your Azure identity. It then asks two questions that decide everything
downstream:

| Question | Your answer here | Why |
| --- | --- | --- |
| Agent kind? | **Agent (Non AI Teammate)** | A human drives this agent |
| Auth mode? | **`obo`** | Actions are attributed to the signed-in user |

It then hands off to `make-a365-agent`, which does the actual registration.

> **Answer the auth-mode question carefully.** It is the single decision that determines your
> entire token chain, and changing it later means rewriting Phase 2.

**Behind the scenes**

```bash
a365 setup all --agent-name "my-agent" --dry-run    # preview first
a365 setup all --agent-name "my-agent"              # apply
```

`a365 setup all` is idempotent — safe to re-run after fixing a problem.

It creates:

- an **agent blueprint** app registration, with a client secret
- an **agent identity** as a child of that blueprint
- the API permissions the agent needs, including `Agent365.Observability.OtelWrite`
- a file `a365.generated.config.json` holding the generated identifiers

**How to verify**

```bash
cat a365.generated.config.json
```

You should see `agentBlueprintId` and an agent identity id. Then confirm in
[Entra](https://entra.microsoft.com) → **App registrations** that the blueprint exists.

⚠️ **If you weren't Global Admin**, the setup summary printed a consent snippet. Permissions are
*created but not granted* until someone runs it. Phase 2 will fail with a consent error otherwise.

### Step 1-2. Store the blueprint secret safely

`a365 setup all` generates a client secret. It must never reach source control.

**.NET**

```bash
dotnet user-secrets set "Agent365:BlueprintClientSecret" "<secret>"
```

**Python** — put it in `.env`, and confirm `.env` is gitignored.

You can re-read it later — on the same machine, as the same user — with:

```bash
a365 setup blueprint --agent-name "my-agent" --show-secret
```

### Step 1-3. Add the sign-in app registration

The blueprint **cannot** sign users in. Entra bars agentic applications from interactive
authorization flows, so you need a separate, ordinary app registration for the web app itself.

Create it in Entra with:

- a redirect URI of `https://localhost:<port>/signin-oidc` (.NET) or your app's callback
- a client secret
- the delegated permission `api://<blueprint-id>/access_agent_as_user`

That last one is the crucial part. It makes the user token your app receives **addressed to the
blueprint**, which is what allows it to be used as the user assertion in Phase 2's hop 2.

✅ **Checkpoint — you can stop here.** The agent is registered and governed. It shows up in your
tenant. It doesn't emit telemetry yet.

## Phase 2: Observability

The longest phase, and where the value is. By the end, every turn produces telemetry attributed to
the user who caused it.

### Step 2-1. Run the observability skill

**What you type**

```text
Instrument this agent with Agent 365 observability. It's an
Agent (Non AI Teammate) using the obo auth mode.
```

**What the skill does**

`instrument-observability` works through eight phases:

| Phase | What changes |
| --- | --- |
| 0.5 | Confirms agent kind and auth mode — **check this is `obo`** |
| 1 | Detects your stack and loads the matching reference patterns |
| 2 | Installs the A365 OpenTelemetry distro |
| 3 | Wires the distro into your entry point |
| 4 | Adds a baggage scope to your message handler |
| 5 | Implements the token resolver |
| 5.5 | Adds the manual instrumentation scopes |
| 6–8 | Updates config, builds, smoke-tests |

> **Verify the auth mode it reports before letting it continue.** The skill's `obo` mode is correct
> for this scenario. It is *not* correct for a Teams-hosted agent — see
> [Known Skill Gaps](../../03-references/Known-Skill-Gaps.md).

The rest of Phase 2 explains what those changes are, in the order the skill makes them.

### Step 2-2. Install the distro

**.NET**

```bash
dotnet add package Microsoft.OpenTelemetry
```

**Python**

```bash
uv add microsoft-opentelemetry
```

### Step 2-3. Wire the exporter into the entry point

**.NET** — in `Program.cs`, after your services are registered:

```csharp
builder.Services.AddSingleton<ObservabilityTokenStore>();

builder.Services.AddMicrosoftOpenTelemetry(options =>
{
    options.EnableA365 = true;
    options.EnableAgent365Exporter = true;
    options.EnableSensitiveData = true;
    // OBO posts to the delegated endpoint - leave UseS2SEndpoint at its default false.
});
```

**Python** — this must run **before** LangChain or the Azure OpenAI SDK are imported, so the
distro can patch them:

```python
from microsoft.opentelemetry import use_microsoft_opentelemetry

use_microsoft_opentelemetry(
    enable_a365=True,
    # Both flags are needed: enable_a365 only registers the span processors.
    a365_enable_observability_exporter=True,
    a365_token_resolver=token_store.get,
    # OBO posts to /observability/ - leave a365_use_s2s_endpoint at its default.
    enable_sensitive_data=True,
    disable_metrics=True,
)
```

> **Import order is a real bug source in Python.** Call this in `app/main.py` before any agent
> import. If LangChain loads first, auto-instrumentation silently doesn't attach and you get no
> `chat` spans at all.

**Two flags, not one.** `enable_a365` registers the span processors. `EnableAgent365Exporter` /
`a365_enable_observability_exporter` is what actually ships them. Setting only the first gives you
correctly-shaped spans that go nowhere.

### Step 2-4. Implement the two-hop token chain

This is the code the skill generates, and the part most worth reading yourself.

**Hop 1 — the blueprint gets a token exchange assertion:**

```csharp
var form = new Dictionary<string, string>
{
    ["client_id"]     = blueprintClientId,
    ["client_secret"] = blueprintClientSecret,
    ["scope"]         = "api://AzureADTokenExchange/.default",
    ["fmi_path"]      = agentIdentityClientId,
    ["grant_type"]    = "client_credentials",
};
// POST to https://login.microsoftonline.com/<tenant>/oauth2/v2.0/token
```

**Hop 2 — the agent identity exchanges the user's token:**

```csharp
var form = new Dictionary<string, string>
{
    ["client_id"]             = agentIdentityClientId,
    ["scope"]                 = resourceScope,
    ["client_assertion_type"] = "urn:ietf:params:oauth:client-assertion-type:jwt-bearer",
    ["client_assertion"]      = t1Token,          // proves which agent
    ["assertion"]             = userAccessToken,  // proves for whom
    ["grant_type"]            = "urn:ietf:params:oauth:grant-type:jwt-bearer",
    ["requested_token_use"]   = "on_behalf_of",
};
```

In Python, MSAL handles this natively — `fmi_path` is supported on
`acquire_token_for_client` as of MSAL 1.37, so you do not need to hand-roll hop 1.

Cache both hops, and refresh a few minutes early. A token that expires mid-turn disables export
without any visible error.

### Step 2-5. Bridge the token to the exporter

The exporter flushes on a background thread with no user context. Deposit the token on the request
thread; let the resolver read it.

```csharp
// On the request thread, once per turn:
var agentToken = await oboTokens.GetAgentTokenAsync(userAssertion, ObservabilityScope);
tokenStore.Set(agentIdentityClientId, tenantId, agentToken);
```

Then hand the store's read method to the distro as the token resolver.

> **Don't try to acquire the token inside the resolver.** There is no user to exchange on behalf
> of by the time it runs.

### Step 2-6. Open a baggage scope around every turn

Baggage carries the identity dimensions the exporter partitions by. **Spans emitted outside an
active baggage scope are dropped** with `Partitioned into 0 identity groups`.

```csharp
using var scope = new BaggageBuilder()
    .TenantId(tenantId)
    .AgentId(agentIdentityClientId)
    .AgentName(agentName)
    .AgentBlueprintId(blueprintClientId)
    .ConversationId(conversationId)
    .SessionId(conversationId)
    .UserId(userId)
    .UserName(userName)
    .UserEmail(userEmail)
    .ChannelName("web")   // not Teams - use a logical channel name
    .Build();
```

`.AgentBlueprintId()` is load-bearing: it populates `TargetAgentBlueprintId` in reporting.

### Step 2-7. Resolve the caller correctly

**This is the single most common cause of "Defender shows it, the admin center doesn't."**

The admin center needs the caller's **directory object id**. Get it wrong and export still returns
`HTTP 200` — the row just never resolves to a user.

**.NET** — use Microsoft.Identity.Web's helper:

```csharp
using Microsoft.Identity.Web;

var userId    = user?.GetObjectId()    ?? "unknown";
var userName  = user?.GetDisplayName() ?? "unknown";
```

> ⚠️ **Do not use `FindFirst("oid")`.** The OIDC handler renames inbound claims, so that lookup
> misses and typically falls through to `ClaimTypes.NameIdentifier` — which is the pairwise `sub`
> hash, not an object id. The admin center cannot resolve a `sub` back to a user.
> `GetObjectId()` is documented to work whether or not claims mapping is enabled.

**Python** — read `oid` from the validated token claims, and `name` for the display name.

### Step 2-8. Wrap the turn in semantic scopes

Agent 365 only accepts spans whose `gen_ai.operation.name` is one of `invoke_agent`, `chat`,
`execute_tool`, `output_messages`. Anything else is dropped per span.

Open an `InvokeAgentScope` at the start of every turn. It becomes the root span, and it is the
**only** span the M365 admin center ingests.

```csharp
var request = new Request(
    content: userText,
    sessionId: conversationId,
    conversationId: conversationId,
    channel: new Channel("web"));

using var invokeScope = InvokeAgentScope.Start(
    request,
    new InvokeAgentScopeDetails(endpoint),
    agentDetails,
    callerDetails);
```

> **Session, conversation and channel must be on the `Request` object, not only in baggage.**
> Baggage lands on span tags, but the exported `invoke_agent` payload is built from this object.
> Omit them and you export a span that is accepted and still shows no run context.

`chat` spans come free from auto-instrumentation on supported stacks. For **LangChain in Python**
they do not — LangChain is soft-warned by the skill, and you may need to wrap LLM calls in
`InferenceScope` manually. Tool calls need `ExecuteToolScope`.

### Step 2-9. Verify export

Turn on the exporter's own logging:

```powershell
$env:OTEL_LOG_LEVEL="INFO"
$env:A365_OBSERVABILITY_LOG_LEVEL="debug"
```

Ask the agent a question, then look for:

- `Partitioned into 1 identity groups` — **not 0**
- an `invoke_agent` span, as a **root** span
- `HTTP 200` on the export
- the caller id in the payload being a **GUID**, not a long base64-ish hash

✅ **Checkpoint — you can stop here.** The agent is registered and observable.

## Phase 3: Work IQ

Give the agent access to Microsoft 365 data — Mail, Calendar and more — through Work IQ MCP
servers, using the signed-in user's own permissions.

> **Availability check.** Work IQ adapters are not available for every stack. At the time of
> writing there is a .NET path but no Python one. Confirm before planning around it.

### Step 3-1. Run the Work IQ skill

**What you type**

```text
Add Work IQ tools to this agent. I want Mail and Calendar.
```

**What the skill does**

`add-workiq-tools` lists the catalog, adds the servers you pick, writes a `ToolingManifest.json`,
wires a registration service into your agent, and walks you through the permissions handoff.

**Behind the scenes**

```bash
a365 develop list-available                          # see the catalog
a365 develop add-mcp-servers --servers mail,calendar # add them
```

**How to verify**

Check `ToolingManifest.json` lists the servers you expected — **once each**. Then ask the agent
something that needs one, e.g. *"What's on my calendar tomorrow?"*

### Step 3-2. Register each tool exactly once

A tool registered twice will be *called* twice. Check that your registration path wraps each tool
one time only.

> **A cosmetic gotcha worth knowing.** In the Agent 365 map you may see one tool call appear as
> **two nodes** — one keyed by the MCP server, one by the tool name. That is one execution
> described twice, because Agent 365 records `ExecuteToolByMCPServer` and `ExecuteToolBySDK` as
> distinct action types. **Do not "fix" it by removing a registration** — verify the actual side
> effect (e.g. exactly one email sent) before changing anything.

✅ **Checkpoint:** the agent can reach Microsoft 365 data as the signed-in user.

## Phase 4: Verify end to end

Everything so far proves the agent *emits* telemetry. This phase proves it *arrives*.

### Step 4-1. Produce some activity

Ask three or four questions from [4.Sample-prompts.md](4.Sample-prompts.md), including at least
one that calls a tool.

### Step 4-2. Check Microsoft Defender

Go to [Advanced hunting](https://security.microsoft.com) and query `CloudAppEvents` for your
agent. Defender accepts every operation, so you should see `InvokeAgent`, `InferenceCall` and
`ExecuteToolByMCPServer` rows.

Defender indexes first — allow around 5 minutes.

### Step 4-3. Check the Microsoft 365 admin center

Go to https://admin.cloud.microsoft, find your agent, and open its activity.

**The admin center ingests `invoke_agent` rows only**, and reads the caller identity off that span.
So:

| Symptom | Where the problem is |
| --- | --- |
| Nothing anywhere | Export, token, or baggage scope — check Phase 2-9 |
| Defender ✅, admin center ❌ | Your `invoke_agent` span. Almost always the caller id — Step 2-7 |
| Both ✅, no user shown | Caller resolved to something that isn't a directory object id |
| Both ✅, no run context | Session/conversation/channel missing from the `Request` — Step 2-8 |

### Step 4-4. Optional — validate the code

```text
Validate the Agent 365 observability code in this project.
```

The `a365-code-validator` skill checks exporter activation, identity binding, span coverage and
token shape, and reports without changing anything.

> ⚠️ **One rule it applies does not fit this scenario.** The validator's "the principal must be the
> agent identity" check is **S2S-specific**. On the OBO path the export route is keyed by the
> caller's app, and that is correct. Don't "fix" a finding that says otherwise here.

### Troubleshooting

| Symptom | Likely cause |
| --- | --- |
| `Partitioned into 0 identity groups` | No active baggage scope around the turn — Step 2-6 |
| `HTTP 200` but nothing lands anywhere | No user in the tenant holds an Agent 365 licence |
| `AADSTS500011` resource principal not found | Agent 365 not provisioned in this tenant |
| Consent errors on the observability scope | The admin consent handoff from Phase 1-1 was never run |
| `MsalUiRequiredException` on first turn after restart | Auth cookie outlived the in-memory token cache — probe for a token on first render and redirect to sign-in |
| No `chat` spans on Python + LangChain | The distro was initialised after LangChain was imported — Step 2-3 |

✅ **Done.** Registered, observable, attributed, and reaching Microsoft 365 data.
