# Step-by-Step Guide: Web App Agent with User OBO

> **Scenario**: Onboarding a user-driven web agent into Microsoft Agent 365
> **Platform**: Microsoft Agent 365 · Microsoft Entra ID · OpenTelemetry
> **Stacks**: .NET Agent Framework (Blazor Server) · Python + LangChain (FastAPI) · Node.js + LangChain (Express)
> **Target Readers**: Agent developers, Entra administrators
> **Last Updated**: February 2026

## Introduction

We have an agent. It works: a user opens a web page, asks a question, the agent reasons over it, calls a few tools, and answers. From the outside it looks finished.

From the point of view of the organization it runs in, however, that agent doesn't exist. Nobody can see it in the tenant inventory. Nobody knows what it did yesterday, on whose behalf, or which data it touched. If a security analyst asks "which agents accessed customer mailboxes last week?", our agent won't be part of the answer, not because it behaved well, but because it never told anyone anything.

**Microsoft Agent 365** is what closes that gap. It gives the agent an identity in the tenant, a way to report its activity to Microsoft Defender, Microsoft Purview and the Microsoft 365 admin center, and a governed path to Microsoft 365 data. In this guide, we're going to take a plain agent running in a web app with no Agent 365 code in it whatsoever, and onboard it step by step.

The onboarding path we're following here is the **User On-Behalf-Of (OBO)** one. It's the right choice when a human drives the agent: the user signs in, and everything the agent does is attributed back to that person, including the granted permissions. There are other paths (a Teams-hosted agent, or an agent acting under its own identity), and if you're not sure which one applies to you, [Choosing Your Onboarding Path](../../02-patterns/Choosing-Your-Onboarding-Path.md) walks through the decision.

Two more things before we start.

First, **we're going to do most of the work by asking an AI coding assistant to do it for us**. Microsoft ships a set of skills, the [Agent 365 Skills](https://github.com/microsoft/agent365-skills), that know how to perform each onboarding step. We describe what we want in natural language, and the skill edits the project. But, and this matters, we're also going to look at what each skill actually did, and at the CLI commands and code underneath it. If you'd rather not use a coding assistant at all, there's a companion guide, [3.Runbook-Manual.md](3.Runbook-Manual.md), that covers the same ground with every command typed and every file written by hand.

Second, **the work is split into phases**. Phase 1 is a setup phase that only pays off at the end of Phase 2, but from Phase 2 onwards every phase is a valid place to stop, with something real to show for it.

| Phase | What you get at the end of it | Rough time |
| --- | --- | --- |
| 0: Get it running | A working agent, and a machine that can run the tooling | 15 to 45 min |
| 1: Sign users in | An Entra app registration, and the sign-in configured and understood | 30 min |
| 2: Registration | The agent exists in your tenant as a governed identity, and users sign in to it | 30 min |
| 3: Observability | Activity flowing into Defender, Purview and the admin center | 60 to 90 min |
| 4: Work IQ | The agent can reach Microsoft 365 data as the signed-in user | 30 min |
| 5: Verification | Proof that it all actually works end to end | 30 min |

Let's get started!

## How to read the steps in this guide

From Phase 2 onwards, each step is built the same way, so you always know what you're looking at:

1. **What you type**: the prompt you give your coding assistant.
2. **What the skill does**: the changes it's about to make, so nothing comes as a surprise.
3. **Behind the scenes**: the CLI command or the code it all comes down to.
4. **How to verify**: how to know it worked, before you move on to the next step.

For onboarding without a coding assistant, use the [manual runbook](3.Runbook-Manual.md). It supplies the complete commands and source edits without requiring us to extract them from the skill-led steps.

Phase 1 is the exception, and you will be required to do some manual work, since signing users in with Entra in a web application is a task that isn't related to Agent 365, so the skills won't cover it.

### Picking your stack and sticking to it

The same agent ships in three stacks, and the onboarding is genuinely different in each of them, so every step that varies is organized the same way: a short introduction that explains what we're doing and why, and then three subsections, **.NET**, **Python** and **Node.js**, always in that order.

**Read the introduction, then read only your own subsection and skip the other two.** They are alternatives rather than a sequence, and nothing later in the guide expects you to have followed more than one of them.

## Prerequisites

Let's get the boring part out of the way first. There are three kinds of prerequisites here: tools on your machine, licences in your tenant, and permissions on your account. Missing any of them will stop you somewhere in the middle, so it's worth checking all three now.

### The tools you need on your machine

| Requirement | Minimum | Check it with | What needs it |
| --- | --- | --- | --- |
| .NET SDK | 8.0 | `dotnet --version` | The A365 CLI itself, and .NET agents |
| Agent 365 CLI | latest | `a365 --version` | Every phase |
| PowerShell | 7.0 | `pwsh --version` | The consent scripts |
| Azure CLI | latest | `az version` | Signing in to the tenant |
| Az PowerShell module | latest | `Get-Module -ListAvailable Az.Accounts` | Granting permissions |
| Git | any | `git --version` | Not applicable |
| Python | 3.12 | `python --version` | Python agents only |
| uv | latest | `uv --version` | Python agents only |
| Node.js | 20.10 | `node --version` | Node.js agents only |

> **You need the .NET 8 SDK even if your agent is written in Python or TypeScript.** This surprises people. The reason is simply that the Agent 365 CLI is distributed as a .NET global tool, so .NET has to be there to run it. It has nothing to do with the language your agent is written in.

The CLI is the one tool you almost certainly don't have yet, so let's install it:

```bash
dotnet tool install --global Microsoft.Agents365.CLI
a365 --version
```

If the second command prints a version number, we're good.

### The licences your tenant needs

| Requirement | What to know |
| --- | --- |
| Microsoft 365 tenant | With Agent 365 enabled |
| Agent 365 licence | **At least one user in the tenant must hold one** |
| Azure subscription | For the Azure OpenAI resource the agent reasons with |

That middle row deserves a warning, because it's the single most confusing failure in this whole guide. If nobody in the tenant holds an Agent 365 licence, your telemetry is accepted with `HTTP 200` and then silently thrown away. Your logs will say the export succeeded, Defender will show nothing, and there's no error message anywhere that tells you why. So check the licence now, not in Phase 5.

### The permissions you need on your account

| Permission | Who needs it | What it's for |
| --- | --- | --- |
| Application Developer (or higher) | You | Creating app registrations |
| Global Administrator | You *or* a colleague | Granting admin consent to the blueprint |
| Azure OpenAI access | You | The model the agent uses. For the Entra credential path you need the **Cognitive Services OpenAI User** role on the resource; for key auth, access to the resource keys |

> **You don't have to be a Global Administrator yourself.** The CLI does everything it's allowed to do, and then prints a PowerShell snippet for an admin to run for the rest. Just be aware that this handoff exists, and line up the person who will run it before you get to Phase 1. Otherwise you'll be blocked at the start of Phase 3 with a consent error.

### The agent we're onboarding

This scenario ships with three starting points, one per stack. They are the same agent three times over: a research assistant that grounds its answers in the Microsoft Learn MCP server. All three are complete and working, and none of them contains a single line of Agent 365 code:

| Stack | Framework and host | Where it lives |
| --- | --- | --- |
| .NET | Agent Framework on Blazor Server | [`0.Resources/Starting-point/dotnet/`](0.Resources/Starting-point/dotnet/) |
| Python | LangChain on FastAPI | [`0.Resources/Starting-point/python/`](0.Resources/Starting-point/python/) |
| Node.js | LangChain on Express, written in TypeScript | [`0.Resources/Starting-point/nodejs/`](0.Resources/Starting-point/nodejs/) |

You can absolutely bring your own agent instead. The guide assumes two things about it: it runs as a web app with one HTTP request per turn, and there's a single place in the code where a turn begins and ends, because that's where the instrumentation goes.

What all three starting points *do* already contain is the Microsoft Entra sign-in. Signing users in is ordinary web app work that doesn't require Agent 365. In Phase 1, you're going to register the application, fill the settings in and understand what the code does, so the piece your token chain will rest on is something you understand rather than a black box.

## Phase 0: Get the agent running first

Before we add anything, let's make sure the agent works as it is.

Phase 3 adds a fair amount of steps (token exchanges, a telemetry exporter, span scopes), and if the agent is broken to begin with, you'll spend hours trying to work out which layer is at fault. Start from something that answers questions correctly, and every failure afterwards is one you introduced.

### Step 0-1. Configure the Azure OpenAI connection

The agent reasons using a model deployed in Azure OpenAI, so the very first thing it needs to know is *which* resource to call and *which* deployment on it to use. You'll find both in the Azure portal, on the Azure OpenAI resource, under **Resource Management → Keys and Endpoint** and **Model deployments** respectively.

Every stack also wants the id of the tenant that owns that resource, and it is worth a warning before we get to the individual files.

> **The tenant id is not optional if you work across more than one tenant.** It's easy to skim past, so here's what happens if you leave it out: the credential hands back a token from whichever tenant you last signed in to, which may not be the one that owns the Azure OpenAI resource, and the service answers with `HTTP 400`, `Tenant provided in token does not match resource token`. Pinning the tenant explicitly avoids an error that otherwise looks like a code problem.

#### .NET

Open `appsettings.json`:

```json
{
  "AzureOpenAI": {
    "Endpoint": "https://<your-resource>.openai.azure.com/",
    "Deployment": "<your-deployment-name>",
    "TenantId": "<tenant that owns the Azure OpenAI resource>"
  },
  "LearnMcp": { "Endpoint": "https://learn.microsoft.com/api/mcp" }
}
```

#### Python

Copy `.env.example` to `.env` (the example file is committed, `.env` is gitignored) and fill it in:

```bash
AZURE_OPENAI_ENDPOINT=https://<your-resource>.openai.azure.com/
AZURE_OPENAI_DEPLOYMENT=<your-deployment-name>
AZURE_OPENAI_API_VERSION=2024-10-21
AZURE_OPENAI_TENANT_ID=<tenant that owns the Azure OpenAI resource>
```

#### Node.js

The Node starting point uses the same `.env` convention as the Python one, read through `dotenv` in `src/config.ts`, so copy `.env.example` to `.env` and fill in the same four values:

```bash
AZURE_OPENAI_ENDPOINT=https://<your-resource>.openai.azure.com/
AZURE_OPENAI_DEPLOYMENT=<your-deployment-name>
AZURE_OPENAI_API_VERSION=2024-10-21
AZURE_OPENAI_TENANT_ID=<tenant that owns the Azure OpenAI resource>
```

Only the endpoint is genuinely required. `src/config.ts` falls back to `gpt-4.1` and to the `2024-10-21` API version if you leave those two out, and it throws a readable error at startup rather than a stack trace if the endpoint is missing.

### Step 0-2. Decide how the agent authenticates to Azure OpenAI

All three starting points support two ways of authenticating, and they choose between them automatically at startup with a very simple rule: *if an API key is configured, use key auth; if not, use Entra credentials.* There's no flag to flip; the presence or absence of the key is the switch.

Here's how the two compare:

|  | **Path A: Entra credentials** *(the default, and the recommended one)* | **Path B: API key** |
| --- | --- | --- |
| What it actually uses | `DefaultAzureCredential` on .NET, `AzureCliCredential` on Python and Node.js, so your `az login` session locally, and a managed identity once hosted on Azure | A resource key, sent as a bearer secret |
| What you have to configure | Nothing beyond Step 0-1; you just need to be signed in | The key itself, kept in a secret store |
| What you need access to | The **Cognitive Services OpenAI User** role on the resource | The resource keys |
| Why you'd pick it | No long-lived secret to leak or rotate, the call carries a real identity, and it's the *only* option in tenants where key auth is disabled by policy | Environments that still depend on keys. The key never expires and carries no identity of its own |

#### Path A: Entra credentials

There's nothing to add to the configuration. Just sign in to the tenant that owns the Azure OpenAI resource:

```bash
az login --tenant <tenant of the Azure OpenAI resource>
```

When you later deploy to Azure, this path keeps working with no code change. On .NET, `DefaultAzureCredential` picks up the managed identity assigned to the App Service automatically. On Python and Node.js you set one extra value, `AZURE_OPENAI_USE_MANAGED_IDENTITY=true`, which is what makes the code swap the Azure CLI credential for `DefaultAzureCredential`.

#### Path B: API key

If you do need key auth, the important thing is to keep the key out of files that get committed, and both `appsettings.json` and `.env.example` are committed. Where the key goes depends on your stack.

**.NET.** User secrets live outside the project folder entirely, so nothing you do can accidentally commit them:

```bash
dotnet user-secrets set "AzureOpenAI:ApiKey" "<your-key>"
```

You can also set the `AzureOpenAI__ApiKey` environment variable instead, which is what you'd do in a hosting environment where user secrets aren't available.

**Python.** The key goes in `.env`, which is gitignored:

```bash
AZURE_OPENAI_API_KEY=<your-key>
```

**Node.js.** Identical to Python, in the same gitignored `.env`:

```bash
AZURE_OPENAI_API_KEY=<your-key>
```

Take a second to confirm `.env` really is ignored before you paste a key into it. The repository has a single `.gitignore` at its root that covers all three starting points, and it ignores `.env` while explicitly keeping `.env.example`, but that's exactly the kind of thing worth checking rather than assuming.

### Step 0-3. Run it

Now we can start the agent.

#### .NET

```bash
cd 0.Resources/Starting-point/dotnet
dotnet run
```

The default `http` launch profile binds to `http://localhost:5140`, which is the address you'll be registering as a redirect URI in Phase 1.

#### Python

```bash
cd 0.Resources/Starting-point/python
uv sync
uv run uvicorn app.main:app --reload
```

`uv sync` creates the virtual environment and installs the dependencies from the lock file, so the first run takes a moment longer than the ones after it. The app listens on `http://localhost:8000`.

#### Node.js

```bash
cd 0.Resources/Starting-point/nodejs
npm install
npm run dev
```

`npm run dev` runs the TypeScript straight through `tsx` in watch mode, restarting the server on every change, which is the equivalent of `--reload` on the Python side. `npm start` does the same thing without the watcher, and `npm run build` compiles into `dist/` if you want a compiled artifact to deploy. Either way the app listens on `http://localhost:8000`, the same port as the Python one, so don't try to run both at once.

### Step 0-4. Verify that it works

Open the app in a browser and ask it something it should be able to answer, for example:

```text
What is Microsoft Entra Conditional Access?
```

You should get a proper answer with links to Microsoft Learn at the end of it, because this agent grounds its answers in the Microsoft Learn MCP server rather than answering from the model's own memory.

✅ **Checkpoint.** The agent answers questions and cites its sources. There is still no trace of Agent 365 anywhere.

## Phase 1: Sign users in

Nothing in this phase is specific to Agent 365. We're going to register an ordinary Entra application, point the agent at it, and read through the sign-in code that already ships in the starting points. If you've built a web app that signs users in with Entra before, the work will be familiar.

We do it first, before touching Agent 365 at all, because the OBO path attributes everything the agent does back to the person who asked for it, and it can't do that until there's a signed-in person to attribute it to.

Only one step will be delegated later, after we have onboarded the agent into Agent 365. The token this sign-in eventually produces has to be addressed to the agent's blueprint, and the blueprint doesn't exist until Phase 2. So this phase gets you a registered sign-in client, the settings filled in and a clear picture of the code, and then Phase 2 supplies the last value and switches the whole thing on in one short step.

### Step 1-1. Create the app registration that signs users in

Signing a user in means sending their browser to Entra and getting them back again, and Entra will only do that for an application it knows about. So the first thing we need is an app registration whose job is to authenticate the human.

Keep the values from this step somewhere handy, because you'll be pasting them into the app's configuration in Step 1-2.

#### 1-1a. Create the registration

1. Go to the [Entra admin center](https://entra.microsoft.com) and navigate to **Identity → Applications → App registrations**.
2. Click **New registration**.
3. Give it a name that makes its role obvious, something like **my-agent-web-signin**. Phase 2 adds two more identities for this one agent, so a vague name will cost you time later.
4. For **Supported account types**, choose **Accounts in this organizational directory only (Single tenant)**.
5. Under **Redirect URI**, select the **Web** platform and enter the callback address your app will actually listen on. That address depends on your stack:

| Stack | Redirect URI to register | Where the address comes from |
| --- | --- | --- |
| .NET | `http://localhost:5140/signin-oidc` | The default `http` profile in `Properties/launchSettings.json` |
| Python | `http://localhost:8000/signin-oidc` | The uvicorn defaults, and `AZURE_AD_REDIRECT_URI` in `.env.example` |
| Node.js | `http://localhost:8000/signin-oidc` | `HOST` and `PORT` in `.env.example`, and the same `AZURE_AD_REDIRECT_URI` |

6. Click **Register**.

You'll land on the **Overview** blade. Copy the **Application (client) ID** and the **Directory (tenant) ID** from there and keep them somewhere handy; we'll need both in a moment.

> **The redirect URI has to match what the browser sees, scheme included.** It's easy to register the `https` address and then run the app over plain `http`, and Entra answers that with `AADSTS50011`, which reads like a configuration mistake in the app rather than a mismatched string. If you'd rather run the .NET app over TLS, launch it with `dotnet run --launch-profile https` and register `https://localhost:7199/signin-oidc` instead. An app registration can hold several redirect URIs, so registering both now and picking later is perfectly reasonable.

> **`localhost` and `127.0.0.1` are not interchangeable here, even though they reach the same process.** The browser treats them as different origins and scopes the session cookie accordingly, so if you register the callback on `localhost` and then browse the app on `127.0.0.1`, the cookie set just before the redirect isn't sent back on the way in. The sign-in then fails in a way that looks like a lost session rather than a mismatched host. All three starting points default to `localhost` for exactly this reason, and the Python and Node ones say so in `.env.example`.

#### 1-1b. Create a client secret

1. In the same registration, go to **Certificates & secrets**.
2. On the **Client secrets** tab, click **New client secret**.
3. Give it a description and pick an expiry.
4. Click **Add**, then **copy the Value immediately**.

The value is shown once, and once you navigate away it's gone forever and you'll have to create another secret.

Store it somewhere the repository can't reach: `dotnet user-secrets` on .NET, the gitignored `.env` on Python and Node.js. Never in `appsettings.json`, which is committed.

#### 1-1c. Check the sign-in permissions

An OIDC sign-in needs `openid`, `profile` and `offline_access`, and Entra treats those as permissions any user can consent to for themselves. Go to **API permissions** and have a look at what's already there. A new registration usually arrives with **Microsoft Graph** → `User.Read` and nothing else, which is fine: the identity libraries add the OIDC scopes to the request themselves, and none of the starting points calls Graph.

So there's nothing to add here yet, and nothing that needs an administrator. This is a blade to get familiar with rather than one to change.

> **We will come back to it once.** In Step 2-3a we add a permission here that points this registration at the agent's blueprint, and that one does need admin consent. It has to wait, because the blueprint doesn't exist yet.

#### 1-1d. If you'd rather use the CLI

The registration and the secret can both be created from the command line instead:

```bash
# Create the registration
az ad app create --display-name "my-agent-web-signin" \
  --sign-in-audience AzureADMyOrg \
  --web-redirect-uris "http://localhost:5140/signin-oidc"

# Add a secret
az ad app credential reset --id <sign-in client app id> --append
```

Swap the redirect URI for `http://localhost:8000/signin-oidc` if you're on the Python or the Node.js starting point.

### Step 1-2. Fill in the sign-in settings

Every stack needs the same three facts about your tenant: the tenant id, and the sign-in client's id and secret. The callback path and the authority are already filled in for you. There's a fourth value, the blueprint id, that stays blank until Phase 2, and leaving it blank now is the correct thing to do rather than an omission we'll be fixing later.

That blueprint id matters more than its one line suggests, because it's what the scope is built from. The scope is `api://<blueprint-id>/access_agent_as_user`, it has to be byte for byte identical in the sign-in request, in the token acquisition and in anything you paste into a debugger later, and a typo in any copy of it produces a token with the wrong audience rather than an error you can read. That's why all three starting points derive it in exactly one place from the blueprint id rather than letting you write the string out by hand.

#### .NET

The `AzureAd` and `Agent365Observability` sections are already in `appsettings.json`, with the tenant-specific values left blank:

```json
{
  "AzureAd": {
    "Instance": "https://login.microsoftonline.com/",
    "TenantId": "",
    "ClientId": "",
    "ClientSecret": "",
    "CallbackPath": "/signin-oidc"
  },
  "Agent365Observability": {
    "AgentBlueprintId": ""
  }
}
```

Fill in the tenant id and client id from the sign-in registration's **Overview** blade in Step 1-1a, and leave `AgentBlueprintId` alone for now. Leave `ClientSecret` empty in the file too, because the file is committed, and put the secret where it belongs instead:

```bash
dotnet user-secrets set "AzureAd:ClientSecret" "<sign-in client secret>"
```

`CallbackPath` has to line up with the redirect URI you registered in Step 1-1a, because `Microsoft.Identity.Web` builds the callback address from the app's own base URL plus this path. If the two disagree you'll get the `AADSTS50011` we warned about above.

The empty `Agent365Observability` section is the one Step 2-3 comes back to. It's named the way it is because that's the section the Agent 365 tooling and instrumentation look in, so filling it in later puts the blueprint id in the one place everything already expects to find it rather than introducing a second copy under a name of our own.

#### Python

The same values live in `.env`, and `.env.example` already lists them with the redirect URI filled in and the rest blank:

```bash
# Entra sign-in for the web app. Leave blank until the runbook creates the app registration.
AZURE_AD_TENANT_ID=
AZURE_AD_CLIENT_ID=
AZURE_AD_CLIENT_SECRET=
AZURE_AD_REDIRECT_URI=http://localhost:8000/signin-oidc

# Agent blueprint id. The runbook fills this in once the agent is registered, and the
# sign-in stays off until it is set.
AGENTS365OBSERVABILITY__AGENTBLUEPRINTID=
```

Fill in the first three and leave the blueprint id blank. `.env` is gitignored, which is why the secret can sit in it directly here while its .NET counterpart has to go into user-secrets.

The double underscore in `AGENTS365OBSERVABILITY__AGENTBLUEPRINTID` is a .NET configuration convention rather than a Python one, and it's there on purpose: it's the name the Agent 365 tooling uses, so reading it directly means the same `.env` serves both the sign-in and everything the observability phase adds. Pydantic won't pick a name like that up on its own, so `app/config.py` maps it explicitly, and derives the scope from it in one place:

```python
agent_blueprint_id: str | None = Field(
    default=None,
    validation_alias="AGENTS365OBSERVABILITY__AGENTBLUEPRINTID",
)

@property
def agent_blueprint_scope(self) -> str:
    blueprint_id = (self.agent_blueprint_id or "").strip()
    if not blueprint_id:
        raise RuntimeError("The agent blueprint id is not configured.")

    return f"api://{blueprint_id}/access_agent_as_user"
```

You'll see `agent_blueprint_scope` again in the code we read through below. It's the scope the sign-in asks for, and Step 2-3 explains where the blueprint id in it comes from.

#### Node.js

The Node starting point reads the same variable names from the same kind of `.env` file, so `.env.example` looks almost identical to the Python one:

```bash
# Entra sign-in for the web app. Leave blank until the runbook creates the app registration.
AZURE_AD_TENANT_ID=
AZURE_AD_CLIENT_ID=
AZURE_AD_CLIENT_SECRET=
AZURE_AD_REDIRECT_URI=http://localhost:8000/signin-oidc

# Agent blueprint id. The runbook fills this in once the agent is registered, and the
# sign-in stays off until it is set.
AGENTS365OBSERVABILITY__AGENTBLUEPRINTID=

HOST=localhost
PORT=8000
```

Fill in the first three and leave the blueprint id blank, exactly as on Python. Keeping the variable names the same across the two stacks isn't an accident: the double-underscore name is the one the Agent 365 tooling writes, so honouring it here means the file the sign-in reads and the file the instrumentation reads are the same file.

`src/config.ts` reads that name straight out of `process.env` and derives the scope from it, which is the Node counterpart of the Pydantic property above:

```ts
agentBlueprintId: optional("AGENTS365OBSERVABILITY__AGENTBLUEPRINTID"),

get agentBlueprintScope(): string {
    const blueprintId = this.agentBlueprintId?.trim();

    if (!blueprintId) {
        throw new Error("The agent blueprint id is not configured.");
    }

    return `api://${blueprintId}/access_agent_as_user`;
},
```

It's a getter rather than a plain field for a reason worth understanding: a field would be evaluated when the settings object is built, which happens at import time, and the blueprint id is legitimately absent then. A getter is only evaluated when something actually asks for the scope, which is exactly the moment the value has to be there.

Note also the explicit `HOST=localhost`. That is the trap from Step 1-1a made concrete, and the Node app defaults to `localhost` rather than to the `127.0.0.1` that Express examples usually reach for.

### Step 1-3. How the app decides whether to sign anybody in

All three starting points read the configuration at startup and ask one question: is every required sign-in value present? If anything is missing, they skip the whole authentication pipeline and behave exactly as they did in Phase 0. If everything is there, they wire it up.

This is the same pattern as the Azure OpenAI key-versus-credential switch you met in Step 0-2: presence of configuration is the switch, and there's no separate flag to forget to flip. All three apps log which mode they started in, so if you fill the settings in and the app still behaves anonymously, the startup line tells you that much before you go looking through code. It won't name the offending key, so if you see it, check each value in turn.

Right now the app will still report the anonymous mode however carefully you filled Step 1-2 in, because the blueprint id is one of the values it looks for and that one is still empty. That's expected, and Step 2-3 is where it changes.

#### .NET

The decision lives in `Agent365SignInOptions.FromConfiguration`, which is a little stricter than the other two and also treats obvious placeholders (anything with angle brackets, anything starting `your-`, an all-zeroes guid) as not configured, so a half-edited `appsettings.json` keeps the anonymous behaviour rather than failing against Entra. `Program.cs` then branches on the result:

```csharp
var entraSignIn = Agent365SignInOptions.FromConfiguration(builder.Configuration);
builder.Services.AddSingleton(entraSignIn);

if (entraSignIn.IsEnabled)
{
    builder.Services.AddAuthentication(OpenIdConnectDefaults.AuthenticationScheme)
        .AddMicrosoftIdentityWebApp(builder.Configuration.GetSection(Agent365SignInOptions.AzureAdSectionName))
        .EnableTokenAcquisitionToCallDownstreamApi([entraSignIn.AgentUserScope])
        .AddInMemoryTokenCaches();

    builder.Services.AddAuthorization();
    builder.Services.AddCascadingAuthenticationState();
    builder.Services.AddMicrosoftIdentityConsentHandler();
    builder.Services.AddControllersWithViews()
        .AddMicrosoftIdentityUI();
}
```

#### Python

It's the same shape, a single conditional in `app/main.py` that either constructs the auth service or doesn't:

```python
auth_service = AuthService(settings) if settings.entra_sign_in_enabled else None
```

#### Node.js

The same conditional again, in `src/main.ts`, with the router mounted only when there's something to mount:

```ts
const authService = settings.entraSignInEnabled ? new AuthService(settings) : undefined;

if (authService) {
    app.use(authService.router);
    console.info(`Entra sign-in is configured; requesting user tokens for ${settings.agentBlueprintScope}.`);
} else {
    console.info(
        "Entra sign-in is not configured; running anonymously. Fill in the AZURE_AD settings in .env to enable it.",
    );

    app.get("/api/me", (_req, res) => {
        res.json({ authenticationConfigured: false, authenticated: false, user: null });
    });
}
```

`AuthService` owns its own `express.Router`, which is what makes the whole sign-in a single object to add or leave out. The anonymous branch still answers `/api/me`, because the front end asks that question on every page load and a 404 there would look like a broken app rather than a deliberate mode. `entraSignInEnabled` is the getter that does the checking, and it is deliberately blunt:

```ts
get entraSignInEnabled(): boolean {
    return [
        this.azureAdTenantId,
        this.azureAdClientId,
        this.azureAdClientSecret,
        this.azureAdRedirectUri,
        this.agentBlueprintId,
    ].every((value) => Boolean(value?.trim()));
},
```

Note that the blueprint id is one of the five, which is why filling in only the first three in Step 1-2 leaves the app anonymous by design.

### Step 1-4. The sign-in code, line by line

We now have an app that will sign users in and a rough idea of how it decides to. What's left is to read the code that actually does it, because in Phase 3 we're going to call into it once per turn and it helps a great deal to know what's on the other side of that call.

Whichever stack you're on, the shape is the same and the destination is identical: a method that hands back an access token for the blueprint's scope, belonging to the person currently signed in. .NET calls it `AcquireUserAssertionAsync`, Python and Node.js call it `acquire_user_assertion` and `acquireUserAssertion`. That token is the *user assertion*, and it's the input to hop 2 of the token chain in Step 3-4. Everything else in this step exists to produce it.

#### .NET

The middle line of that `AddAuthentication` block is the one that does the work we actually came for. `AddMicrosoftIdentityWebApp` on its own signs the user in and gives you an id token, which tells you who they are and nothing more. `EnableTokenAcquisitionToCallDownstreamApi` turns the sign-in into an authorization-code flow that also comes back with an *access* token for the scope you name, the blueprint's scope, and `AddInMemoryTokenCaches` is where that token is kept so we can ask for it again on every turn.

`AddMicrosoftIdentityUI`, with `app.MapControllers()` further down, is what contributes the ready-made `/MicrosoftIdentity/Account/SignIn` and `SignOut` endpoints. Leave `MapControllers()` out and the redirect to the sign-in endpoint lands on a 404, which is a confusing way to discover that a controller is missing.

The middleware is registered under the same condition, in the order the pipeline needs:

```csharp
if (entraSignIn.IsEnabled)
{
    app.UseAuthentication();
    app.UseAuthorization();
}
```

Requiring a user is then two changes. `Components/Routes.razor` switches to an `AuthorizeRouteView` when sign-in is on, falling back to the plain `RouteView` when it isn't, because an `AuthorizeRouteView` in an app with no authentication services throws about a missing `AuthenticationStateProvider`:

```razor
@if (SignInOptions.IsEnabled)
{
    <AuthorizeRouteView RouteData="routeData" DefaultLayout="typeof(Layout.MainLayout)">
        <NotAuthorized>
            <RedirectToLogin />
        </NotAuthorized>
    </AuthorizeRouteView>
}
else
{
    <RouteView RouteData="routeData" DefaultLayout="typeof(Layout.MainLayout)" />
}
```

And `Components/RedirectToLogin.razor` sends an unauthenticated visitor to the sign-in endpoint:

```razor
@inject NavigationManager Navigation

@code {
    protected override void OnInitialized()
    {
        var returnUrl = Uri.EscapeDataString(Navigation.Uri);
        Navigation.NavigateTo($"MicrosoftIdentity/Account/SignIn?redirectUri={returnUrl}", forceLoad: true);
    }
}
```

The `forceLoad: true` forces sign-in as a full browser round trip to Entra, and Blazor's client-side router would otherwise try to handle the navigation itself and go nowhere.

Finally, the part the token chain will call. `Components/Pages/Home.razor` exposes the assertion through a method whose name you'll see again:

```csharp
public async Task<string> AcquireUserAssertionAsync()
{
    if (!SignInOptions.IsEnabled)
    {
        throw new InvalidOperationException("Entra sign-in is not configured.");
    }

    try
    {
        var tokenAcquisition = Services.GetRequiredService<ITokenAcquisition>();
        return await tokenAcquisition.GetAccessTokenForUserAsync([SignInOptions.AgentUserScope]);
    }
    catch (MsalUiRequiredException ex)
    {
        Services.GetRequiredService<MicrosoftIdentityConsentAndConditionalAccessHandler>()
            .HandleException(ex);
        return string.Empty;
    }
    catch (MicrosoftIdentityWebChallengeUserException ex)
    {
        Services.GetRequiredService<MicrosoftIdentityConsentAndConditionalAccessHandler>()
            .HandleException(ex);
        return string.Empty;
    }
}
```

Because the token came from the cache that `AddInMemoryTokenCaches` set up during sign-in, this call is normally silent, with no redirect and no prompt. The two `catch` blocks are there for the cases where it isn't: `MsalUiRequiredException` when there's no usable cached token, and `MicrosoftIdentityWebChallengeUserException` when Entra wants something interactive, typically a conditional access policy demanding a fresh sign-in or a consent prompt that was never answered. Both are handed to the consent handler, which turns them into a redirect the user can complete rather than an exception that kills the turn.

The services are resolved from `IServiceProvider` rather than injected with `@inject`, which is needed since `ITokenAcquisition` only exists in the container when sign-in is enabled, and an `@inject` directive would fail at render time in anonymous mode, before any of our conditionals get a chance to run.

#### Python

FastAPI has no built-in identity story, so on Python the authorization-code flow is driven directly with MSAL, in `app/auth.py`. The flow needs somewhere to survive the round trip to Entra, and that somewhere has to be the server, so `AuthService` keeps a dictionary of sessions and hands the browser an opaque cookie that points into it. No token ever reaches the browser.

Going out:

```python
async def signin(self, request: Request) -> RedirectResponse:
    session_id = self._get_session_id(request) or self._new_session_id()
    session = self._sessions[session_id]
    # The flow dictionary contains the state, nonce and PKCE verifier that MSAL must
    # validate when Entra redirects back, so it stays in the server-side session.
    flow = self._client.initiate_auth_code_flow(
        scopes=[self._settings.agent_blueprint_scope],
        redirect_uri=self._settings.azure_ad_redirect_uri,
    )
    session["flow"] = flow

    response = RedirectResponse(flow["auth_uri"])
    self._set_session_cookie(response, session_id)
    return response
```

`initiate_auth_code_flow` generates the state, the nonce and the PKCE challenge, and returns them in the `flow` dictionary that `acquire_token_by_auth_code_flow` validates the callback against, which is why we keep it rather than just the URL. Note the `scopes` argument: it's `agent_blueprint_scope`, the blueprint's scope, and that single line is what makes the resulting token usable as an assertion.

The cookie that carries the session id is set `httponly` so the browser can't read it and `samesite="lax"` so it still arrives on the redirect back from Entra. `strict` would drop it, and the callback would look like a session that never existed.

Coming back, `/signin-oidc` completes the flow and remembers who signed in:

```python
result = self._client.acquire_token_by_auth_code_flow(
    session.pop("flow"),
    dict(request.query_params),
)
if "error" in result:
    raise HTTPException(
        status_code=status.HTTP_401_UNAUTHORIZED,
        detail=result.get("error_description") or result["error"],
    )

claims = result.get("id_token_claims", {})
session["claims"] = claims
```

The `session.pop` is required since a flow is good for exactly one callback, and leaving it in place would let a replayed callback reuse it. The claims we keep are the ones the page needs to greet the user by name, and the code goes on to record the MSAL account id for that username, which is what `acquire_token_silent` looks the cached token up by later.

Then the method the token chain calls:

```python
def acquire_user_assertion(self, request: Request) -> str:
    """Return a blueprint-scoped access token for the signed-in user."""
    session = self._get_session(request)
    if not session:
        raise AuthRequiredError("Sign in before chatting with the agent.")

    account = self._get_account(session)
    if not account:
        raise AuthRequiredError("Sign in before chatting with the agent.")

    result = self._client.acquire_token_silent(
        [self._settings.agent_blueprint_scope],
        account=account,
    )
    if not result or "access_token" not in result:
        raise AuthRequiredError("Sign in again so the app can get a user assertion.")

    return result["access_token"]
```

`acquire_token_silent` reads from the cache MSAL populated during sign-in and refreshes the token when it can, so this is normally a local operation. When it genuinely can't produce a token it raises `AuthRequiredError`, which `/api/chat` turns into a 401 rather than a 500:

```python
if auth_service:
    try:
        auth_service.acquire_user_assertion(http_request)
    except AuthRequiredError as error:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail=str(error),
        ) from error
```

The whole OBO chain starts from the signed-in user, so an anonymous turn is one that can't be attributed to anybody and won't be exported.

#### Node.js

Express is in the same position as FastAPI, with no identity story of its own, so `src/auth.ts` drives the authorization-code flow directly with `@azure/msal-node`. The structure deliberately mirrors the Python one: a `Map` of server-side sessions, an opaque cookie that points into it, and no token anywhere near the browser.

The one real difference is that Node's MSAL is lower level than Python's. There is no `initiate_auth_code_flow` that bundles state, nonce and PKCE into a single object for you, so we generate the PKCE pair and the state ourselves and keep them for the callback:

```ts
private async signin(req: Request, res: Response): Promise<void> {
    const sessionId = this.getSessionId(req) ?? this.newSessionId();
    const session = this.sessions.get(sessionId)!;

    const { verifier, challenge } = await this.crypto.generatePkceCodes();
    const state = this.crypto.createNewGuid();
    session.flow = { state, codeVerifier: verifier };

    const authUrl = await this.client.getAuthCodeUrl({
        scopes: [this.settings.agentBlueprintScope],
        redirectUri: this.settings.azureAdRedirectUri,
        codeChallenge: challenge,
        codeChallengeMethod: "S256",
        state,
    });

    this.setSessionCookie(res, sessionId);
    res.redirect(authUrl);
}
```

The important line is the same one as on Python: `scopes` is `agentBlueprintScope`, so the token that eventually comes back is addressed to the blueprint and can be used as an assertion. The verifier stays on the server because it is the secret half of the PKCE pair, and the state stays with it because we have to compare it ourselves when Entra redirects back.

The cookie is set the way it is for the same reason as on Python:

```ts
res.cookie(SESSION_COOKIE_NAME, sessionId, {
    httpOnly: true,
    // Entra redirects back from another site, so a strict cookie would be withheld on
    // the callback and the server-side session would look as if it had been lost.
    sameSite: "lax",
});
```

Coming back, the callback does by hand what MSAL does for you in Python:

```ts
// A flow is good for exactly one callback; dropping it here stops a replayed
// callback from reusing the same verifier.
session.flow = undefined;

const { code, state, error, error_description: errorDescription } = req.query;

if (typeof error === "string") {
    res.status(401).send(typeof errorDescription === "string" ? errorDescription : error);
    return;
}

if (typeof code !== "string" || state !== flow.state) {
    res.status(401).send("The sign-in response did not match the request.");
    return;
}

const result = await this.client.acquireTokenByCode({
    code,
    scopes: [this.settings.agentBlueprintScope],
    redirectUri: this.settings.azureAdRedirectUri,
    codeVerifier: flow.codeVerifier,
});

session.claims = (result.idTokenClaims ?? {}) as Record<string, unknown>;
session.accountId = result.account?.homeAccountId;
```

That `state !== flow.state` comparison is not optional, since it's what stops an attacker from getting a victim's browser to complete a sign-in the attacker started, and on Python it happens inside `acquire_token_by_auth_code_flow` where you never see it. Clearing `session.flow` before we validate anything is the equivalent of the Python `session.pop`, and it matters for the same reason: one callback per flow, so a replayed callback finds nothing to reuse.

Then the method the token chain calls, the Node counterpart of the two above:

```ts
/** Return a blueprint-scoped access token for the signed-in user. */
async acquireUserAssertion(req: Request): Promise<string> {
    const session = this.getSession(req);
    if (!session) {
        throw new AuthRequiredError("Sign in before chatting with the agent.");
    }

    const account = await this.getAccount(session);
    if (!account) {
        throw new AuthRequiredError("Sign in before chatting with the agent.");
    }

    const result = await this.client
        .acquireTokenSilent({ account, scopes: [this.settings.agentBlueprintScope] })
        .catch(() => null);

    if (!result?.accessToken) {
        throw new AuthRequiredError("Sign in again so the app can get a user assertion.");
    }

    return result.accessToken;
}
```

`acquireTokenSilent` reads MSAL's cache and refreshes the token when it can, so this is normally a local operation with no network call at all. The `.catch(() => null)` is there because Node's MSAL throws when it has nothing usable rather than returning an empty result, and we'd rather turn every one of those cases into the same `AuthRequiredError` than have two different failure shapes to handle upstream. `/api/chat` then turns that into a 401:

```ts
if (authService) {
    try {
        await authService.acquireUserAssertion(req);
    } catch (error) {
        if (error instanceof AuthRequiredError) {
            res.status(401).json({ reply: error.message });
            return;
        }

        console.error("Could not acquire the user assertion", error);
        res.status(401).json({ reply: "Sign in before chatting with the agent." });
        return;
    }
}
```

Right now the assertion is fetched and thrown away, which looks pointless and is on purpose: it proves the sign-in works before there's anything to spend the token on. Step 3-5 is where the return value stops being discarded.

Be aware that this sample is meant for testing scenarios. The session map lives in the process, so restarting the app signs everybody out, and running more than one instance behind a load balancer would hand users a cookie the next instance has never heard of. That's a fine trade for a sample you run on your laptop, and it is the first thing to replace with a shared session store if you take this pattern into production.

#### A note on gating

Requiring a signed-in user is the one place where the stacks genuinely differ in kind rather than in syntax. On .NET, `[Authorize]` and `AuthorizeRouteView` produce the redirect for free, so an anonymous visitor never sees the chat page at all. On Python and Node.js we do it ourselves: the page still renders, `/api/me` tells the front end whether anybody is signed in so it can show either a sign-in link or a name, and `/api/chat` refuses the turn with a 401. Neither approach is more correct, but they look quite different in the browser and it's useful to know which one you should be seeing.

✅ **Checkpoint.** The sign-in client is registered and the app is pointed at it, and you've read the code that will use it. The sign-in is still dormant, because the scope it asks for is built from a blueprint id that doesn't exist yet. Phase 2 creates the blueprint and switches it on.

## Phase 2: Register the agent

Now the agent stops being just code on your laptop and becomes an object in your tenant.

Two objects, actually, and the difference between them matters for everything that follows:

- The **blueprint** is the parent app registration. It holds the permissions, and it owns the agent. Think of it as the definition of the agent.
- The **agent identity** is a child principal of that blueprint. It's the thing that actually *acts*, the principal your telemetry will be attributed to.

The phase ends by going back to the sign-in from Phase 1 and giving it the piece it was missing.

### Step 2-1. Run the setup skill

Nothing in this step depends on your stack. The CLI registers identities in Entra, and it doesn't care what language the agent is written in.

**What you type**

```text
Set up Agent 365 for this agent. It's a web app where users sign in,
not a Teams agent and not an AI Teammate. Use the OBO auth mode.
```

**What the skill does**

The `a365-setup` skill runs first. It checks every prerequisite we listed earlier, offers to install anything that's missing, and confirms which Azure identity you're signed in as. Then it asks you two questions, and these two answers determine everything that follows:

| Question | Your answer for this scenario | Why |
| --- | --- | --- |
| Agent kind? | **Agent (Non AI Teammate)** | A human drives this agent; it doesn't have its own mailbox or presence in Teams |
| Auth mode? | **`obo`** | Everything the agent does is attributed to the signed-in user |

Once you've answered, `a365-setup` hands off to `make-a365-agent`, which performs the actual registration. For our scenario, an agent running in a web app where a human signs in, we need to pick **`obo`**.

**Behind the scenes**

Whatever the skill says, this is what it comes down to:

```bash
a365 setup all --agent-name "my-agent" --dry-run    # preview what will happen
a365 setup all --agent-name "my-agent"              # actually do it
```

Always run the dry run first and read the output. And don't worry about running the real command more than once: `a365 setup all` is idempotent, so it's safe to re-run after fixing a problem.

Here's what it creates for you:

- an **agent blueprint** app registration, together with a client secret
- an **agent identity**, as a child of that blueprint
- the API permissions the agent needs, including `Agent365.Observability.OtelWrite`, which is the one that lets it write telemetry
- a file called `a365.generated.config.json`, holding all the generated identifiers

**How to verify**

Have a look at what was generated, by opening the `a365.generated.config.json` file with your editor of choice.

You should see an `agentBlueprintId` and an agent identity id in there. Then go to the [Entra admin center](https://entra.microsoft.com) → **App registrations** and confirm the blueprint is listed.

> ⚠️ **If you're not a Global Administrator**, look carefully at the summary the CLI printed. It will contain a consent snippet for an admin to run. Until somebody runs it, the permissions exist but are not granted, and Phase 3 will fail with a consent error that looks like a bug in your code. This is the handoff we mentioned in the prerequisites.

### Step 2-2. Store the blueprint secret somewhere safe

`a365 setup all` generated a client secret for the blueprint. That secret is what proves, when we build the token chain in Phase 3, that your code is allowed to act as this agent, so it must never end up in source control.

If you lose it, you don't have to re-register anything. You can read it back, on the same machine, signed in as the same user, with:

```bash
a365 setup blueprint --agent-name "my-agent" --show-secret
```

Where it goes depends on your stack, and it's the same choice you made for the Azure OpenAI key back in Step 0-2.

#### .NET

Put it in user secrets, which live outside the project folder entirely:

```bash
dotnet user-secrets set "Agent365:BlueprintClientSecret" "<secret>"
```

#### Python

Put it in `.env`, and take a second to confirm that `.env` really is listed in `.gitignore`:

```bash
AGENT365_BLUEPRINT_CLIENT_SECRET=<secret>
```

#### Node.js

The same, in the same kind of gitignored `.env`:

```bash
AGENT365_BLUEPRINT_CLIENT_SECRET=<secret>
```

### Step 2-3. Connect the sign-in to the blueprint

Here is where the two halves meet. Phase 1 left us with an app that can authenticate a user, and Step 2-1 gave us a blueprint. What we don't have yet is a token that links them, which is the whole point of the OBO path.

The obvious question at this point is why the blueprint can't just sign users in itself, given that it's an app registration like any other. The reason is that a blueprint is an **agentic application**, and Microsoft Entra bars agentic applications from interactive `/authorize` flows. A blueprint can never present a sign-in page. That's precisely why Phase 1 came first, and why what we registered there was a separate, completely ordinary application.

So this scenario has three identities in it, and keeping them straight in your head makes everything else easier:

| Identity | Who creates it | What it does |
| --- | --- | --- |
| **Sign-in client** | You, in Step 1-1 | Signs the user in, and requests the blueprint's scope |
| **Blueprint** | `a365 setup all`, in Step 2-1 | Owns the permissions, and authenticates hop 1 of the token chain |
| **Agent identity** | `a365 setup all`, in Step 2-1 | The principal the agent acts as, and that spans are exported as |

Keep `a365.generated.config.json` open, because you'll need the **blueprint's app id** twice below.

#### 2-3a. Give the sign-in app permission to call the blueprint

This is the step that makes the entire token chain possible, so it's worth doing slowly. It's portal work, identical whatever your agent is written in.

1. Still in the sign-in registration, go to **API permissions**.
2. Click **Add a permission**.
3. Choose the **APIs my organization uses** tab.
4. Paste the **blueprint's app id** into the search box and select it from the results.
5. Choose **Delegated permissions**.
6. Tick **`access_agent_as_user`**.
7. Click **Add permissions**.

> **If the blueprint doesn't come up in the search**, search by its app id rather than its display name because the CLI appends `" Blueprint"` to the name you chose, so what you type may not match. And if you find the API but it exposes no scopes at all, open the **blueprint's** registration, go to **Expose an API → Add a scope**, create a scope named exactly `access_agent_as_user`, set **Who can consent?** to **Admins and users**, leave the state **Enabled**, and then come back here and repeat the steps above.

Then click **Grant admin consent for \<your tenant\>**. This one genuinely needs an administrator, because `access_agent_as_user` is not a permission users can consent to for themselves. If the button is greyed out for you, this is the second of the two admin handoffs in this guide. A permission that's recorded but not consented to behaves exactly like one that was never added.

From the command line, the same two operations are:

```bash
# The scope id is on the blueprint's "Expose an API" blade
az ad app permission add --id <sign-in client app id> \
  --api <blueprint-app-id> --api-permissions <scope-id>=Scope

az ad app permission admin-consent --id <sign-in client app id>
```

Note that `az ad app permission add` only records the permission; the consent grant on the second line is what makes it usable.

> **Don't mix up the two secrets.** You now have a blueprint secret and a sign-in client secret, and they do completely different jobs. The blueprint secret authenticates hop 1 of the token chain; the sign-in client secret authenticates the web sign-in. Swapping them produces authentication errors that are genuinely hard to read.

#### 2-3b. Give the app the blueprint id

This is the value we left blank in Step 1-2, and it's the one that switches the sign-in on. Take `agentBlueprintId` from `a365.generated.config.json` and put it where the app expects it.

That single value does two things at once. It completes the set of settings the startup check looks for, so the authentication pipeline you read through in Phase 1 finally gets registered, and it supplies the resource half of `api://<blueprint-id>/access_agent_as_user`, which is the scope the sign-in asks for.

That scope is the part worth slowing down over, because an app can sign users in perfectly well and never ask for it. You would have a working login and a token that the next phase rejects. The scope determines who the token is *addressed to*, and hop 2 of the token chain will only accept an assertion addressed to the blueprint. Not `User.Read`, and not the blueprint's `.default`.

#### .NET

In `appsettings.json`:

```json
"Agent365Observability": {
  "AgentBlueprintId": "<blueprint app id>"
}
```

#### Python

In `.env`:

```bash
AGENTS365OBSERVABILITY__AGENTBLUEPRINTID=<blueprint app id>
```

#### Node.js

In `.env`, with the same variable name as Python, since both samples read it through the same key:

```bash
AGENTS365OBSERVABILITY__AGENTBLUEPRINTID=<blueprint app id>
```

Restart the app afterwards, whichever stack you're on. On Python and Node.js the value is read once when the process starts, so a running app won't take into account the changes.

#### 2-3c. Verify the token you get back

Open the app. The stacks announce themselves differently here. On .NET you should be redirected to Entra before the chat page renders at all, because `AuthorizeRouteView` refuses to show a protected page to an anonymous visitor. On Python and Node.js the page still loads, and the line under the title changes from the anonymous message to a **Sign in** link, because there we do the gating ourselves rather than getting it from the framework. Either way, the first time on a tenant where an admin hasn't already consented, you'll be asked to approve the permissions.

Once you're back, we want to look at the token the app is holding:

- On **.NET**, set a breakpoint on the `return await tokenAcquisition.GetAccessTokenForUserAsync(...)` line in `Components/Pages/Home.razor` and reload the page. The first render probes for the token, so the breakpoint hits without you having to send a message. Copy the return value out of the debugger.
- On **Python**, set a breakpoint on the `return result["access_token"]` line in `app/auth.py` and send a message. `/api/chat` calls `acquire_user_assertion` before it does anything else, so the breakpoint hits on the first turn.
- On **Node.js**, set a breakpoint on the `return result.accessToken` line in `src/auth.ts` and send a message, for the same reason. The sample runs its TypeScript through `tsx` rather than compiling first, so point your editor's debugger at `npm run dev` and it will stop in the `.ts` file you're reading. If you'd rather use Chrome DevTools, `node --inspect node_modules/tsx/dist/cli.mjs src/main.ts` gets you the same thing.

Paste what you copied into [jwt.ms](https://jwt.ms), which decodes it in the browser without sending it anywhere, and look at four claims:

| Claim | What it should say |
| --- | --- |
| `aud` | The **blueprint's** app id, or `api://<blueprint-id>`, **not** the sign-in client's id |
| `scp` | It should contain `access_agent_as_user` |
| `oid` | The signed-in user's object id |
| `tid` | Your tenant id |

If `aud` is the sign-in client, or Microsoft Graph, then the scope wasn't requested correctly. The usual cause is a blueprint id that's present but wrong, a stale one from an earlier `a365 setup all` run, say, which builds a scope pointing at a resource that isn't your blueprint.

While you have the decoded token in front of you, make a note of the `oid` value, since Step 3-7 will reference it.

✅ **Checkpoint.** This is a perfectly good place to stop. The agent is registered and governed, it shows up in your tenant, and users sign in to it with a token addressed to the blueprint. It doesn't emit any telemetry yet; that's the next phase.

## Phase 3: Observability

This is the longest phase, and it's the one that delivers most of the value. By the end of it, every single turn the agent takes will produce telemetry, attributed to the user who caused it, and visible in Defender, Purview and the Microsoft 365 admin center.

It's also the phase with the most moving parts, so here's the shape of it before we start. We need to install the telemetry distro, wire it into the app's startup, obtain a token that the exporter is allowed to use, make sure every turn carries the identity information the service partitions on, and finally wrap the turn in the specific span types Agent 365 accepts.

### Step 3-2. Install the distro

The Agent 365 telemetry support ships as an OpenTelemetry distro: a wrapper around standard OTel that adds the Agent 365 exporter and the span processing the service expects. There's one for each of our three stacks, and they're deliberately close to each other in shape, which is why the steps that follow read so similarly.

#### .NET

```bash
dotnet add package Microsoft.OpenTelemetry
```

#### Python

```bash
uv add microsoft-opentelemetry
```

#### Node.js

```bash
npm install @microsoft/opentelemetry
```

The Node package brings its own copy of the OpenTelemetry SDK along with it, so you don't need to add `@opentelemetry/sdk-node` yourself. You will want `@opentelemetry/api` if you plan to touch spans directly, but nothing in this guide does.

### Step 3-3. Wire the exporter into the entry point

Now we initialise the distro when the app starts. All three stacks are doing the same thing here: handing the distro a callback it can use to fetch a token later, and telling it to actually export rather than merely decorate. Where they differ is in how much of the LLM instrumentation you get for free.

#### .NET

In `Program.cs`. Note that this hangs off `builder` rather than `builder.Services`, because the distro configures the whole OpenTelemetry pipeline rather than registering one more service:

```csharp
using Microsoft.OpenTelemetry;

var observabilityTokenStore = new ObservabilityTokenStore();
builder.Services.AddSingleton(observabilityTokenStore);

builder.UseMicrosoftOpenTelemetry(o =>
{
    o.Exporters = builder.Environment.IsDevelopment()
        ? ExportTarget.Agent365 | ExportTarget.Console
        : ExportTarget.Agent365;

    // The console metric exporter prints every histogram bucket on a timer, which buries the
    // spans we actually want to read. Traces and logs still reach Agent 365.
    o.Instrumentation.EnableMetrics = false;

    // OBO posts to /observability/, so UseS2SEndpoint stays at its default of false.
    o.Agent365.TokenResolver = (agentId, tenantId) =>
        Task.FromResult(observabilityTokenStore.Get(agentId, tenantId));
});
```

`o.Exporters` is a flags enum. During development we set it to `Agent365 | Console` so that spans, as well as being sent to Agent 365, show up in the terminal, which makes troubleshooting far easier. `TokenResolver` is the hook the exporter calls when it needs a token, and it reads from a store that stays empty until Step 3-5 fills it, so nothing is expected to come out of it yet.

This code gets spans out of the process, however the LLM calls only emit spans if the chat client is instrumented too, through a second `UseOpenTelemetry()` call. The starting point builds the agent straight from the Azure OpenAI chat client, so we slot the instrumentation in between the two:

```csharp
var instrumentedChatClient = azureClient.GetChatClient(aoaiDeployment)
    .AsIChatClient()
    .AsBuilder()
    .UseFunctionInvocation()
    .UseOpenTelemetry(configure: cfg => cfg.EnableSensitiveData = true)
    .Build();

return instrumentedChatClient.AsAIAgent(
    instructions: "...",        // unchanged from the starting point
    name: "LearnMcpAgent",
    tools: learnMcpTools.Cast<AITool>().ToList());
```

`UseFunctionInvocation()` intercepts tool calls so they surface as tool spans, and `UseOpenTelemetry()` emits the `chat` spans that `InvokeAgentScope` anchors as children in Step 3-8. `EnableSensitiveData` writes the prompts and completions into the span attributes.

#### Python

In `app/main.py`:

```python
from microsoft.opentelemetry import use_microsoft_opentelemetry

use_microsoft_opentelemetry(
    enable_a365=True,
    # Both flags are needed: enable_a365 only registers the span processors.
    a365_enable_observability_exporter=True,
    a365_token_resolver=token_store.get,
    # OBO posts to /observability/, so leave a365_use_s2s_endpoint at its default.
    enable_sensitive_data=True,
    disable_metrics=True,
)
```

**On Python there are two switches:** `enable_a365` registers the span processors that shape the spans, while `a365_enable_observability_exporter` is what actually ships them.

> **On Python, where you put this call matters.** It has to run before LangChain or the Azure OpenAI SDK are imported, because the distro works by patching those libraries as they load. If LangChain is imported first, the auto-instrumentation silently doesn't attach, and you end up with no `chat` spans at all. The agent works perfectly, and the LLM calls are simply invisible. Put the call at the very top of `app/main.py`, above the agent imports.

#### Node.js

Node has the same two-switch design as Python, and the same load-order sensitivity, but it's rather less forgiving about the second one. So rather than putting the call at the top of `main.ts`, create a small dedicated module, `src/observability.ts`:

```typescript
import { useMicrosoftOpenTelemetry } from "@microsoft/opentelemetry";

import { tokenStore } from "./token-store.js";

useMicrosoftOpenTelemetry({
    a365: {
        enabled: true,
        // Both flags are needed: `enabled` alone only registers the span processors.
        enableObservabilityExporter: true,
        tokenResolver: (agentId, tenantId) => tokenStore.get(agentId, tenantId),
        // OBO posts to /observability/, so useS2SEndpoint stays at its default of false.
    },
    instrumentationOptions: {
        langchain: {},
    },
    // Writes prompts and completions onto the spans. Useful while you're learning to read
    // the telemetry, worth reconsidering before this reaches production.
    enableSensitiveData: true,
    // Also print the spans to the terminal while developing.
    enableConsoleExporters: true,
});
```

Note that `enableSensitiveData` and `enableConsoleExporters` sit at the top level rather than inside the `a365` block, because they apply to the whole distro rather than to the Agent 365 exporter specifically. They're the Node equivalents of `EnableSensitiveData` and the `Console` export target on .NET.

Then make it the very first import in `src/main.ts`, above every other one:

```typescript
import "./observability.js";

import { fileURLToPath } from "node:url";
// ... the rest of the existing imports
```

> **Why a separate file rather than a call at the top of `main.ts`?** Because ES module imports are hoisted. Every `import` in a module is resolved and executed before any of that module's own statements run, so `import { LearnAgent } from "./agent.js"` pulls in LangChain and the Azure OpenAI SDK *before* a `useMicrosoftOpenTelemetry()` call sitting in the body of the same file ever executes. The patching then has nothing left to attach to. Putting the call in its own module and importing that module first is what guarantees it runs before LangChain loads. This is exactly the Python trap from the section above, except that on Python you can fix it by moving a line, and on Node you can't.

One good news about the Node distro: LangChain auto-instrumentation is on by default, so passing `instrumentationOptions.langchain` is really just making the intent explicit. You get `chat` spans without doing anything else, which is the opposite of the situation on Python. For the same reason, don't also register the LangChain instrumentation by hand; doing both produces every span twice.

Finally, because Node processes usually exit on a signal rather than draining politely, flush on the way out:

```typescript
import { shutdownMicrosoftOpenTelemetry } from "@microsoft/opentelemetry";

for (const signal of ["SIGINT", "SIGTERM"] as const) {
    process.once(signal, () => {
        void shutdownMicrosoftOpenTelemetry().finally(() => process.exit(0));
    });
}
```

Without this, the last batch of spans is still sitting in the exporter's queue when the process dies, and the final turn of every debugging session goes missing.

### Step 3-4. Implement the two-hop token chain

This is the most important part of the OBO path, and the part most worth reading even if the skill wrote it for you. It is also the part that's most nearly identical across the three stacks, because what's really going on is two HTTP requests to Entra, and the shape of those requests doesn't depend on your language.

The exporter needs a token to talk to the Agent 365 Observability API, and it has to be a specific one: a token issued to the agent identity, acting on behalf of the signed-in user. A plain delegated user token is rejected, because its principal is the human rather than the agent. Getting that token takes two hops.

**Hop 1**: the blueprint proves that it owns the agent identity, and gets back an assertion. Here it is as a form post, in C# for concreteness:

```csharp
var form = new Dictionary<string, string>
{
    ["client_id"]     = blueprintClientId,
    ["client_secret"] = blueprintClientSecret,
    ["scope"]         = "api://AzureADTokenExchange/.default",
    ["fmi_path"]      = agentIdentityClientId,
    ["grant_type"]    = "client_credentials",
};
// POST to https://login.microsoftonline.com/<tenant>/oauth2/v2.0/token
```

The `fmi_path` parameter is what turns this from an ordinary client-credentials call into an agent flow. It effectively says: *issue me an assertion I can use to act as this child identity*. What comes back is not an access token and can't be used as one. It's only usable as a client assertion in the second hop.

**Hop 2**: the agent identity exchanges the user's token for the one we actually want:

```csharp
var form = new Dictionary<string, string>
{
    ["client_id"]             = agentIdentityClientId,
    ["scope"]                 = resourceScope,
    ["client_assertion_type"] = "urn:ietf:params:oauth:client-assertion-type:jwt-bearer",
    ["client_assertion"]      = t1Token,          // proves which agent
    ["assertion"]             = userAccessToken,  // proves for whom
    ["grant_type"]            = "urn:ietf:params:oauth:grant-type:jwt-bearer",
    ["requested_token_use"]   = "on_behalf_of",
};
```

Look at the two assertions side by side, because that pairing is the whole idea: `client_assertion` says *which agent is asking*, and `assertion` says *who it's asking for*. That second one is the user token we so carefully addressed to the blueprint back in Step 2-3, and the app now obtains it on every turn: through `AcquireUserAssertionAsync()` on .NET, `acquire_user_assertion()` on Python, and `acquireUserAssertion(req)` on Node.js. The result is a token that represents the agent acting for that specific person.

Both hops are plain form posts, so you can implement them with whatever HTTP client your stack already uses. That said, two of the three stacks can save you the trouble of hand-rolling them:

#### .NET

There's no shortcut here, so the two form posts above are what you write. `HttpClient` with a `FormUrlEncodedContent` body is all it takes, and reading the JSON response for `access_token` and `expires_in` gives you everything the caching advice below needs.

#### Python

MSAL supports `fmi_path` natively on `acquire_token_for_client` as of MSAL 1.37, so hop 1 needs no hand-written HTTP at all.

#### Node.js

`@azure/msal-node` version 5 has both halves: `fmiPath` on the client-credential request for hop 1, and `acquireTokenOnBehalfOf` for hop 2. You already have MSAL in the project from Phase 1, so reusing it means one fewer HTTP client to look after and gives you MSAL's token cache for free. Using the raw form posts above works equally well, and has the advantage of matching what you'd write in any other language, which is why they're what we've shown.

#### All three stacks

One last practical point, and it applies everywhere: **cache both hops, and refresh a few minutes before expiry**. A token that expires halfway through a turn disables the export with no visible error at all. The agent keeps answering, and the telemetry quietly stops.

### Step 3-5. Bridge the token across to the exporter

We have a token. Now the exporter has to be able to find it, and that's less trivial than it sounds.

The exporter doesn't flush spans on the request thread, but on a background loop, where there is no HTTP request, no signed-in user, and therefore nothing to exchange on behalf of. So the pattern is to acquire the token while we still have a user, park it somewhere both threads can see, and let the exporter read it from there.

The store itself is a small dictionary keyed on the agent id and the tenant id, and its read method is the one we already handed to the distro back in Step 3-3. That's the whole bridge: the code below is what finally puts something in the store for the background exporter to find.

#### .NET

```csharp
// On the request thread, once per turn:
var userAssertion = await AcquireUserAssertionAsync();   // the blueprint-scoped token verified in Step 2-3c
var agentToken = await oboTokens.GetAgentTokenAsync(userAssertion, ObservabilityScope);
observabilityTokenStore.Set(agentIdentityClientId, tenantId, agentToken);
```

#### Python

```python
# In the /api/chat handler, before invoking the agent:
user_assertion = auth.acquire_user_assertion(request)
agent_token = obo_tokens.get_agent_token(user_assertion, OBSERVABILITY_SCOPE)
token_store.set(agent_identity_client_id, tenant_id, agent_token)
```

#### Node.js

The starting point already calls `acquireUserAssertion(req)` in the `/api/chat` handler, purely to reject anonymous callers with a 401. It throws away the token it gets back, which was fine when nothing needed it. Now something does, so keep it:

```typescript
const userAssertion = await authService.acquireUserAssertion(req);
const agentToken = await oboTokens.getAgentToken(userAssertion, OBSERVABILITY_SCOPE);
tokenStore.set(agentIdentityClientId, tenantId, agentToken);
```

The `tokenStore` here is the same module `src/observability.ts` imports, and it needs to stay that way. If you build the store inside `main.ts` and pass it in, you're back to the import-ordering problem from Step 3-3, because `observability.ts` has to be able to import it without dragging `main.ts` along behind it. A tiny standalone `src/token-store.ts` exporting a single shared instance is the least fragile arrangement.

> **Don't try to acquire the token inside the resolver itself.** It's a tempting simplification, and it cannot work on any of the three stacks: by the time the resolver runs there is no user left to act on behalf of.

### Step 3-6. Open a baggage scope around every turn

Baggage is OpenTelemetry's mechanism for carrying contextual values alongside the current execution context, and Agent 365 uses it to carry the identity dimensions it partitions telemetry by: which tenant, which agent, which user, which conversation.

**Important!** Spans emitted outside an active baggage scope are dropped, and the exporter tells you so with the message `Partitioned into 0 identity groups`. Everything looks like it's working, but nothing really arrives.

The values are the same in all three stacks, and so is the rule that the scope has to be open for the whole turn rather than merely opened before it. What differs is how each language expresses "for the whole turn".

`.AgentBlueprintId()` is worth calling out specifically, whichever stack you're on: it populates `TargetAgentBlueprintId` in reporting, which is how the activity gets tied back to the blueprint you registered in Phase 2.

#### .NET

```csharp
using var scope = new BaggageBuilder()
    .TenantId(tenantId)
    .AgentId(agentIdentityClientId)
    .AgentName(agentName)
    .AgentBlueprintId(blueprintClientId)
    .ConversationId(conversationId)
    .SessionId(conversationId)
    .UserId(userId)
    .UserName(userName)
    .UserEmail(userEmail)
    .ChannelName("web")   // this isn't Teams, so use a logical channel name
    .Build();
```

Note the `using`: the scope stays open until the end of the enclosing block, so make sure the agent invocation happens inside that block.

#### Python

```python
with (
    BaggageBuilder()
    .tenant_id(tenant_id)
    .agent_id(agent_identity_client_id)
    .agent_name(agent_name)
    .agent_blueprint_id(blueprint_client_id)
    .conversation_id(conversation_id)
    .session_id(conversation_id)
    .user_id(user_id)
    .user_name(user_name)
    .user_email(user_email)
    .channel_name("web")
    .build()
):
    reply = await agent.ask(session_id, message)
```

#### Node.js

Node's builder is the same fluent shape, but `.build()` gives you a scope you `run()` a callback inside rather than something that closes at the end of a block:

```typescript
import { BaggageBuilder } from "@microsoft/opentelemetry";

const scope = new BaggageBuilder()
    .tenantId(tenantId)
    .agentId(agentIdentityClientId)
    .agentName(agentName)
    .agentBlueprintId(blueprintClientId)
    .conversationId(sessionId)
    .sessionId(sessionId)
    .userId(userId)
    .userName(userName)
    .userEmail(userEmail)
    .channelName("web")
    .build();

const reply = await scope.run(() => agent.ask(sessionId, message));
```

The callback shape is doing the same job as `using` on .NET and `with` on Python: it defines the region of code the baggage is active for. The awkward part is that it's easy to write `scope.run(() => { ... })` and forget to return the promise from inside, at which point `run()` returns before the agent has finished and the baggage is gone by the time the spans are created. Return the promise, and `await` the result of `run()`, exactly as above.

### Step 3-7. Resolve the caller correctly

The Microsoft 365 admin center needs the caller's **directory object id** to show you who did what. If you give it anything else, the export still returns `HTTP 200` and the row still arrives. It just never resolves to a person, and you get activity attributed to nobody.

The object id is the `oid` claim, the one you looked at in jwt.ms back in Step 2-3c. The trap in every stack is that there are several other claims sitting nearby that look like plausible identifiers and are not: `sub` is a pairwise identifier that differs per application, and the `nameidentifier` claim that some frameworks map `oid` onto can turn out to be a base64-looking hash instead.

#### .NET

Use the helper from `Microsoft.Identity.Web` rather than reaching for a raw claim, because it knows which of the several candidate claims is the real object id:

```csharp
using Microsoft.Identity.Web;

var userId    = user?.GetObjectId()    ?? "unknown";
var userName  = user?.GetDisplayName() ?? "unknown";
```

#### Python

Read `oid` from the validated token claims, and `name` for the display name.

#### Node.js

The claims are already on the session object that `AuthService` keeps, so this is a read rather than a parse. The sample's `profile()` helper deliberately exposes only `name` and `username`, since that's all the chat page needs, so add `oid` alongside them:

```typescript
const claims = session.claims ?? {};
const userId    = asString(claims["oid"]) ?? "unknown";
const userName  = asString(claims["name"]) ?? "unknown";
const userEmail = asString(claims["preferred_username"]) ?? "";
```

Take the `oid` from the ID token claims stored on the session, not from a decode of the access token you send to the observability API. They agree in this scenario, but relying on that means the day you change which resource you request, the caller identity changes with it for no visible reason.

### Step 3-8. Wrap the turn in the semantic scopes

We're nearly there, but there's one more constraint to satisfy: Agent 365 doesn't accept arbitrary spans. It only ingests spans whose `gen_ai.operation.name` is one of `invoke_agent`, `chat`, `execute_tool` or `output_messages`. Anything else is dropped, span by span.

The one that matters most is `invoke_agent`. Open an `InvokeAgentScope` at the start of every turn: it becomes the root span for that turn, and it is the only span the Microsoft 365 admin center ingests. Defender is happy to take everything; the admin center is not.

> **The session, conversation and channel have to be on the request object, not only in baggage.** This trips people up because baggage *does* land on the span tags, so it looks like the information is there. But the exported `invoke_agent` payload is built from the request object you pass to the scope, so if you leave them out you export a span that is accepted and yet shows no run context at all.

#### .NET

```csharp
var request = new Request(
    content: userText,
    sessionId: conversationId,
    conversationId: conversationId,
    channel: new Channel("web"));

using var invokeScope = InvokeAgentScope.Start(
    request,
    new InvokeAgentScopeDetails(endpoint),
    agentDetails,
    callerDetails);
```

#### Python

```python
with InvokeAgentScope.start(
    request=Request(
        content=user_text,
        session_id=conversation_id,
        conversation_id=conversation_id,
        channel=Channel(name="web"),
    ),
    invoke_scope_details=InvokeAgentScopeDetails(endpoint=endpoint),
    agent_details=agent_details,
    caller_details=caller_details,
):
    reply = await agent.ask(session_id, message)
```

#### Node.js

Two naming details to know before you write this. First, the request contract is exported as **`A365Request`** rather than `Request`, because `Request` is already a global in the DOM and Node's own type definitions, and importing a second one produces confusing errors. Second, the scope makes itself the active span through `withActiveSpanAsync`, which takes a callback in the same way the baggage scope does:

```typescript
import { InvokeAgentScope, type A365Request } from "@microsoft/opentelemetry";

const request: A365Request = {
    content: message,
    sessionId,
    conversationId: sessionId,
    channel: { name: "web" },
};

const invokeScope = InvokeAgentScope.start(
    request,
    { endpoint: { host: settings.host, port: settings.port, protocol: "http" } },
    agentDetails,
    callerDetails,
);

try {
    const reply = await invokeScope.withActiveSpanAsync(() => agent.ask(sessionId, message));
    invokeScope.recordOutputMessages(reply);
    return reply;
} catch (error) {
    invokeScope.recordError(error as Error);
    throw error;
} finally {
    invokeScope.dispose();
}
```

The `try`/`catch`/`finally` is doing what `using` does on .NET. The `finally` is the important half: a scope that's never disposed is a span that's never ended, and a span that's never ended is never exported, so a turn that throws would vanish entirely rather than showing up as a failure.

#### What about the other span types?

On supported stacks, `chat` spans come free from auto-instrumentation, and that covers .NET (given the `UseOpenTelemetry()` call from Step 3-3) and Node.js (where LangChain instrumentation is on by default). **LangChain on Python is the exception**. The skill only soft-warns about this, so watch for it: you may need to wrap your LLM calls in an `InferenceScope` by hand.

Tool calls follow the same pattern with `ExecuteToolScope`. On Node.js the LangChain instrumentation covers the Microsoft Learn MCP calls the sample makes, so you shouldn't need to add them yourself; check Step 3-9's output before assuming either way.

### Step 3-9. Verify that the telemetry is actually leaving

Before we go looking in Defender, let's confirm from the app's own logs that spans are being exported. Turn on the exporter's logging:

```powershell
$env:OTEL_LOG_LEVEL="INFO"
$env:A365_OBSERVABILITY_LOG_LEVEL="debug"
```

Both variables matter, and this catches people out on Node in particular: `OTEL_LOG_LEVEL` controls the OpenTelemetry SDK's own diagnostics, while `A365_OBSERVABILITY_LOG_LEVEL` is what makes the Agent 365 components talk. Set only the first and you'll see the SDK start up and then apparent silence from the part you actually wanted to watch.

Ask the agent a question and read the output. There are four things to look for, and all four have to be right:

- `Partitioned into 1 identity groups`, **not 0**. Zero means the baggage scope isn't active around the turn (Step 3-6).
- An `invoke_agent` span, and it must be a **root** span.
- `HTTP 200` on the export itself.
- The caller id in the payload is a **GUID**, not a long base64-looking hash. If it's the latter, you're reading the wrong claim, so go back to Step 3-7.

✅ **Checkpoint.** This is another good place to stop. The agent is registered, and it's observable.

## Phase 5: Verify it end to end

Everything so far proves the agent *emits* telemetry. This phase proves it *arrives*, which is not the same thing at all. As we've seen, there are several ways for a span to be accepted and then quietly discarded.

Nothing in this phase depends on your stack. You're looking at portals now, and by this point the three implementations are indistinguishable from the outside, which is rather the point of the whole exercise.

### Step 5-1. Produce some activity

Ask the agent three or four questions. There's a set of them in [4.Sample-prompts.md](4.Sample-prompts.md) if you want a starting point. Make sure at least one of them causes a tool call, so we have more than just inference spans to look at.

### Step 5-2. Check Microsoft Defender

Go to [Advanced hunting](https://security.microsoft.com) in the Defender portal and query the `CloudAppEvents` table. Defender accepts every operation type, so this is where you should see the fullest picture: `InvokeAgent`, `InferenceCall` and `ExecuteToolByMCPServer` rows. Here's a query to start from:

```sql
CloudAppEvents
| where ActionType in ("InvokeAgent", "InferenceCall", "ExecuteToolBySDK", "ExecuteToolByGateway", "ExecuteToolByMCPServer")
| where RawEventData.TargetAgentName == "your-agent-name" or RawEventData.AgentName == "your-agent-name"
| order by Timestamp desc
```

Defender has to index the events, so give it around five minutes before concluding something is wrong.

### Step 5-3. Check the Microsoft 365 admin center

Now go to https://admin.cloud.microsoft, find your agent in the inventory, and open its activity.

This surface behaves differently from Defender, and understanding how saves a lot of debugging: the admin center ingests `invoke_agent` rows only, and it reads the caller identity off that one span. Which means the combination of what you see in each portal tells you precisely where a problem is:

| What you see | Where the problem is |
| --- | --- |
| Nothing anywhere | Export, token, or baggage scope. Go back to Step 3-9 |
| Defender ✅, admin center ❌ | Your `invoke_agent` span. Nine times out of ten it's the caller id. Step 3-7 |
| Both ✅, but no user shown | The caller resolved to something that isn't a directory object id |
| Both ✅, but no run context | Session, conversation or channel missing from the request object. Step 3-8 |

### Step 5-4. Optional: let a skill check the code for you

There's a skill that reviews the instrumentation and reports what's wrong without changing anything:

```text
Validate the Agent 365 observability code in this project.
```

`a365-code-validator` checks that the exporter is actually activated, that the runtime agent identity is bound correctly, that the required spans are present, and that the token has the right shape for the endpoint you're posting to. It understands all three stacks, and it's read-only by default, so it's safe to run at any point.

## Troubleshooting

For a diagnostic sequence from the running process through tenant reporting, use the [cross-scenario troubleshooting guide](../../03-references/Troubleshooting.md). The checks below point back to this runbook's implementation steps.

If something isn't working, this table covers the failures you're most likely to hit, and where each one comes from. The first group applies whatever you're writing in; the second group is stack-specific.

| Symptom | Likely cause |
| --- | --- |
| `Partitioned into 0 identity groups` | No active baggage scope around the turn. Step 3-6 |
| `HTTP 200`, but nothing lands anywhere | No user in the tenant holds an Agent 365 licence |
| `AADSTS500011` resource principal not found | Agent 365 isn't provisioned in this tenant |
| Consent errors on the observability scope | The admin consent handoff from Step 2-1 was never run |
| `AADSTS50011` redirect URI mismatch | The registered redirect URI doesn't match the address the browser is on, scheme included. Step 1-1a |
| Hop 2 rejects the assertion | The sign-in asked for the wrong scope, so the user token isn't addressed to the blueprint. Step 2-3c |
| The app starts in anonymous mode with a filled-in `.env` | The settings are read once at startup, so restart the process. Step 2-3b |
| Sign-in loops back to the sign-in page | The browser is on `127.0.0.1` and the app set its cookie on `localhost`, or the other way round. Step 1-1a |

And the ones that only affect one stack:

| Symptom | Stack | Likely cause |
| --- | --- | --- |
| `MsalUiRequiredException` on the first turn after a restart | .NET | The auth cookie is encrypted at rest and survives the restart; the in-memory token cache doesn't. Sign out and back in, or handle it as Step 1-4 does |
| No `chat` spans | Python | The distro was initialised after LangChain was imported. Step 3-3 |
| No `chat` spans | Node.js | `./observability.js` isn't the first import in `main.ts`, so LangChain was loaded before the distro could patch it. Step 3-3 |
| Every span appears twice | Node.js | The LangChain instrumentation was registered by hand as well as by the distro, which enables it by default. Step 3-3 |
| Everyone is signed out after a restart | Node.js | Sessions live in an in-process `Map`, which is fine for a sample and the first thing to replace for real. Step 1-4 |
| The last turn's spans never arrive | Node.js | The process exited before the exporter flushed. Add the `shutdownMicrosoftOpenTelemetry()` handler from Step 3-3 |
| Breakpoints land in the wrong file | Node.js | You're debugging compiled output from `npm run build`. Run through `npm run dev`, which executes the TypeScript directly. Step 2-3c |

## Wrapping up

We started with an ordinary web agent that answered questions for anyone who opened the page and knew nothing about the tenant it ran in. We gave it an identity, registered a separate sign-in app because a blueprint can't sign users in, switched on the sign-in that turns an anonymous chat page into one that knows who is asking and holds a token addressed to the blueprint, built the two-hop token chain that lets the agent act on behalf of the person driving it, instrumented every turn so the activity shows up in Defender and the admin center attributed to the right user, and finally gave it access to Microsoft 365 data under that same user's permissions.

Whichever of the three stacks you followed, you ended up in the same place. The .NET version leans on `Microsoft.Identity.Web` and gets a lot of the sign-in handed to it; the Python version does more of the MSAL work by hand, and the Node version does more still because MSAL's Node bindings leave PKCE and state to the caller. The registration, the token chain, the baggage and the spans are the same in all three, because those are properties of Agent 365 rather than of your language.

What's really important as a takeaway is that none of the work we have done changed what the agent *does*. It answers exactly the same questions it answered in Phase 0. What changed is that the organization can now see it, govern it, and hold it accountable, which is the difference between a demo and something you can actually put in front of users.
