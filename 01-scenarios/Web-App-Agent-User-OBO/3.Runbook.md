# Step-by-Step Guide — Web App Agent with User OBO

> **Scenario**: Onboarding a user-driven web agent into Microsoft Agent 365
> **Platform**: Microsoft Agent 365 · Microsoft Entra ID · OpenTelemetry
> **Stacks**: .NET Agent Framework (Blazor Server) · Python + LangChain (FastAPI)
> **Target Readers**: Agent developers, Entra administrators
> **Last Updated**: February 2026

## Introduction

We have an agent. It works: a user opens a web page, asks a question, the agent reasons over it, calls a few tools, and answers. From the outside it looks finished.

From the point of view of the organization it runs in, however, that agent doesn't exist. Nobody can see it in the tenant inventory. Nobody knows what it did yesterday, on whose behalf, or which data it touched. If a security analyst asks "which agents accessed customer mailboxes last week?", our agent won't be part of the answer, not because it behaved well, but because it never told anyone anything.

**Microsoft Agent 365** is what closes that gap. It gives the agent an identity in the tenant, a way to report its activity to Microsoft Defender, Microsoft Purview and the Microsoft 365 admin center, and a governed path to Microsoft 365 data. In this guide, we're going to take exactly that kind of agent — a plain web app with no Agent 365 code in it whatsoever — and onboard it step by step.

The onboarding path we're following here is the **User On-Behalf-Of (OBO)** one. It's the right choice when a human drives the agent: the user signs in, and everything the agent does is attributed back to that person. There are other paths (a Teams-hosted agent, or an agent acting under its own identity), and if you're not sure which one applies to you, [Choosing Your Onboarding Path](../../02-patterns/Choosing-Your-Onboarding-Path.md) walks through the decision.

Two more things before we start.

First, **we're going to do most of the work by asking an AI coding assistant to do it for us**. Microsoft ships a set of skills, the [Agent 365 Skills](https://github.com/microsoft/agent365-skills), that know how to perform each onboarding step. We describe what we want in natural language, and the skill edits the project. But — and this matters — we're also going to look at what each skill actually did, and at the CLI commands and code underneath it. If you'd rather not use a coding assistant at all, you can follow this guide by hand: every step includes the manual equivalent.

Second, **the work is split into phases, and every phase is a valid place to stop**. You get real value from Phase 1 alone, Phase 2 gives you more, and nothing later breaks if you never get to it.

| Phase | What you get at the end of it | Rough time |
| --- | --- | --- |
| 0 — Get it running | A working agent, and a machine that can run the tooling | 15–45 min |
| 1 — Registration and sign-in | The agent exists in your tenant as a governed identity, and users sign in to it | 45 min |
| 2 — Observability | Activity flowing into Defender, Purview and the admin center | 60–90 min |
| 3 — Work IQ | The agent can reach Microsoft 365 data as the signed-in user | 30 min |
| 4 — Verification | Proof that it all actually works end to end | 30 min |

Let's get started!

## How to read the steps in this guide

From Phase 1 onwards, each step is built the same way, so you always know what you're looking at:

1. **What you type** — the prompt you give your coding assistant.
2. **What the skill does** — the changes it's about to make, so nothing comes as a surprise.
3. **Behind the scenes** — the CLI command or the code it all comes down to.
4. **How to verify** — how to know it worked, before you move on to the next step.

If you're doing this manually, read parts 3 and 4 and ignore the rest. The guide works that way too.

Two steps break that pattern, and deliberately so: creating the sign-in registration (Step 1-3) and writing the sign-in code (Step 1-4) are things no skill does for you, so they're written as portal clicks and source edits from start to finish.

## Prerequisites

Let's get the boring part out of the way first. There are three kinds of prerequisites here: tools on your machine, licences in your tenant, and permissions on your account. Missing any of them will stop you somewhere in the middle, so it's worth checking all three now.

### The tools you need on your machine

| Requirement | Minimum | Check it with | What needs it |
| --- | --- | --- | --- |
| .NET SDK | 8.0 | `dotnet --version` | The A365 CLI itself, and .NET agents |
| Agent 365 CLI | latest | `a365 --version` | Every phase |
| PowerShell | 7.0 | `pwsh --version` | The consent scripts |
| Azure CLI | latest | `az version` | Signing in to the tenant |
| Az PowerShell module | latest | `Get-Module -ListAvailable Az.Accounts` | Granting permissions |
| Git | any | `git --version` | — |
| Python | 3.12 | `python --version` | Python agents only |
| uv | latest | `uv --version` | Python agents only |

> **You need the .NET 8 SDK even if your agent is written in Python.** This surprises people. The reason is simply that the Agent 365 CLI is distributed as a .NET global tool, so .NET has to be there to run it. It has nothing to do with the language your agent is written in.

The CLI is the one tool you almost certainly don't have yet, so let's install it:

```bash
dotnet tool install --global Microsoft.Agents365.CLI
a365 --version
```

If the second command prints a version number, we're good.

### The licences your tenant needs

| Requirement | What to know |
| --- | --- |
| Microsoft 365 tenant | With Agent 365 enabled |
| Agent 365 licence | **At least one user in the tenant must hold one** |
| Azure subscription | For the Azure OpenAI resource the agent reasons with |

That middle row deserves a warning, because it's the single most confusing failure in this whole guide. If nobody in the tenant holds an Agent 365 licence, your telemetry is accepted with `HTTP 200` and then silently thrown away. Your logs will say the export succeeded, Defender will show nothing, and there's no error message anywhere that tells you why. So check the licence now, not in Phase 4.

### The permissions you need on your account

| Permission | Who needs it | What it's for |
| --- | --- | --- |
| Application Developer (or higher) | You | Creating app registrations |
| Global Administrator | You *or* a colleague | Granting admin consent to the blueprint |
| Azure OpenAI access | You | The model the agent uses. For the Entra credential path you need the **Cognitive Services OpenAI User** role on the resource; for key auth, access to the resource keys |

> **You don't have to be a Global Administrator yourself.** The CLI does everything it's allowed to do, and then prints a PowerShell snippet for an admin to run for the rest. Just be aware that this handoff exists, and line up the person who will run it before you get to Phase 1 — otherwise you'll be blocked at the start of Phase 2 with a consent error.

### The agent we're onboarding

This scenario ships with two starting points, one per stack. Both are complete, working agents with no Agent 365 code in them at all:

| Stack | Where it lives |
| --- | --- |
| .NET | [`0.Resources/Starting-point/dotnet/`](0.Resources/Starting-point/dotnet/) |
| Python | [`0.Resources/Starting-point/python/`](0.Resources/Starting-point/python/) |

You can absolutely bring your own agent instead. The guide assumes two things about it: it runs as a web app with one HTTP request per turn, and there's a single place in the code where a turn begins and ends, because that's where the instrumentation goes.

What it does *not* assume is that the app already signs anybody in. Neither starting point does — open either of them today and you get an anonymous chat page. That's a deliberate choice, because on the OBO path the sign-in carries real weight: the token it produces is the first link in the token chain, and it has to be addressed to an audience that doesn't exist until we register the agent. So we register first, in Step 1-3, and then write the sign-in code in Step 1-4 once there's something to point it at. If your own agent already signs users in, Step 1-4 will mostly be a matter of changing which scope you ask for.

## Phase 0: Get the agent running first

Before we add anything, let's make sure the agent works as it is.

Phase 2 adds a fair amount of machinery — token exchanges, a telemetry exporter, span scopes — and if the agent is broken to begin with, you'll spend hours trying to work out which layer is at fault. Start from something that answers questions correctly, and every failure afterwards is one you introduced.

### Step 0-1. Configure the Azure OpenAI connection

The agent reasons using a model deployed in Azure OpenAI, so the very first thing it needs to know is *which* resource to call and *which* deployment on it to use.


If you're on **.NET**, open `appsettings.json`:

```json
{
  "AzureOpenAI": {
    "Endpoint": "https://<your-resource>.openai.azure.com/",
    "Deployment": "gpt-4.1",
    "TenantId": "<tenant that owns the Azure OpenAI resource>"
  },
  "LearnMcp": { "Endpoint": "https://learn.microsoft.com/api/mcp" }
}
```

If you're on **Python**, copy `.env.example` to `.env` (the example file is committed; `.env` is gitignored) and fill it in:

```bash
AZURE_OPENAI_ENDPOINT=https://<your-resource>.openai.azure.com/
AZURE_OPENAI_DEPLOYMENT=gpt-4.1
AZURE_OPENAI_API_VERSION=2024-10-21
AZURE_OPENAI_TENANT_ID=<tenant that owns the Azure OpenAI resource>
```

You'll find the endpoint and the deployment name in the Azure portal, on the Azure OpenAI resource, under **Resource Management → Keys and Endpoint** and **Model deployments** respectively.

> **The tenant id is not optional if you work across more than one tenant.** It's easy to skim past, so here's what happens if you leave it out: the credential hands back a token from whichever tenant you last signed in to, which may not be the one that owns the Azure OpenAI resource, and the service answers with `HTTP 400 – Tenant provided in token does not match resource token`. Pinning the tenant explicitly avoids an error that otherwise looks like a code problem.

### Step 0-2. Decide how the agent authenticates to Azure OpenAI

Both starting points support two ways of authenticating, and they choose between them automatically at startup with a very simple rule: *if an API key is configured, use key auth; if not, use Entra credentials.* There's no flag to flip — the presence or absence of the key is the switch.

Here's how the two compare:

|  | **Path A — Entra credentials** *(the default, and the recommended one)* | **Path B — API key** |
| --- | --- | --- |
| What it actually uses | `DefaultAzureCredential` on .NET, `AzureCliCredential` on Python, so your `az login` session locally, and a managed identity once hosted on Azure | A resource key, sent as a bearer secret |
| What you have to configure | Nothing beyond Step 0-1 — you just need to be signed in | The key itself, kept in a secret store |
| What you need access to | The **Cognitive Services OpenAI User** role on the resource | The resource keys |
| Why you'd pick it | No long-lived secret to leak or rotate, the call carries a real identity, and it's the *only* option in tenants where key auth is disabled by policy | Environments that still depend on keys. The key never expires and carries no identity of its own |

#### Path A — Entra credentials

There's nothing to add to the configuration. Just sign in to the tenant that owns the Azure OpenAI resource:

```bash
az login --tenant <tenant of the Azure OpenAI resource>
```

Then double-check that no key is configured anywhere, because if one is, the code silently takes Path B and you'll think you're testing something you aren't. On .NET that means `AzureOpenAI:ApiKey` is unset — including in user-secrets, which are easy to forget about — and `AzureOpenAI__ApiKey` isn't in your environment. On Python it means `AZURE_OPENAI_API_KEY` is blank in `.env`.

When you later deploy to Azure, this path keeps working with no code change: .NET picks up the managed identity assigned to the App Service automatically through `DefaultAzureCredential`, and Python needs one extra setting, `AZURE_OPENAI_USE_MANAGED_IDENTITY=true`.

#### Path B — API key

If you do need key auth, the important thing is to keep the key out of files that get committed — and both `appsettings.json` and `.env.example` are committed:

```bash
# .NET — user secrets are stored outside the project folder
dotnet user-secrets set "AzureOpenAI:ApiKey" "<your-key>"
# or set the AzureOpenAI__ApiKey environment variable instead

# Python — in .env, which is gitignored
AZURE_OPENAI_API_KEY=<your-key>
```

Now we can start the agent. On **.NET**:

```bash
cd 0.Resources/Starting-point/dotnet
dotnet run
```

On **Python**:

```bash
cd 0.Resources/Starting-point/python

```

### Step 0-4. Verify that it works

Open the app in a browser and ask it something it should be able to answer, for example:

```text
What is Microsoft Entra Conditional Access?
```

You should get a proper answer with links to Microsoft Learn at the end of it, because this agent grounds its answers in the Microsoft Learn MCP server rather than answering from the model's own memory.

✅ **Checkpoint.** The agent answers questions and cites its sources. There is still no trace of Agent 365 anywhere — that starts now.

## Phase 1: Register the agent and sign users in

In this phase the agent stops being just code on your laptop and becomes an object in your tenant — and it learns who is talking to it.

Two objects, actually, and it's worth understanding the difference now because everything in Phase 2 depends on it:

- The **blueprint** is the parent app registration. It holds the permissions, and it owns the agent. Think of it as the definition of the agent.
- The **agent identity** is a child principal of that blueprint. It's the thing that actually *acts* — the principal your telemetry will be attributed to.

### Step 1-1. Run the setup skill

**What you type**

```text
Set up Agent 365 for this agent. It's a web app where users sign in —
not a Teams agent and not an AI Teammate. Use the OBO auth mode.
```

**What the skill does**

The `a365-setup` skill runs first. It checks every prerequisite we listed earlier, offers to install anything that's missing, and confirms which Azure identity you're signed in as. Then it asks you two questions, and these two answers determine everything that follows:

| Question | Your answer for this scenario | Why |
| --- | --- | --- |
| Agent kind? | **Agent (Non AI Teammate)** | A human drives this agent; it doesn't have its own mailbox or presence in Teams |
| Auth mode? | **`obo`** | Everything the agent does is attributed to the signed-in user |

Once you've answered, `a365-setup` hands off to `make-a365-agent`, which performs the actual registration.

> **Take your time over the auth-mode question.** It's the single decision that determines your entire token chain. Choosing wrongly here doesn't fail immediately — it fails much later, in Phase 2, and correcting it means rewriting the token code. If in doubt, `obo` is the correct answer for a web app where a human signs in.

**Behind the scenes**

Whatever the skill says, this is what it comes down to:

```bash
a365 setup all --agent-name "my-agent" --dry-run    # preview what will happen
a365 setup all --agent-name "my-agent"              # actually do it
```

Always run the dry run first and read the output. And don't worry about running the real command more than once: `a365 setup all` is idempotent, so it's safe to re-run after fixing a problem.

Here's what it creates for you:

- an **agent blueprint** app registration, together with a client secret
- an **agent identity**, as a child of that blueprint
- the API permissions the agent needs, including `Agent365.Observability.OtelWrite`, which is the one that lets it write telemetry
- a file called `a365.generated.config.json`, holding all the generated identifiers

That last file is the one you'll keep coming back to, so keep it open.

**How to verify**

Have a look at what was generated:

```bash
cat a365.generated.config.json
```

You should see an `agentBlueprintId` and an agent identity id in there. Then go to the [Entra admin center](https://entra.microsoft.com) → **App registrations** and confirm the blueprint is listed.

> ⚠️ **If you're not a Global Administrator**, look carefully at the summary the CLI printed. It will contain a consent snippet for an admin to run. Until somebody runs it, the permissions exist but are not granted, and Phase 2 will fail with a consent error that looks like a bug in your code. This is the handoff we mentioned in the prerequisites.

### Step 1-2. Store the blueprint secret somewhere safe

`a365 setup all` generated a client secret for the blueprint. That secret is what proves, in Phase 2, that your code is allowed to act as this agent — so it must never end up in source control.

On **.NET**, put it in user secrets, which live outside the project folder entirely:

```bash
dotnet user-secrets set "Agent365:BlueprintClientSecret" "<secret>"
```

On **Python**, put it in `.env`, and take a second to confirm that `.env` really is listed in `.gitignore`.

If you lose it, you don't have to re-register anything. You can read it back — on the same machine, signed in as the same user — with:

```bash
a365 setup blueprint --agent-name "my-agent" --show-secret
```

### Step 1-3. Create the app registration that signs users in

This step catches almost everybody out, so let's start with why it's needed at all.

The obvious assumption is that the blueprint we just created can sign users in. It can't. A blueprint is an **agentic application**, and Microsoft Entra deliberately bars agentic applications from interactive `/authorize` flows. It cannot present a sign-in page. So we need a second, completely ordinary app registration whose only job is to authenticate the human and ask for the blueprint's scope.

That gives us three identities in this scenario, and keeping them straight in your head makes everything else easier:

| Identity | Who creates it | What it does |
| --- | --- | --- |
| **Sign-in client** | You, in this step | Signs the user in, and requests the blueprint's scope |
| **Blueprint** | `a365 setup all`, in Step 1-1 | Owns the permissions, and authenticates hop 1 of the token chain |
| **Agent identity** | `a365 setup all`, in Step 1-1 | The principal the agent acts as, and that spans are exported as |

Keep `a365.generated.config.json` open, because you'll need the **blueprint's app id** a couple of times below.

#### 1-3a. Create the registration

1. Go to the [Entra admin center](https://entra.microsoft.com) and navigate to **Identity → Applications → App registrations**.
2. Click **New registration**.
3. Give it a name that makes its role obvious, something like **my-agent-web-signin**. You'll be looking at a list with the blueprint in it, so a vague name will cost you time later.
4. For **Supported account types**, choose **Accounts in this organizational directory only (Single tenant)**.
5. Under **Redirect URI**, select the **Web** platform and enter the callback address your app will actually listen on. On .NET that's `http://localhost:5140/signin-oidc`, which is the URL the default `http` profile in `Properties/launchSettings.json` binds to; on Python it's `http://localhost:8000/signin-oidc`.
6. Click **Register**.

You'll land on the **Overview** blade. Copy the **Application (client) ID** and the **Directory (tenant) ID** from there and keep them somewhere handy; we'll need both in a moment.

> **The redirect URI has to match what the browser sees, character for character, scheme included.** It's easy to register the `https` address and then run the app over plain `http`, and Entra answers that with `AADSTS50011`, which reads like a configuration mistake in the app rather than a mismatched string. If you'd rather run the .NET app over TLS, launch it with `dotnet run --launch-profile https` and register `https://localhost:7199/signin-oidc` instead. An app registration can hold several redirect URIs, so registering both now and picking later is perfectly reasonable.

#### 1-3b. Create a client secret
1. In the same registration, go to **Certificates & secrets**.
2. On the **Client secrets** tab, click **New client secret**.
3. Give it a description and pick an expiry.
4. Click **Add**, then **copy the Value immediately**.

The value is shown once, and once you navigate away it's gone forever and you'll have to create another secret.

Store it exactly the way we stored the blueprint secret in Step 1-2: `dotnet user-secrets` on .NET, the gitignored `.env` on Python. Never in `appsettings.json`.

> **Don't mix up the two secrets.** You now have a blueprint secret and a sign-in client secret, and they do completely different jobs. The blueprint secret authenticates hop 1 of the token chain; the sign-in client secret authenticates the web sign-in. Swapping them produces authentication errors that are genuinely hard to read.

#### 1-3c. Give the sign-in app permission to call the blueprint

This is the step that makes the entire token chain possible, so it's worth doing slowly.

1. Still in the sign-in registration, go to **API permissions**.
2. Click **Add a permission**.
3. Choose the **APIs my organization uses** tab.
4. Paste the **blueprint's app id** into the search box and select it from the results.
5. Choose **Delegated permissions**.
6. Tick **`access_agent_as_user`**.
7. Click **Add permissions**.

> **If the blueprint doesn't come up in the search**, search by its app id rather than its display name — the CLI appends `" Blueprint"` to the name you chose, so what you type may not match. And if you find the API but it exposes no scopes at all, open the **blueprint's** registration, go to **Expose an API → Add a scope**, create a scope named exactly `access_agent_as_user`, set **Who can consent?** to **Admins and users**, leave the state **Enabled**, and then come back here and repeat the steps above.

While you're on this blade, make sure the ordinary sign-in permissions are there too: **Microsoft Graph → Delegated permissions → `openid`, `profile`, `offline_access`, `User.Read`**. The OIDC sign-in itself needs them.

Finally, click **Grant admin consent for \<your tenant\>**. If that button is greyed out for you, this is the second point where you need an administrator: the permissions are configured, but they can't be used until somebody with the right role consents to them.

#### 1-3d. If you'd rather use the CLI

Everything above can be done from the command line instead:

```bash
# Create the registration
az ad app create --display-name "my-agent-web-signin" \
  --sign-in-audience AzureADMyOrg \
  --web-redirect-uris "http://localhost:5140/signin-oidc"

# Add a secret
az ad app credential reset --id <sign-in client app id> --append

# Add the delegated permission. The scope id is on the blueprint's "Expose an API" blade
az ad app permission add --id <sign-in client app id> \
  --api <blueprint-app-id> --api-permissions <scope-id>=Scope

# Grant admin consent
az ad app permission admin-consent --id <sign-in client app id>
```

Swap the redirect URI for `http://localhost:8000/signin-oidc` if you're on the Python starting point, and note that `az ad app permission add` only records the permission — the consent grant on the last line is what makes it usable.

### Step 1-4. Teach the app to sign users in

We now have a registration that *can* sign users in, and an app that doesn't know it exists. This step closes that gap, and it deserves more care than a normal "add authentication to your web app" step, so let's be precise about what we're adding and why.

There are two jobs to do here, and only the first one is the familiar web-app sign-in:

1. **Authenticate the user**, so the app knows who is asking and can put a name and an object id on the telemetry later.
2. **Obtain an access token whose audience is the blueprint**, by requesting the scope `api://<blueprint-id>/access_agent_as_user` during sign-in. This is the *user assertion*, and Phase 2 feeds it into hop 2 of the token chain.

The second job is the one that's easy to get wrong, because an app can sign users in perfectly well and still never ask for that scope — you'd have a working login and a token that hop 2 rejects. The scope determines who the token is *addressed to*, and hop 2 will only accept an assertion addressed to the blueprint. Not `User.Read`, and not the blueprint's `.default`.

> **If you're running the skills rather than typing this yourself**, be aware that `instrument-observability` assumes the sign-in already exists — it writes the token chain and the instrumentation, not the login. Do this step by hand before you start Phase 2, or you'll be handing the token service an assertion that nothing ever produces.

#### 1-4a. Configuration

Let's start with the settings, because both stacks need the same four facts: the tenant, the sign-in client's id and secret, and the blueprint id that the scope is built from.

On **.NET**, add an `AzureAd` section to `appsettings.json`, along with the blueprint id the scope is built from:

```json
{
  "AzureAd": {
    "Instance": "https://login.microsoftonline.com/",
    "TenantId": "<tenant id>",
    "ClientId": "<sign-in client app id>",
    "CallbackPath": "/signin-oidc",
    "SignedOutCallbackPath": "/signout-callback-oidc"
  },
  "Agent365Observability": {
    "TenantId": "<tenant id>",
    "AgentBlueprintId": "<blueprint app id>"
  }
}
```

The `Agent365Observability` section is the one `a365 setup all` writes to and Phase 2 reads from, so putting the blueprint id there now means Phase 2 finds it already populated instead of introducing a second copy under a name of our own.

The secret, as always, goes outside the file:

```bash
dotnet user-secrets set "AzureAd:ClientSecret" "<sign-in client secret>"
```

`CallbackPath` has to line up with the redirect URI you registered in Step 1-3a — `Microsoft.Identity.Web` builds the callback address from the app's own base URL plus this path, so if the two disagree you'll get the `AADSTS50011` we warned about above.

On **Python**, in `.env`:

```bash
A365_WEBCLIENT_CLIENT_ID=<sign-in client app id>
A365_WEBCLIENT_CLIENT_SECRET=<sign-in client secret>
A365_WEBCLIENT_REDIRECT_URI=http://localhost:8000/signin-oidc
AGENT365OBSERVABILITY__TENANTID=<tenant id>
AGENT365OBSERVABILITY__AGENTBLUEPRINTID=<blueprint app id>
HOST=localhost
```

That last line looks like a detail and behaves like a trap. The Python starting point binds to `127.0.0.1` by default, and while `127.0.0.1` and `localhost` reach the same process, the browser treats them as different origins and scopes the session cookie accordingly. Register the redirect URI on `localhost`, then browse the app on `127.0.0.1`, and the cookie set before the redirect simply isn't sent back on the callback — the sign-in fails in a way that looks like a lost session rather than a mismatched host. Binding to `localhost` keeps the two aligned.

The blueprint id and tenant id both come from `a365.generated.config.json`, and the key names above are the ones `a365 setup all` uses, so Phase 2 will find them already in place rather than adding a second copy under different names. What we still need is one derived value — the scope itself — and it's worth giving it a name rather than pasting the string around:

```csharp
// .NET, in Program.cs, near the top
var blueprintClientId = builder.Configuration["Agent365Observability:AgentBlueprintId"]
    ?? throw new InvalidOperationException("Agent365Observability:AgentBlueprintId is not configured.");
var agentUserScope = $"api://{blueprintClientId}/access_agent_as_user";
```

```python
# Python, on the Settings class in app/config.py
a365_blueprint_id: str = Field("", validation_alias="AGENT365OBSERVABILITY__AGENTBLUEPRINTID")
a365_tenant_id: str = Field("", validation_alias="AGENT365OBSERVABILITY__TENANTID")
webclient_client_id: str = Field("", validation_alias="A365_WEBCLIENT_CLIENT_ID")
webclient_client_secret: str = Field("", validation_alias="A365_WEBCLIENT_CLIENT_SECRET")
webclient_redirect_uri: str = Field(
    "http://localhost:8000/signin-oidc", validation_alias="A365_WEBCLIENT_REDIRECT_URI"
)

@property
def agent_user_scope(self) -> str:
    return f"api://{self.a365_blueprint_id}/access_agent_as_user"
```

Pydantic won't pick those environment variables up on its own, hence the explicit `validation_alias` on each one: the double underscore in `AGENT365OBSERVABILITY__AGENTBLUEPRINTID` is a .NET configuration convention rather than a Python one, and we keep it so that the same `.env` works for both the sign-in and everything Phase 2 adds.

The .NET snippet reads the blueprint id from a configuration section that Phase 2 will fill in properly. For now, add it to `appsettings.json` yourself with the `agentBlueprintId` value out of `a365.generated.config.json`, and Phase 2 will simply find it already there.

#### 1-4b. Wiring the sign-in on .NET

The Blazor starting point has no authentication at all, so we add it. Two packages first:

```bash
dotnet add package Microsoft.Identity.Web
dotnet add package Microsoft.Identity.Web.UI
```

`Microsoft.Identity.Web` does the OIDC handshake and, importantly for us, maintains the token cache that hands out the user assertion later. `Microsoft.Identity.Web.UI` contributes the ready-made `/MicrosoftIdentity/Account/SignIn` and `SignOut` endpoints, which saves us writing controllers of our own.

Then, in `Program.cs`, before `builder.Build()`:

```csharp
builder.Services.AddAuthentication(OpenIdConnectDefaults.AuthenticationScheme)
    .AddMicrosoftIdentityWebApp(builder.Configuration.GetSection("AzureAd"))
    .EnableTokenAcquisitionToCallDownstreamApi([agentUserScope])
    .AddInMemoryTokenCaches();

builder.Services.AddAuthorization();
builder.Services.AddCascadingAuthenticationState();
builder.Services.AddMicrosoftIdentityConsentHandler();
builder.Services.AddControllersWithViews().AddMicrosoftIdentityUI();
```

That middle line is the one that does the work we actually came for. `AddMicrosoftIdentityWebApp` on its own signs the user in and gives you an id token, which tells you who they are and nothing more. `EnableTokenAcquisitionToCallDownstreamApi` turns the sign-in into an authorization-code flow that also comes back with an *access* token for the scope you name — the blueprint's scope — and `AddInMemoryTokenCaches` is where that token is kept so we can ask for it again on every turn.

The middleware has to be told about it too, further down where the pipeline is built:

```csharp
app.UseAuthentication();
app.UseAuthorization();
app.UseAntiforgery();

app.MapStaticAssets();
app.MapControllers();
app.MapRazorComponents<App>()
    .AddInteractiveServerRenderMode();
```

`MapControllers()` is what exposes the sign-in endpoints from `Microsoft.Identity.Web.UI`; leave it out and the redirect to `/MicrosoftIdentity/Account/SignIn` lands on a 404.

Next, the app needs to actually *require* a user. In `Components/Routes.razor`, swap the plain `RouteView` for an `AuthorizeRouteView` and say what should happen when nobody is signed in:

```razor
<Router AppAssembly="typeof(Program).Assembly" NotFoundPage="typeof(Pages.NotFound)">
    <Found Context="routeData">
        <AuthorizeRouteView RouteData="routeData" DefaultLayout="typeof(Layout.MainLayout)">
            <NotAuthorized>
                <RedirectToLogin />
            </NotAuthorized>
        </AuthorizeRouteView>
        <FocusOnNavigate RouteData="routeData" Selector="h1" />
    </Found>
</Router>
```

`RedirectToLogin` doesn't exist yet, so create `Components/RedirectToLogin.razor`:

```razor
@inject NavigationManager Navigation

@code {
    protected override void OnInitialized()
    {
        var returnUrl = Uri.EscapeDataString(Navigation.ToBaseRelativePath(Navigation.Uri));
        Navigation.NavigateTo($"MicrosoftIdentity/Account/SignIn?redirectUri=/{returnUrl}", forceLoad: true);
    }
}
```

The `forceLoad: true` matters more than it looks: sign-in is a full browser round trip to Entra, and Blazor's client-side router would otherwise try to handle the navigation itself and go nowhere.

Finally, mark the chat page as protected by adding two lines at the top of `Components/Pages/Home.razor`:

```razor
@using Microsoft.AspNetCore.Authorization
@attribute [Authorize]
```

And this is how the page gets hold of the assertion when it needs it — inject `ITokenAcquisition`, and ask for the same scope we built in Step 1-4a:

```csharp
@inject IConfiguration Configuration
@inject ITokenAcquisition TokenAcquisition
@inject MicrosoftIdentityConsentAndConditionalAccessHandler ConsentHandler

private string AgentUserScope =>
    $"api://{Configuration["Agent365Observability:AgentBlueprintId"]}/access_agent_as_user";

private async Task<string?> AcquireUserAssertionAsync()
{
    try
    {
        return await TokenAcquisition.GetAccessTokenForUserAsync([AgentUserScope]);
    }
    catch (Exception ex)
    {
        // Consent or conditional access needs an interactive round trip.
        ConsentHandler.HandleException(ex);
        Logger.LogWarning(ex, "Could not acquire the user assertion for the agent blueprint.");
        return null;
    }
}
```

Reading the scope out of configuration here is a stopgap, and a deliberate one: Phase 2 introduces a small `A365Config` object that holds the tenant id, the blueprint id and the agent identity id together, and once it exists this becomes `A365.AgentUserScope`. There's no point building that object now, when the sign-in is the only thing that needs it.

Because the token came from the cache that `AddInMemoryTokenCaches` set up during sign-in, this call is normally silent — no redirect, no prompt. The `catch` is there for the cases where it isn't: a conditional access policy that demands a fresh interaction, or a consent prompt that was never answered. Handing those to the consent handler is what turns them into a redirect the user can complete, rather than an exception the turn dies on.

#### 1-4c. Wiring the sign-in on Python

FastAPI has no built-in identity story, so on Python we drive the authorization-code flow ourselves with MSAL:

```bash
uv add msal
```

MSAL needs somewhere to keep the token cache between the redirect to Entra and the callback that follows it, and that somewhere has to be the server. We keep a dictionary of sessions, hand the browser an opaque cookie that points into it, and no token ever leaves the process:

```python
import msal, secrets

SESSION_COOKIE = "learn_agent_sid"


class _Session:
    def __init__(self) -> None:
        self.cache = msal.SerializableTokenCache()
        self.user: dict[str, str] | None = None
        self.flow: dict | None = None


class SignInService:
    def __init__(self, settings):
        self._settings = settings
        self._sessions: dict[str, _Session] = {}

    def _msal_app(self, session):
        return msal.ConfidentialClientApplication(
            client_id=self._settings.webclient_client_id,
            client_credential=self._settings.webclient_client_secret,
            authority=f"https://login.microsoftonline.com/{self._settings.a365_tenant_id}",
            token_cache=session.cache,
        )

    def begin_sign_in(self, sid: str) -> str:
        session = self._sessions[sid]
        flow = self._msal_app(session).initiate_auth_code_flow(
            scopes=[self._settings.agent_user_scope],
            redirect_uri=self._settings.webclient_redirect_uri,
        )
        session.flow = flow
        return flow["auth_uri"]

    def complete_sign_in(self, sid: str, query_params: dict) -> dict[str, str]:
        session = self._sessions[sid]
        result = self._msal_app(session).acquire_token_by_auth_code_flow(session.flow, query_params)
        session.flow = None
        if "error" in result:
            raise RuntimeError(f"{result.get('error')}: {result.get('error_description', '')}")
        claims = result.get("id_token_claims", {})
        session.user = {
            "oid": claims.get("oid", ""),
            "name": claims.get("name", ""),
            "username": claims.get("preferred_username", ""),
        }
        return session.user

    def acquire_user_assertion(self, sid: str | None) -> str | None:
        """Token whose audience is the agent blueprint — the OBO user assertion."""
        session = self._sessions.get(sid or "")
        if session is None or session.user is None:
            return None
        app = self._msal_app(session)
        accounts = app.get_accounts()
        if not accounts:
            return None
        result = app.acquire_token_silent([self._settings.agent_user_scope], account=accounts[0])
        return result.get("access_token") if result else None
```

Two small pieces are elided above to keep the shape readable: `ensure_session`, which mints a session id with `secrets.token_urlsafe(32)` when the cookie is missing, and `current_user` and `sign_out`, which are a lookup and a `pop` on the same dictionary. The full version is in the reference implementation, under `app/a365/auth.py`.

`initiate_auth_code_flow` is doing more than it appears to: it generates the state, the nonce and the PKCE challenge, and returns them in a `flow` dictionary that `acquire_token_by_auth_code_flow` validates the callback against. That dictionary has to survive the round trip to Entra, which is exactly why the session lives server-side. Note the `scopes` argument in both places — it's `agent_user_scope`, the blueprint's scope, and that single line is what makes the resulting token usable as an assertion.

Then expose the three endpoints in `app/main.py`:

```python
@app.get("/signin")
async def signin(request: Request) -> RedirectResponse:
    sid, created = sign_in.ensure_session(request.cookies.get(SESSION_COOKIE))
    response = RedirectResponse(sign_in.begin_sign_in(sid), status_code=302)
    if created:
        response.set_cookie(SESSION_COOKIE, sid, httponly=True, samesite="lax", path="/")
    return response


@app.get("/signin-oidc")
async def signin_callback(request: Request) -> RedirectResponse:
    try:
        sign_in.complete_sign_in(request.cookies.get(SESSION_COOKIE), dict(request.query_params))
    except Exception as ex:
        logger.warning("Sign-in failed: %s", ex)
        return RedirectResponse("/?signin=failed", status_code=302)
    return RedirectResponse("/", status_code=302)


@app.get("/signout")
async def signout(request: Request) -> RedirectResponse:
    sign_in.sign_out(request.cookies.get(SESSION_COOKIE))
    response = RedirectResponse("/", status_code=302)
    response.delete_cookie(SESSION_COOKIE, path="/")
    return response
```

The path on `/signin-oidc` has to match the redirect URI you registered, and the cookie is set with `httponly` so the browser can't read it and `samesite="lax"` so it still arrives on the redirect back from Entra — `strict` would drop it and the callback would look like a session that never existed.

The chat page also needs a way to reach `/signin`, and something to tell it whether it should. Add a small endpoint the page can poll:

```python
@app.get("/api/me")
async def me(request: Request) -> dict[str, object]:
    user = sign_in.current_user(request.cookies.get(SESSION_COOKIE))
    return {"signedIn": user is not None, "name": (user or {}).get("name", "")}
```

Then, in `app/static/app.js`, call it on load and show either the user's name or a link to `/signin`. This is the one place where the Blazor and FastAPI versions genuinely diverge: .NET gets the redirect for free from `[Authorize]` and `AuthorizeRouteView`, whereas on Python we're doing that gating ourselves.

Last, refuse to answer without a user. In the `/api/chat` handler:

```python
user = sign_in.current_user(request.cookies.get(SESSION_COOKIE))
if user is None:
    raise HTTPException(401, "Sign in to talk to the agent.")
```

There's a reason to be strict here rather than lenient. The whole OBO chain starts from the signed-in user, so an anonymous turn is one that can't be attributed to anybody and won't be exported — better to say so plainly than to answer the question and quietly lose the telemetry.

#### 1-4d. A wrinkle worth knowing about now

On .NET there's a mismatch that will bite you the first time you restart the app with a browser still open, and it's much easier to understand now than to debug in Phase 2.

The authentication cookie is encrypted with Data Protection keys that live on disk, so it survives a restart. The MSAL token cache we configured with `AddInMemoryTokenCaches` does not. After a restart, then, the browser presents a perfectly valid cookie, `[Authorize]` is satisfied, the page renders — and there is no cached token to exchange. The first message fails with `MsalUiRequiredException`, which reads like a broken token chain rather than an empty cache.

The fix is to find out at page load instead of on the first message: probe for the token when the component first renders, and if it isn't there, send the user through sign-in again. The reference implementation does this in `OnAfterRenderAsync` and appends a marker to the return URL, so that a sign-in that still doesn't produce a token reports the problem rather than bouncing the browser between the app and Entra indefinitely.

#### 1-4e. Verify the token you get back

Rather than hoping we got it right and finding out in Phase 2, let's check now.

Run the app and open it. You should be redirected to Entra, and — the first time, on a tenant where an admin hasn't already consented — asked to approve the permissions. Sign in, come back, and grab the access token your app received: on .NET that's the return value of `AcquireUserAssertionAsync()`, on Python it's what `acquire_user_assertion()` hands back. Paste it into [jwt.ms](https://jwt.ms), which decodes it in the browser without sending it anywhere, and look at four claims:

| Claim | What it should say |
| --- | --- |
| `aud` | The **blueprint's** app id, or `api://<blueprint-id>` — **not** the sign-in client's id |
| `scp` | It should contain `access_agent_as_user` |
| `oid` | The signed-in user's object id |
| `tid` | Your tenant id |

If `aud` is the sign-in client, or Microsoft Graph, then the scope wasn't requested correctly — check that the scope you passed to `EnableTokenAcquisitionToCallDownstreamApi` or to `initiate_auth_code_flow` really is `api://<blueprint-id>/access_agent_as_user`. Fix that now: hop 2 in Phase 2 will fail with an assertion error otherwise, and at that point it will look like a problem with the token chain rather than with the sign-in.

✅ **Checkpoint — and a perfectly good place to stop.** The agent is registered and governed, it shows up in your tenant, and users sign in to it with a token addressed to the blueprint. It doesn't emit any telemetry yet; that's the next phase.

## Phase 2: Observability

This is the longest phase, and it's the one that delivers most of the value. By the end of it, every single turn the agent takes will produce telemetry, attributed to the user who caused it, and visible in Defender, Purview and the Microsoft 365 admin center.

It's also the phase with the most moving parts, so here's the shape of it before we start. We need to install the telemetry distro, wire it into the app's startup, obtain a token that the exporter is allowed to use, make sure every turn carries the identity information the service partitions on, and finally wrap the turn in the specific span types Agent 365 accepts. Miss any one of those and the telemetry either never leaves the process, or leaves and is discarded on arrival.

### Step 2-1. Run the observability skill

**What you type**

**What the skill does**

| --- | --- |
| 0.5 | Confirms the agent kind and the auth mode — **check that it says `obo`** |
| 1 | Detects your stack and loads the matching reference patterns |
| 2 | Installs the A365 OpenTelemetry distro |

### Step 2-2. Install the distro

The Agent 365 telemetry support ships as an OpenTelemetry distro: a wrapper around standard OTel that adds the Agent 365 exporter and the span processing the service expects.

On **.NET**:

```bash
dotnet add package Microsoft.OpenTelemetry
```

On **Python**:

```bash
uv add microsoft-opentelemetry
```

### Step 2-3. Wire the exporter into the entry point

Now we initialise the distro when the app starts.

On **.NET**, in `Program.cs`, after your services are registered:

```csharp
builder.Services.AddSingleton<ObservabilityTokenStore>();

builder.Services.AddMicrosoftOpenTelemetry(options =>
{
    options.EnableA365 = true;
    options.EnableAgent365Exporter = true;
    options.EnableSensitiveData = true;
    // OBO posts to the delegated endpoint, so leave UseS2SEndpoint at its default of false.
});
```

On **Python**, in `app/main.py`:

```python
from microsoft.opentelemetry import use_microsoft_opentelemetry

use_microsoft_opentelemetry(
    enable_a365=True,
    # Both flags are needed: enable_a365 only registers the span processors.
    a365_enable_observability_exporter=True,
    a365_token_resolver=token_store.get,
    # OBO posts to /observability/, so leave a365_use_s2s_endpoint at its default.
    enable_sensitive_data=True,
    disable_metrics=True,
)
```

**There are two flags, not one, and you need both.** `enable_a365` registers the span processors, which shape the spans correctly. `EnableAgent365Exporter` (or `a365_enable_observability_exporter` in Python) is what actually ships them anywhere. If you set only the first, you get beautifully-formed spans that go absolutely nowhere, with no error to tell you so.

> **On Python, where you put this call matters enormously.** It has to run before LangChain or the Azure OpenAI SDK are imported, because the distro works by patching those libraries as they load. If LangChain is imported first, the auto-instrumentation silently doesn't attach, and you end up with no `chat` spans at all — the agent works perfectly, and the LLM calls are simply invisible. Put the call at the very top of `app/main.py`, above the agent imports.

### Step 2-4. Implement the two-hop token chain

This is the most important part of the OBO path, and the part most worth reading even if the skill wrote it for you.

The exporter needs a token to talk to the Agent 365 Observability API, and it has to be a specific one: a token issued to the agent identity, acting on behalf of the signed-in user. A plain delegated user token is rejected, because its principal is the human rather than the agent. Getting that token takes two hops.

**Hop 1** — the blueprint proves that it owns the agent identity, and gets back an assertion:

```csharp
var form = new Dictionary<string, string>
{
    ["client_id"]     = blueprintClientId,
    ["client_secret"] = blueprintClientSecret,
    ["scope"]         = "api://AzureADTokenExchange/.default",
    ["fmi_path"]      = agentIdentityClientId,
    ["grant_type"]    = "client_credentials",
};
// POST to https://login.microsoftonline.com/<tenant>/oauth2/v2.0/token
```

The `fmi_path` parameter is what turns this from an ordinary client-credentials call into an agent flow. It effectively says: *issue me an assertion I can use to act as this child identity*. What comes back is not an access token and can't be used as one — it's only usable as a client assertion in the second hop.

**Hop 2** — the agent identity exchanges the user's token for the one we actually want:

```csharp
var form = new Dictionary<string, string>
{
    ["client_id"]             = agentIdentityClientId,
    ["scope"]                 = resourceScope,
    ["client_assertion_type"] = "urn:ietf:params:oauth:client-assertion-type:jwt-bearer",
    ["client_assertion"]      = t1Token,          // proves which agent
    ["assertion"]             = userAccessToken,  // proves for whom
    ["grant_type"]            = "urn:ietf:params:oauth:grant-type:jwt-bearer",
    ["requested_token_use"]   = "on_behalf_of",
};
```

Look at the two assertions side by side, because that pairing is the whole idea: `client_assertion` says *which agent is asking*, and `assertion` — the user token we so carefully addressed to the blueprint back in Step 1-3, and that the app now obtains on every turn through `AcquireUserAssertionAsync()` on .NET or `acquire_user_assertion()` on Python — says *who it's asking for*. The result is a token that represents the agent acting for that specific person.

On **Python** you don't need to hand-roll hop 1: MSAL supports `fmi_path` natively on `acquire_token_for_client` as of MSAL 1.37.

One last practical point: **cache both hops, and refresh a few minutes before expiry**. A token that expires halfway through a turn disables the export with no visible error at all — the agent keeps answering, and the telemetry quietly stops.

### Step 2-5. Bridge the token across to the exporter

We have a token. Now the exporter has to be able to find it, and that's less trivial than it sounds.

The exporter doesn't flush spans on the request thread. It flushes them on a background loop, where there is no HTTP request, no signed-in user, and therefore nothing to exchange on behalf of. So the pattern is: acquire the token while we still have a user, park it somewhere both threads can see, and let the exporter read it from there.

```csharp
// On the request thread, once per turn:
var userAssertion = await AcquireUserAssertionAsync();   // the token from Step 1-4
var agentToken = await oboTokens.GetAgentTokenAsync(userAssertion, ObservabilityScope);
tokenStore.Set(agentIdentityClientId, tenantId, agentToken);
```

The token store is a small dictionary keyed on the agent id and the tenant id. Hand its read method to the distro as the token resolver, and the background exporter can pick the token up whenever it needs to.

> **Don't try to acquire the token inside the resolver itself.** It's a tempting simplification, and it cannot work: by the time the resolver runs there is no user left to act on behalf of.

### Step 2-6. Open a baggage scope around every turn

Baggage is OpenTelemetry's mechanism for carrying contextual values alongside the current execution context, and Agent 365 uses it to carry the identity dimensions it partitions telemetry by — which tenant, which agent, which user, which conversation.

This one has the harshest failure mode in the whole guide: spans emitted outside an active baggage scope are dropped, and the exporter tells you so with the message `Partitioned into 0 identity groups`. Everything looks like it's working, and nothing arrives.

```csharp
using var scope = new BaggageBuilder()
    .TenantId(tenantId)
    .AgentId(agentIdentityClientId)
    .AgentName(agentName)
    .AgentBlueprintId(blueprintClientId)
    .ConversationId(conversationId)
    .SessionId(conversationId)
    .UserId(userId)
    .UserName(userName)
    .UserEmail(userEmail)
    .ChannelName("web")   // this isn't Teams, so use a logical channel name
    .Build();
```

Note the `using` — the scope has to be open for the whole turn, which means it has to wrap the agent invocation, not merely precede it.

`.AgentBlueprintId()` is worth calling out specifically: it populates `TargetAgentBlueprintId` in reporting, which is how the activity gets tied back to the blueprint you registered in Phase 1.

### Step 2-7. Resolve the caller correctly

The Microsoft 365 admin center needs the caller's **directory object id** to show you who did what. If you give it anything else, the export still returns `HTTP 200` and the row still arrives — it just never resolves to a person, and you get activity attributed to nobody.

On **.NET**, use the helper from `Microsoft.Identity.Web`:

```csharp
using Microsoft.Identity.Web;

var userId    = user?.GetObjectId()    ?? "unknown";
var userName  = user?.GetDisplayName() ?? "unknown";
```

> ⚠️ **Do not reach for `FindFirst("oid")` here**, even though it looks like the obvious way to read the object id. The OIDC handler renames inbound claims, so that lookup misses, and it typically falls through to `ClaimTypes.NameIdentifier` — which is the pairwise `sub` hash, not an object id at all. The admin center has no way to resolve a `sub` back to a user, so you end up with unattributed activity and no clue why. `GetObjectId()` is documented to work whether or not claims mapping is enabled, which is exactly why we use it.

On **Python**, read `oid` from the validated token claims, and `name` for the display name.

### Step 2-8. Wrap the turn in the semantic scopes

We're nearly there, but there's one more constraint to satisfy: Agent 365 doesn't accept arbitrary spans. It only ingests spans whose `gen_ai.operation.name` is one of `invoke_agent`, `chat`, `execute_tool` or `output_messages`. Anything else is dropped, span by span.

The one that matters most is `invoke_agent`. Open an `InvokeAgentScope` at the start of every turn: it becomes the root span for that turn, and it is the only span the Microsoft 365 admin center ingests. Defender is happy to take everything; the admin center is not.

```csharp
var request = new Request(
    content: userText,
    sessionId: conversationId,
    conversationId: conversationId,
    channel: new Channel("web"));

using var invokeScope = InvokeAgentScope.Start(
    request,
    new InvokeAgentScopeDetails(endpoint),
    agentDetails,
    callerDetails);
```

> **The session, conversation and channel have to be on the `Request` object, not only in baggage.** This trips people up because baggage *does* land on the span tags, so it looks like the information is there. But the exported `invoke_agent` payload is built from this `Request` object, so if you leave them out you export a span that is accepted and yet shows no run context at all.

What about the other span types? On supported stacks, `chat` spans come free from auto-instrumentation. **LangChain on Python is the exception** — the skill only soft-warns about this, so watch for it: you may need to wrap your LLM calls in an `InferenceScope` by hand. Tool calls need `ExecuteToolScope` in the same way.

### Step 2-9. Verify that the telemetry is actually leaving

Before we go looking in Defender, let's confirm from the app's own logs that spans are being exported. Turn on the exporter's logging:

```powershell
$env:OTEL_LOG_LEVEL="INFO"
$env:A365_OBSERVABILITY_LOG_LEVEL="debug"
```

Ask the agent a question and read the output. There are four things to look for, and all four have to be right:

- `Partitioned into 1 identity groups` — **not 0**. Zero means the baggage scope isn't active around the turn (Step 2-6).
- An `invoke_agent` span, and it must be a **root** span.
- `HTTP 200` on the export itself.
- The caller id in the payload is a **GUID**, not a long base64-looking hash. If it's the latter, you're hitting the `FindFirst("oid")` trap from Step 2-7.

✅ **Checkpoint — another good place to stop.** The agent is registered, and it's observable.

## Phase 4: Verify it end to end

Everything so far proves the agent *emits* telemetry. This phase proves it *arrives*, which is not the same thing at all — as we've seen, there are several ways for a span to be accepted and then quietly discarded.

### Step 4-1. Produce some activity

Ask the agent three or four questions. There's a set of them in [4.Sample-prompts.md](4.Sample-prompts.md) if you want a starting point. Make sure at least one of them causes a tool call, so we have more than just inference spans to look at.

### Step 4-2. Check Microsoft Defender

Go to [Advanced hunting](https://security.microsoft.com) in the Defender portal and query the `CloudAppEvents` table. Defender accepts every operation type, so this is where you should see the fullest picture — `InvokeAgent`, `InferenceCall` and `ExecuteToolByMCPServer` rows. Here's a query to start from:

```sql
CloudAppEvents
| where ActionType in ("InvokeAgent", "InferenceCall", "ExecuteToolBySDK", "ExecuteToolByGateway", "ExecuteToolByMCPServer")
| where RawEventData.TargetAgentName == "your-agent-name" or RawEventData.AgentName == "your-agent-name"
| order by Timestamp desc
```

Defender has to index the events, so give it around five minutes before concluding something is wrong.

### Step 4-3. Check the Microsoft 365 admin center

Now go to https://admin.cloud.microsoft, find your agent in the inventory, and open its activity.

This surface behaves differently from Defender, and understanding how saves a lot of debugging: the admin center ingests `invoke_agent` rows only, and it reads the caller identity off that one span. Which means the combination of what you see in each portal tells you precisely where a problem is:

| What you see | Where the problem is |
| --- | --- |
| Nothing anywhere | Export, token, or baggage scope — go back to Step 2-9 |
| Defender ✅, admin center ❌ | Your `invoke_agent` span. Nine times out of ten it's the caller id — Step 2-7 |
| Both ✅, but no user shown | The caller resolved to something that isn't a directory object id |
| Both ✅, but no run context | Session, conversation or channel missing from the `Request` object — Step 2-8 |

### Step 4-4. Optional — let a skill check the code for you

There's a skill that reviews the instrumentation and reports what's wrong without changing anything:

```text
Validate the Agent 365 observability code in this project.
```

`a365-code-validator` checks that the exporter is actually activated, that the runtime agent identity is bound correctly, that the required spans are present, and that the token has the right shape for the endpoint you're posting to. It's read-only by default, so it's safe to run at any point.

## Troubleshooting

If something isn't working, this table covers the failures you're most likely to hit, and where each one comes from:

| Symptom | Likely cause |
| --- | --- |
| `Partitioned into 0 identity groups` | No active baggage scope around the turn — Step 2-6 |
| `HTTP 200`, but nothing lands anywhere | No user in the tenant holds an Agent 365 licence |
| `AADSTS500011` resource principal not found | Agent 365 isn't provisioned in this tenant |
| Consent errors on the observability scope | The admin consent handoff from Step 1-1 was never run |
| `MsalUiRequiredException` on the first turn after a restart | The auth cookie outlived the in-memory token cache — Step 1-4d |
| `AADSTS50011` redirect URI mismatch | The registered redirect URI doesn't match the address the browser is on, scheme included — Step 1-3a |
| Hop 2 rejects the assertion | The sign-in asked for the wrong scope, so the user token isn't addressed to the blueprint — Step 1-4e |
| No `chat` spans on Python + LangChain | The distro was initialised after LangChain was imported — Step 2-3 |

## Wrapping up

We started with an ordinary web agent that answered questions for anyone who opened the page and knew nothing about the tenant it ran in. We gave it an identity, registered a separate sign-in app because a blueprint can't sign users in, wrote the sign-in code that turns an anonymous chat page into one that knows who is asking and holds a token addressed to the blueprint, built the two-hop token chain that lets the agent act on behalf of the person driving it, instrumented every turn so the activity shows up in Defender and the admin center attributed to the right user, and finally gave it access to Microsoft 365 data under that same user's permissions.

The thing worth taking away is that none of this changed what the agent *does*. It answers exactly the same questions it answered in Phase 0. What changed is that the organization can now see it, govern it, and hold it accountable — which is the difference between a demo and something you can actually put in front of users.

If you want to compare your result against a finished implementation, both stacks are available in full: the [.NET agent](https://github.com/qmatteoq/agent365-demos/tree/main/dotnet-agent-no-teams) and the [Python agent](https://github.com/qmatteoq/agent365-demos/tree/main/python-agent-no-teams).
