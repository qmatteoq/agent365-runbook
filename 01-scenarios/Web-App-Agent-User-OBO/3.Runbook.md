# Step-by-Step Guide: Web App Agent with User OBO

> **Scenario**: Onboarding a user-driven web agent into Microsoft Agent 365
> **Platform**: Microsoft Agent 365 · Microsoft Entra ID · OpenTelemetry
> **Stacks**: .NET Agent Framework (Blazor Server) · Python + LangChain (FastAPI)
> **Target Readers**: Agent developers, Entra administrators
> **Last Updated**: February 2026

## Introduction

We have an agent. It works: a user opens a web page, asks a question, the agent reasons over it, calls a few tools, and answers. From the outside it looks finished.

From the point of view of the organization it runs in, however, that agent doesn't exist. Nobody can see it in the tenant inventory. Nobody knows what it did yesterday, on whose behalf, or which data it touched. If a security analyst asks "which agents accessed customer mailboxes last week?", our agent won't be part of the answer, not because it behaved well, but because it never told anyone anything.

**Microsoft Agent 365** is what closes that gap. It gives the agent an identity in the tenant, a way to report its activity to Microsoft Defender, Microsoft Purview and the Microsoft 365 admin center, and a governed path to Microsoft 365 data. In this guide, we're going totake a plain agent running in a web app with no Agent 365 code in it whatsoever, and onboard it step by step.

The onboarding path we're following here is the **User On-Behalf-Of (OBO)** one. It's the right choice when a human drives the agent: the user signs in, and everything the agent does is attributed back to that person, including the granted permissions. There are other paths (a Teams-hosted agent, or an agent acting under its own identity), and if you're not sure which one applies to you, [Choosing Your Onboarding Path](../../02-patterns/Choosing-Your-Onboarding-Path.md) walks through the decision.

Two more things before we start.

First, **we're going to do most of the work by asking an AI coding assistant to do it for us**. Microsoft ships a set of skills, the [Agent 365 Skills](https://github.com/microsoft/agent365-skills), that know how to perform each onboarding step. We describe what we want in natural language, and the skill edits the project. But, and this matters, we're also going to look at what each skill actually did, and at the CLI commands and code underneath it. If you'd rather not use a coding assistant at all, you can follow this guide by hand: every step includes the manual equivalent.

Second, **the work is split into phases**. Phase 1 is a setup phase that only pays off at the end of Phase 2, but from Phase 2 onwards every phase is a valid place to stop, with something real to show for it.

| Phase | What you get at the end of it | Rough time |
| --- | --- | --- |
| 0: Get it running | A working agent, and a machine that can run the tooling | 15 to 45 min |
| 1: Sign users in | An Entra app registration, and the sign-in configured and understood | 30 min |
| 2: Registration | The agent exists in your tenant as a governed identity, and users sign in to it | 30 min |
| 3: Observability | Activity flowing into Defender, Purview and the admin center | 60 to 90 min |
| 4: Work IQ | The agent can reach Microsoft 365 data as the signed-in user | 30 min |
| 5: Verification | Proof that it all actually works end to end | 30 min |

Let's get started!

## How to read the steps in this guide

From Phase 2 onwards, each step is built the same way, so you always know what you're looking at:

1. **What you type**: the prompt you give your coding assistant.
2. **What the skill does**: the changes it's about to make, so nothing comes as a surprise.
3. **Behind the scenes**: the CLI command or the code it all comes down to.
4. **How to verify**: how to know it worked, before you move on to the next step.

If you're doing this manually, read parts 3 and 4 and ignore the rest. The guide works that way too.

Phase 1 is the exception, and deliberately so. Signing users in with Entra is ordinary web application work that Agent 365 neither provides nor replaces, so no skill does it for you. That phase is portal clicks and configuration, followed by a walkthrough of the sign-in code that already ships in the starting points. Nothing there asks you to write anything, but it's the foundation everything after it stands on, so it's worth reading rather than skimming.

## Prerequisites

Let's get the boring part out of the way first. There are three kinds of prerequisites here: tools on your machine, licences in your tenant, and permissions on your account. Missing any of them will stop you somewhere in the middle, so it's worth checking all three now.

### The tools you need on your machine

| Requirement | Minimum | Check it with | What needs it |
| --- | --- | --- | --- |
| .NET SDK | 8.0 | `dotnet --version` | The A365 CLI itself, and .NET agents |
| Agent 365 CLI | latest | `a365 --version` | Every phase |
| PowerShell | 7.0 | `pwsh --version` | The consent scripts |
| Azure CLI | latest | `az version` | Signing in to the tenant |
| Az PowerShell module | latest | `Get-Module -ListAvailable Az.Accounts` | Granting permissions |
| Git | any | `git --version` | Not applicable |
| Python | 3.12 | `python --version` | Python agents only |
| uv | latest | `uv --version` | Python agents only |

> **You need the .NET 8 SDK even if your agent is written in Python.** This surprises people. The reason is simply that the Agent 365 CLI is distributed as a .NET global tool, so .NET has to be there to run it. It has nothing to do with the language your agent is written in.

The CLI is the one tool you almost certainly don't have yet, so let's install it:

```bash
dotnet tool install --global Microsoft.Agents365.CLI
a365 --version
```

If the second command prints a version number, we're good.

### The licences your tenant needs

| Requirement | What to know |
| --- | --- |
| Microsoft 365 tenant | With Agent 365 enabled |
| Agent 365 licence | **At least one user in the tenant must hold one** |
| Azure subscription | For the Azure OpenAI resource the agent reasons with |

That middle row deserves a warning, because it's the single most confusing failure in this whole guide. If nobody in the tenant holds an Agent 365 licence, your telemetry is accepted with `HTTP 200` and then silently thrown away. Your logs will say the export succeeded, Defender will show nothing, and there's no error message anywhere that tells you why. So check the licence now, not in Phase 5.

### The permissions you need on your account

| Permission | Who needs it | What it's for |
| --- | --- | --- |
| Application Developer (or higher) | You | Creating app registrations |
| Global Administrator | You *or* a colleague | Granting admin consent to the blueprint |
| Azure OpenAI access | You | The model the agent uses. For the Entra credential path you need the **Cognitive Services OpenAI User** role on the resource; for key auth, access to the resource keys |

> **You don't have to be a Global Administrator yourself.** The CLI does everything it's allowed to do, and then prints a PowerShell snippet for an admin to run for the rest. Just be aware that this handoff exists, and line up the person who will run it before you get to Phase 1. Otherwise you'll be blocked at the start of Phase 3 with a consent error.

### The agent we're onboarding

This scenario ships with two starting points, one per stack. Both are complete, working agents with no Agent 365 observability code in them at all:

| Stack | Where it lives |
| --- | --- |
| .NET | [`0.Resources/Starting-point/dotnet/`](0.Resources/Starting-point/dotnet/) |
| Python | [`0.Resources/Starting-point/python/`](0.Resources/Starting-point/python/) |

You can absolutely bring your own agent instead. The guide assumes two things about it: it runs as a web app with one HTTP request per turn, and there's a single place in the code where a turn begins and ends, because that's where the instrumentation goes.

What both starting points *do* already contain is the Microsoft Entra sign-in. That's a deliberate choice. Signing users in is ordinary web app work with nothing Agent 365 about it, and making you write authentication code in the middle of an onboarding guide would put the emphasis in the wrong place. So we ship it, dormant: with the Entra settings blank, both apps skip authentication entirely and serve an anonymous chat page, which is what lets Phase 0 run before anything is registered. Phase 1 registers the application, fills the settings in and walks through what the code does, so the piece your token chain will rest on is something you understand rather than a black box.

## Phase 0: Get the agent running first

Before we add anything, let's make sure the agent works as it is.

Phase 3 adds a fair amount of steps (token exchanges, a telemetry exporter, span scopes), and if the agent is broken to begin with, you'll spend hours trying to work out which layer is at fault. Start from something that answers questions correctly, and every failure afterwards is one you introduced.

### Step 0-1. Configure the Azure OpenAI connection

The agent reasons using a model deployed in Azure OpenAI, so the very first thing it needs to know is *which* resource to call and *which* deployment on it to use.


If you're on **.NET**, open `appsettings.json`:

```json
{
  "AzureOpenAI": {
    "Endpoint": "https://<your-resource>.openai.azure.com/",
    "Deployment": "gpt-4.1",
    "TenantId": "<tenant that owns the Azure OpenAI resource>"
  },
  "LearnMcp": { "Endpoint": "https://learn.microsoft.com/api/mcp" }
}
```

If you're on **Python**, copy `.env.example` to `.env` (the example file is committed; `.env` is gitignored) and fill it in:

```bash
AZURE_OPENAI_ENDPOINT=https://<your-resource>.openai.azure.com/
AZURE_OPENAI_DEPLOYMENT=gpt-4.1
AZURE_OPENAI_API_VERSION=2024-10-21
AZURE_OPENAI_TENANT_ID=<tenant that owns the Azure OpenAI resource>
```

You'll find the endpoint and the deployment name in the Azure portal, on the Azure OpenAI resource, under **Resource Management → Keys and Endpoint** and **Model deployments** respectively.

> **The tenant id is not optional if you work across more than one tenant.** It's easy to skim past, so here's what happens if you leave it out: the credential hands back a token from whichever tenant you last signed in to, which may not be the one that owns the Azure OpenAI resource, and the service answers with `HTTP 400 – Tenant provided in token does not match resource token`. Pinning the tenant explicitly avoids an error that otherwise looks like a code problem.

### Step 0-2. Decide how the agent authenticates to Azure OpenAI

Both starting points support two ways of authenticating, and they choose between them automatically at startup with a very simple rule: *if an API key is configured, use key auth; if not, use Entra credentials.* There's no flag to flip; the presence or absence of the key is the switch.

Here's how the two compare:

|  | **Path A: Entra credentials** *(the default, and the recommended one)* | **Path B: API key** |
| --- | --- | --- |
| What it actually uses | `DefaultAzureCredential` on .NET, `AzureCliCredential` on Python, so your `az login` session locally, and a managed identity once hosted on Azure | A resource key, sent as a bearer secret |
| What you have to configure | Nothing beyond Step 0-1; you just need to be signed in | The key itself, kept in a secret store |
| What you need access to | The **Cognitive Services OpenAI User** role on the resource | The resource keys |
| Why you'd pick it | No long-lived secret to leak or rotate, the call carries a real identity, and it's the *only* option in tenants where key auth is disabled by policy | Environments that still depend on keys. The key never expires and carries no identity of its own |

#### Path A: Entra credentials

There's nothing to add to the configuration. Just sign in to the tenant that owns the Azure OpenAI resource:

```bash
az login --tenant <tenant of the Azure OpenAI resource>
```

When you later deploy to Azure, this path keeps working with no code change: .NET picks up the managed identity assigned to the App Service automatically through `DefaultAzureCredential`, and Python needs one extra setting, `AZURE_OPENAI_USE_MANAGED_IDENTITY=true`.

#### Path B: API key

If you do need key auth, the important thing is to keep the key out of files that get committed, and both `appsettings.json` and `.env.example` are committed:

```bash
# .NET — user secrets are stored outside the project folder
dotnet user-secrets set "AzureOpenAI:ApiKey" "<your-key>"
# or set the AzureOpenAI__ApiKey environment variable instead

# Python — in .env, which is gitignored
AZURE_OPENAI_API_KEY=<your-key>
```

### Step 0-3. Run it

Now we can start the agent. On **.NET**:

```bash
cd 0.Resources/Starting-point/dotnet
dotnet run
```

On **Python**:

```bash
cd 0.Resources/Starting-point/python

```

Open the app in a browser and ask it something it should be able to answer, for example:

```text
What is Microsoft Entra Conditional Access?
```

You should get a proper answer with links to Microsoft Learn at the end of it, because this agent grounds its answers in the Microsoft Learn MCP server rather than answering from the model's own memory.

✅ **Checkpoint.** The agent answers questions and cites its sources. There is still no trace of Agent 365 anywhere.

## Phase 1: Sign users in

Nothing in this phase is specific to Agent 365. We're going to register an ordinary Entra application, point the agent at it, and read through the sign-in code that already ships in the starting points. If you've built a web app that signs users in with Entra before, none of it will surprise you.

We do it first, before touching Agent 365 at all, because it's a prerequisite rather than a consequence. The OBO path attributes everything the agent does back to the person who asked for it, and it can't do that until there's a signed-in person to attribute it to. Doing it now also keeps the two concerns apart: by the time anything Agent 365 specific appears, the authentication underneath it is already registered, configured and understood.

One part of it has to wait, and it's worth knowing that up front. The token this sign-in eventually produces has to be addressed to the agent's blueprint, and the blueprint doesn't exist until Phase 2. So this phase gets you a registered sign-in client, the settings filled in and a clear picture of the code, and then Phase 2 supplies the last value and switches the whole thing on in one short step. Nothing visible changes until then, which is expected rather than a sign that something went wrong.

### Step 1-1. Create the app registration that signs users in

Signing a user in means sending their browser to Entra and getting them back again, and Entra will only do that for an application it knows about. So the first thing we need is an app registration whose job is to authenticate the human.

Keep the values from this step somewhere handy, because you'll be pasting them into the app's configuration in Step 1-2.

#### 1-1a. Create the registration

1. Go to the [Entra admin center](https://entra.microsoft.com) and navigate to **Identity → Applications → App registrations**.
2. Click **New registration**.
3. Give it a name that makes its role obvious, something like **my-agent-web-signin**. Phase 2 adds two more identities for this one agent, so a vague name will cost you time later.
4. For **Supported account types**, choose **Accounts in this organizational directory only (Single tenant)**.
5. Under **Redirect URI**, select the **Web** platform and enter the callback address your app will actually listen on. On .NET that's `http://localhost:5140/signin-oidc`, which is the URL the default `http` profile in `Properties/launchSettings.json` binds to; on Python it's `http://localhost:8000/signin-oidc`.
6. Click **Register**.

You'll land on the **Overview** blade. Copy the **Application (client) ID** and the **Directory (tenant) ID** from there and keep them somewhere handy; we'll need both in a moment.

> **The redirect URI has to match what the browser sees, character for character, scheme included.** It's easy to register the `https` address and then run the app over plain `http`, and Entra answers that with `AADSTS50011`, which reads like a configuration mistake in the app rather than a mismatched string. If you'd rather run the .NET app over TLS, launch it with `dotnet run --launch-profile https` and register `https://localhost:7199/signin-oidc` instead. An app registration can hold several redirect URIs, so registering both now and picking later is perfectly reasonable.

#### 1-1b. Create a client secret

1. In the same registration, go to **Certificates & secrets**.
2. On the **Client secrets** tab, click **New client secret**.
3. Give it a description and pick an expiry.
4. Click **Add**, then **copy the Value immediately**.

The value is shown once, and once you navigate away it's gone forever and you'll have to create another secret.

Store it somewhere the repository can't reach: `dotnet user-secrets` on .NET, the gitignored `.env` on Python. Never in `appsettings.json`, which is committed.

#### 1-1c. Check the sign-in permissions

An OIDC sign-in needs `openid`, `profile` and `offline_access`, and Entra treats those as permissions any user can consent to for themselves. Go to **API permissions** and have a look at what's already there. A new registration usually arrives with **Microsoft Graph → `User.Read`** and nothing else, which is fine: the identity libraries add the OIDC scopes to the request themselves, and neither starting point calls Graph.

So there's nothing to add here yet, and nothing that needs an administrator. This is a blade to get familiar with rather than one to change.

> **We will come back to it once.** In Step 2-3a we add a permission here that points this registration at the agent's blueprint, and that one does need admin consent. It has to wait, because the blueprint doesn't exist yet.

#### 1-1d. If you'd rather use the CLI

The registration and the secret can both be created from the command line instead:

```bash
# Create the registration
az ad app create --display-name "my-agent-web-signin" \
  --sign-in-audience AzureADMyOrg \
  --web-redirect-uris "http://localhost:5140/signin-oidc"

# Add a secret
az ad app credential reset --id <sign-in client app id> --append
```

Swap the redirect URI for `http://localhost:8000/signin-oidc` if you're on the Python starting point.

### Step 1-2. Fill in the sign-in settings

Both stacks need the same three facts about your tenant: the tenant id, and the sign-in client's id and secret. The callback path and the authority are already filled in for you. There's a fourth value, the blueprint id, that stays blank until Phase 2.

On **.NET**, the `AzureAd` and `Agent365Observability` sections are already in `appsettings.json`, with the tenant-specific values left blank:

```json
{
  "AzureAd": {
    "Instance": "https://login.microsoftonline.com/",
    "TenantId": "",
    "ClientId": "",
    "ClientSecret": "",
    "CallbackPath": "/signin-oidc"
  },
  "Agent365Observability": {
    "AgentBlueprintId": ""
  }
}
```

Fill in the tenant id and client id from the sign-in registration's **Overview** blade in Step 1-1a, and leave `AgentBlueprintId` alone for now. Leave `ClientSecret` empty in the file too, because the file is committed, and put the secret where it belongs instead:

```bash
dotnet user-secrets set "AzureAd:ClientSecret" "<sign-in client secret>"
```

`CallbackPath` has to line up with the redirect URI you registered in Step 1-1a, because `Microsoft.Identity.Web` builds the callback address from the app's own base URL plus this path. If the two disagree you'll get the `AADSTS50011` we warned about above.

The empty `Agent365Observability` section is the one Step 2-3 comes back to. It's named the way it is because that's the section the Agent 365 tooling and instrumentation look in, so filling it in later puts the blueprint id in the one place everything already expects to find it rather than introducing a second copy under a name of our own.

On **Python**, the same values live in `.env`, and `.env.example` already lists them with the redirect URI filled in and the rest blank:

```bash
# Entra sign-in for the web app. Leave blank until the runbook creates the app registration.
AZURE_AD_TENANT_ID=
AZURE_AD_CLIENT_ID=
AZURE_AD_CLIENT_SECRET=
AZURE_AD_REDIRECT_URI=http://localhost:8000/signin-oidc

# Agent blueprint id. The runbook fills this in once the agent is registered, and the
# sign-in stays off until it is set.
AGENTS365OBSERVABILITY__AGENTBLUEPRINTID=
```

Fill in the first three and leave the blueprint id blank. `.env` is gitignored, which is why the secret can sit in it directly here while its .NET counterpart has to go into user-secrets.

The double underscore in `AGENTS365OBSERVABILITY__AGENTBLUEPRINTID` is a .NET configuration convention rather than a Python one, and it's there on purpose: it's the name the Agent 365 tooling uses, so reading it directly means the same `.env` serves both the sign-in and everything the observability phase adds. Pydantic won't pick a name like that up on its own, so `app/config.py` maps it explicitly, and derives the scope from it in one place:

```python
agent_blueprint_id: str | None = Field(
    default=None,
    validation_alias="AGENTS365OBSERVABILITY__AGENTBLUEPRINTID",
)

@property
def agent_blueprint_scope(self) -> str:
    blueprint_id = (self.agent_blueprint_id or "").strip()
    if not blueprint_id:
        raise RuntimeError("The agent blueprint id is not configured.")

    return f"api://{blueprint_id}/access_agent_as_user"
```

You'll see `agent_blueprint_scope` again in the code we read through below. It's the scope the sign-in asks for, and building it in exactly one place is worth more than it looks: it's a string that has to be identical in the sign-in request, in the token acquisition and in whatever you paste into a debugger later, and a typo in any copy of it produces a token with the wrong audience rather than an error. Step 2-3 explains where that blueprint id comes from and why the scope has to be built this way.

Notice also the `HOST=localhost` in `.env.example`, which looks like a detail and behaves like a trap. `127.0.0.1` and `localhost` reach the same process, but the browser treats them as different origins and scopes the session cookie accordingly. Register the redirect URI on `localhost`, then browse the app on `127.0.0.1`, and the cookie set before the redirect simply isn't sent back on the callback. The sign-in fails in a way that looks like a lost session rather than a mismatched host, which is why the starting point defaults to `localhost` rather than leaving you to discover it.

### Step 1-3. How the app decides whether to sign anybody in

The next four steps don't ask you to type anything. The sign-in already ships in both starting points, and what follows is a walkthrough of it.

That's worth your time even so. The observability phase builds a two-hop token chain directly on top of this sign-in, and when a hop rejects a token (which it will, at least once), the difference between a five minute fix and a lost afternoon is knowing where that token came from. If you're bringing your own agent rather than one of the starting points, this walkthrough doubles as the specification of what your app has to do.

Start with the switch that has kept the sign-in out of your way until now.

Both starting points read the configuration at startup and ask one question: is every required sign-in value present? If anything is missing, they skip the whole authentication pipeline and behave exactly as they did in Phase 0. If everything is there, they wire it up. On .NET that decision lives in `Agent365SignInOptions.FromConfiguration`, which is a little stricter and also treats obvious placeholders (anything with angle brackets, anything starting `your-`, an all-zeroes guid) as not configured, so a half-edited `appsettings.json` keeps the anonymous behaviour rather than failing against Entra. `Program.cs` then branches on the result:

```csharp
var entraSignIn = Agent365SignInOptions.FromConfiguration(builder.Configuration);
builder.Services.AddSingleton(entraSignIn);

if (entraSignIn.IsEnabled)
{
    builder.Services.AddAuthentication(OpenIdConnectDefaults.AuthenticationScheme)
        .AddMicrosoftIdentityWebApp(builder.Configuration.GetSection(Agent365SignInOptions.AzureAdSectionName))
        .EnableTokenAcquisitionToCallDownstreamApi([entraSignIn.AgentUserScope])
        .AddInMemoryTokenCaches();

    builder.Services.AddAuthorization();
    builder.Services.AddCascadingAuthenticationState();
    builder.Services.AddMicrosoftIdentityConsentHandler();
    builder.Services.AddControllersWithViews()
        .AddMicrosoftIdentityUI();
}
```

On Python it's the same shape, a single conditional in `app/main.py` that either constructs the auth service or doesn't:

```python
auth_service = AuthService(settings) if settings.entra_sign_in_enabled else None
```

This is the same pattern as the Azure OpenAI key-versus-credential switch you met in Step 0-2: presence of configuration is the switch, and there's no separate flag to forget to flip. Both apps log which mode they started in, so if you fill the settings in and the app still behaves anonymously, the startup line tells you that much before you go looking through code. It won't name the offending key, so if you see it, check each value in turn.

Right now the app will still report the anonymous mode however carefully you filled Step 1-2 in, because the blueprint id is one of the values it looks for and that one is still empty. That's expected, and Step 2-3 is where it changes.

### Step 1-4. The .NET sign-in, line by line

The middle line of that `AddAuthentication` block is the one that does the work we actually came for. `AddMicrosoftIdentityWebApp` on its own signs the user in and gives you an id token, which tells you who they are and nothing more. `EnableTokenAcquisitionToCallDownstreamApi` turns the sign-in into an authorization-code flow that also comes back with an *access* token for the scope you name, the blueprint's scope, and `AddInMemoryTokenCaches` is where that token is kept so we can ask for it again on every turn.

`AddMicrosoftIdentityUI`, with `app.MapControllers()` further down, is what contributes the ready-made `/MicrosoftIdentity/Account/SignIn` and `SignOut` endpoints. Leave `MapControllers()` out and the redirect to the sign-in endpoint lands on a 404, which is a confusing way to discover that a controller is missing.

The middleware is registered under the same condition, in the order the pipeline needs:

```csharp
if (entraSignIn.IsEnabled)
{
    app.UseAuthentication();
    app.UseAuthorization();
}
```

Requiring a user is then two changes. `Components/Routes.razor` switches to an `AuthorizeRouteView` when sign-in is on, falling back to the plain `RouteView` when it isn't, because an `AuthorizeRouteView` in an app with no authentication services throws about a missing `AuthenticationStateProvider`:

```razor
@if (SignInOptions.IsEnabled)
{
    <AuthorizeRouteView RouteData="routeData" DefaultLayout="typeof(Layout.MainLayout)">
        <NotAuthorized>
            <RedirectToLogin />
        </NotAuthorized>
    </AuthorizeRouteView>
}
else
{
    <RouteView RouteData="routeData" DefaultLayout="typeof(Layout.MainLayout)" />
}
```

And `Components/RedirectToLogin.razor` sends an unauthenticated visitor to the sign-in endpoint:

```razor
@inject NavigationManager Navigation

@code {
    protected override void OnInitialized()
    {
        var returnUrl = Uri.EscapeDataString(Navigation.Uri);
        Navigation.NavigateTo($"MicrosoftIdentity/Account/SignIn?redirectUri={returnUrl}", forceLoad: true);
    }
}
```

The `forceLoad: true` matters more than it looks. Sign-in is a full browser round trip to Entra, and Blazor's client-side router would otherwise try to handle the navigation itself and go nowhere.

Finally, the part the token chain will call. `Components/Pages/Home.razor` exposes the assertion through a method whose name you'll see again:

```csharp
public async Task<string> AcquireUserAssertionAsync()
{
    if (!SignInOptions.IsEnabled)
    {
        throw new InvalidOperationException("Entra sign-in is not configured.");
    }

    try
    {
        var tokenAcquisition = Services.GetRequiredService<ITokenAcquisition>();
        return await tokenAcquisition.GetAccessTokenForUserAsync([SignInOptions.AgentUserScope]);
    }
    catch (MsalUiRequiredException ex)
    {
        Services.GetRequiredService<MicrosoftIdentityConsentAndConditionalAccessHandler>()
            .HandleException(ex);
        return string.Empty;
    }
    catch (MicrosoftIdentityWebChallengeUserException ex)
    {
        Services.GetRequiredService<MicrosoftIdentityConsentAndConditionalAccessHandler>()
            .HandleException(ex);
        return string.Empty;
    }
}
```

Because the token came from the cache that `AddInMemoryTokenCaches` set up during sign-in, this call is normally silent, with no redirect and no prompt. The two `catch` blocks are there for the cases where it isn't: `MsalUiRequiredException` when there's no usable cached token, and `MicrosoftIdentityWebChallengeUserException` when Entra wants something interactive, typically a conditional access policy demanding a fresh sign-in or a consent prompt that was never answered. Both are handed to the consent handler, which turns them into a redirect the user can complete rather than an exception that kills the turn.

The services are resolved from `IServiceProvider` rather than injected with `@inject`, which is unusual enough to be worth a word. `ITokenAcquisition` only exists in the container when sign-in is enabled, and an `@inject` directive would fail at render time in anonymous mode, before any of our conditionals get a chance to run.

### Step 1-5. The Python sign-in, line by line

FastAPI has no built-in identity story, so on Python the authorization-code flow is driven directly with MSAL, in `app/auth.py`. The flow needs somewhere to survive the round trip to Entra, and that somewhere has to be the server, so `AuthService` keeps a dictionary of sessions and hands the browser an opaque cookie that points into it. No token ever reaches the browser.

Going out:

```python
async def signin(self, request: Request) -> RedirectResponse:
    session_id = self._get_session_id(request) or self._new_session_id()
    session = self._sessions[session_id]
    # The flow dictionary contains the state, nonce and PKCE verifier that MSAL must
    # validate when Entra redirects back, so it stays in the server-side session.
    flow = self._client.initiate_auth_code_flow(
        scopes=[self._settings.agent_blueprint_scope],
        redirect_uri=self._settings.azure_ad_redirect_uri,
    )
    session["flow"] = flow

    response = RedirectResponse(flow["auth_uri"])
    self._set_session_cookie(response, session_id)
    return response
```

`initiate_auth_code_flow` is doing more than it appears to. It generates the state, the nonce and the PKCE challenge, and returns them in the `flow` dictionary that `acquire_token_by_auth_code_flow` validates the callback against, which is why we keep it rather than just the URL. Note the `scopes` argument: it's `agent_blueprint_scope`, the blueprint's scope, and that single line is what makes the resulting token usable as an assertion.

The cookie that carries the session id is set `httponly` so the browser can't read it and `samesite="lax"` so it still arrives on the redirect back from Entra. `strict` would drop it, and the callback would look like a session that never existed.

Coming back, `/signin-oidc` completes the flow and remembers who signed in:

```python
result = self._client.acquire_token_by_auth_code_flow(
    session.pop("flow"),
    dict(request.query_params),
)
if "error" in result:
    raise HTTPException(
        status_code=status.HTTP_401_UNAUTHORIZED,
        detail=result.get("error_description") or result["error"],
    )

claims = result.get("id_token_claims", {})
session["claims"] = claims
```

The `session.pop` is deliberate: a flow is good for exactly one callback, and leaving it in place would let a replayed callback reuse it. The claims we keep are the ones the page needs to greet the user by name, and the code goes on to record the MSAL account id for that username, which is what `acquire_token_silent` looks the cached token up by later.

Then the method the token chain calls, the counterpart of `AcquireUserAssertionAsync`:

```python
def acquire_user_assertion(self, request: Request) -> str:
    """Return a blueprint-scoped access token for the signed-in user."""
    session = self._get_session(request)
    if not session:
        raise AuthRequiredError("Sign in before chatting with the agent.")

    account = self._get_account(session)
    if not account:
        raise AuthRequiredError("Sign in before chatting with the agent.")

    result = self._client.acquire_token_silent(
        [self._settings.agent_blueprint_scope],
        account=account,
    )
    if not result or "access_token" not in result:
        raise AuthRequiredError("Sign in again so the app can get a user assertion.")

    return result["access_token"]
```

`acquire_token_silent` reads from the cache MSAL populated during sign-in and refreshes the token when it can, so this is normally a local operation. When it genuinely can't produce a token it raises `AuthRequiredError`, which `/api/chat` turns into a 401 rather than a 500:

```python
if auth_service:
    try:
        auth_service.acquire_user_assertion(http_request)
    except AuthRequiredError as error:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail=str(error),
        ) from error
```

There's a reason to be strict here rather than lenient. The whole OBO chain starts from the signed-in user, so an anonymous turn is one that can't be attributed to anybody and won't be exported. Better to refuse plainly than to answer the question and quietly lose the telemetry.

The gating is the one place where the two stacks genuinely diverge. On .NET, `[Authorize]` and `AuthorizeRouteView` produce the redirect for free; on Python we do it ourselves, with `/api/me` telling the front end whether anybody is signed in so it can render a sign-in link or a name.

### Step 1-6. A wrinkle worth knowing about now

On .NET there's a mismatch that will bite you the first time you restart the app with a browser still open, and it's much easier to understand now than to debug later.

The authentication cookie is encrypted with Data Protection keys that live on disk, so it survives a restart. The MSAL token cache configured by `AddInMemoryTokenCaches` does not. After a restart, then, the browser presents a perfectly valid cookie, the authorization check is satisfied, the page renders, and there is no cached token to exchange. The first message fails with `MsalUiRequiredException`, which reads like a broken token chain rather than an empty cache.

The starting point handles this by finding out at page load instead of on the first message. `Home.razor` probes for the token in `OnAfterRenderAsync` on first render, so a missing cached token sends the user through sign-in immediately rather than surfacing as a failed chat turn several minutes later:

```csharp
protected override async Task OnAfterRenderAsync(bool firstRender)
{
    if (!firstRender || !SignInOptions.IsEnabled || AuthenticationStateTask is null)
    {
        return;
    }

    var authenticationState = await AuthenticationStateTask;
    if (authenticationState.User.Identity?.IsAuthenticated != true)
    {
        return;
    }

    _ = await AcquireUserAssertionAsync();
}
```

✅ **Checkpoint.** The sign-in client is registered and the app is pointed at it, and you've read the code that will use it. The sign-in is still dormant, because the scope it asks for is built from a blueprint id that doesn't exist yet. Phase 2 creates the blueprint and switches it on.

## Phase 2: Register the agent

Now the agent stops being just code on your laptop and becomes an object in your tenant.

Two objects, actually, and the difference between them matters for everything that follows:

- The **blueprint** is the parent app registration. It holds the permissions, and it owns the agent. Think of it as the definition of the agent.
- The **agent identity** is a child principal of that blueprint. It's the thing that actually *acts*, the principal your telemetry will be attributed to.

The phase ends by going back to the sign-in from Phase 1 and giving it the piece it was missing.

### Step 2-1. Run the setup skill

**What you type**

### Step 2-2. Store the blueprint secret somewhere safe

`a365 setup all` generated a client secret for the blueprint. That secret is what proves, when we build the token chain in Phase 3, that your code is allowed to act as this agent, so it must never end up in source control.

On **.NET**, put it in user secrets, which live outside the project folder entirely:

```bash
dotnet user-secrets set "Agent365:BlueprintClientSecret" "<secret>"
```

On **Python**, put it in `.env`, and take a second to confirm that `.env` really is listed in `.gitignore`.

```bash

```

### Step 2-3. Connect the sign-in to the blueprint

Here is where the two halves meet. Phase 1 left us with an app that can authenticate a user, and Step 2-1 gave us a blueprint. What we don't have yet is a token that links them, which is the whole point of the OBO path.

The obvious question at this point is why the blueprint can't just sign users in itself, given that it's an app registration like any other. It can't, and the reason is deliberate: a blueprint is an **agentic application**, and Microsoft Entra bars agentic applications from interactive `/authorize` flows. A blueprint can never present a sign-in page. That's precisely why Phase 1 came first, and why what we registered there was a separate, completely ordinary application.

So this scenario has three identities in it, and keeping them straight in your head makes everything else easier:

| Identity | Who creates it | What it does |
| --- | --- | --- |
| **Sign-in client** | You, in Step 1-1 | Signs the user in, and requests the blueprint's scope |
| **Blueprint** | `a365 setup all`, in Step 2-1 | Owns the permissions, and authenticates hop 1 of the token chain |
| **Agent identity** | `a365 setup all`, in Step 2-1 | The principal the agent acts as, and that spans are exported as |

Keep `a365.generated.config.json` open, because you'll need the **blueprint's app id** twice below.

#### 2-3a. Give the sign-in app permission to call the blueprint

This is the step that makes the entire token chain possible, so it's worth doing slowly.

1. Still in the sign-in registration, go to **API permissions**.
2. Click **Add a permission**.
3. Choose the **APIs my organization uses** tab.
4. Paste the **blueprint's app id** into the search box and select it from the results.
5. Choose **Delegated permissions**.
6. Tick **`access_agent_as_user`**.
7. Click **Add permissions**.

> **If the blueprint doesn't come up in the search**, search by its app id rather than its display name because the CLI appends `" Blueprint"` to the name you chose, so what you type may not match. And if you find the API but it exposes no scopes at all, open the **blueprint's** registration, go to **Expose an API → Add a scope**, create a scope named exactly `access_agent_as_user`, set **Who can consent?** to **Admins and users**, leave the state **Enabled**, and then come back here and repeat the steps above.

Then click **Grant admin consent for \<your tenant\>**. This one genuinely needs an administrator, because `access_agent_as_user` is not a permission users can consent to for themselves. If the button is greyed out for you, this is the second of the two admin handoffs in this guide. A permission that's recorded but not consented to behaves exactly like one that was never added.

From the command line, the same two operations are:

```bash
# The scope id is on the blueprint's "Expose an API" blade
az ad app permission add --id <sign-in client app id> \
  --api <blueprint-app-id> --api-permissions <scope-id>=Scope

az ad app permission admin-consent --id <sign-in client app id>
```

Note that `az ad app permission add` only records the permission; the consent grant on the second line is what makes it usable.

> **Don't mix up the two secrets.** You now have a blueprint secret and a sign-in client secret, and they do completely different jobs. The blueprint secret authenticates hop 1 of the token chain; the sign-in client secret authenticates the web sign-in. Swapping them produces authentication errors that are genuinely hard to read.

#### 2-3b. Give the app the blueprint id

This is the value we left blank in Step 1-2, and it's the one that switches the sign-in on. Take `agentBlueprintId` from `a365.generated.config.json` and put it where the app expects it.

On **.NET**, in `appsettings.json`:

```json
"Agent365Observability": {
  "AgentBlueprintId": "<blueprint app id>"
}
```

On **Python**, in `.env`:

```bash
AGENTS365OBSERVABILITY__AGENTBLUEPRINTID=<blueprint app id>
```

That single value does two things at once. It completes the set of settings the startup check looks for, so the authentication pipeline you read through in Phase 1 finally gets registered, and it supplies the resource half of `api://<blueprint-id>/access_agent_as_user`, which is the scope the sign-in asks for.

That scope is the part worth slowing down over, because an app can sign users in perfectly well and never ask for it. You would have a working login and a token that the next phase rejects. The scope determines who the token is *addressed to*, and hop 2 of the token chain will only accept an assertion addressed to the blueprint. Not `User.Read`, and not the blueprint's `.default`.

Restart the app. The startup line should now report the signed-in mode rather than the anonymous one.

#### 2-3c. Verify the token you get back

Rather than hoping we got it right and finding out in the observability phase, let's check now.

Open the app. The two stacks announce themselves differently here. On .NET you should be redirected to Entra before the chat page renders at all, because `AuthorizeRouteView` refuses to show a protected page to an anonymous visitor. On Python the page still loads, and the line under the title changes from the anonymous message to a **Sign in** link, because there we do the gating ourselves rather than getting it from the framework. Either way, the first time on a tenant where an admin hasn't already consented, you'll be asked to approve the permissions.

Once you're back, we want to look at the token the app is holding, and neither app puts it on screen, deliberately: an access token in the DOM is an access token in somebody's browser history. So use the debugger, which takes a minute:

- On **.NET**, set a breakpoint on the `return await tokenAcquisition.GetAccessTokenForUserAsync(...)` line in `Components/Pages/Home.razor` and reload the page. The first render probes for the token, so the breakpoint hits without you having to send a message. Copy the return value out of the debugger.
- On **Python**, set a breakpoint on the `return result["access_token"]` line in `app/auth.py` and send a message. `/api/chat` calls `acquire_user_assertion` before it does anything else, so the breakpoint hits on the first turn.

Paste what you copied into [jwt.ms](https://jwt.ms), which decodes it in the browser without sending it anywhere, and look at four claims:

| Claim | What it should say |
| --- | --- |
| `aud` | The **blueprint's** app id, or `api://<blueprint-id>`, **not** the sign-in client's id |
| `scp` | It should contain `access_agent_as_user` |
| `oid` | The signed-in user's object id |
| `tid` | Your tenant id |

If `aud` is the sign-in client, or Microsoft Graph, then the scope wasn't requested correctly. The usual cause is a blueprint id that's present but wrong, a stale one from an earlier `a365 setup all` run, say, which builds a scope pointing at a resource that isn't your blueprint. A blueprint id that's missing entirely fails more loudly than that: sign-in never switches on at all, and you get the anonymous page. Fix this now either way, because hop 2 in the next phase will fail with an assertion error otherwise, and at that point it will look like a problem with the token chain rather than with the sign-in.

✅ **Checkpoint.** This is a perfectly good place to stop. The agent is registered and governed, it shows up in your tenant, and users sign in to it with a token addressed to the blueprint. It doesn't emit any telemetry yet; that's the next phase.

## Phase 3: Observability

This is the longest phase, and it's the one that delivers most of the value. By the end of it, every single turn the agent takes will produce telemetry, attributed to the user who caused it, and visible in Defender, Purview and the Microsoft 365 admin center.

It's also the phase with the most moving parts, so here's the shape of it before we start. We need to install the telemetry distro, wire it into the app's startup, obtain a token that the exporter is allowed to use, make sure every turn carries the identity information the service partitions on, and finally wrap the turn in the specific span types Agent 365 accepts. Miss any one of those and the telemetry either never leaves the process, or leaves and is discarded on arrival.

### Step 3-1. Run the observability skill

**What you type**

```text

Agent (Non AI Teammate) using the obo auth mode.
```

**What the skill does**

`instrument-observability` works through eight internal phases:

| Phase | What it changes |
| --- | --- |
| 0.5 | Confirms the agent kind and the auth mode. **Check that it says `obo`** |
| 1 | Detects your stack and loads the matching reference patterns |
| 2 | Installs the A365 OpenTelemetry distro |
| 3 | Wires the distro into your entry point |
| 4 | Adds a baggage scope to your message handler |
| 5 | Implements the token resolver |
| 5.5 | Adds the manual instrumentation scopes |
| 6 to 8 | Updates configuration, builds, and smoke-tests the result |

It is *not* correct for a Teams-hosted agent, and the skill has been known to choose it there anyway. That something is the sign-in you configured in Phase 1 and switched on in Step 2-3, so make sure Step 2-3c is done and verified before running this one.

The rest of Phase 3 walks through what those changes actually are, in the order the skill makes them. **If you ran the skill, you don't need to perform these steps**. Read them as an explanation of the code you now have, and as a checklist if something isn't working.

### Step 3-2. Install the distro

The Agent 365 telemetry support ships as an OpenTelemetry distro: a wrapper around standard OTel that adds the Agent 365 exporter and the span processing the service expects.

On **.NET**:

```bash
dotnet add package Microsoft.OpenTelemetry
```

On **Python**:

```bash
uv add microsoft-opentelemetry
```

### Step 3-3. Wire the exporter into the entry point

Now we initialise the distro when the app starts.

On **.NET**, in `Program.cs`, after your services are registered:

```csharp
builder.Services.AddSingleton<ObservabilityTokenStore>();

builder.Services.AddMicrosoftOpenTelemetry(options =>
{
    options.EnableA365 = true;
    options.EnableAgent365Exporter = true;
    options.EnableSensitiveData = true;
    // OBO posts to the delegated endpoint, so leave UseS2SEndpoint at its default of false.
});
```

On **Python**, in `app/main.py`:

```python
from microsoft.opentelemetry import use_microsoft_opentelemetry

use_microsoft_opentelemetry(
    enable_a365=True,
    # Both flags are needed: enable_a365 only registers the span processors.
    a365_enable_observability_exporter=True,
    a365_token_resolver=token_store.get,
    # OBO posts to /observability/, so leave a365_use_s2s_endpoint at its default.
    enable_sensitive_data=True,
    disable_metrics=True,
)
```

**There are two flags, not one, and you need both.** `enable_a365` registers the span processors, which shape the spans correctly. `EnableAgent365Exporter` (or `a365_enable_observability_exporter` in Python) is what actually ships them anywhere. If you set only the first, you get beautifully-formed spans that go absolutely nowhere, with no error to tell you so.

> **On Python, where you put this call matters enormously.** It has to run before LangChain or the Azure OpenAI SDK are imported, because the distro works by patching those libraries as they load. If LangChain is imported first, the auto-instrumentation silently doesn't attach, and you end up with no `chat` spans at all. The agent works perfectly, and the LLM calls are simply invisible. Put the call at the very top of `app/main.py`, above the agent imports.

### Step 3-4. Implement the two-hop token chain

This is the most important part of the OBO path, and the part most worth reading even if the skill wrote it for you.

The exporter needs a token to talk to the Agent 365 Observability API, and it has to be a specific one: a token issued to the agent identity, acting on behalf of the signed-in user. A plain delegated user token is rejected, because its principal is the human rather than the agent. Getting that token takes two hops.

**Hop 1**: the blueprint proves that it owns the agent identity, and gets back an assertion:

```csharp
var form = new Dictionary<string, string>
{
    ["client_id"]     = blueprintClientId,
    ["client_secret"] = blueprintClientSecret,
    ["scope"]         = "api://AzureADTokenExchange/.default",
    ["fmi_path"]      = agentIdentityClientId,
    ["grant_type"]    = "client_credentials",
};
// POST to https://login.microsoftonline.com/<tenant>/oauth2/v2.0/token
```

The `fmi_path` parameter is what turns this from an ordinary client-credentials call into an agent flow. It effectively says: *issue me an assertion I can use to act as this child identity*. What comes back is not an access token and can't be used as one. It's only usable as a client assertion in the second hop.

**Hop 2**: the agent identity exchanges the user's token for the one we actually want:

```csharp
var form = new Dictionary<string, string>
{
    ["client_id"]             = agentIdentityClientId,
    ["scope"]                 = resourceScope,
    ["client_assertion_type"] = "urn:ietf:params:oauth:client-assertion-type:jwt-bearer",
    ["client_assertion"]      = t1Token,          // proves which agent
    ["assertion"]             = userAccessToken,  // proves for whom
    ["grant_type"]            = "urn:ietf:params:oauth:grant-type:jwt-bearer",
    ["requested_token_use"]   = "on_behalf_of",
};
```

Look at the two assertions side by side, because that pairing is the whole idea: `client_assertion` says *which agent is asking*, and `assertion` (the user token we so carefully addressed to the blueprint back in Step 2-3, and that the app now obtains on every turn through `AcquireUserAssertionAsync()` on .NET or `acquire_user_assertion()` on Python) says *who it's asking for*. The result is a token that represents the agent acting for that specific person.

On **Python** you don't need to hand-roll hop 1: MSAL supports `fmi_path` natively on `acquire_token_for_client` as of MSAL 1.37.

One last practical point: **cache both hops, and refresh a few minutes before expiry**. A token that expires halfway through a turn disables the export with no visible error at all. The agent keeps answering, and the telemetry quietly stops.

### Step 3-5. Bridge the token across to the exporter

We have a token. Now the exporter has to be able to find it, and that's less trivial than it sounds.

The exporter doesn't flush spans on the request thread. It flushes them on a background loop, where there is no HTTP request, no signed-in user, and therefore nothing to exchange on behalf of. So the pattern is: acquire the token while we still have a user, park it somewhere both threads can see, and let the exporter read it from there.

```csharp
// On the request thread, once per turn:
var userAssertion = await AcquireUserAssertionAsync();   // the blueprint-scoped token verified in Step 2-3c
var agentToken = await oboTokens.GetAgentTokenAsync(userAssertion, ObservabilityScope);
tokenStore.Set(agentIdentityClientId, tenantId, agentToken);
```

The token store is a small dictionary keyed on the agent id and the tenant id. Hand its read method to the distro as the token resolver, and the background exporter can pick the token up whenever it needs to.

> **Don't try to acquire the token inside the resolver itself.** It's a tempting simplification, and it cannot work: by the time the resolver runs there is no user left to act on behalf of.

### Step 3-6. Open a baggage scope around every turn

Baggage is OpenTelemetry's mechanism for carrying contextual values alongside the current execution context, and Agent 365 uses it to carry the identity dimensions it partitions telemetry by: which tenant, which agent, which user, which conversation.

This one has the harshest failure mode in the whole guide: spans emitted outside an active baggage scope are dropped, and the exporter tells you so with the message `Partitioned into 0 identity groups`. Everything looks like it's working, and nothing arrives.

```csharp
using var scope = new BaggageBuilder()
    .TenantId(tenantId)
    .AgentId(agentIdentityClientId)
    .AgentName(agentName)
    .AgentBlueprintId(blueprintClientId)
    .ConversationId(conversationId)
    .SessionId(conversationId)
    .UserId(userId)
    .UserName(userName)
    .UserEmail(userEmail)
    .ChannelName("web")   // this isn't Teams, so use a logical channel name
    .Build();
```

Note the `using`: the scope has to be open for the whole turn, which means it has to wrap the agent invocation, not merely precede it.

`.AgentBlueprintId()` is worth calling out specifically: it populates `TargetAgentBlueprintId` in reporting, which is how the activity gets tied back to the blueprint you registered in Phase 2.

### Step 3-7. Resolve the caller correctly

The Microsoft 365 admin center needs the caller's **directory object id** to show you who did what. If you give it anything else, the export still returns `HTTP 200` and the row still arrives. It just never resolves to a person, and you get activity attributed to nobody.

On **.NET**, use the helper from `Microsoft.Identity.Web`:

```csharp
using Microsoft.Identity.Web;

var userId    = user?.GetObjectId()    ?? "unknown";
var userName  = user?.GetDisplayName() ?? "unknown";
```

> ⚠️ **Do not reach for `FindFirst("oid")` here**, even though it looks like the obvious way to read the object id. The OIDC handler renames inbound claims, so that lookup misses, and it typically falls through to `ClaimTypes.NameIdentifier`, which is the pairwise `sub` hash, not an object id at all. The admin center has no way to resolve a `sub` back to a user, so you end up with unattributed activity and no clue why. `GetObjectId()` is documented to work whether or not claims mapping is enabled, which is exactly why we use it.

On **Python**, read `oid` from the validated token claims, and `name` for the display name.

### Step 3-8. Wrap the turn in the semantic scopes

We're nearly there, but there's one more constraint to satisfy: Agent 365 doesn't accept arbitrary spans. It only ingests spans whose `gen_ai.operation.name` is one of `invoke_agent`, `chat`, `execute_tool` or `output_messages`. Anything else is dropped, span by span.

The one that matters most is `invoke_agent`. Open an `InvokeAgentScope` at the start of every turn: it becomes the root span for that turn, and it is the only span the Microsoft 365 admin center ingests. Defender is happy to take everything; the admin center is not.

```csharp
var request = new Request(
    content: userText,
    sessionId: conversationId,
    conversationId: conversationId,
    channel: new Channel("web"));

using var invokeScope = InvokeAgentScope.Start(
    request,
    new InvokeAgentScopeDetails(endpoint),
    agentDetails,
    callerDetails);
```

> **The session, conversation and channel have to be on the `Request` object, not only in baggage.** This trips people up because baggage *does* land on the span tags, so it looks like the information is there. But the exported `invoke_agent` payload is built from this `Request` object, so if you leave them out you export a span that is accepted and yet shows no run context at all.

What about the other span types? On supported stacks, `chat` spans come free from auto-instrumentation. **LangChain on Python is the exception**. The skill only soft-warns about this, so watch for it: you may need to wrap your LLM calls in an `InferenceScope` by hand. Tool calls need `ExecuteToolScope` in the same way.

### Step 3-9. Verify that the telemetry is actually leaving

Before we go looking in Defender, let's confirm from the app's own logs that spans are being exported. Turn on the exporter's logging:

```powershell
$env:OTEL_LOG_LEVEL="INFO"
$env:A365_OBSERVABILITY_LOG_LEVEL="debug"
```

Ask the agent a question and read the output. There are four things to look for, and all four have to be right:

- `Partitioned into 1 identity groups`, **not 0**. Zero means the baggage scope isn't active around the turn (Step 3-6).
- An `invoke_agent` span, and it must be a **root** span.
- `HTTP 200` on the export itself.
- The caller id in the payload is a **GUID**, not a long base64-looking hash. If it's the latter, you're hitting the `FindFirst("oid")` trap from Step 3-7.

✅ **Checkpoint.** This is another good place to stop. The agent is registered, and it's observable.
## Phase 4: Work IQ

With observability in place, we can give the agent access to Microsoft 365 data, Mail, Calendar and more, through the Work IQ MCP servers. And it reaches that data using the signed-in user's own permissions, so the agent can never see anything the person driving it couldn't already see.

> **Check availability before you plan around this.** The Work IQ adapters are not available for every stack. At the time of writing there's a .NET path but no Python one.
### Step 4-1. Run the Work IQ skill

**What you type**

```text
Add Work IQ tools to this agent. I want Mail and Calendar.
```

**What the skill does**

`add-workiq-tools` shows you the catalog of available servers, adds the ones you pick, writes a `ToolingManifest.json` describing them, wires a registration service into your agent code, and walks you through the permissions handoff that each server needs.

**Behind the scenes**

```bash
a365 develop list-available                          # see what's in the catalog

```

**How to verify**

Open `ToolingManifest.json` and check that the servers you asked for are listed, and that each appears **exactly once**, since duplicate registrations are a known failure mode. Then ask the agent something that can only be answered by calling one of them:

```text
What's on my calendar tomorrow?
```

✅ **Checkpoint.** The agent can now reach Microsoft 365 data as the signed-in user.

## Phase 5: Verify it end to end

Everything so far proves the agent *emits* telemetry. This phase proves it *arrives*, which is not the same thing at all. As we've seen, there are several ways for a span to be accepted and then quietly discarded.

### Step 5-1. Produce some activity

Ask the agent three or four questions. There's a set of them in [4.Sample-prompts.md](4.Sample-prompts.md) if you want a starting point. Make sure at least one of them causes a tool call, so we have more than just inference spans to look at.

### Step 5-2. Check Microsoft Defender

Go to [Advanced hunting](https://security.microsoft.com) in the Defender portal and query the `CloudAppEvents` table. Defender accepts every operation type, so this is where you should see the fullest picture: `InvokeAgent`, `InferenceCall` and `ExecuteToolByMCPServer` rows. Here's a query to start from:

```sql
CloudAppEvents
| where ActionType in ("InvokeAgent", "InferenceCall", "ExecuteToolBySDK", "ExecuteToolByGateway", "ExecuteToolByMCPServer")
| where RawEventData.TargetAgentName == "your-agent-name" or RawEventData.AgentName == "your-agent-name"
| order by Timestamp desc
```

Defender has to index the events, so give it around five minutes before concluding something is wrong.

### Step 5-3. Check the Microsoft 365 admin center

Now go to https://admin.cloud.microsoft, find your agent in the inventory, and open its activity.

This surface behaves differently from Defender, and understanding how saves a lot of debugging: the admin center ingests `invoke_agent` rows only, and it reads the caller identity off that one span. Which means the combination of what you see in each portal tells you precisely where a problem is:

| What you see | Where the problem is |
| --- | --- |
| Nothing anywhere | Export, token, or baggage scope. Go back to Step 3-9 |
| Defender ✅, admin center ❌ | Your `invoke_agent` span. Nine times out of ten it's the caller id. Step 3-7 |
| Both ✅, but no user shown | The caller resolved to something that isn't a directory object id |
| Both ✅, but no run context | Session, conversation or channel missing from the `Request` object. Step 3-8 |

### Step 5-4. Optional: let a skill check the code for you

There's a skill that reviews the instrumentation and reports what's wrong without changing anything:

```text
Validate the Agent 365 observability code in this project.
```

`a365-code-validator` checks that the exporter is actually activated, that the runtime agent identity is bound correctly, that the required spans are present, and that the token has the right shape for the endpoint you're posting to. It's read-only by default, so it's safe to run at any point.

## Troubleshooting

If something isn't working, this table covers the failures you're most likely to hit, and where each one comes from:

| Symptom | Likely cause |
| --- | --- |
| `Partitioned into 0 identity groups` | No active baggage scope around the turn. Step 3-6 |
| `HTTP 200`, but nothing lands anywhere | No user in the tenant holds an Agent 365 licence |
| `AADSTS500011` resource principal not found | Agent 365 isn't provisioned in this tenant |
| Consent errors on the observability scope | The admin consent handoff from Step 2-1 was never run |
| `MsalUiRequiredException` on the first turn after a restart | The auth cookie outlived the in-memory token cache. Step 1-6 |
| `AADSTS50011` redirect URI mismatch | The registered redirect URI doesn't match the address the browser is on, scheme included. Step 1-1a |
| Hop 2 rejects the assertion | The sign-in asked for the wrong scope, so the user token isn't addressed to the blueprint. Step 2-3c |
| No `chat` spans on Python + LangChain | The distro was initialised after LangChain was imported. Step 3-3 |

## Wrapping up

We started with an ordinary web agent that answered questions for anyone who opened the page and knew nothing about the tenant it ran in. We gave it an identity, registered a separate sign-in app because a blueprint can't sign users in, switched on the sign-in that turns an anonymous chat page into one that knows who is asking and holds a token addressed to the blueprint, built the two-hop token chain that lets the agent act on behalf of the person driving it, instrumented every turn so the activity shows up in Defender and the admin center attributed to the right user, and finally gave it access to Microsoft 365 data under that same user's permissions.

The thing worth taking away is that none of this changed what the agent *does*. It answers exactly the same questions it answered in Phase 0. What changed is that the organization can now see it, govern it, and hold it accountable, which is the difference between a demo and something you can actually put in front of users.

If you want to compare your result against a finished implementation, both stacks are available in full: the [.NET agent](https://github.com/qmatteoq/agent365-demos/tree/main/dotnet-agent-no-teams) and the [Python agent](https://github.com/qmatteoq/agent365-demos/tree/main/python-agent-no-teams).
