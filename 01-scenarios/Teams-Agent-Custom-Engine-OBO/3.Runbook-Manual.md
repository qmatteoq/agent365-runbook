# Manual runbook: Teams agent with custom engine OBO

> **Scenario**: Onboarding a custom engine agent in Teams into Microsoft Agent 365 by hand
> **Platform**: Microsoft Agent 365, Azure Bot Service, Microsoft Entra ID, OpenTelemetry
> **Worked examples**: .NET Agent Framework, Python + LangChain, Node.js + LangChain
> **Target readers**: Agent developers, Azure and Entra administrators
> **Last updated**: September 2026

## Introduction

An agent can answer messages in Teams without giving administrators the information they need to understand its use. We're going to onboard our agent into Microsoft Agent 365, then add telemetry that connects each request to the person who sent it, the model calls, the tools and the answer.

This guide covers the commands, configuration and source changes directly, so we can follow it with our own agent and an ordinary editor without a coding assistant. The optional Microsoft Learn research sample lets us try the steps in a separate application while learning how they work. We don't need to clone it to onboard our agent, and it isn't a production application template.

We're following the custom engine on-behalf-of (OBO) path. Azure Bot Service owns the Teams channel, and its OAuth connection obtains a delegated observability token for the Teams user. The bot's application identity and that user's identity are both part of the flow. An AI Teammate instead operates with its own agent identity and agent user account; use the [AI Teammate / Autopilot guide](../AI-Teammate-Agent-Identity/3.Runbook-Manual.md) for that scenario.

| Phase | What we finish with | Rough time |
| --- | --- | --- |
| 0: Get it working | A protected messaging endpoint and an agent answering in Teams | 60 to 90 min |
| 1: Registration | A blueprint and agent identity alongside the existing bot | 30 min |
| 2: Observability | OBO authentication and instrumented turns in our chosen stack | 90 to 120 min |
| 3: Work IQ | A tooling manifest and tenant grants, with the runtime limitations identified | 30 min |
| 4: Verification | Evidence in Defender and the Microsoft 365 admin center | 30 min |

Phase 3 is optional. The registration and instrumentation do not depend on Work IQ.

## How to read the steps in this guide

Each step explains why we need it, then gives us the commands or edits and a way to check the result. Where the languages differ, follow only the **.NET**, **Python** or **Node.js** subsection. Run project commands from our agent's project directory. Merge configuration into the existing settings, retaining unrelated values, and use our deployment's secret store for credentials. Commands use PowerShell 7.

The registration steps apply to an existing custom engine agent. The source examples use Microsoft 365 Agents SDK hosting, with Microsoft Agent Framework and `Microsoft.Extensions.AI` on .NET, or LangChain on Python and Node.js. If our host uses another SDK, adapt the wrappers to its channel validation, authenticated turn data and OAuth token APIs. We keep the agent's model, tools and business logic, and choose instrumentation for the framework making those calls.

### Map the examples to our application

We will use the following integration points in our own code. The paths identify the optional sample's implementation; our files and class names can differ.

| Integration point | .NET example | Python example | Node.js example |
| --- | --- | --- | --- |
| Application startup and services | `Program.cs` | `app\main.py` | `src\main.ts` |
| Messaging endpoint and channel authentication | ASP.NET `MapPost` and JWT middleware | aiohttp route and JWT middleware | Agents SDK `startServer` |
| Agent message handler | `Agent\LearnAgent.cs` | `on_message` in `app\main.py` | `agentApp.onActivity` in `src\main.ts` |
| Existing model and tool execution | `AIAgent` and its `IChatClient` | LangChain agent in `app\agent.py` | LangChain agent in `src\agent.ts` |
| Configuration | `IConfiguration` | Environment loaded before SDK imports | Environment loaded before SDK imports |

In Phase 2, we pass our existing turn implementation into a telemetry wrapper as an asynchronous callback. The callback runs the model and tools, sends the response once and returns its text for telemetry. We retain our session store, cancellation, routing and error handling. The complete sample edits show that wiring with a research agent, but calls such as `learnAgent.ask(...)` stand for our own application logic.

These callbacks show a single final text response. If our agent streams responses, sends adaptive cards or delivers results asynchronously, keep that delivery behavior and place the corresponding invocation and output scopes around the actual operations. Don't replace it with the sample's text reply just to use the wrapper unchanged.

Names such as `LearnTeams`, `LearnTeamsAgent.Chat`, local file paths and port `3978` are example values. Use our agent's name, namespace, configured port and messaging path instead, keeping any renamed activity source consistent between instrumentation and subscription. The Observability API application ID and scope are service identifiers, not example values. The authorization handler and Azure Bot OAuth connection names must match their configuration throughout.

All three optional samples expose `POST /api/messages` on port **3978**. Their .NET project targets **`net10.0`**; the Node telemetry package in this guide requires **Node.js 22 or later**. An existing application should retain its supported runtime and dependencies, checking compatibility with the pinned SDK examples before applying them.

### Keep the identities separate

We will have several identifiers by the end of registration. They have different jobs:

| Value | Where we use it |
| --- | --- |
| Bot app client ID | Channel authentication, OAuth connection client, telemetry agent ID and token-cache key |
| Bot app secret | Outbound channel authentication and the Azure Bot OAuth connection |
| Blueprint client ID | Agent 365 governance and `agent_blueprint_id` in telemetry |
| Child agent identity | Inventory created by registration; not the export ID on this OBO route |
| Teams app ID | Identity of our Teams app package; retained when updating the app |
| User's Entra object ID | Caller attribution, read from the authenticated activity |

> Keep a secure copy of the bot credentials before running `a365 setup all`. Setup can replace the values in the local configuration with blueprint credentials. That does not make the blueprint the channel app, and it does not revoke the original Entra secret. Restore the original bot settings before restarting.

### Step 0-3. Protect the messaging endpoint

Our messaging endpoint must validate channel requests before running application code. If our host already authenticates Azure Bot requests, keep its authentication schemes, issuer rules and authorization policies, and check rejection in Step 0-4. The following examples fill gaps in the educational hosts; don't replace a working authentication setup or duplicate its middleware. They use public-cloud Azure Bot Service and a single-tenant bot app.

#### .NET

Merge these sections into `appsettings.json`, retaining the other application settings:

```json
{
  "TokenValidation": {
    "Enabled": true,
    "Audiences": ["<bot-app-client-id>"],
    "TenantId": "<tenant-id>"
  },
  "Connections": {
    "ServiceConnection": {
      "Settings": {
        "AuthType": "ClientSecret",
        "AuthorityEndpoint": "https://login.microsoftonline.com/<tenant-id>",
        "ClientId": "<bot-app-client-id>",
        "TenantId": "<tenant-id>",
        "ClientSecret": "",
        "Scopes": ["https://api.botframework.com/.default"]
      }
    }
  },
  "ConnectionsMap": [
    {"ServiceUrl": "*", "Connection": "ServiceConnection"}
  ]
}
```

The single-tenant connection uses our tenant's authority. Match the connection name to the one our Agents SDK host uses. Keep the secret outside this file; for the local .NET sample, use:

```powershell
dotnet user-secrets set "Connections:ServiceConnection:Settings:ClientSecret" "<bot-app-secret>"
dotnet add package Microsoft.AspNetCore.Authentication.JwtBearer --version 10.0.8
```

The first command stores the local reply credential; a deployed application should use its existing secret-management mechanism. The second supplies the ASP.NET bearer handler for the .NET 10 example. Setting `TokenValidation` values alone does not secure an ASP.NET endpoint: it needs a registered authentication handler, middleware and authorization.

Add these imports to `Program.cs`:

```csharp
using Microsoft.AspNetCore.Authentication.JwtBearer;
using Microsoft.IdentityModel.Tokens;
```

These are the bearer authentication types. After `var builder = WebApplication.CreateBuilder(args);`, add:

```csharp
var botAudience = builder.Configuration["Connections:ServiceConnection:Settings:ClientId"];
if (!Guid.TryParse(botAudience, out _))
    throw new InvalidOperationException("Set the bot app client ID before enabling Teams.");

builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.MetadataAddress =
            "https://login.botframework.com/v1/.well-known/openidconfiguration";
        options.MapInboundClaims = false;
        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = true,
            ValidIssuer = "https://api.botframework.com",
            ValidateAudience = true,
            ValidAudience = botAudience,
            ValidateLifetime = true,
            ValidateIssuerSigningKey = true
        };
    });
builder.Services.AddAuthorization();
```

This validates the signed channel JWT issued by public-cloud Azure Bot Service. It is not the Entra access token returned by the OAuth connection in Phase 2, and it is not the AI Teammate authentication configuration.

Immediately after `var app = builder.Build();`, add:

```csharp
app.UseAuthentication();
app.UseAuthorization();
```

The middleware authenticates requests before the endpoint runs. Apply the appropriate authorization policy to our messaging route. In the sample, change the closing `});` of `app.MapPost("/api/messages", ...)` to `}).RequireAuthorization();` and keep `app.MapGet("/")` public as its health route.

```dotenv
CONNECTIONS__SERVICE_CONNECTION__SETTINGS__CLIENTID=<bot-app-client-id>
CONNECTIONS__SERVICE_CONNECTION__SETTINGS__CLIENTSECRET=<bot-app-secret>
```

```dotenv
Connections__ServiceConnection__Settings__ClientId=<bot-app-client-id>

```

This configuration uses the JavaScript connection name `ServiceConnection`; the Python example uses `SERVICE_CONNECTION`. Load configuration before SDK imports because the SDK reads the connection while its module loads. The sample does this with `import "./env.js"` in `src\main.ts`, and its `startServer` call supplies JWT middleware for the messaging endpoint.


```powershell
Invoke-WebRequest http://localhost:3978/ | Select-Object StatusCode
```

2. Set **Messaging endpoint** to our HTTPS messaging URL. For the local sample, use `https://<printed-tunnel-host>/api/messages`.
3. Select **Apply**.

## Phase 1: Register the agent

### Step 1-1. Save the channel settings

Make the changes in a development copy or staging environment and stop the local host if one is running. Record the bot client ID and tenant, retain access to its secret through our secret store, and back up the configuration securely. Don't run setup against a live production working directory. A local `.env` can contain secrets; don't commit it or its backup.

Registration can change the local channel settings. Afterward, we'll put the bot's settings back and keep the new Agent 365 configuration.

### Step 1-2. Create the blueprint and child identity

From our agent's project folder, preview the registration. Replace `LearnTeams` with our chosen agent name throughout the commands and telemetry settings, and use our deployed messaging URL or the local tunnel URL:

```powershell
a365 setup all --agent-name "LearnTeams" --tenant-id "<tenant-id>" `
    --authmode obo --m365 --messaging-endpoint "<https-messaging-url>" --dry-run
```

The preview shows the intended registration. We choose `obo` and omit `--aiteammate`, because the agent is still a custom engine bot. `--m365` registers the Microsoft 365 endpoint metadata; it does not replace our Azure Bot registration.

Apply the same setup and complete the bot-permission step:

```powershell
a365 setup all --agent-name "LearnTeams" --tenant-id "<tenant-id>" `
    --authmode obo --m365 --messaging-endpoint "<https-messaging-url>"
a365 setup permissions bot --agent-name "LearnTeams" --tenant-id "<tenant-id>"
```

These commands create the blueprint and child identity and configure the platform permissions. Follow any **Action Required** output, including resource-service-principal provisioning and administrator consent. A command that finishes by printing a consent URL has not completed that administrator's work.

Read the non-secret identifiers:

```powershell
Get-Content .\a365.generated.config.json -Raw |
    ConvertFrom-Json |
    Select-Object agentBlueprintId, agentIdentityId, agentIdentityClientId
```

Record `agentBlueprintId`. Generated identity fields vary across CLI versions, so don't substitute one for the bot client ID if a selected field is empty. Confirm the blueprint in Entra and the agent in the Microsoft 365 admin center's **Agents** inventory.

### Step 1-3. Restore the bot connection

Compare the local connection settings against Step 0-3. Restore the bot client ID, secret, tenant and channel scopes if setup replaced them. On .NET, keep both the audience and `ServiceConnection` pointed at the bot app; on Python and Node.js, restore the correctly spelled connection keys.

Keep the generated Agent 365 configuration and the blueprint credential in secure storage, but don't load the blueprint secret into the bot connection. The telemetry implementation below doesn't use that secret: it gets its token from Azure Bot OAuth.

Apply the configuration through our normal deployment process, or restart the local host, then send another Teams request. Registration is complete when the blueprint exists, the consent handoff is finished, and the bot still answers.

## Phase 2: Add observability

We need a delegated token before any spans are exported. We will configure Teams SSO and an Azure Bot OAuth connection, register an authorization handler, then wrap the agent turn with baggage and an `invoke_agent` scope. Model and tool instrumentation will run inside that scope.

If our application already uses OpenTelemetry, extend its existing initialization with Agent 365 export and the required identity fields. Don't install a second tracer provider, duplicate an invocation scope, or disable existing exporters and instrumentors just to match the example. The full implementations below show the configuration for a host without Agent 365 instrumentation; merge the relevant parts into our startup and lifecycle handling.

Keep the agent's model and tool implementations. The .NET example uses `Microsoft.Extensions.AI` chat middleware, and the Python and Node.js examples use LangChain instrumentation. For another framework, use its compatible model and tool instrumentation and confirm the same span contract in Step 2-6. The invocation wrapper alone cannot produce inference and tool spans for an unsupported framework.

### Step 2-1. Configure the bot's delegated permission and Teams SSO

The [observability authentication guide](https://learn.microsoft.com/microsoft-agent-365/developer/observability-authentication-setup#custom-engine-using-obo) documents this route. The permission belongs on the **bot app registration**, even though registration also created permissions on the blueprint.

If our bot already has Teams SSO, retain its working Application ID URI, scope, authorized clients and app-package settings. Add the observability permission and check the remaining values against that configuration. The steps below establish SSO when it is missing, using `api://botid-<bot-app-client-id>` as the example URI. Use our agent's display name in consent text.

1. Open the bot app in Entra **App registrations**, then **API permissions**, **Add a permission**, **APIs my organization uses**.
2. Search for the Observability API, application ID `9b975845-388f-4429-889e-eab1ef63949c`. Choose **Delegated permissions**, select **Agent365.Observability.OtelWrite**, then **Add permissions**.
3. Ask the administrator to select **Grant admin consent for \<tenant\>** and confirm the permission shows **Granted**.
4. Open **Authentication**, select **Add a platform**, then **Web**. Set **Redirect URIs** to `https://token.botframework.com/.auth/web/redirect` and select **Configure**. This is the public-cloud, global Bot Service redirect, not our tunnel URL.
5. Open **Expose an API**, select **Add** next to **Application ID URI**, enter `api://botid-<bot-app-client-id>`, and select **Save**.
6. Select **Add a scope**. Set **Scope name** to `access_as_user`, **Who can consent?** to **Admins only**, **Admin consent display name** to `Use the Learn Teams agent`, **Admin consent description** to `Allow Teams to access the Learn Teams agent as the signed-in user`, and **State** to **Enabled**. Select **Add scope**.
7. Under **Authorized client applications**, select **Add a client application**. Add `1fec8e78-bce4-4aaf-ab1b-5451cc387264` for Teams desktop/mobile and `5e3ce6c0-2b1f-4285-8d4b-75ee78787346` for Teams web, selecting our `access_as_user` scope for each.
8. Open **Manifest**, set `api.requestedAccessTokenVersion` to `2`, and select **Save**.

The bot's `access_as_user` scope lets Teams obtain an SSO token for our bot. It is separate from the Observability API scope that the OAuth connection requests downstream. Follow the [Teams SSO registration reference](https://learn.microsoft.com/microsoftteams/platform/bots/how-to/authentication/bot-sso-register-aad) for additional Microsoft 365 client IDs if we also test the Copilot surface.

```csharp
    public async Task<string> RunAsync(
        ITurnContext context, string token, string question, Func<Task<string>> run)
    {
        if (string.IsNullOrWhiteSpace(token))
            throw new InvalidOperationException("The observability OAuth handler returned no token.");
        var jwt = new JwtSecurityTokenHandler().ReadJwtToken(token);
        var lifetime = jwt.ValidTo - DateTime.UtcNow - TimeSpan.FromMinutes(1);

        var userId = context.Activity.From.AadObjectId;
        if (string.IsNullOrWhiteSpace(userId))
            throw new InvalidOperationException("The Teams activity has no caller Entra object ID.");
        var userName = context.Activity.From.Name ?? "";
        var caller = new CallerDetails(userDetails:
            new UserDetails(userId: userId, userName: userName));
        var parent = Activity.Current;
        var previousBaggage = Baggage.Current;
        Activity.Current = null;
        Baggage.Current = default;
        try
        {
            using var baggage = new BaggageBuilder()
                .TenantId(agent.TenantId).AgentId(agent.AgentId)
                .AgentName(agent.AgentName).AgentBlueprintId(agent.AgentBlueprintId)
                .ConversationId(conversation).SessionId(conversation)
                .UserId(userId).UserName(userName).ChannelName("msteams").Build();
            var request = new A365Request(question, sessionId: conversation,
                conversationId: conversation, channel: new Channel("msteams"));
            using var invoke = InvokeAgentScope.Start(request,
                new InvokeAgentScopeDetails(new Uri("https://teams.microsoft.com")), agent, caller);
            invoke.RecordInputMessages([question]);
            try
            {
                var answer = await run();
                invoke.RecordOutputMessages([answer]);
                return answer;
            }
            catch (Exception error)

                Activity.Current?.SetStatus(ActivityStatusCode.Error, "Research turn failed.");

    }

    public void Dispose() => tokens.Dispose();

    public override void OnEnd(Activity activity)

        foreach (var pair in Baggage.Current.GetBaggage())

    }
}
```

#### Add a synchronous exporter cache

Create `app\token_store.py`:

```python
import base64
import json
import threading
import time


class TokenStore:
    def __init__(self):
        self._lock = threading.Lock()
        self._tokens: dict[tuple[str, str], tuple[str, float]] = {}

    def set(self, agent_id: str, tenant_id: str, token: str) -> None:
        payload = token.split(".")[1]
        claims = json.loads(base64.urlsafe_b64decode(payload + "=" * (-len(payload) % 4)))
        expires = float(claims["exp"]) - 60
        if expires <= time.time():
            raise ValueError("The observability token has expired.")
        with self._lock:
            self._tokens[(agent_id, tenant_id)] = (token, expires)

    def get(self, agent_id: str, tenant_id: str) -> str:
        with self._lock:
            entry = self._tokens.get((agent_id, tenant_id))
        if entry is None or entry[1] <= time.time():
            raise RuntimeError("No current OAuth token for this telemetry identity.")
        return entry[0]


token_store = TokenStore()
```

The background exporter calls a synchronous resolver, so this is not an `async def`. The lock protects the cache across the request and exporter threads. We decode only the expiry from the token returned by the trusted OAuth service; malformed tokens fail rather than becoming entries without an expiry.

#### Add the token cache

Create `src\token-store.ts`:

```typescript
interface Entry {
    token: string;
    expiresAt: number;
}

class TokenStore {
    private readonly entries = new Map<string, Entry>();

    set(agentId: string, tenantId: string, token: string): void {
        const payload = token.split(".")[1];
        if (!payload) throw new Error("OAuth returned a malformed observability token.");
        const claims: unknown = JSON.parse(Buffer.from(payload, "base64url").toString("utf8"));
        if (!claims || typeof claims !== "object" ||
            !("exp" in claims) || typeof claims.exp !== "number") {
            throw new Error("The observability token has no numeric expiry.");
        }
        const expiresAt = claims.exp * 1000 - 60_000;
        if (expiresAt <= Date.now()) throw new Error("The observability token has expired.");
        this.entries.set(`${agentId}:${tenantId}`, { token, expiresAt });
    }

    get(agentId: string, tenantId: string): string {
        const entry = this.entries.get(`${agentId}:${tenantId}`);
        if (!entry || entry.expiresAt <= Date.now()) {
            throw new Error("No current OAuth token for this telemetry identity.");
        }
        return entry.token;
    }
}

export const tokenStore = new TokenStore();
```

The cache only stores tokens returned during authenticated turns and refuses an expired token. Decoding `exp` is for cache timing, not a substitute for channel JWT validation.

Keep the sample's `build` and `typecheck` scripts, and change `engines.node` to `>=22.0.0`. Its `tsx` dependency handles TypeScript while the distro loader hooks ESM imports. For an application that runs compiled JavaScript, retain the build process and start its compiled bootstrap with the distro loader; `tsx` is not required for that deployment. Use the loader-enabled entry point in the deployment command as well as locally.

#### Add the turn wrapper

Create `src\teams-telemetry.ts`:

```typescript
import "./env.js";
import { context as otelContext, ROOT_CONTEXT } from "@opentelemetry/api";
import { BaggageBuilder, InvokeAgentScope, type AgentDetails } from "@microsoft/opentelemetry";
import type { TurnContext } from "@microsoft/agents-hosting";
import { tokenStore } from "./token-store.js";

function id(key: string): string {
    const value = process.env[key]?.trim().toLowerCase();
    if (!value || !/^[0-9a-f]{8}(-[0-9a-f]{4}){3}-[0-9a-f]{12}$/.test(value)) {
        throw new Error(`Set ${key} to its GUID.`);
    }
    return value;
}

const agentId = id("Connections__ServiceConnection__Settings__ClientId");
const tenantId = id("Connections__ServiceConnection__Settings__TenantId");
const blueprintId = id("A365_BLUEPRINT_ID");
const agentName = process.env.A365_AGENT_NAME?.trim() || "LearnTeams";
const agent: AgentDetails = { agentId, tenantId, agentBlueprintId: blueprintId, agentName };

export async function runTurn(
    context: TurnContext, token: string, question: string, run: () => Promise<string>,
): Promise<string> {
    tokenStore.set(agentId, tenantId, token);
    const conversationId = context.activity.conversation?.id;
    const userId = context.activity.from?.aadObjectId;
    if (!conversationId || !userId) {
        throw new Error("The Teams activity needs a conversation and caller Entra object ID.");
    }
    const userName = context.activity.from?.name ?? "";
    return otelContext.with(ROOT_CONTEXT, async () => {
        const baggage = new BaggageBuilder()
            .tenantId(tenantId).agentId(agentId).agentName(agentName)
            .agentBlueprintId(blueprintId).conversationId(conversationId)
            .sessionId(conversationId).userId(userId).userName(userName)
            .channelName("msteams").build();
        return baggage.run(async () => {
            const scope = InvokeAgentScope.start(
                { content: question, conversationId, sessionId: conversationId,
                  channel: { name: "msteams" } },
                { endpoint: { host: "teams.microsoft.com", protocol: "https" } },
                agent, { userDetails: { userId, userName } },
            );
            try {
                return await scope.withActiveSpanAsync(async () => {
                    scope.recordInputMessages([question]);
                    const answer = await run();
                    scope.recordOutputMessages([answer]);
                    return answer;
                });
            } catch (error) {
                scope.recordError(error instanceof Error ? error : new Error(String(error)));
                throw error;
            } finally {
                scope.dispose();
            }
        });
    });
}
```

The baggage and `AgentDetails` use the same bot client ID. `ROOT_CONTEXT` prevents an incoming parent span from turning the invocation into a child of an unrelated HTTP trace. Both the invocation and its children retain the conversation and human caller.

Import the wrapper in our message-handler module (`src\main.ts` in the sample):

```typescript
import { runTurn } from "./teams-telemetry.js";
```

This configures an Azure Bot OAuth handler; Bot Service performs the token exchange. Keep our application's existing storage instead of adopting the sample's `MemoryStorage`. In the route we instrument, acquire the token and pass the existing model-and-reply logic into `runTurn`. The complete sample route is:

```typescript
agentApp.onActivity("message", async (context: TurnContext) => {
    const question = context.activity.text?.trim();
    if (!question) {
        await context.sendActivity("Ask me a question about the Microsoft ecosystem.");
        return;
    }
    try {
        const response = await agentApp.authorization.getToken(context, "oboConnectionProfile");
        if (!response.token) throw new Error("The observability OAuth handler returned no token.");
        await runTurn(context, response.token, question, async () => {
            const conversationId = context.activity.conversation?.id;
            if (!conversationId) throw new Error("The Teams activity has no conversation ID.");
            const answer = await learnAgent.ask(conversationId, question);
            await context.sendActivity(answer);
            return answer;
        });
    } catch (error) {
        console.error("The instrumented Teams turn failed.", error);
        await context.sendActivity(
            "Sorry, I couldn't complete this turn. Please try again after sign-in.",
        );
    }
}, ["oboConnectionProfile"]);
```

The final handler-name array enables sign-in before the callback; retain any other handlers the route needs. Replace `learnAgent.ask(...)` with our existing agent invocation and keep its conversation handling. The callback sends the answer once and returns it for telemetry; `runTurn` does not send another reply. Retain unrelated routes and error handling. The sample's `src\agent.ts` supplies LangChain model and tool calls without further changes.

Connect distro shutdown to our host's graceful shutdown lifecycle. For a local process without an existing shutdown hook, add this import in `main.ts` and the signal handlers before `startServer(...)`:

```typescript
import { shutdownMicrosoftOpenTelemetry } from "@microsoft/opentelemetry";

for (const signal of ["SIGINT", "SIGTERM"] as const) {
    process.once(signal, () => {
        void shutdownMicrosoftOpenTelemetry().then(
            () => process.exit(0),
            (error: unknown) => {
                console.error("Telemetry shutdown failed.", error);
                process.exit(1);
            },
        );
    });
}
```

This flushes pending spans on a normal local shutdown and reports a flush failure. A production host should first stop accepting traffic and drain active turns before shutting down telemetry.

Run our application's checks, then restart or redeploy it through the loader-enabled entry point. For the sample:

```powershell

npm start
```

The handler now acquires an OBO token, stores it and runs the full agent turn inside the invocation.

### Step 2-6. Check one complete trace

Send a new question from our personal Teams chat. Complete the sign-in card if Teams cannot perform the first exchange silently. The OAuth connection returns the observability token; don't paste that token into logs, an online decoder or a configuration file.

Read the console spans and compare them with this contract:

| Check | Expected value |
| --- | --- |
| Export destination | Delegated `/observability` route |
| `gen_ai.agent.id` | Bot app client ID, matching the OAuth client's `azp` and cache key |
| Blueprint metadata | `agentBlueprintId` from registration |
| Caller | Teams user's Entra object ID |
| Channel | `msteams` |
| Request | Conversation ID and session ID present on the invocation request |
| Root | One `invoke_agent` for the agent turn |
| Children | `chat` for real model calls and `execute_tool` for real tool calls |
| Completion | Input and output messages recorded on the invocation |

`RecordOutputMessages` records the answer on the invocation while it is still open. `OutputScope`, whose operation is `output_messages`, is useful for a later delivery that happens after that scope closes; we don't add a second output operation for the same answer here.

The .NET chat middleware and LangChain instrumentors supply child spans, but framework and distro upgrades can change what they emit. Don't treat a root span alone as complete instrumentation. If inference or tool spans are absent, check the subscription/import order and confirm which operations the request actually performed. A turn without a tool call should have no `execute_tool` span; we don't need to add tools just for onboarding. For the educational sample, a question that fetches a Microsoft Learn page exercises both the model and a tool. Don't wrap the entire agent loop in an `InferenceScope` just to manufacture a `chat` row.

> This exercise records prompts, answers and tool content, including console copies. Use synthetic questions and restrict access to the logs. Review sensitive-data capture and retention before using real tenant content; switching off framework capture doesn't remove the explicit input/output recording in our wrappers.

The cache is partitioned by agent and tenant, matching the exporter's contract, and is refreshed on authenticated turns. The per-turn caller is recorded on the span. Don't reuse this cache as a Work IQ token store: downstream business tools need the token for the particular user and resource.

## Phase 3: Work IQ

### Step 3-1. Choose servers and complete consent manually

We can prepare the Work IQ catalog and grants without changing the working observability path:

```powershell

```

Read the current server names, audiences and scopes. Use the exact catalog names in the next command; Mail and Calendar commonly appear as follows:

```powershell
a365 develop add-mcp-servers "mcp_MailTools" "mcp_CalendarTools" --project-path .

```

Use our registered agent name in the permissions command. The first command writes `ToolingManifest.json`, the second configures the tenant grants and may print an administrator consent handoff, and the third lists what we selected. None of these commands edits the agent or registers runtime tools with its model.

### Step 3-2. Keep the runtime boundary explicit

A tooling manifest and consent describe which Work IQ servers the agent may access. Runtime integration also needs authenticated server discovery, MCP connections and registration of the returned tools with the agent's model or orchestration framework.

The .NET and Node.js Work IQ extensions take an Agents SDK turn and authorization handler, but they also need the correct discovery identity, compatible MCP package versions and a token for each tool resource. A Python LangChain MCP client needs code to consume the selected servers; the manifest alone doesn't configure it. In all three cases, our `oboConnectionProfile` is scoped only to observability and must not be reused as a Mail or Calendar credential.

This guide covers server selection and consent, not the runtime Work IQ integration. Keep our existing tools while completing observability. If our agent already integrates Work IQ, verify its discovery and delegated access separately; if we need to add that integration, follow the [Agent 365 tooling documentation](https://learn.microsoft.com/microsoft-agent-365/developer/). The optional educational sample uses only Microsoft Learn tools until we add runtime Work IQ support.

If discovery returns a service error, record the HTTP status, request/correlation ID and resource name for the administrator or support team. Don't disable authentication, probe with fabricated identities, downgrade the working model stack or claim that an email was sent based only on a tooling manifest.

## Troubleshooting

The [cross-scenario troubleshooting guide](../../03-references/Troubleshooting.md) covers missing activity, token and identity mismatches, and channel credentials overwritten during setup. Use it alongside the manual checks below.

| Symptom | What to check |
| --- | --- |
| Teams stops answering after setup | Restore the bot credentials and audience from Phase 0; the blueprint cannot replace the channel app |
| `AADSTS82001` on a channel reply | The service connection is using an agentic blueprint instead of the ordinary bot app |
| Unsigned POST reaches the model | .NET endpoint authorization or the Python/Node JWT middleware is missing; remove public access until authentication is fixed |
| OAuth never starts or token is empty | The instrumented route's sign-in handler list is missing or doesn't match the configured handler |
| Python says the auth handler isn't configured | Include `TYPE=UserAuthorization` and use the uppercased handler name in both calls |
| Node logs an undefined app ID | Check the connection name and configuration loading before SDK imports |
| Connection test fails with redirect mismatch | Use the Bot Service redirect URI on the bot app's Web platform, not the tunnel |
| Export returns `401 InvalidAudience` | The OAuth connection must request the named Observability API scope |
| Export returns 403 | Check delegated consent and that export ID, token client and cache key all name the bot app |
| Export partitions into zero identity groups | Baggage isn't active around the model call |
| Export partitions into two identity groups | The baggage agent ID and `AgentDetails` agent ID differ |
| Only root spans arrive | Check .NET processor/source registration, or Python/Node initialization before model imports; Node ESM needs the distro loader on its entry point |
| Caller doesn't resolve in the admin center | Use `aadObjectId`, not the channel-local user ID or a fabricated email |
| HTTP 200 but no tenant activity | Check Agent 365 licensing, the root invocation/request, ingestion delay and the selected tenant |
| Final traces disappear on exit | Stop normally so the provider flushes; forced process termination can lose buffered spans |
| Work IQ server appears in the manifest but no tool runs | Check runtime discovery, MCP connection and tool registration; Phase 3 adds catalog configuration and consent only |

## Wrapping up

Our Teams agent now has an Agent 365 registration and telemetry we can follow through a request, while Azure Bot Service remains responsible for the channel and the user's OAuth exchange. We kept the agent's model, tools and application behavior, and added identity and observability at the host and turn boundaries.

On this custom engine OBO route, the token names the bot app, so the export ID and cache key must use that app too; the blueprint belongs in the governance metadata. Phase 3 adds Work IQ server selection and grants, while runtime tool access needs its own integration. If we used the educational sample, apply the same integration points to our own agent, retaining its hosting, secret management and state isolation.
