# Step-by-Step Guide: Teams Agent with Custom Engine OBO (Manual Path)

> **Scenario**: Onboarding a Teams-hosted custom engine agent into Microsoft Agent 365, entirely by hand
> **Platform**: Microsoft Agent 365 · Azure Bot Service · Microsoft Entra ID · OpenTelemetry
> **Stacks**: .NET Agent Framework · Python + LangChain · Node.js + LangChain
> **Target Readers**: Agent developers, Azure and Entra administrators
> **Last Updated**: February 2026

## Introduction

We're going to take a **custom engine agent** that already lives in Microsoft Teams and onboard it into Microsoft Agent 365.

By custom engine agent we mean an agent you built yourself, with your own reasoning loop and your own model, reached through an Azure Bot registration that carries messages between the user and Teams or Microsoft 365 Copilot. It runs inside the Microsoft 365 ecosystem and yet tells the organization nothing about what it does. There is no record of which user asked what, which tools were called, or which data was touched.

Agent 365 turns that black box into something governed. It gives the agent a registered identity, publishes its activity to Microsoft Defender, Microsoft Purview and the Microsoft 365 admin center, and opens a controlled path to Microsoft 365 data.

This guide is the **manual path**. Its sibling, [3.Runbook.md](3.Runbook.md), does most of the same work by asking an AI coding assistant to edit your project through the [Agent 365 Skills](https://github.com/microsoft/agent365-skills). That route is quicker when it fits. It also assumes you have GitHub Copilot, Claude Code or something comparable, that you may point it at your codebase, and that you are willing to review a large generated diff. 

So here every command is typed and every line of code is written by you. There are no prompts anywhere below, and nothing assumes an assistant is running.

If you've read the [web app scenario](../Web-App-Agent-User-OBO/3.Runbook-Manual.md), this one will feel inverted. There we hand-wrote a two-hop token exchange and the configuration was thin. Here the Bot Framework Token Service performs the on-behalf-of exchange for us, so there is very little token code and a great deal of configuration. Almost all the difficulty lives in Azure Bot Service, and it surfaces as HTTP status codes during a turn instead of as build errors.

### This guide does not assume you use our sample

The repository ships three starting points, and you're welcome to use one. But most people arriving here already have an agent they want to onboard, so the guide is written for that case.

Every step that touches code is therefore built in two parts. First, **what the step needs from your agent**, expressed as a contract: the thing your code must already do, or the place the new code has to go. Second, **how that looks in the sample**, as a worked example you can pattern-match against. If your agent satisfies the contract, treat the example as reference material.

The guide does assume the shape below. These four are what "custom engine agent in Teams" means, so they hold for any agent of that shape:

| Assumption | Why it's load-bearing |
| --- | --- |
| Your agent is hosted on the **Microsoft 365 Agents SDK** | The token in Phase 2 comes from the SDK's authorization layer. Without it there is no `TurnContext` to ask |
| It exposes **`POST /api/messages`** | The Azure Bot resource delivers there, and the SDK's adapter listens there |
| It has **its own Azure Bot registration** | This is what makes it a *custom engine* agent rather than an AI Teammate, and it decides which identity your telemetry is attributed to |
| There is **one place where a turn begins and ends** | That's where the baggage scope and the spans go. A message handler, usually |

If your agent is hosted some other way, on a raw web framework with your own JWT validation, say, this scenario is the wrong one. The token acquisition here has no meaning outside the Agents SDK. Consider the [web app scenario](../Web-App-Agent-User-OBO/3.Runbook-Manual.md) instead, which builds the token chain by hand and assumes nothing about your host.

## Read this before you touch anything

Two facts will cost you an afternoon each if you meet them by surprise.
### `a365 setup all` overwrites your bot credentials

The setup command in Phase 1 rewrites the bot channel credentials in your configuration with the blueprint's, and it replaces the bot secret **in place**. The original secret is not recoverable afterwards.

Back them up now, outside the repository:

```powershell
# Python and Node.js
Copy-Item .env "$env:USERPROFILE\bot-credentials-backup.env"

# .NET: record the ClientId and ClientSecret from user-secrets somewhere safe
dotnet user-secrets list > "$env:USERPROFILE\bot-credentials-backup.txt"
```

Step 1-3 restores them, and it is not an optional step.

### The bot app and the blueprint must stay separate

Once you notice you're managing two app registrations, it's tempting to collapse them and let the blueprint be the bot. It cannot be, for two independent reasons:

- Entra bars agentic applications from obtaining client-credentials tokens, which fails as `AADSTS82001`, so a blueprint can never sign the outbound Bot Framework replies.
- It's also the wrong audience for validating the inbound token from Teams.

Keep them as two identities. Everything below depends on that separation, and a third identity, the agent identity, arrives in Phase 1 to make three.

## Prerequisites

Three kinds: tools on your machine, licences in your tenant, and permissions on your account.

### The tools you need on your machine

| Requirement | Minimum | Check it with | What needs it |
| --- | --- | --- | --- |
| .NET SDK | 8.0 for the CLI, 10.0 for the .NET sample | `dotnet --version` | The A365 CLI itself, and .NET agents |
| Agent 365 CLI | latest | `a365 --version` | Phases 1 and 3 |
| Azure CLI | latest | `az version` | The bot resource and its OAuth connections |
| PowerShell | 7.0 | `pwsh --version` | Consent scripts and packaging |

| uv | latest | `uv --version` | Python agents only |
| Node.js | 20.10 | `node --version` | Node.js agents only |

> **You need the .NET 8 SDK even if your agent is written in Python or TypeScript**, because the Agent 365 CLI is distributed as a .NET global tool. It has nothing to do with the language your agent is written in. The .NET sample in this repository targets `net10.0`, so that stack wants the .NET 10 SDK for the agent itself.

Install the CLI, or update it if you installed it a while ago, because it moves quickly:

```bash
dotnet tool install --global Microsoft.Agents.A365.DevTools.Cli
dotnet tool update --global Microsoft.Agents.A365.DevTools.Cli
a365 --version
```

If `a365` isn't found afterwards, the global tools directory isn't on your `PATH`. Add `%USERPROFILE%\.dotnet\tools` on Windows or `$HOME/.dotnet/tools` on macOS and Linux, then open a new terminal.

Then sign in to the tenant you'll register the agent in:

```bash

az account show --query "{user:user.name, tenantId:tenantId}" -o json
```

Read the second command's output and confirm the tenant is the one you meant. You do need a subscription for the Azure Bot resource itself, which is a separate matter and covered in Phase 0.

## Phase 0: Get the agent answering in Teams first

Before adding anything, the agent has to work in Teams exactly as it is. Phase 2 introduces a token, an exporter and a set of spans, and debugging those on top of a channel that was never delivering is miserable.

**If your agent already answers in Teams**, treat this phase as a checklist. By the end of it you need six things, and Phase 1 onwards refers to all of them by these names:

| What | Where it comes from |
| --- | --- |
| The **bot app client id** | The Entra app registration behind your Azure Bot |
| The **bot app secret** | The same registration |
| Your **tenant id** | The same registration's overview page |
| An **Azure Bot resource** with the Teams channel enabled | Azure portal |
| A **messaging endpoint** reaching your agent's `/api/messages` | The bot resource's configuration |
| An **app package installed in Teams** | Sideloaded, or already published |

If you have all six, skip to Phase 1.

### Step 0-1. Create the bot's app registration

This is the identity the agent uses to authenticate the replies it sends back to the channel.

> ⚠️ **This is the "bot app" from the warning above.** It is not the Agent 365 blueprint, which doesn't exist yet. When it arrives in Phase 1 the two must stay separate, so name this one in a way that makes its role obvious.

1. Go to the [Microsoft Entra admin center](https://entra.microsoft.com) and open **Identity → Applications → App registrations**.
2. Click **New registration**.
3. For **Name**, use something recognisable such as `learn-agent-bot`.
4. Under **Supported account types**, choose **Accounts in this organizational directory only (Single tenant)** unless you specifically need cross-tenant.
5. Leave **Redirect URI** empty. A bot doesn't use one.
6. Click **Register**.

On the **Overview** page, copy two values:

| Value on the Overview page | What this guide calls it |
| --- | --- |
| **Application (client) ID** | The **bot app client id** |
| **Directory (tenant) ID** | Your **tenant id** |

Then create the secret:

1. Open **Certificates & secrets**.
2. On the **Client secrets** tab, click **New client secret**.
3. Give it a description and an expiry, then click **Add**.
4. **Copy the `Value` column immediately**, not the `Secret ID`. It is shown once, and if you navigate away you'll have to delete the secret and make another.

That secret is the one `a365 setup all` overwrites in Phase 1, which is what the warning at the top was about.

From the CLI instead:

```bash
az ad app create --display-name "learn-agent-bot" --sign-in-audience AzureADMyOrg
az ad app credential reset --id <bot-app-client-id> --append
```

`az ad app create` prints the registration as JSON, and its `appId` is the bot app client id. The second command prints the secret, and again that output is the only time you see it.

### Step 0-2. Create the Azure Bot resource

The app registration is an identity and knows nothing about Teams. The **Azure Bot** resource connects that identity to the messaging channels and holds the endpoint Teams delivers to.

1. Go to the [Azure portal](https://portal.azure.com), search the marketplace for **Azure Bot**, and click **Create**.
2. Fill in the **Basics** tab:

| Field | What to put |
| --- | --- |
| Bot handle | A globally unique name, such as `learn-agent-bot-<yourname>` |
| Subscription / Resource group | Wherever you like; create a resource group if in doubt |
| Data residency | Global, unless your organization requires otherwise |
| Pricing tier | F0 (Free) is plenty here |
| Type of App | Single Tenant, matching Step 0-1 |
| Creation type | **Use existing app registration** |
| App ID | The bot app client id from Step 0-1 |
| App tenant ID | Your tenant id from Step 0-1 |

3. Click **Review + create**, then **Create**.

> **Choose "Use existing app registration", not "Create new".** Letting Azure create one leaves you with a registration whose secret you never saw, and you need that secret in Step 0-5. It's recoverable, since you can add a new secret to whichever app it made, but it's an avoidable detour.

From the CLI:

```bash
az bot create \
  --resource-group <resource-group> \
  --name <bot-handle> \
  --app-type SingleTenant \
  --appid <bot-app-client-id> \
  --tenant-id <tenant-id> \
  --sku F0
```

Then enable the Teams channel:

1. In the bot resource, open **Channels**.
2. Click **Microsoft Teams**, accept the terms, and click **Apply**.
3. Confirm **Microsoft Teams** appears in the connected channels list.

Without this, everything else can be perfectly configured and Teams still refuses to route messages to your agent.

### Step 0-3. Start a dev tunnel

The bot resource needs somewhere to deliver messages, and `localhost` means nothing to a cloud service. A dev tunnel gives you a public HTTPS URL forwarding to your machine.

If this is your first time, sign in once:

```bash
devtunnel user login
```

Then host the tunnel on whichever port your agent listens on. The samples here use 3978, which is the Bot Framework convention:

```bash
devtunnel host -p 3978 --allow-anonymous
```

The output includes a line like `Connect via browser: https://abc123-3978.euw.devtunnels.ms`.

> **Read the URL from the command output rather than constructing it.** Dev tunnel URLs look predictable and are not derived from the tunnel name. Keep that terminal open for the rest of the guide, because closing it kills the URL.

If your agent listens on a different port, use that port here and everywhere below that says 3978.

### Step 0-4. Point the bot at the tunnel

1. Go back to your bot in the [Azure portal](https://portal.azure.com).
2. Under **Settings**, click **Configuration**.
3. In **Messaging endpoint**, enter your tunnel host followed by `/api/messages`, so for the example above `https://abc123-3978.euw.devtunnels.ms/api/messages`.
4. Click **Apply** and wait for the confirmation.

Three things to get right:

- **The `/api/messages` path is required.** The tunnel host alone isn't an endpoint; the Agents SDK listens on that specific path.
- **It has to be `https`.** The Bot Service will not deliver to an unencrypted endpoint.
- **No trailing slash and no port number.** The tunnel already maps to your local port.

From the CLI:

```bash
az bot update \
  --resource-group <resource-group> \
  --name <bot-handle> \
  --endpoint "https://<tunnel-host>/api/messages"
```

> Restarting the dev tunnel can give you a new URL, and the messaging endpoint has to be updated to match. When the agent stops answering in Teams after a break, check this first.

### Step 0-5. Give the agent its bot credentials

**What this step needs from your agent.** It has to authenticate the replies it sends back to the channel, which means the Agents SDK needs three values: the bot app client id, its secret, and the tenant id. The SDK reads them from a connection it calls `ServiceConnection`, and it reads them from configuration rather than from your code. Separately, the SDK validates the inbound token from Teams, and the expected audience is that same client id.

If your agent is already answering in Teams, this is all configured and you can move on. What matters for later is knowing *where* those values live in your project, because Phase 1 overwrites them and Step 1-3 puts them back.

**These are the values to back up before Phase 1.** Copy them somewhere outside the repository now, while they're in front of you.

#### .NET

In `appsettings.json`. The client id goes in two places, because one validates inbound tokens and the other authenticates outbound replies:

```jsonc
"TokenValidation": {
  "Audiences": [ "<bot-app-client-id>" ]
},
"Connections": {
  "ServiceConnection": {
    "Settings": {
      "ClientId": "<bot-app-client-id>",
      "TenantId": "<tenant-id>"
    }
  }
}
```

The secret never goes in that file, which is committed. Put it in user secrets:

```powershell
dotnet user-secrets set "Connections:ServiceConnection:Settings:ClientSecret" "<bot-app-secret>"
```

> An empty `TokenValidation.Audiences` is what puts an agent into anonymous mode, where it accepts unauthenticated calls. That's convenient for local testing with the Agents Playground and wrong for anything Teams delivers to.

#### Python

In `.env`, copied from the committed `.env.example`:

```bash
CONNECTIONS__SERVICE_CONNECTION__SETTINGS__CLIENTID=<bot-app-client-id>
CONNECTIONS__SERVICE_CONNECTION__SETTINGS__CLIENTSECRET=<bot-app-secret>
CONNECTIONS__SERVICE_CONNECTION__SETTINGS__TENANTID=<tenant-id>
```

The SDK parses these by splitting on the double underscore, so each segment becomes one level of a nested configuration dictionary. `load_configuration_from_env` keeps only the `AGENTAPPLICATION`, `CONNECTIONS` and `CONNECTIONSMAP` branches, which is why unrelated environment variables in the same file are ignored rather than rejected.

#### Node.js

Also in `.env`, with a different spelling of the same three keys:

```bash
Connections__ServiceConnection__Settings__ClientId=<bot-app-client-id>
Connections__ServiceConnection__Settings__ClientSecret=<bot-app-secret>
Connections__ServiceConnection__Settings__TenantId=<tenant-id>
```

> **Don't copy the Python spelling across.** The JavaScript SDK parses these as `Connections__<id>__Settings__<property>` and splits on the double underscore, so the connection id has to be a single segment: `ServiceConnection`, not `SERVICE_CONNECTION`. A key with an extra separator is discarded without an error, so you get a server that starts cleanly, logs `for appId undefined`, and refuses every message Teams sends it.

There's a second ordering trap on Node. The Agents SDK reads these variables while `@microsoft/agents-hosting` is being *imported*, not when the server starts, so `.env` has to be loaded before that import runs. ES module imports are all evaluated before any of the importing module's own statements, which means a `dotenv.config()` call in the body of `main.ts` executes far too late. The fix is a one-line module that does nothing but load the environment, imported first:

```typescript
// src/env.ts
import "dotenv/config";
```

That module exists only to be imported first. Nothing else goes in it, because anything that pulls in the SDK would defeat the purpose:

```typescript
// src/main.ts. This import must stay first.
import "./env.js";

import { AgentApplication, MemoryStorage, TurnContext, TurnState } from "@microsoft/agents-hosting";
```

The symptom when that order slips is the same quiet `appId undefined` as the misspelled keys above, so check both together.

### Step 0-6. Configure the model

**What this step needs from your agent.** Somewhere to reason. If your agent already answers questions, this is done and you can skip the step entirely. The samples use Azure OpenAI and read an endpoint, a deployment name and the tenant that owns the resource.

> **Don't leave the tenant id out if you work across more than one tenant.** Without it the credential returns a token from whichever tenant you last signed in to, which may not own the Azure OpenAI resource, and the service answers `HTTP 400` with "Tenant provided in token does not match resource token". It reads like a code problem and isn't.

#### .NET

In `appsettings.json`:

```jsonc
"AzureOpenAI": {
  "Endpoint": "https://<your-resource>.openai.azure.com/",
  "Deployment": "<your chat deployment name>",
  "TenantId": "<tenant that owns the Azure OpenAI resource>"
}
```

#### Python

In `.env`:

```bash
AZURE_OPENAI_ENDPOINT=https://<your-resource>.openai.azure.com
AZURE_OPENAI_DEPLOYMENT=<your chat deployment name>
AZURE_OPENAI_API_VERSION=2024-10-21
AZURE_OPENAI_TENANT_ID=<tenant that owns the Azure OpenAI resource>
```

#### Node.js

The same four settings, in `.env`:

```bash
AZURE_OPENAI_ENDPOINT=https://<your-resource>.openai.azure.com/
AZURE_OPENAI_DEPLOYMENT=<your chat deployment name>
AZURE_OPENAI_API_VERSION=2024-10-21
AZURE_OPENAI_TENANT_ID=<tenant that owns the Azure OpenAI resource>
```

`AZURE_OPENAI_DEPLOYMENT` has no default in the Node sample, and `src/config.ts` throws at startup when it's missing, because a guessed deployment name fails later with an error pointing at the wrong place.

---

All three samples then choose between two ways of authenticating to the model, based on whether a key is configured:

|  | **Path A: Entra credentials** *(default, recommended)* | **Path B: API key** |
| --- | --- | --- |
| What it uses | `DefaultAzureCredential` on .NET, `AzureCliCredential` on Python and Node.js, and a managed identity once hosted on Azure | A resource key, sent as a bearer secret |
| Extra configuration | None; you just need to be signed in | The key, kept out of tracked files |
| What you need access to | The **Cognitive Services OpenAI User** role on the resource | The resource keys |
| Why you'd pick it | No long-lived secret, and it's the only option where key auth is disabled by policy | Environments that still depend on keys |

For Path A, sign in and make sure no key is set anywhere, including user secrets:

```bash
az login --tenant <tenant of the Azure OpenAI resource>
```

Once hosted on Azure, .NET picks up the assigned managed identity automatically. Python and Node.js each need `AZURE_OPENAI_USE_MANAGED_IDENTITY=true`.

For Path B, keep the key outside committed files:

```bash
# .NET
dotnet user-secrets set "AzureOpenAI:ApiKey" "<key>"

# Python and Node.js, in the gitignored .env
AZURE_OPENAI_API_KEY=<key>
```

Start the agent so it listens on the port the tunnel forwards to.

#### .NET

```bash
dotnet run
```

#### Python

```bash
uv run python -m app.main
```

#### Node.js

```bash

```

**What this step needs from your agent.** Teams doesn't discover bots; it installs *apps*. An app is a zip containing a manifest and two icons, and the manifest has to point at your bot app client id. If your agent is already installed in Teams you can skip the rest of this step.

Two identifiers appear in that manifest and they are unrelated:

- The **bot id**, which is your bot app client id, tells Teams which bot to route messages to.
- The **Teams app id** identifies the app package itself. It corresponds to nothing in Entra or Azure. Teams uses it to decide whether an upload is an update to an app you already installed or a brand new one, so it needs to stay stable across rebuilds, otherwise every build leaves another copy of the agent in your app list.

Each sample ships a script that fills in both and builds the zip:

```powershell
./build-app-package.ps1 -BotId <bot-app-client-id>
```

It generates a Teams app id on the first build and caches it in `teams-app-id.local.json` next to the script, reading it back on later builds. That file matches the repository's `.gitignore` pattern for `*.local.json`, so it stays on your machine. Because each sample keeps its own cache file, the three stacks get different Teams app ids automatically, which is what lets you install more than one of them in the same tenant.

If you already have a Teams app id, pass it explicitly:

```powershell
./build-app-package.ps1 -BotId <bot-app-client-id> -TeamsAppId <existing-teams-app-id>
```

One part of the manifest matters later, in Step 2-1, so it's worth looking at now:

```jsonc
"webApplicationInfo": {
  "id": "${{BOT_ID}}",
  "resource": "api://botid-${{BOT_ID}}"
}
```

That `resource` value is the audience Teams issues its single sign-on token for. The OAuth connection we create in Phase 2 has to declare exactly the same string, and when it does, the user is never prompted to sign in a second time. If your own manifest uses a different resource, note it down now and use yours rather than ours in Step 2-1.

Then sideload the package:

1. Open Microsoft Teams and go to **Apps** in the left rail.
2. Click **Manage your apps**, then **Upload an app**.
3. Choose **Upload a custom app** and select `appPackage.zip`.
4. Click **Add**.

> If **Upload a custom app** isn't there, custom app uploading is disabled for your account, and a Teams administrator has to enable it. That's the "Teams app upload permission" from the prerequisites.

Because the manifest declares `copilotAgents.customEngineAgents` and includes `copilot` in the bot's scopes, the same package also surfaces the agent inside Microsoft 365 Copilot.

### Step 0-8. Verify

Message the agent in Teams:

```text
What is Microsoft Entra Conditional Access?
```

You should get an answer. If nothing comes back, the problem is nearly always in the plumbing rather than the agent:

| What you see | Where to look |
| --- | --- |
| No reply, and nothing in the agent's console | The messaging endpoint is wrong, or the tunnel died. Steps 0-3 and 0-4 |
| The agent logs a request but Teams shows an error | The bot credentials don't match the app registration. Step 0-5 |
| `401` in the agent's console | `TokenValidation.Audiences` doesn't contain the bot app client id on .NET, or the connection keys aren't being read at all on Node.js. Step 0-5 |
| `for appId undefined` on Node.js | The `Connections__…` keys are misspelled, or `.env` is loaded after the SDK import. Step 0-5 |
| It works in the Agents Playground but not in Teams | The Teams channel isn't enabled on the bot. Step 0-2 |
| `404 DeploymentNotFound` on the first question | The chat deployment doesn't exist on your resource. Step 0-6 |

✅ **Checkpoint.** The agent answers in Teams, and there is no Agent 365 anything yet.

## Phase 1: Register the agent

Now the agent becomes an object in your tenant, visible to the people who govern it.

Registration creates two things: a **blueprint**, the parent app registration that holds the permissions, and an **agent identity**, a child principal of that blueprint. Neither replaces your bot app registration. All three coexist, and Phase 2 gets much easier once you can tell them apart:

| Identity | Created by | What it does here |
| --- | --- | --- |
| **Bot app** | You, in Step 0-1 | Authenticates the channel, signs outbound replies, and **is the identity your telemetry is attributed to** |
| **Blueprint** | `a365 setup all` | Holds the permissions, and represents the agent in the tenant inventory |
| **Agent identity** | `a365 setup all` | A child principal of the blueprint. On this path it does **not** carry the telemetry |

That third row is the one that surprises people coming from the web app scenario, where the agent identity is exactly what telemetry is attributed to. Step 2-3 explains why this path is different.

Nothing in this phase depends on your stack.

### Step 1-1. Back up your bot credentials

Do this before anything else. These are the values from Step 0-5: the bot app client id, its secret and the tenant id. The next step overwrites them, and the secret cannot be recovered afterwards.

If you skipped ahead and already ran setup, create a new secret on the bot app registration in Entra and use that from here on.

### Step 1-2. Register the blueprint and the agent identity

Run this from your agent's project folder, because the CLI writes its output file there. Run the dry run first and read it:

```bash
a365 setup all --agent-name "my-agent" --m365 --authmode obo --dry-run
a365 setup all --agent-name "my-agent" --m365 --authmode obo
```

Three flags, and each earns its place:

`--agent-name` is the base name everything else derives from. The CLI creates an app registration called `<name> Blueprint` and an identity called `<name> Identity`, so remember that when you go looking for the blueprint later and type the bare name into a search box.

`--m365` registers the agent for Teams and Microsoft 365 Copilot. It is not optional in this scenario. Omit it and the agent registers as though it had no messaging surface, which fails later in a place that gives you no clue this was the cause.

`--authmode obo` gives the agent identity principal-scoped delegated grants. It's the default, and we pass it explicitly because a command you paste into a runbook should say what it means.

Then grant the permissions. These are two separate commands, and the order matters:

```bash
a365 setup permissions mcp --agent-name "my-agent"
a365 setup permissions bot --agent-name "my-agent"
```

`a365 setup permissions bot` is the Messaging Bot API grant, and it is a **required follow-up to `--m365`**. The CLI's own help lists MCP permissions as its prerequisite, which is why `mcp` runs first even if you have no intention of using Work IQ. Skipping the bot grant is easy, because nothing fails immediately when you do.

Both need tenant-wide consent. If you're not a Global Administrator the CLI doesn't fail; it prints a `/v2.0/adminconsent` URL to forward to someone who is.

**How to verify.** Open `a365.generated.config.json` in your editor and confirm it has an `agentBlueprintId`. Then go to [Entra](https://entra.microsoft.com) → **App registrations** and check the blueprint is listed.

Keep that file open. Phase 2 needs two values from it:

| Field | What it is |
| --- | --- |
| `agentBlueprintId` | The blueprint's app id, used for the blueprint roll-up in reporting |
| `agentIdentityClientId` | The agent identity's app id. Present, and **not** what telemetry is attributed to on this path |
| The Agent User Id | Needed only if you do Phase 3. It's what the Work IQ extension exchanges tokens for |

## Phase 2: Observability

Now we make the agent report what it does. By the end, every message it handles produces telemetry attributed to the Teams user who sent it.

The shape of this phase is different from the web app scenario. We are not writing a token chain. We configure an OAuth connection on the Azure Bot resource, and the Bot Framework Token Service performs the on-behalf-of exchange for us. The code is small: one call to fetch a token, a baggage scope, and the semantic spans. The configuration around it is where the care goes.

Five things have to be true at once for a span to arrive. When something doesn't work in Step 2-8, it is nearly always one of these:

| Requirement | What happens when it's missing |
| --- | --- |
| The OAuth connection asks for the **named** observability scope | `401 InvalidAudience` on export |
| The exporter is switched on, not merely registered | Spans are enriched and then dropped |
| `gen_ai.agent.id` is the **bot app client id** | `HTTP 403` on export |
| A baggage scope is open around the whole turn, agreeing with `AgentDetails` | `Partitioned into 0 identity groups`, or `2` and half the spans vanish |
| A root `invoke_agent` span exists, carrying the caller's directory object id | Defender shows orphans, or the admin center shows activity attributed to nobody |

### Step 2-1. Create the OAuth connection

This is the piece that replaces the entire two-hop token chain from the web app scenario. It's one command, and every argument in it does real work:

```bash
az bot authsetting create -g <resource-group> -n <azure-bot-name> \
  -c oboConnectionProfile \
  --client-id <bot-app-client-id> --client-secret <bot-app-secret> \
  --service AadV2 \
  --provider-scope-string \
    "api://9b975845-388f-4429-889e-eab1ef63949c/Agent365.Observability.OtelWrite" \
  --parameters tenantID=<tenant-id> tokenExchangeUrl=api://botid-<bot-app-client-id>
```

Going through the parts that matter:

**`-c oboConnectionProfile`** names the connection. You'll repeat this name in configuration in Step 2-5, and the two have to agree exactly. Any name works as long as you're consistent.

**`--provider-scope-string` has to be the named scope**, exactly as written. The GUID is not your tenant or your agent; it's the fixed app id of the Agent 365 Observability API, so it's the same for everyone. Reaching for `/.default` out of habit produces a token the export endpoint rejects with `401 InvalidAudience`, because a delegated token carries scopes rather than roles.

**`--client-id` is the bot app registration, not the blueprint.** This is what makes the `azp` claim on the resulting token the bot app, which Step 2-3 explains is the whole basis of this path.

**`tokenExchangeUrl` keeps Teams single sign-on silent.** It has to match the `webApplicationInfo.resource` value in your Teams manifest, which we looked at in Step 0-7. When they agree, the user is never asked to sign in a second time. When they disagree, the agent works and interrupts the user with a sign-in card on every conversation.

> The resource id `9b975845-…` and the scope name are preview-era values. Re-verify them against current documentation before assuming they're still right.

**How to verify.** List the connection back and confirm the scope survived:

```bash
az bot authsetting show -g <resource-group> -n <azure-bot-name> -c oboConnectionProfile
```

The Azure portal also has a **Test connection** button on the connection, under **Configuration → OAuth Connection Settings**. Use it now: it exercises the connection interactively and tells you whether the scope and the client credentials work, without involving your agent at all.

### Step 2-3. Work out which agent id to use

This is the step that most distinguishes this scenario. Get it wrong and the export returns `HTTP 403`, which reads like a permissions problem when the cause is an identifier.

Three values have to be identical:

```text
gen_ai.agent.id  ==  the token's azp claim  ==  the id in the export route
```

On a custom engine agent, all three are the **bot app registration's client id**. Not the agent identity, and not the blueprint, even though Phase 1 just created both of those.

The reason follows from where the token comes from. The OAuth connection in Step 2-1 was configured with the bot app's credentials, so the token the Bot Framework Token Service hands back says the bot app is the authorized party. The service checks that claim against the id in the export route, and rejects the request when they disagree. A Teams turn carries no agentic identity, so the agent has no credential with which to make itself the `azp` instead.

This came out of testing against the live service. One token, three candidate ids:

| Id used in the export route | Result |
| --- | --- |
| Agent identity | `403` |
| Blueprint | `403` |
| **Bot app registration** | `415` |

A `415` there is the pass. It means authorization succeeded and only the content type of the probe was wrong.

**What this step needs from your agent.** A single configuration value holding the bot app client id, read from one place. The safest source is the SDK's own connection settings, which you already filled in during Step 0-5, because duplicating the id under a new name gives you two values that can drift apart.

#### .NET

```csharp
var observabilityAgentId = builder.Configuration["Connections:ServiceConnection:Settings:ClientId"]
    ?? throw new InvalidOperationException("The bot app client id is not configured.");
```

#### Python

Read it from the same environment variable the SDK uses, as a property on your settings object:

```python
@property
def observability_agent_id(self) -> str:
    value = os.environ.get("CONNECTIONS__SERVICE_CONNECTION__SETTINGS__CLIENTID", "").strip()
    if not value:
        raise RuntimeError("The bot app client id is not configured.")
    return value
```

#### Node.js

```typescript
observabilityAgentId: required("Connections__ServiceConnection__Settings__ClientId"),
```

Adding an SDK key to your own settings object is a little unusual, since `src/config.ts` otherwise keeps the SDK's keys out of it. It's the lesser of two evils: the alternative is a second copy of the same client id under a different name, and the day somebody updates one and not the other you get a `403` with nothing to point at.

### Step 2-5. Configure the auth handler

**What this step needs from your agent.** The Agents SDK has to know that a named auth handler exists and which OAuth connection backs it. This is configuration rather than code, and the handler id you choose here is the string you'll pass when asking for the token in Step 2-7.

The key path is the same across all three SDKs, with different casing conventions. The middle segment, `obo` below, is the handler id: name it whatever you like as long as every reference agrees.

#### .NET

In `appsettings.json`, inside the existing `AgentApplication` section:

```jsonc
"AgentApplication": {
  "UserAuthorization": {
    "Default": "obo",
    "AutoSignIn": true,
    "Handlers": {
      "obo": {
        "Settings": {
          "AzureBotOAuthConnectionName": "oboConnectionProfile"
        }
      }
    }
  }
}
```

`Handlers` and `Settings` are capitalised, because the SDK binds this section by property name and the JSON has to match. `Default` names the handler used when a caller doesn't name one; it's spelled `DefaultHandlerName` if you bind `UserAuthorizationOptions` directly at the root instead of nesting it under `AgentApplication` as we do here. We always name the handler explicitly below, so nothing here depends on that key.

#### Python

In `.env`:

```bash
AGENTAPPLICATION__USERAUTHORIZATION__HANDLERS__OBO__SETTINGS__AZUREBOTOAUTHCONNECTIONNAME=oboConnectionProfile
```

The SDK splits these on the double underscore into a nested dictionary, so each segment above is one level. `load_configuration_from_env` keeps only the `AGENTAPPLICATION`, `CONNECTIONS` and `CONNECTIONSMAP` branches, and quietly ignores everything else in your environment.

> **On Python the handler id is case-sensitive, and the environment variable convention makes it uppercase.** The id here is `OBO`, taken verbatim from that segment, so the string you pass when asking for the token has to be `OBO` too. Ask for `obo` and you get `ValueError: Auth handler obo not recognized or not configured`. Node matches handler ids case-insensitively and .NET reads them from JSON where you control the casing, so this trap is specific to Python.

#### Node.js

In `.env`:

```bash
AgentApplication__UserAuthorization__handlers__obo__settings__azureBotOAuthConnectionName=oboConnectionProfile
```

Node matches handler ids case-insensitively, so the casing of the `obo` segment is up to you as long as you're consistent enough to read it later.

---

You don't need a `type` key on any of the three. All of them default a handler with no type to the Azure Bot OAuth variant, which is what we want here.

> **The connection name has to match Step 2-1 exactly.** A typo doesn't raise an error. It gives you a handler that resolves to nothing, an empty token, and an export that fails authentication for a reason pointing nowhere near this file.

### Step 2-6. Wire the exporter into the entry point

**What this step needs from your agent.** Four things, none of which depend on the file names below:

1. **A place that runs once at startup**, where the distro is initialised. On Python and Node it has to run *before* your LLM library is imported, because the distro instruments by patching those libraries as they load.
2. **A token store the exporter can read from a background thread.** The exporter flushes on its own loop, where there is no turn and no user, so it cannot fetch a token itself. It calls a resolver you supply, synchronously, with the agent id and the tenant id.
3. **Both exporter switches turned on**, not just the first.
4. **A flush on shutdown**, if your host exits on a signal.

The store is the piece most likely to be new code in your project. Its contract is small: `set(agentId, tenantId, token)` called during a turn, and a synchronous `get(agentId, tenantId)` returning the token or nothing, called by the exporter. Whatever you already use for short-lived caching is fine, as long as reads are safe from another thread and expired tokens come back as absent rather than stale.

> **Two switches, not one.** Enabling Agent 365 registers the span processor that enriches spans. Enabling the *exporter* is a separate flag, and it's the one that sends anything. Set only the first and your spans are enriched and then discarded, with no error to tell you.

The subsections below show all of this in the supplied samples. If you're bringing your own agent, expect the file names to differ while the ordering rules still hold.

#### .NET

In `Program.cs`. Put the `using` directives at the top with the others, because the file uses top-level statements and C# rejects a `using` after the first statement:

```csharp
using Microsoft.Agents.A365.Observability.Hosting.Caching;
using Microsoft.OpenTelemetry;
```

Then, before `builder.Build()`:

```csharp
var observabilityAgentId = builder.Configuration["Connections:ServiceConnection:Settings:ClientId"]
    ?? throw new InvalidOperationException("The bot app client id is not configured.");

var observabilityTokens = new ServiceTokenCache();
builder.Services.AddSingleton(observabilityTokens);

builder.UseMicrosoftOpenTelemetry(o =>
{
    o.Exporters = ExportTarget.Agent365 | ExportTarget.Console;

    // Exporting to Agent 365 alone suppresses infrastructure instrumentation, and the
    // HTTP spans are how you see the export request itself while debugging.
    o.Instrumentation.EnableAspNetCoreInstrumentation = true;
    o.Instrumentation.EnableHttpClientInstrumentation = true;
    o.Instrumentation.EnableAzureSdkInstrumentation = true;

    // The delegated route. UseS2SEndpoint stays false: the service-to-service endpoint
    // accepts application tokens only and refuses a delegated one.
    o.Agent365.UseS2SEndpoint = false;
    o.Agent365.TokenResolver = observabilityTokens.GetObservabilityToken;
});
```

`ServiceTokenCache` ships with the distro and fits this case: it holds a token string per agent and tenant, expires entries itself, and its `GetObservabilityToken` method matches the resolver delegate's signature, so you hand the method over instead of wrapping it in a lambda.

> **Use `ServiceTokenCache`, not `AgenticTokenCache`.** They sit in the same namespace and the names are close enough to grab the wrong one. `AgenticTokenCache` expects an `AgenticTokenStruct` built from an agentic turn, which is the AI Teammate path. `ServiceTokenCache` takes a token you already hold, which is our situation.

Drop `ExportTarget.Console` once you're past Step 2-8, or keep it behind an environment check. It helps while you're learning to read the telemetry and turns into noise once you can.

#### Python

Create a module whose only job is to initialise the distro, `app/observability.py`:

```python
"""Initialises the Agent 365 distro. Must be imported before LangChain."""

from __future__ import annotations

from microsoft.opentelemetry import use_microsoft_opentelemetry

from app.token_store import token_store

use_microsoft_opentelemetry(
    # Registers the span processors that shape and enrich the spans.
    enable_a365=True,
    # And this is what actually ships them. Both are needed.
    a365_enable_observability_exporter=True,
    # Called as resolver(agent_id, tenant_id) on the exporter's worker thread.
    a365_token_resolver=token_store.get,
    # The delegated route. The S2S endpoint takes application tokens only.
    a365_use_s2s_endpoint=False,
    # Turn off the enrichers this agent doesn't use. See the note below.
    instrumentation_options={
        "openai_agents": {"enabled": False},
        "agent_framework": {"enabled": False},
        "semantic_kernel": {"enabled": False},
    },
    enable_sensitive_data=True,
    enable_console=True,
    disable_metrics=True,

```

> **If your agent uses LangChain, disable the enrichers you aren't using**, as above. There's a registration race: the Agent Framework enrichers register first, and their presence makes the distro skip the LangChain enricher, which is the one that maps this agent's messages and conversation id into the shape Agent 365 expects. You end up with `chat` spans that are technically fine and semantically empty. If your agent uses Agent Framework or Semantic Kernel instead, leave the corresponding entry enabled and disable the others.

Then make it the first import in `app/main.py`, above anything that pulls in your agent:

```python
import app.observability  # noqa: F401  # must precede the agent import below

from app.agent import LearnAgent
```

> **On Python, where this call happens decides whether it works at all.** The distro instruments LangChain and the Azure OpenAI SDK by patching them as they load, so it has to run before they're imported. Import them first and the patching silently finds nothing to attach to: no `chat` spans, an agent that answers perfectly, and LLM calls that are simply invisible.

> **A misspelled option is silently ignored.** `use_microsoft_opentelemetry` takes `**kwargs` and does not validate them, so `a365_token_resolvr` raises nothing. It leaves the resolver unset, the distro falls back to `DefaultAzureCredential`, and your OBO token is never used. If export fails on auth and the code looks right, check these names character by character.

You'll also need the small store the resolver reads from, `app/token_store.py`. It has to import nothing from the rest of your app, so that importing it from `observability.py` doesn't drag your agent in early:

```python
"""Holds the observability token so the exporter's background thread can read it."""

from __future__ import annotations

import threading
import time

# Treat the token as expired slightly early. One that lapses between the turn and the
# exporter's next flush stops the export with no visible error.
_SAFETY_MARGIN_SECONDS = 300


class ObservabilityTokenStore:
    def __init__(self) -> None:
        self._lock = threading.Lock()
        self._tokens: dict[tuple[str, str], tuple[str, float]] = {}

    def set(self, agent_id: str, tenant_id: str, token: str, expires_in: int = 3600) -> None:
        expires_at = time.monotonic() + max(expires_in - _SAFETY_MARGIN_SECONDS, 0)
        with self._lock:
            self._tokens[(agent_id, tenant_id)] = (token, expires_at)

    def get(self, agent_id: str, tenant_id: str) -> str | None:
        """The resolver the distro calls. Synchronous, on the exporter's worker thread."""
        with self._lock:
            entry = self._tokens.get((agent_id, tenant_id))

        if entry is None:
            return None

        token, expires_at = entry
        return token if time.monotonic() < expires_at else None


token_store = ObservabilityTokenStore()
```

`get` runs on the exporter's worker thread while `set` runs on the turn, so this dictionary is genuinely touched from two threads at once and needs the lock. And `get` is synchronous because that is what the distro expects: it calls the resolver without awaiting it, so an `async def` here would hand the exporter a coroutine object instead of a token.

#### Node.js

Node has the same two-switch design and the same load-order sensitivity as Python, but it's less forgiving, because moving a line up the file doesn't fix it. Create `src/observability.ts`:

        // The delegated route. The S2S endpoint takes application tokens only.

`enableSensitiveData` and `enableConsoleExporters` sit at the top level rather than inside the `a365` block, because they apply to the whole distro rather than to the Agent 365 exporter specifically.

Then make it the very first import in `src/main.ts`, above the one that loads `.env`:

```typescript
import "./observability.js";
import "./env.js";

import { AgentApplication, MemoryStorage, TurnContext, TurnState } from "@microsoft/agents-hosting";
```

> **Why a separate file rather than a call at the top of `main.ts`?** ES module imports are hoisted. Every `import` in a module is resolved and executed before any of that module's own statements run, so `import { LearnAgent } from "./agent.js"` pulls in LangChain before a `useMicrosoftOpenTelemetry()` call sitting in the body of the same file ever executes. The patching then has nothing left to attach to.

LangChain auto-instrumentation is on by default in the Node distro, so `instrumentationOptions.langchain` just makes the intent explicit. Don't also register the LangChain instrumentation by hand, because doing both produces every span twice.

The store is the Node counterpart of the Python one, in `src/token-store.ts`, and it has the same rule about importing nothing from the rest of the app:

```typescript
/** Holds the observability token so the exporter's background flush can read it. */

const SAFETY_MARGIN_MS = 5 * 60 * 1000;

interface Entry {
    token: string;
    expiresAt: number;
}

class ObservabilityTokenStore {
    private readonly tokens = new Map<string, Entry>();

    private static key(agentId: string, tenantId: string): string {
        return `${agentId}:${tenantId}`;
    }

    set(agentId: string, tenantId: string, token: string, expiresInSeconds = 3600): void {
        const expiresAt = Date.now() + Math.max(expiresInSeconds * 1000 - SAFETY_MARGIN_MS, 0);
        this.tokens.set(ObservabilityTokenStore.key(agentId, tenantId), { token, expiresAt });
    }

    get(agentId: string, tenantId: string): string | null {
        const entry = this.tokens.get(ObservabilityTokenStore.key(agentId, tenantId));

        if (!entry || Date.now() >= entry.expiresAt) {
            return null;
        }

        return entry.token;
    }
}

export const tokenStore = new ObservabilityTokenStore();
```

There's no lock, because Node is single-threaded. Finally, because Node processes usually exit on a signal rather than draining politely, flush on the way out, at the bottom of `src/main.ts`:

```typescript
import { shutdownMicrosoftOpenTelemetry } from "@microsoft/opentelemetry";

for (const signal of ["SIGINT", "SIGTERM"] as const) {
    process.once(signal, () => {
        void shutdownMicrosoftOpenTelemetry().finally(() => process.exit(0));
    });
}
```

Without this, the last batch of spans is still queued when the process dies, and the final turn of every debugging session goes missing.

### Step 2-7. Get the token and instrument the turn

This is the only step that touches your agent's own code, and it brings the four pieces together.

**What this step needs from your agent.** One place where a turn begins and ends, with the `TurnContext` in scope. In the Agents SDK that's your message handler. Inside it, in this order:

1. **Fetch the token** from the auth handler and put it in the store, before anything can flush.
2. **Read the caller** off the incoming activity.
3. **Open a baggage scope** around the whole turn.
4. **Open an `invoke_agent` scope** inside it, and run your agent within that.

Baggage and the semantic scopes are the two that need a word of explanation first.

**Baggage** is how OpenTelemetry carries contextual values alongside the execution context, and Agent 365 uses it to carry the dimensions it partitions telemetry by: tenant, agent, user, conversation. Spans emitted outside an active baggage scope are dropped, and the exporter says so with `Partitioned into 0 identity groups`. The scope has to stay open for the *whole* turn, which is why every version below wraps the agent call inside it.

**The semantic scopes** exist because Agent 365 only ingests spans whose `gen_ai.operation.name` is one of `invoke_agent`, `chat`, `execute_tool` or `output_messages`. Anything else is dropped span by span. The one that matters most is `invoke_agent`: it becomes the root span of the turn, and it's the only span the Microsoft 365 admin center ingests.

Three rules apply whatever you're writing in:

> **The channel name is `msteams`.** The exporter records whatever you give it verbatim, so a wrong value doesn't fail. It quietly misreports where the activity came from.

> **The baggage agent id and the `AgentDetails` agent id must be the same value**, and both must be the bot app client id from Step 2-3. If they disagree the turn splits into two identity groups, only one of which has a token, so half your spans arrive and half vanish behind an `HTTP 200`.

> **Read the caller's directory object id**, which on a Teams activity is `aadObjectId`. The channel-local `id` is a different thing, and giving the exporter that one still returns `HTTP 200` and still writes a row. The row simply never resolves to a person.

#### .NET

One precondition first. `GetTurnTokenAsync` returns a token that was **already acquired for this turn**; it is not a way to start a sign-in. The SDK acquires it when the route declares an auto sign-in handler, so register your message route with the handler name from Step 2-5:

```csharp
OnActivity(ActivityTypes.Message, OnMessageAsync, rank: RouteRank.Last, autoSignInHandlers: ["obo"]);
```

Without that argument the handler never runs, the turn holds no token, and `GetTurnTokenAsync` returns nothing at all with no error to explain it.

The handler also needs the four settings and the token cache. `Program.cs` created them as local variables, which the agent class cannot see, so inject them. In the supplied sample that means adding fields and constructor parameters to `LearnAgent`; in your own agent, put them wherever that agent already receives its dependencies:

```csharp
private readonly ServiceTokenCache _observabilityTokens;
private readonly string _observabilityAgentId;
private readonly string _tenantId;
private readonly string _agentName;
private readonly string _blueprintId;

public LearnAgent(
    AgentApplicationOptions options,
    AIAgent agent,
    ConversationSessionStore sessions,
    ILogger<LearnAgent> logger,
    ServiceTokenCache observabilityTokens,
    IConfiguration configuration) : base(options)
{
    _agent = agent;
    _sessions = sessions;
    _logger = logger;
    _observabilityTokens = observabilityTokens;

    _observabilityAgentId = configuration["Connections:ServiceConnection:Settings:ClientId"]
        ?? throw new InvalidOperationException("The bot app client id is not configured.");

    var section = configuration.GetSection("Agent365Observability");
    _tenantId = section["TenantId"]
        ?? throw new InvalidOperationException("Agent365Observability:TenantId is not configured.");
    _blueprintId = section["AgentBlueprintId"]
        ?? throw new InvalidOperationException("Agent365Observability:AgentBlueprintId is not configured.");
    _agentName = section["AgentName"] ?? "my-agent";

    OnConversationUpdate(ConversationUpdateEvents.MembersAdded, WelcomeAsync);
    OnMessage("/reset", ResetAsync);
    OnActivity(ActivityTypes.Message, OnMessageAsync, rank: RouteRank.Last, autoSignInHandlers: ["obo"]);
}
```

Throwing at startup names the missing key. An empty string instead travels all the way to Entra and comes back as an authentication error that names nothing. Now the handler itself:

```csharp
using Microsoft.Agents.A365.Observability.Hosting.Caching;
using Microsoft.Agents.A365.Observability.Runtime.Common;
using Microsoft.Agents.A365.Observability.Runtime.Tracing.Contracts;
using Microsoft.Agents.A365.Observability.Runtime.Tracing.Scopes;

private const string ObservabilityScope =
    "api://9b975845-388f-4429-889e-eab1ef63949c/Agent365.Observability.OtelWrite";

private async Task OnMessageAsync(ITurnContext turnContext, ITurnState turnState, CancellationToken cancellationToken)
{
    var question = turnContext.Activity.Text?.Trim();
    if (string.IsNullOrEmpty(question)) { /* unchanged from the starting point */ return; }

    var conversationId = turnContext.Activity.Conversation?.Id ?? "unknown";
    var from = turnContext.Activity.From;

    // 1. The token. Losing telemetry is never a reason to fail the user's turn.
    try
    {
        var token = await UserAuthorization.GetTurnTokenAsync(turnContext, "obo", cancellationToken);

        if (!string.IsNullOrEmpty(token))
        {
            _observabilityTokens.RegisterObservability(
                _observabilityAgentId,
                _tenantId,
                token,
                [ObservabilityScope],
                TimeSpan.FromHours(1));
        }
    }
    catch (Exception ex)
    {
        _logger.LogWarning(ex, "Could not get an observability token for this turn.");
    }

    // 2. The caller. AadObjectId is the directory object id; Id is channel-local.
    var userId = from?.AadObjectId ?? from?.Id ?? "unknown";
    var userName = from?.Name ?? "unknown";

    var agentDetails = new AgentDetails(
        agentId: _observabilityAgentId,
        agentName: _agentName,
        agentBlueprintId: _blueprintId,
        tenantId: _tenantId);

    var callerDetails = new CallerDetails(
        userDetails: new UserDetails(userId: userId, userEmail: string.Empty, userName: userName));

    // 3. The baggage scope, open for the whole turn.
    using var baggage = new BaggageBuilder()
        .TenantId(_tenantId)
        .AgentId(_observabilityAgentId)
        .AgentName(_agentName)
        .AgentBlueprintId(_blueprintId)
        .ConversationId(conversationId)
        .SessionId(conversationId)
        .UserId(userId)
        .UserName(userName)
        .ChannelName("msteams")
        .Build();

    // 4. The invoke_agent span, with the agent call inside it.
    var request = new Request(
        content: question,
        sessionId: conversationId,
        channel: new Channel("msteams"),
        conversationId: conversationId);

    using var invokeScope = InvokeAgentScope.Start(
        request,
        new InvokeAgentScopeDetails(new Uri($"https://{_blueprintId}.agent.invalid/")),
        agentDetails,
        callerDetails);

    invokeScope.RecordInputMessages([question]);

    await turnContext.SendActivityAsync(new Activity { Type = ActivityTypes.Typing }, cancellationToken);

    try
    {
        var session = await _sessions.GetOrCreateAsync(conversationId, cancellationToken);
        var response = await _agent.RunAsync(question, session, cancellationToken: cancellationToken);
        var answer = string.IsNullOrWhiteSpace(response.Text)
            ? "I couldn't find an answer to that in the Microsoft Learn documentation."
            : response.Text;

        invokeScope.RecordOutputMessages([answer]);
        await turnContext.SendActivityAsync(MessageFactory.Text(answer), cancellationToken);
    }
    catch (Exception ex)
    {
        // Record the failure on the span before replying, otherwise the turn exports as
        // though it succeeded and you lose the one trace that would explain the outage.
        invokeScope.RecordError(ex);
        _logger.LogError(ex, "Failed to answer in conversation {ConversationId}.", conversationId);
        await turnContext.SendActivityAsync(
            MessageFactory.Text("Sorry, something went wrong while researching that. Please try again."),
            cancellationToken);
    }
}
```

Both `using` declarations do different jobs. The baggage scope stays open to the end of the block, which is why the agent call sits inside it. The invoke scope is a span, and a span that is never disposed is never ended, and a span that is never ended is never exported.

Two more details. `AgentDetails`, `CallerDetails` and `UserDetails` take every parameter as optional, and `UserDetails` is declared `(userId, userEmail, userName, userClientIP)` with the email in the middle, so name the arguments or you'll silently swap the name and the email. And nothing ever resolves the endpoint URI, so build it from the blueprint GUID under the reserved `.invalid` TLD instead of inventing a hostname that might one day exist.

> **If you use `BaggageBuilder.FromTurnContext()`**, chain your explicit `.AgentId()` *after* it. That helper fills in the user, channel and conversation for you, which is convenient, but it also writes `gen_ai.agent.id` from `Recipient.AgenticAppId`, and on this path that value is wrong. `BaggageBuilder` keeps a single dictionary, so whichever call comes last wins.

#### Python

The token comes from the module-level `Authorization` instance the SDK wiring already created. Before that works, the route has to declare the handler, exactly as .NET does: the decorators take a keyword-only `auth_handlers` list, and without it no token is acquired for the turn.

Note the handler id is `OBO` in both places here, matching the uppercase environment key from Step 2-5, because Python compares these strings exactly.

`get_token` is async and returns a `TokenResponse` whose `token` attribute is the string:

```python
from microsoft.opentelemetry.a365.core import (
    AgentDetails,
    CallerDetails,
    Channel,
    InvokeAgentScope,
    InvokeAgentScopeDetails,
    Request as A365Request,
    ServiceEndpoint,
    UserDetails,
)
from microsoft.opentelemetry.a365.core.middleware.baggage_builder import BaggageBuilder

from app.token_store import token_store

OBO_AUTH_HANDLER = "OBO"


@AGENT_APP.activity("message", auth_handlers=[OBO_AUTH_HANDLER])
async def on_message(context: TurnContext, _state: TurnState) -> None:
    question = (context.activity.text or "").strip()
    if not question:
        await context.send_activity("Ask me a question about the Microsoft ecosystem.")
        return

    conversation_id = context.activity.conversation.id
    sender = context.activity.from_property

    # 1. The token. Losing telemetry is never a reason to fail the user's turn.
    try:
        token_response = await AUTHORIZATION.get_token(context, OBO_AUTH_HANDLER)
        if token_response and token_response.token:
            token_store.set(
                settings.observability_agent_id,
                settings.a365_tenant_id,
                token_response.token,
            )
    except Exception:
        logger.warning("Could not get an observability token for this turn.", exc_info=True)

    # 2. The caller. aad_object_id is the directory object id; id is channel-local.
    user_id = getattr(sender, "aad_object_id", None) or getattr(sender, "id", "") or "unknown"
    user_name = getattr(sender, "name", "") or "unknown"

    agent_details = AgentDetails(
        agent_id=settings.observability_agent_id,
        agent_name=settings.a365_agent_name,
        agent_blueprint_id=settings.a365_blueprint_id,
        tenant_id=settings.a365_tenant_id,
    )
    caller_details = CallerDetails(
        user_details=UserDetails(user_id=user_id, user_email="", user_name=user_name)
    )

    # 3. The baggage scope, open for the whole turn.
    with (
        BaggageBuilder()
        .tenant_id(settings.a365_tenant_id)
        .agent_id(settings.observability_agent_id)
        .agent_name(settings.a365_agent_name)
        .agent_blueprint_id(settings.a365_blueprint_id)
        .conversation_id(conversation_id)
        .session_id(conversation_id)
        .user_id(user_id)
        .user_name(user_name)
        .channel_name("msteams")
        .build()
    ):
        # 4. The invoke_agent span, with the agent call inside it.
        with InvokeAgentScope.start(
            A365Request(
                content=question,
                session_id=conversation_id,
                conversation_id=conversation_id,
                channel=Channel(name="msteams"),
            ),
            InvokeAgentScopeDetails(
                endpoint=ServiceEndpoint(hostname=f"{settings.a365_blueprint_id}.agent.invalid")
            ),
            agent_details,
            caller_details,
        ) as scope:
            scope.record_input_messages([question])

            try:
                answer = await LEARN_AGENT.ask(conversation_id, question)
            except Exception as error:
                scope.record_error(error)
                logger.exception("The agent failed to answer.")
                await context.send_activity("Sorry, something went wrong. Please try again.")
                return

            scope.record_output_messages([answer])

    await context.send_activity(answer)
```

`ServiceEndpoint` wants a bare **hostname** rather than a URI, so passing a URI string fails later, from inside the scope, as `AttributeError: 'str' object has no attribute 'hostname'`.

`answer` is assigned inside the `with` and read after it, which is fine because `with` doesn't introduce a scope in Python, and the only path that skips the assignment returns first.

> **If your Python agent uses LangChain**, make sure you passed the `instrumentation_options` block from Step 2-6 that disables the enrichers you aren't using. Without it the LangChain enricher loses a registration race and you get `chat` spans with no messages in them.

#### Node.js

The token comes from `agentApp.authorization`, and `getToken` returns a `TokenResponse` whose `token` property is the string. As on the other two stacks, the route has to declare the handler first. On Node that's the **third argument** to `onActivity`, an array of handler ids, and it defaults to empty, which means no token is acquired for the turn:

```typescript
import {
    BaggageBuilder,
    InvokeAgentScope,
    type A365Request,
    type AgentDetails,
    type CallerDetails,
} from "@microsoft/opentelemetry";

import { tokenStore } from "./token-store.js";

const OBO_AUTH_HANDLER = "obo";

agentApp.onActivity("message", async (context: TurnContext) => {
    const question = context.activity.text?.trim();

    if (!question) {
        await context.sendActivity("Ask me a question about the Microsoft ecosystem.");
        return;
    }

    const conversationId = context.activity.conversation?.id ?? "unknown";
    const from = context.activity.from;

    // 1. The token. Losing telemetry is never a reason to fail the user's turn.
    try {
        const response = await agentApp.authorization.getToken(context, OBO_AUTH_HANDLER);

        if (response?.token) {
            tokenStore.set(settings.observabilityAgentId, settings.a365TenantId, response.token);
        }
    } catch (error) {
        console.warn("Could not get an observability token for this turn.", error);
    }

    // 2. The caller. aadObjectId is the directory object id; id is channel-local.
    const userId = from?.aadObjectId ?? from?.id ?? "unknown";
    const userName = from?.name ?? "unknown";

    const agentDetails: AgentDetails = {
        agentId: settings.observabilityAgentId,
        agentName: settings.a365AgentName,
        agentBlueprintId: settings.a365BlueprintId,
        tenantId: settings.a365TenantId,
    };

    const callerDetails: CallerDetails = {
        userDetails: { userId, userName },
    };

    // 3. The baggage scope, open for the whole turn.
    const baggage = new BaggageBuilder()
        .tenantId(settings.a365TenantId)
        .agentId(settings.observabilityAgentId)
        .agentName(settings.a365AgentName)
        .agentBlueprintId(settings.a365BlueprintId)
        .conversationId(conversationId)
        .sessionId(conversationId)
        .userId(userId)
        .userName(userName)
        .channelName("msteams")
        .build();

    try {
        const answer = await baggage.run(async () => {
            // 4. The invoke_agent span, with the agent call inside it.
            const request: A365Request = {
                content: question,
                sessionId: conversationId,
                conversationId,
                channel: { name: "msteams" },
            };

            const invokeScope = InvokeAgentScope.start(
                request,
                { endpoint: { host: `${settings.a365BlueprintId}.agent.invalid` } },
                agentDetails,
                callerDetails,
            );

            try {
                invokeScope.recordInputMessages([question]);
                const reply = await invokeScope.withActiveSpanAsync(() =>
                    learnAgent.ask(conversationId, question),
                );
                invokeScope.recordOutputMessages([reply]);
                return reply;
            } catch (error) {
                invokeScope.recordError(error as Error);
                throw error;
            } finally {
                // A scope that is never disposed is a span that never ends,
                // and a span that never ends is never exported.
                invokeScope.dispose();
            }
        });

        await context.sendActivity(answer);
    } catch (error) {
        console.error("The agent failed to answer.", error);
        await context.sendActivity("Sorry, something went wrong. Please try again.");
    }
}, [OBO_AUTH_HANDLER]);
```

That trailing `[OBO_AUTH_HANDLER]` is the argument that makes the whole step work. Leave it off and everything else here is correct, the export fails authentication, and nothing points at the route registration as the cause.

`baggage.run()` is synchronous: it calls your function and returns whatever that function returned. Because the callback is `async`, what it returns is a promise, which is why the `await` sits in front of `baggage.run(...)`. Write `baggage.run(() => { learnAgent.ask(...); })` with a forgotten `return` and `run()` completes immediately, the baggage is gone by the time the spans are created, and you're back to `Partitioned into 0 identity groups`.

Note also that the Node endpoint object takes **`host`**, where Python takes `hostname` and .NET takes a `Uri`. The `.invalid` convention is the same in all three.

### Step 2-8. Verify that telemetry is leaving

Before looking at any portal, confirm from the agent's own logs that spans are being exported. Turn on both log levels:

```powershell
$env:OTEL_LOG_LEVEL="INFO"
$env:A365_OBSERVABILITY_LOG_LEVEL="debug"
```

Both matter. `OTEL_LOG_LEVEL` controls the OpenTelemetry SDK's own diagnostics, while `A365_OBSERVABILITY_LOG_LEVEL` is what makes the Agent 365 components talk. Set only the first and you'll watch the SDK start up and then hear nothing from the part you wanted to see.

Restart the agent, send it a message from Teams, and read the output. Five things have to be right:

| What to look for | What it means when it's wrong |
| --- | --- |
| `Partitioned into 1 identity groups` | `0` means no baggage scope around the turn. `2` means baggage and `AgentDetails` disagree on the agent id. Step 2-7 |
| An `invoke_agent` span, and it's a **root** span | The invoke scope isn't wrapping the turn, or was never disposed. Step 2-7 |
| `chat` spans for the model call | Import order on Python and Node, or a missing enricher. Step 2-6 |
| `HTTP 200` on the export | `401` is the connection's scope (Step 2-1), `403` is the agent id (Step 2-3) |
| The agent id in the export URL is the **bot app client id** | Step 2-3 |

If nothing is exported at all and there's no error, check the two switches from Step 2-6 before anything else. Spans that are enriched and never exported produce no error anywhere.

If the token is the problem, the fastest way to isolate it is the **Test connection** button on the OAuth connection from Step 2-1. If that works and your agent still gets nothing, the connection is fine and the handler configuration in Step 2-5 is where to look.

✅ **Checkpoint.** The agent is registered, and it's observable.

## Phase 3: Work IQ

With observability working, we can look at giving the agent access to Microsoft 365 data, Mail, Calendar and more, through the Work IQ MCP servers, using the permissions of the Teams user it's acting for.

This phase splits into two halves that are in different states of readiness. The catalog and permissions half is CLI work that doesn't care what your agent is written in. The runtime half wires the tools into your agent, and on this scenario the published extensions fit, because they expect the Agents SDK turn context you already have.

> ⚠️ **A known service-side issue on this path.** While the reference agents for this scenario were built, `a365 develop add-mcp-servers` returned a **500 from `/agents/v2/{auid}/mcpServers`**. It failed for a completely made-up AUID too, which pointed at the route rather than at any configuration. If you hit a 500 here, try it with a nonsense AUID before debugging your own wiring, and treat this phase as optional.

### Step 3-1. Choose the servers and get them granted

Start from the live catalog, because the names change and the next command wants them verbatim:

```bash
a365 develop list-available
```

Entries look like this, each with the OAuth scope it needs and the audience it's addressed to:

```text
  mcp_MailTools
     URL: https://agent365.svc.cloud.microsoft/agents/servers/mcp_MailTools
     Required Scope: Tools.ListInvoke.All
     Audience: 16b1878d-62c7-4009-aa25-68989d63bbad

  mcp_CalendarTools
     URL: https://agent365.svc.cloud.microsoft/agents/servers/mcp_CalendarTools
     Required Scope: Tools.ListInvoke.All
     Audience: 910333d2-47e9-43ca-981f-6df2f4531ef4
```

Alongside Mail and Calendar you'll find Teams, SharePoint, OneDrive, Word, Excel, Planner, Microsoft 365 Copilot and a set of third-party connectors. Note the shape of the names, `mcp_MailTools` rather than `mail`.

Add the ones you want. They're positional arguments, one per server, and the command writes `ToolingManifest.json` in the project directory:

```bash
a365 develop add-mcp-servers "mcp_MailTools" "mcp_CalendarTools"
```

That writes a manifest and grants nothing, so the permissions are a separate command:

```bash
a365 setup permissions mcp --agent-name "my-agent"
```

You may have run that already in Step 1-2, in which case run it again now that the manifest exists, because it reads the manifest to decide what to grant. It needs tenant-wide consent, and non-administrators get a `/v2.0/adminconsent` URL to forward rather than an error.

**How to verify.** Ask the CLI what it thinks is configured:

```bash
a365 develop list-configured
```

Every server you asked for should appear exactly once. Duplicates are a known failure mode and cause the tools to be registered twice.

For local testing you'll also want a bearer token, which the CLI fetches interactively using the scopes in the manifest:

```bash
a365 develop get-token -o raw
```

Leave `--resource` off unless you also pass `--scopes`, since naming a resource explicitly turns off the manifest-driven scope resolution. These tokens expire, so expect to re-run it during a session.

### Step 3-2. Wire the tools into the agent

**What this step needs from your agent.** The Work IQ extensions take the `Authorization` object and the `TurnContext` from the Agents SDK, perform an on-behalf-of exchange per server audience, and hand you back a list of tools to merge into your agent's existing tools. Because your agent is already on the Agents SDK, both arguments exist. A web app has neither, which is why the web app scenario stops at the CLI half.

Install the extension for your stack:

```bash
# .NET
dotnet add package Microsoft.Agents.A365.Tooling
dotnet add package Microsoft.Agents.A365.Tooling.Extensions.AgentFramework

# Node.js
npm install @microsoft/agents-a365-tooling @microsoft/agents-a365-tooling-extensions-langchain
```

> **Python with LangChain has no extension package.** There is no `microsoft-agents-a365-tooling-extensions-langchain` on PyPI, and the skills hard-stop on this combination rather than half-instrument it. If you're on Python, read this step for the shape and come back when support lands, or call the MCP endpoints yourself using the audiences and scopes from the catalog.

On .NET, register the services at startup:

```csharp
builder.Services.AddSingleton<IMcpToolRegistrationService, McpToolRegistrationService>();
builder.Services.AddSingleton<IMcpToolServerConfigurationService, McpToolServerConfigurationService>();
```

Inject `IMcpToolRegistrationService` into your agent class the same way you injected `ServiceTokenCache` in Step 2-7, then fetch the tools inside the turn and give them to the model. The tools have to reach whatever runs your reasoning loop, so fit this to your own agent instead of copying it:

```csharp
var a365Tools = await _toolService.GetMcpToolsAsync(
    _agentUserId,       // the Agent User Id from a365.generated.config.json, not the bot app id
    UserAuthorization,  // the typed instance, not a string
    "obo",              // the auth handler name from Step 2-5
    turnContext);

// Hand them to the model. In the supplied sample the agent is built once at startup from a
// fixed tool list, so the simplest change is to pass per-turn tools through ChatOptions:
var chatOptions = new ChatOptions { Tools = [.. a365Tools] };
var response = await _agent.RunAsync(question, session, options: new() { ChatOptions = chatOptions },
    cancellationToken: cancellationToken);
```

> **The first argument is the Agent User Id, not the bot app client id.** This is the one place on this path where the bot app is *not* the right identifier, which is easy to get wrong having just spent Step 2-3 learning the opposite. The tooling extension uses it to perform the per-audience on-behalf-of exchange, and it comes from `a365.generated.config.json`.

On Node.js, the LangChain extension returns a **new** agent with the tools attached, because tools are immutable on `createAgent`. That means you cannot attach tools to an agent built once at startup; the agent has to be rebuilt, or at least re-wrapped, inside the turn:

```typescript
const toolService = new McpToolRegistrationService();

// Inside the message handler, where the turn context exists.
let agentForThisTurn = learnAgent.graph;   // whatever object your agent core exposes

try {
    agentForThisTurn = await toolService.addToolServersToAgent(
        agentForThisTurn,
        agentApp.authorization,
        OBO_AUTH_HANDLER,
        context,
        process.env.BEARER_TOKEN ?? "",   // local dev only; empty in production
    );
} catch (error) {
    // Fall back to the agent without Work IQ tools rather than failing the turn.
    console.error("Could not add MCP tool servers.", error);
}
```

Then invoke `agentForThisTurn` rather than the original. Ignoring the return value is the most common mistake here: the call succeeds, and no tools are attached. The supplied sample keeps its LangChain graph private inside `LearnAgent`, so you'll need to expose it or move the tool registration inside that class.

The `BEARER_TOKEN` argument is a development convenience. In production the extension performs the per-audience exchange through the authorization context you passed in, so leave it empty. For local runs set it to the token from `a365 develop get-token`, and set `SKIP_TOOLING_ON_ERRORS=true` so a server you haven't consented to yet doesn't take the whole turn down.

**How to verify.** Ask the agent something only a tool can answer, such as `What's on my calendar tomorrow?`, and check the spans from Step 2-8 for `execute_tool`.

> **Register each tool exactly once.** A tool registered twice is called twice, with whatever real-world consequences that implies for a mail-sending tool. That said, be careful about what looks like a duplicate: in the Agent 365 map a single tool call can appear as two nodes, one keyed by the MCP server and one by the tool name, because Agent 365 records `ExecuteToolByMCPServer` and `ExecuteToolBySDK` as distinct action types. Check the real side effect before "fixing" anything. If you sent one email, you made one tool call, whatever the map shows.

## Phase 4: Verify it end to end

Everything so far proves the agent *emits* telemetry. This phase proves it *arrives*, and the two can come apart.

Nothing here depends on your stack.

### Step 4-1. Produce some activity

Send the agent several messages. There's a set in [4.Sample-prompts.md](4.Sample-prompts.md) if you want a starting point. Include at least one that calls a tool, and if you can, send them from two different Teams users so you can confirm attribution follows the right person.

Send them as users who hold an Agent 365 licence. Without one the telemetry is accepted and discarded.

### Step 4-2. Check Microsoft Defender

Go to [Advanced hunting](https://security.microsoft.com) and query `CloudAppEvents`. Defender accepts every operation type, so this is the fullest picture you'll get:

```kusto
CloudAppEvents
| where ActionType in ("InvokeAgent", "InferenceCall", "ExecuteToolBySDK", "ExecuteToolByGateway", "ExecuteToolByMCPServer")
| where RawEventData.TargetAgentName == "my-agent" or RawEventData.AgentName == "my-agent"
| order by Timestamp desc
```

Defender has to index the events, so give it around five minutes. If you get impatient, drop the name filter and look for anything at all in the last hour: an empty table then is a different problem from a name that doesn't match.

### Step 4-3. Check the Microsoft 365 admin center

Go to https://admin.cloud.microsoft, find your agent, and open its activity.

This surface ingests `invoke_agent` rows only, and reads the caller identity off that one span. Comparing the two portals therefore tells you where a problem lives:

| What you see | Where the problem is |
| --- | --- |
| Nothing anywhere | The token, the agent id, or the baggage scope. Steps 2-3 to 2-7 |
| `403` on the export | `gen_ai.agent.id` isn't the bot app client id. Step 2-3 |
| `401 InvalidAudience` | The OAuth connection is on `/.default` instead of the named scope. Step 2-1 |
| Half the spans missing | Baggage and `AgentDetails` disagree, so you have two identity groups. Step 2-7 |
| Defender ✅, admin center ❌ | Your `invoke_agent` span, usually the caller id. Step 2-7 |
| Activity arrives but resolves to nobody | The caller is the channel-local id rather than `aadObjectId`. Step 2-7 |
| The agent stopped answering after a restart | `a365 setup all` overwrote the bot credentials. Step 1-3 |

### Step 4-4. Read your own instrumentation back

There's no skill to check the code on this path, so here is the checklist one would run, as questions you can answer by reading your own code:

| Question | Where to look |
| --- | --- |
| Does the OAuth connection ask for the named scope rather than `/.default`? | Step 2-1 |
| Is the exporter *enabled*, not merely registered? | Both flags, Step 2-6 |
| Is the agent id the **bot app client id** in all three places? | Step 2-3 |
| Does the route declare its auth handler? `autoSignInHandlers` on .NET, `auth_handlers` on Python, the third argument on Node | Step 2-7 |
| Does the handler name in the code match the configured id, including its case on Python? | Steps 2-5 and 2-7 |
| Does the baggage scope wrap the agent call rather than sit before it? | Step 2-7 |
| Do the baggage agent id and `AgentDetails.agentId` come from one value? | Step 2-7 |
| Is the invoke scope disposed on every path, including the failing one? | Step 2-7 |
| Is the caller id `aadObjectId` rather than the channel-local `id`? | Step 2-7 |

If you do have a coding assistant available after all, the `a365-code-validator` skill is read-only and safe to point at code you wrote by hand.

> ⚠️ **Expect one false positive from that validator on this path.** It flags `gen_ai.agent.id` not matching the agent identity as a blocker. On a custom engine agent that is correct behaviour, as Step 2-3 established, so don't let it talk you into "fixing" a working agent.

## Troubleshooting

The first group applies whatever you're writing in; the second is stack-specific.

| Symptom | Likely cause |
| --- | --- |
| `401 InvalidAudience` on export | The OAuth connection uses `/.default` instead of the named scope. Step 2-1 |
| `403` on the export route | The agent id, the token's `azp` and the store key don't all agree. It has to be the bot app. Step 2-3 |
| `AADSTS82001` | You tried to use the blueprint as the bot. They must stay separate |
| Spans enriched but nothing exported | Only one of the two exporter switches is on. Step 2-6 |
| `Partitioned into 0 identity groups` | No baggage scope around the turn. Step 2-7 |
| `Partitioned into 2 identity groups` | Baggage and `AgentDetails` disagree on the agent id. Step 2-7 |
| `HTTP 200` but nothing lands anywhere | No user in the tenant holds an Agent 365 licence |
| The token is always empty | The route doesn't declare the auth handler, or the handler name doesn't match the configured id, or the connection name is misspelled. Steps 2-5 and 2-7 |
| `ValueError: Auth handler ... not recognized` | Python only, and it's the case. The configured id is `OBO` and the code asked for `obo`. Step 2-5 |
| The user is asked to sign in on every conversation | `tokenExchangeUrl` doesn't match `webApplicationInfo.resource` in the Teams manifest. Steps 0-7 and 2-1 |
| Teams stopped reaching the agent | The dev tunnel URL changed and the endpoint wasn't updated (Step 0-4), or the bot credentials were overwritten (Step 1-3) |
| Activity arrives but resolves to nobody | The caller id is channel-local rather than `aadObjectId`. Step 2-7 |
| `404 DeploymentNotFound` on the first question | The chat deployment doesn't exist on your resource. Step 0-6 |

And the ones that only affect one stack:

| Symptom | Stack | Likely cause |
| --- | --- | --- |
| `GetTurnTokenAsync` returns nothing, with no error | .NET | The route doesn't declare `autoSignInHandlers`, so the turn holds no token to return. Step 2-7 |
| The token is empty and the route looks right | Node.js | The third argument to `onActivity`, the `authHandlers` array, is missing. It defaults to empty. Step 2-7 |
| The token is empty on the first turn only | Python | The `auth_handlers` keyword is missing from the route decorator. Step 2-7 |
| `CS0433` duplicate type errors after adding the distro | .NET | The legacy `Observability.Runtime` or `.Hosting` packages are also referenced directly. Step 2-2 |
| The agent id is right in chat and wrong elsewhere | .NET | `FromTurnContext()` overwrote it. Chain `.AgentId()` after it. Step 2-7 |
| `401` in the console, and it works in the Playground | .NET | `TokenValidation.Audiences` is still empty, which is anonymous mode. Step 0-5 |
| No `chat` spans | Python | The distro was initialised after LangChain was imported. Step 2-6 |
| `chat` spans exist but carry no messages | Python | The Agent Framework or Semantic Kernel enrichers won the registration race. Disable them. Step 2-7 |
| `AttributeError: 'str' object has no attribute 'hostname'` | Python | `ServiceEndpoint` was given a URI instead of a bare hostname. Step 2-7 |
| A distro option seems to have no effect | Python | It's misspelled. The call takes `**kwargs` and ignores what it doesn't recognise. Step 2-6 |
| No `chat` spans | Node.js | `./observability.js` isn't the first import in `main.ts`. Step 2-6 |
| Every span appears twice | Node.js | LangChain instrumentation was registered by hand as well as by the distro. Step 2-6 |
| Baggage is empty despite an open scope | Node.js | The callback passed to `run()` doesn't return its promise. Step 2-7 |
| No tools attached, and no error | Node.js | The return value of `addToolServersToAgent` was ignored. Step 3-2 |
| `for appId undefined`, and Teams gets no reply | Node.js | The `Connections__…` keys are misspelled, or `.env` loads after the SDK import. Step 0-5 |
| The last turn's spans never arrive | Node.js | The process exited before the exporter flushed. Add the shutdown handler. Step 2-6 |

## Wrapping up

We started with a Teams agent that worked and told nobody anything. It now has a registered identity in the tenant, reports every turn to Defender and the admin center attributed to the Teams user who sent the message, and can reach Microsoft 365 data under that user's permissions.

Compared with the web app scenario, there was very little code to write. The two-hop token chain you'd hand-roll in a web app was replaced by one OAuth connection on the Azure Bot resource and a single call for the token. The difficulty moved into configuration: the named scope on that connection, the `--m365` flag and its required follow-up command, the agent id that has to be the bot app rather than the agent identity setup just created, the auto sign-in handler on the route without which the token is never acquired, and the bot credentials setup quietly overwrites. All of those surface as HTTP status codes during a turn, which is why each one has a step of its own above.

The three identities are what to carry away. The bot app authenticates the channel and owns the telemetry, the blueprint holds the permissions and represents the agent in the inventory, and the agent identity exists without carrying the activity on this path. Almost every confusing failure in this guide is one of those three standing in for another.

If you want to compare against a finished implementation, the [.NET agent](https://github.com/qmatteoq/agent365-demos/tree/main/dotnet-agent-teams) and the [Python agent](https://github.com/qmatteoq/agent365-demos/tree/main/python-agent-teams) live in the demos repository, and the [Node.js starting point](0.Resources/Starting-point/nodejs/) in this repository is the reference for that stack.
