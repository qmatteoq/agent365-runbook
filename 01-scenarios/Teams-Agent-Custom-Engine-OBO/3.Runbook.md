# Step-by-Step Guide — Teams Agent with Custom Engine OBO

> **Scenario**: Onboarding a Teams-hosted custom engine agent into Microsoft Agent 365
> **Platform**: Microsoft Agent 365 · Azure Bot Service · Microsoft Entra ID · OpenTelemetry
> **Stacks**: .NET Agent Framework · Python + LangChain
> **Target Readers**: Agent developers, Azure and Entra administrators
> **Last Updated**: February 2026

## Overview

This runbook onboards a working Teams agent into Microsoft Agent 365. You drive it with a **coding
agent** running the Agent 365 Skills, and every step also shows the CLI command or code underneath.

Compared to the [web app scenario](../Web-App-Agent-User-OBO/3.Runbook.md), there is **less code**
— the Bot Framework Token Service does the on-behalf-of exchange for you — and **more
configuration**. Most of the difficulty is in Azure Bot Service, not in your source.

| Phase | You get | Time |
| --- | --- | --- |
| 0 — Prerequisites | A working Teams agent and the tooling installed | 30–60 min |
| 1 — Registration | The agent exists in your tenant as a governed identity | 30 min |
| 2 — Observability | Activity in Defender, Purview and the admin center | 60–90 min |
| 3 — Work IQ | Microsoft 365 data access | 30 min |
| 4 — Verify | Proof it works end to end | 30 min |

Where you'll be working:

| Location | URL | Task |
| --- | --- | --- |
| Your terminal | — | Skills, CLI, builds, dev tunnel |
| Azure portal | https://portal.azure.com | Azure Bot resource and OAuth connections |
| Microsoft Entra admin center | https://entra.microsoft.com | App registrations, consent |
| Teams Developer Portal | https://dev.teams.microsoft.com | App package and endpoint |
| Microsoft 365 admin center | https://admin.cloud.microsoft | Agent inventory and activity |
| Microsoft Defender | https://security.microsoft.com | Advanced hunting |

Each step in Phases 1–3 is structured as **what you type → what the skill does → behind the
scenes → how to verify**. If you'd rather not use a coding agent, read the last two parts only.

## ⚠️ Read this before you start

Two things in this scenario can destroy work irreversibly. Both are avoidable in thirty seconds.

### `a365 setup all` overwrites your bot credentials

It rewrites the bot channel credentials in your configuration with the **blueprint's**, and it
replaces the bot secret **in place** — the original is not recoverable afterwards.

Worse, it **fails silently**. Your running process keeps the old values in memory and carries on
working. You find out on the next restart, possibly days later, with no obvious cause.

**Before Phase 1, back up your bot credentials outside the repo:**

```powershell
Copy-Item .env "$env:USERPROFILE\bot-credentials-backup.env"   # Python
# .NET: record the ClientId and ClientSecret from user-secrets somewhere safe
```

You will restore them in Step 1-3.

### Bot app and blueprint must stay separate

You may be tempted to let the blueprint *be* the bot. It cannot be:

- Entra bars agentic applications from client-credentials tokens (`AADSTS82001`), so a blueprint
  can never sign Bot Framework replies.
- It is also the wrong audience for validating the inbound Teams token.

Keep them as two identities. The runbook depends on that separation.

## Phase 0: Get the agent working in Teams first

**Do not skip this.** Onboarding a Teams agent that doesn't yet answer in Teams means debugging two
unrelated problems at once.

### Step 0-1. Start a dev tunnel

```bash
devtunnel host -p 3978 --allow-anonymous
```

> **Read the URL from the output.** Dev tunnel URLs are **not** derived from the tunnel name. Do
> not guess or reconstruct one — copy it from the host output while it runs.

### Step 0-2. Point the bot at the tunnel

Set the Azure Bot resource's messaging endpoint to `https://<tunnel-host>/api/messages`.

### Step 0-3. Run and sideload

```bash
# .NET
dotnet run

# Python
uv run python -m app.main
```

Then build and sideload the Teams app package:

```powershell
./build-app-package.ps1 -BotId <bot-app-client-id> -TeamsAppId <teams-app-id>
```

### Step 0-4. Verify

Message the agent in Teams: *"What is Microsoft Entra Conditional Access?"* You should get an
answer citing Microsoft Learn.

✅ **Checkpoint:** the agent answers in Teams. No Agent 365 anything yet.

## Phase 1: Register the agent

### Step 1-1. Back up your bot credentials

Do this now. See the warning above.

### Step 1-2. Run the setup skill

**What you type**

```text
Set up Agent 365 for this agent. It's a custom engine agent hosted in Teams
with its own bot registration — not an AI Teammate. Use the OBO auth mode.
```

**What the skill does**

`a365-setup` verifies prerequisites and Azure identity, then asks the two decisive questions:

| Question | Your answer | Why |
| --- | --- | --- |
| Agent kind? | **Agent (Non AI Teammate)** | A human drives it; it has its own bot registration |
| Auth mode? | **`obo`** | Attribution follows the Teams user |

It then hands off to `make-a365-agent`.

> ⚠️ **The skills have a gap here.** `instrument-observability` offers only `obo` (meaning the
> *agentic* on-behalf-of path) and `s2s`. Neither is exactly "custom engine using OBO". Answer
> `obo` — it is the closer of the two — but **do not accept the token code it generates without
> checking it against Phase 2 below.** Details in
> [Known Skill Gaps](../../03-references/Known-Skill-Gaps.md).

**Behind the scenes**

```bash
a365 setup all --agent-name "my-agent" --m365 --dry-run   # preview
a365 setup all --agent-name "my-agent" --m365             # apply
a365 setup permissions bot                                # required after --m365
```

`--m365` is what registers the agent for Teams and Microsoft 365 Copilot. `a365 setup permissions
bot` is a **required follow-up** — easy to miss, and things fail later without it.

**How to verify**

```bash
cat a365.generated.config.json
```

Confirm `agentBlueprintId` exists, then check the blueprint in
[Entra](https://entra.microsoft.com) → **App registrations**.

⚠️ If you weren't Global Admin, run the consent snippet the setup summary printed — or get an admin
to. Phase 2 fails without it.

### Step 1-3. Restore your bot credentials

**This is the step people skip, and it is why their agent breaks a week later.**

Compare your configuration against the backup from Step 1-1. If `a365 setup all` overwrote the bot
client id or secret with the blueprint's, **put the originals back**.

```powershell
# Python - diff against the backup
Compare-Object (Get-Content .env) (Get-Content "$env:USERPROFILE\bot-credentials-backup.env")
```

Then **restart the agent** and message it in Teams. If it still answers, the credentials are intact.
Testing without a restart proves nothing — the old values are still in memory.

✅ **Checkpoint — you can stop here.** The agent is registered and governed.

## Phase 2: Observability

### Step 2-1. Create the OAuth connection

**Do this before touching code.** It is what makes the rest simple, and it's where this scenario's
real work lives.

```bash
az bot authsetting create -g <resource-group> -n <azure-bot-name> \
  -c oboConnectionProfile \
  --client-id <bot-app-client-id> --client-secret <bot-app-secret> \
  --service AadV2 \
  --provider-scope-string \
    "api://9b975845-388f-4429-889e-eab1ef63949c/Agent365.Observability.OtelWrite" \
  --parameters tenantID=<tenant-id> tokenExchangeUrl=api://botid-<bot-app-client-id>
```

| Argument | Why it's exactly that |
| --- | --- |
| `--provider-scope-string` | A **named** scope. A delegated token carries scopes, not roles — leaving the default `api://botid-…/defaultScopes` produces `401 InvalidAudience` |
| `tokenExchangeUrl` | Keeps Teams SSO silent. The manifest declares one `webApplicationInfo.resource`; the connection exchanges that SSO token for its own |
| `--client-id` | The **bot app**, not the blueprint. This is what makes the token's `azp` correct |

> The resource id `9b975845-…` and the scope name are preview-era values. Re-verify against current
> documentation.

### Step 2-2. Run the observability skill

**What you type**

```text
Instrument this agent with Agent 365 observability. It's a custom engine agent
in Teams using OBO. The observability token comes from an Azure Bot OAuth
connection called oboConnectionProfile — don't build an MSAL or FMI token chain.
```

Being explicit here matters. Left to its defaults the skill may generate a full MSAL/FMI chain you
do not need and that will not work on this path.

**What the skill does**

Installs the distro, wires it into your entry point, adds a baggage scope, implements a token
resolver, adds the semantic scopes, updates config, builds and smoke-tests.

Review the token code it produces against Steps 2-4 and 2-5 before accepting it.

### Step 2-3. Wire the exporter

**.NET** — in `Program.cs`, note the processor registration order:

```csharp
var observabilityTokenStore = new ObservabilityTokenStore();
builder.Services.AddSingleton(observabilityTokenStore);

// Registered BEFORE UseMicrosoftOpenTelemetry so this processor sits ahead of the
// A365 export processor: OnEnd runs in registration order, and the identity has to be
// on the span before the exporter reads it.
builder.Services.AddOpenTelemetry()
    .WithTracing(t => t.AddProcessor(new BaggageBackfillProcessor()));

builder.UseMicrosoftOpenTelemetry(o =>
{
    o.Exporters = ExportTarget.Agent365;
    // Exporting to Agent 365 alone suppresses infrastructure instrumentation.
    o.Instrumentation.EnableAspNetCoreInstrumentation = true;
    o.Instrumentation.EnableHttpClientInstrumentation = true;
    o.Instrumentation.EnableAzureSdkInstrumentation = true;
});
```

> **Registration order is load-bearing in .NET.** Register the backfill processor *before*
> `UseMicrosoftOpenTelemetry`. Get it wrong and the inference span — the prompt, the system
> instructions and the completion — is dropped.

**Python** — before any LangChain or Azure OpenAI import:

```python
use_microsoft_opentelemetry(
    enable_a365=True,
    a365_enable_observability_exporter=True,
    a365_token_resolver=token_store.get,
    # The delegated route. Its S2S counterpart takes application tokens only and
    # refuses a delegated one - the two are not interchangeable.
    a365_use_s2s_endpoint=False,
    enable_sensitive_data=True,
    disable_metrics=True,
)
```

`a365_use_s2s_endpoint=False` is explicit on purpose. The S2S endpoint accepts application tokens
only and rejects a delegated one.

### Step 2-4. Get the observability agent id right

**The single most important step in this runbook.**

```text
gen_ai.agent.id  ==  the token's azp  ==  the token store key
```

For a custom engine agent, all three are the **bot app registration's client id** — not the agent
identity, not the blueprint. A mismatch is `HTTP 403`.

Read it from the SDK's own connection settings rather than duplicating it, so the two can't drift:

```csharp
var observabilityAgentId = builder.Configuration["Connections:BotConnection:Settings:ClientId"];
```

```python
@property
def observability_agent_id(self) -> str:
    return self.bot_client_id   # from CONNECTIONS__SERVICE_CONNECTION__SETTINGS__CLIENTID
```

Verified empirically against the live service — one token, three candidate ids:

| Id in the export URL | Result |
| --- | --- |
| Agent identity | `403` |
| Blueprint | `403` |
| **Bot app registration** | `415` — authorised, wrong content type for the probe |

### Step 2-5. Get the token — one call

```python
token_response = await AUTHORIZATION.get_token(context, OBO_AUTH_HANDLER)
token_store.set(settings.observability_agent_id, settings.a365_tenant_id, token)
```

That is the entire token acquisition. The connection from Step 2-1 is already scoped to the
Observability API, so the Bot Framework Token Service performs the OBO exchange internally and
returns a finished token. **No MSAL, no `fmi_path`, no blueprint secret.**

Do it **at the start of the turn**, before generating the answer, so the token is waiting when the
first spans flush. And **swallow failures** — losing traces is not a reason to fail the user's
question:

```python
if OBSERVABILITY_ENABLED:
    await _publish_observability_token(context)
```

### Step 2-6. Baggage — and make the ids agree

```python
BaggageBuilder()
    .tenant_id(settings.a365_tenant_id)
    # Must match AgentDetails: auto-instrumented spans take gen_ai.agent.id from
    # baggage, and the exporter partitions on it. If the two disagree the turn splits
    # into two identity groups and only one has a token.
    .agent_id(settings.observability_agent_id)
    .agent_name(...)
    .agent_blueprint_id(settings.a365_blueprint_id)
    .conversation_id(conversation_id)
    .session_id(conversation_id)
    .user_id(user["id"]).user_name(user["name"]).user_email(user["email"])
    .channel_name("msteams")
    .build()
```

Two things to get right:

- **`channel_name` is `msteams`**, not `web`. The exporter records it verbatim.
- **The baggage agent id must equal the `AgentDetails` agent id.** Use one source value for both.

### Step 2-7. Resolve the caller from the turn context

Read the user off the incoming activity — `id`, `name`, `email`. Unlike the web app scenario there
is no signed-in principal to inspect; the channel tells you who sent the message.

### Step 2-8. Wrap the turn in semantic scopes

```python
InvokeAgentScope.start(
    Request(
        content=message,
        session_id=conversation_id,
        conversation_id=conversation_id,
        channel=Channel(name="msteams"),
    ),
    InvokeAgentScopeDetails(endpoint=endpoint),
    build_agent_details(settings),
    build_caller_details(user),
)
```

> **Session, conversation and channel must be on the `Request` object**, not only in baggage. The
> exported `invoke_agent` payload is built from this object; omit them and the span is accepted but
> shows no run context.

On **Python + LangChain**, disable the enrichers that would otherwise pre-empt the LangChain one:

```python
instrumentation_options={
    "openai_agents": {"enabled": False},
    "agent_framework": {"enabled": False},
    "semantic_kernel": {"enabled": False},
}
```

Agent Framework and Semantic Kernel enrichers register first and make the distro skip the LangChain
enricher — the one that maps this agent's messages and conversation id into the shape Agent 365
expects. `openai_agents` is off for a different reason: it isn't used, and the distro logs an
import traceback on every start.

### Step 2-9. Verify export

```powershell
$env:OTEL_LOG_LEVEL="INFO"
$env:A365_OBSERVABILITY_LOG_LEVEL="debug"
```

Send a Teams message, then look for:

- `Partitioned into 1 identity groups` — **not 0, and not 2**
- a root `invoke_agent` span
- `HTTP 200` on the export
- the agent id in the URL being the **bot app client id**

> `2 identity groups` means baggage and `AgentDetails` disagree — Step 2-6.

✅ **Checkpoint — you can stop here.**

## Phase 3: Work IQ

```text
Add Work IQ tools to this agent. I want Mail and Calendar.
```

`add-workiq-tools` runs `a365 develop list-available`, adds the servers you choose via
`a365 develop add-mcp-servers`, writes `ToolingManifest.json`, and wires a registration service.

> ⚠️ **Known service-side issue.** While building the reference agents, this path returned a
> **500 from `/agents/v2/{auid}/mcpServers`** for this agent. It failed for a bogus AUID too, so
> the route was broken rather than the wiring. If you hit a 500 here, verify with a nonsense AUID
> before debugging your own configuration — and treat Phase 3 as optional on this scenario.

Register each tool **exactly once**. A tool registered twice is called twice.

> In the Agent 365 map, one tool call may appear as **two nodes** — one keyed by the MCP server,
> one by the tool name — because Agent 365 records `ExecuteToolByMCPServer` and `ExecuteToolBySDK`
> as distinct action types. Verify the real side effect (e.g. exactly one email sent) before
> "fixing" a duplicate that isn't one.

## Phase 4: Verify end to end

### Step 4-1. Produce activity

Send several messages from [4.Sample-prompts.md](4.Sample-prompts.md), including one that calls a
tool, and ideally from two different Teams users.

### Step 4-2. Check Defender

[Advanced hunting](https://security.microsoft.com) → `CloudAppEvents`. Expect `InvokeAgent`,
`InferenceCall` and `ExecuteToolByMCPServer` rows. Allow ~5 minutes.

### Step 4-3. Check the Microsoft 365 admin center

https://admin.cloud.microsoft → your agent → activity.

| Symptom | Where the problem is |
| --- | --- |
| Nothing anywhere | Token, agent id, or baggage scope — Steps 2-4 to 2-6 |
| `403` on export | `gen_ai.agent.id` isn't the bot app client id — Step 2-4 |
| `401 InvalidAudience` | OAuth connection is on `/.default` instead of the named scope — Step 2-1 |
| Half the spans missing | Baggage and `AgentDetails` disagree — two identity groups — Step 2-6 |
| Defender ✅, admin center ❌ | Your `invoke_agent` span, usually the caller — Step 2-7 |
| Agent stopped answering after a restart | `a365 setup all` overwrote the bot credentials — Step 1-3 |

### Step 4-4. Optional — validate the code

```text
Validate the Agent 365 observability code in this project.
```

> ⚠️ **Expect a false positive.** `a365-code-validator` flags `gen_ai.agent.id` not matching the
> agent identity as a blocker. On this path that is **correct behaviour** — it must be the bot app
> client id. Don't "fix" it.

### Troubleshooting

| Symptom | Likely cause |
| --- | --- |
| `403` on the export route | Agent id / `azp` / store key mismatch — Step 2-4 |
| `401 InvalidAudience` | OAuth connection scope wrong — Step 2-1 |
| `AADSTS82001` | You tried to use the blueprint as the bot. They must stay separate |
| `Partitioned into 0 identity groups` | No baggage scope around the turn |
| `Partitioned into 2 identity groups` | Baggage vs `AgentDetails` id mismatch |
| Inference span missing (.NET) | Backfill processor registered after `UseMicrosoftOpenTelemetry` |
| No `chat` spans (Python) | Distro initialised after LangChain was imported |
| `HTTP 200` but nothing lands | No user in the tenant holds an Agent 365 licence |
| Teams stopped reaching the agent | Dev tunnel URL changed, or bot credentials were overwritten |

✅ **Done.** Registered, observable, and attributed to the Teams user who asked.
