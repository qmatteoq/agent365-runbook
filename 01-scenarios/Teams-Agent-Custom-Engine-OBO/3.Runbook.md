# Step-by-Step Guide: Teams Agent with Custom Engine OBO

> **Scenario**: Onboarding a Teams-hosted custom engine agent into Microsoft Agent 365
> **Platform**: Microsoft Agent 365 · Azure Bot Service · Microsoft Entra ID · OpenTelemetry
> **Stacks**: .NET Agent Framework · Python + LangChain · Node.js + LangChain
> **Target Readers**: Agent developers, Azure and Entra administrators
> **Last Updated**: February 2026

## Introduction

In this guide we're going to take a **custom engine agent** that already lives in Microsoft Teams and onboard it into Microsoft Agent 365.

By custom engine agent we mean an agent you built yourself, with your own reasoning loop and your own model, hosted on your favorite platform; the agent uses an Azure Bot registration to handle the communication channel between the user and the target platform (in our case, Teams and Copilot). However, despite this agent is running inside the Microsoft 365 ecosystem, it doesn't tell the organization anything about what it's doing. There's no record of which user asked what, which tools were called, or which data was touched.

Agent 365 is what turns that black box into something governed. It gives the agent a registered identity, publishes its activity to Microsoft Defender, Microsoft Purview and the Microsoft 365 admin center, and opens a controlled path to Microsoft 365 data.

If you've already read the [web app scenario](../Web-App-Agent-User-OBO/3.Runbook.md), you'll find this one has a different approach to manage authorization and authentication. There, we hand-wrote a two-hop token exchange. Here, there's much less code and much more configuration, because the Bot Framework Token Service performs the on-behalf-of exchange for us. Almost all of the difficulty in this scenario lives in Azure Bot Service, not in your source files.

As usual, we're going to drive most of the work with an AI coding assistant running the [Agent 365 Skills](https://github.com/microsoft/agent365-skills), and every step also shows the CLI command or code underneath, so you can do it by hand or review what the skill produced.

If we don't have access to a coding assistant, [3.Runbook-Manual.md](3.Runbook-Manual.md) follows the same phases with the portal setup, CLI commands and source edits written out for all three stacks.

The work is split into phases, and each phase is a valid place to stop:

| Phase | What you get at the end of it | Rough time |
| --- | --- | --- |
| 0: Get it working | An Azure Bot, a Teams agent that answers, and the tooling installed | 60 to 90 min |
| 1: Registration | The agent exists in your tenant as a governed identity | 30 min |
| 2: Observability | Activity in Defender, Purview and the admin center | 60 to 90 min |
| 3: Work IQ | Access to Microsoft 365 data | 30 min |
| 4: Verification | Proof that it works end to end | 30 min |

One thing that's worth knowing up front: this scenario has you moving between a lot of different portals. Here's the full list, so nothing comes as a surprise:

| Where | URL | What you'll do there |
| --- | --- | --- |
| Your terminal | N/A | Skills, CLI, builds, the dev tunnel |
| Azure portal | https://portal.azure.com | Creating the Azure Bot resource, its channels and its OAuth connections |
| Microsoft Entra admin center | https://entra.microsoft.com | App registrations and consent |
| Microsoft Teams | N/A | Sideloading the app package and testing the agent |
| Microsoft 365 admin center | https://admin.cloud.microsoft | Agent inventory and activity |
| Microsoft Defender | https://security.microsoft.com | Advanced hunting |

From Phase 1 onwards, the skill-led steps follow **what you type → what the skill does → behind the scenes → how to verify**. For complete instructions without an assistant, use the [manual runbook](3.Runbook-Manual.md).

### Picking your stack and sticking to it

The same agent ships in three stacks, and the onboarding is genuinely different in each of them, so every step that varies is organized the same way: a short introduction that explains what we're doing and why, and then three subsections, **.NET**, **Python** and **Node.js**, always in that order.

**Read the introduction, then read only your own subsection and skip the other two.** They are alternatives rather than a sequence, and nothing later in the guide expects you to have followed more than one of them. Steps that are identical whatever you're on have no subsections at all, which is how you can tell at a glance that there's nothing to choose.

Let's get started, but first, there are two things you genuinely need to know before you touch anything.

---

## ⚠️ Read this before you start
### `a365 setup all` will overwrite your bot credentials

When you run the setup command in Phase 1, it rewrites the bot channel credentials in your configuration with the **blueprint's** ones, and it replaces the bot secret **in place**. The original secret is not recoverable afterwards.

So before you start Phase 1, back the credentials up somewhere outside the repository:

```powershell
# Python and Node.js
Copy-Item .env "$env:USERPROFILE\bot-credentials-backup.env"

# .NET: record the ClientId and ClientSecret from user-secrets somewhere safe
```

We'll restore them in Step 1-3, and that step is not optional.

### The bot app and the blueprint have to stay separate

Once you see that you're managing two app registrations, it's tempting to simplify by letting the blueprint *be* the bot. It cannot be, for two independent reasons:

- Entra bars agentic applications from obtaining client-credentials tokens (you'll get `AADSTS82001`), so a blueprint can never sign the outbound Bot Framework replies.
- It's also the wrong audience for validating the inbound token from Teams.

Keep them as two identities. Everything in this guide depends on that separation.

## Phase 0: Get the agent answering in Teams first

Before we add anything, let's get the agent working in Teams exactly as it is.

> **A shortcut worth knowing about.** The .NET starting point runs in *anonymous mode* by default, meaning it accepts unauthenticated calls, so you can try the agent out with the [Microsoft 365 Agents Playground](https://www.npmjs.com/package/@microsoft/teams-app-test-tool) (`npm install -g @microsoft/teams-app-test-tool`, then `teamsapptester`) before creating any Azure resources at all. That's a good way to confirm the model configuration works in isolation. But Teams itself needs the real thing, so everything below still has to happen.

### Step 0-1. Create the bot's app registration

We start with the identity the agent uses to authenticate its replies back to the Bot Framework.

> ⚠️ **This is the app registration we called "the bot app" in the warning at the top.** It is *not* the Agent 365 blueprint. That doesn't exist yet, and when it does in Phase 1, the two have to stay separate. Keep a note of which is which from the very beginning; almost every confusing failure later on comes from mixing them up.

1. Go to the [Microsoft Entra admin center](https://entra.microsoft.com) and open **Identity** → **Applications** → **App registrations**.
2. Click **New registration**.
3. For **Name**, use something you'll recognise later, like `learn-agent-bot`.
4. Under **Supported account types**, choose **Accounts in this organizational directory only (Single tenant)** unless you specifically need the agent to work across tenants.
5. Leave **Redirect URI** empty. A bot doesn't use one.
6. Click **Register**.

On the **Overview** page that appears, copy two values and keep them somewhere handy. You'll need both several times:

| Value on the Overview page | What this guide calls it |
| --- | --- |
| **Application (client) ID** | The **bot app client id** |
| **Directory (tenant) ID** | Your **tenant id** |

Now create the secret the agent will authenticate with:

1. In the left menu, open **Certificates & secrets**.
2. On the **Client secrets** tab, click **New client secret**.
3. Give it a description and an expiry, then click **Add**.
4. **Copy the `Value` column immediately.** Not the `Secret ID`, the `Value`. It's only shown once, and there is no way to retrieve it afterwards; if you navigate away you'll have to delete the secret and create another.

> This is the secret that `a365 setup all` will overwrite in Phase 1, which is why we asked you to back it up before starting that phase. Now you know exactly which value that warning was about.

If you'd rather use the CLI:

```bash
az ad app create --display-name "learn-agent-bot" --sign-in-audience AzureADMyOrg
az ad app credential reset --id <bot-app-client-id> --append
```

The second command prints the secret in its output. Again, this is the only time you'll see it.

### Step 0-2. Create the Azure Bot resource

The app registration is an identity; it doesn't know anything about Teams. The **Azure Bot** resource is what connects that identity to the messaging channels, and it's what actually holds the messaging endpoint Teams delivers to.

1. Go to the [Azure portal](https://portal.azure.com) and search the marketplace for **Azure Bot**. Click **Create**.
2. Fill in the **Basics** tab:
| Field | What to put |
| --- | --- |
| Bot handle | A globally unique name, e.g. `learn-agent-bot-<yourname>` |
| Subscription / Resource group | Wherever you want it; create a new resource group if in doubt |
| Data residency | Global, unless your organization requires otherwise |
| Pricing tier | F0 (Free) is plenty for this guide |
| Type of App | Single Tenant, matching what you chose in Step 0-1 |
| Creation type | Use existing app registration |
| App ID | The bot app client id from Step 0-1 |
| App tenant ID | Your tenant id from Step 0-1 |

3. Click **Review + create**, then **Create**, and wait for the deployment to finish.

> **Choose "Use existing app registration", not "Create new".** If you let Azure create one for you, you'll end up with an app registration whose secret you never saw, and you need that secret in Step 0-5. It's recoverable (you can just add a new secret to whichever app it created), but it's an avoidable detour.

The equivalent CLI command, if you prefer:

```bash
az bot create \
  --resource-group <resource-group> \
  --name <bot-handle> \
  --app-type SingleTenant \
  --appid <bot-app-client-id> \
  --tenant-id <tenant-id> \
  --sku F0
```

Finally, tell the bot it should talk to Teams:

1. In the bot resource, open **Channels** in the left menu.
2. Click **Microsoft Teams**, accept the terms, and click **Apply**.
3. Confirm that **Microsoft Teams** now appears in the list of connected channels.

Without this, everything else can be perfectly configured and Teams will still refuse to route messages to your agent.

### Step 0-3. Start a dev tunnel

The bot resource now needs somewhere to deliver messages to, and since the agent is running on your laptop, Teams can't reach it. `localhost` means nothing to a cloud service. A dev tunnel gives us a public HTTPS URL that forwards straight to your machine:

```bash
devtunnel host -p 3978 --allow-anonymous
```

The output includes a line like `Connect via browser: https://abc123-3978.euw.devtunnels.ms`. That host is what we need next.

> **Read the URL from the command output.** Don't construct it. This catches people out constantly, because dev tunnel URLs look predictable and are **not** derived from the tunnel name. Copy it from the output, and keep that terminal window open for the rest of the guide: close it and the URL dies with it.

If this is your first time using dev tunnels, you'll need to sign in once first:

```bash
devtunnel user login
```

### Step 0-4. Point the bot at the tunnel

Now we tell the Azure Bot resource where to deliver messages.

1. Go back to your bot in the [Azure portal](https://portal.azure.com).
2. In the left menu, under **Settings**, click **Configuration**.
3. In the **Messaging endpoint** field, enter your tunnel host followed by `/api/messages`, so, for the example above, `https://abc123-3978.euw.devtunnels.ms/api/messages`.
4. Click **Apply** at the top of the blade, and wait for the confirmation notification.

Three things to pay attention to:

- **The `/api/messages` path is required.** The tunnel host on its own isn't an endpoint; the Microsoft 365 Agents SDK listens on that specific path.
- **It has to be `https`, not `http`.** The Bot Service will not deliver to an unencrypted endpoint.
- **No trailing slash**, and no port number in the URL. The tunnel already maps to port 3978 on your side.

Or, from the CLI:

```bash
az bot update \
  --resource-group <resource-group> \
  --name <bot-handle> \
  --endpoint "https://<tunnel-host>/api/messages"
```

> **Be aware that** every time you restart the dev tunnel, you might get a new URL, and the messaging endpoint has to be updated to match. When the agent stops responding in Teams after a break, this is the first thing to check.

### Step 0-5. Give the agent its bot credentials

The agent needs the app registration's details so it can authenticate the replies it sends back to the channel. Two values go in, the client id and the tenant id, and a third, the secret, goes somewhere the repository can't see. Where each stack puts them differs, but the shape of what we're configuring is the same everywhere: a connection called `ServiceConnection` that the Microsoft 365 Agents SDK reads at startup.

**These are the values to back up before Phase 1.** Whichever stack you're on, copy them somewhere outside the repository as soon as you've filled them in, while they're still fresh. This is the backup the warning at the top of the guide was asking for.

#### .NET

In `appsettings.json`, note that the client id goes in *two* places, because one validates inbound tokens from Teams and the other authenticates outbound replies:

```jsonc
"TokenValidation": {
  "Audiences": [ "<bot-app-client-id>" ]
},
"Connections": {
  "ServiceConnection": {
    "Settings": {
      "ClientId": "<bot-app-client-id>",
      "TenantId": "<tenant-id>"
    }
  }
}
```

The secret never goes in that file. Put it in user-secrets instead:

```powershell
dotnet user-secrets set "Connections:ServiceConnection:Settings:ClientSecret" "<bot-app-secret>"
```

> Leaving `TokenValidation.Audiences` empty is what puts the .NET starting point into anonymous mode. This is useful for the Agents Playground, but it won't work if the agent is published in Teams / Copilot.

#### Python

In `.env`, copied from the committed `.env.example`, which is safe to commit because `.env` itself is gitignored:

```bash
CONNECTIONS__SERVICE_CONNECTION__SETTINGS__CLIENTID=<bot-app-client-id>
CONNECTIONS__SERVICE_CONNECTION__SETTINGS__CLIENTSECRET=<bot-app-secret>
CONNECTIONS__SERVICE_CONNECTION__SETTINGS__TENANTID=<tenant-id>
```

#### Node.js

Also in `.env`, copied from `.env.example`, but with a different spelling of the same three keys:

```bash
Connections__ServiceConnection__Settings__ClientId=<bot-app-client-id>
Connections__ServiceConnection__Settings__ClientSecret=<bot-app-secret>
Connections__ServiceConnection__Settings__TenantId=<tenant-id>
```

> **Don't copy the Python keys across.** The JavaScript SDK parses these names as `Connections__<id>__Settings__<property>` and splits on the double underscore, so the connection id has to be a single segment: `ServiceConnection`, not `SERVICE_CONNECTION`. A key with an extra separator in it is simply discarded, it doesn't raise an error, so you end up with a server that starts up cleanly, logs `for appId undefined`, and then refuses every message Teams sends it.

Another point of attention is that the Microsoft 365 Agents SDK reads these variables while `@microsoft/agents-hosting` is being *imported*, not when the server is started, so `.env` has to be loaded before that import runs. ES module imports are all evaluated before any of the importing module's own statements, which means a `dotenv.config()` call in the body of `main.ts` executes far too late. The starting point solves it with a one-line module, `src/env.ts`, that does nothing but `import "dotenv/config"`, imported first in `src/main.ts`:

```typescript
// This import must stay first.
import "./env.js";

import { AgentApplication, MemoryStorage, TurnContext, TurnState } from "@microsoft/agents-hosting";
```

The symptom when the order slips is the same quiet `appId undefined` as above, which is why the two are worth keeping in mind together.

### Step 0-6. Configure Azure OpenAI

Next, the agent needs to know which model to reason with.

#### .NET

In `appsettings.json`:

```jsonc
"AzureOpenAI": {
  "Endpoint": "https://<your-resource>.openai.azure.com/",
  "Deployment": "<your chat deployment name>",
  "TenantId": "<tenant that owns the Azure OpenAI resource>"
}
```

#### Python

In `.env`, copied from the committed `.env.example`:

```bash
AZURE_OPENAI_ENDPOINT=https://<your-resource>.openai.azure.com
AZURE_OPENAI_DEPLOYMENT=<your chat deployment name>
AZURE_OPENAI_API_VERSION=2024-10-21
AZURE_OPENAI_TENANT_ID=<tenant that owns the Azure OpenAI resource>
```

#### Node.js

The same four settings, in `.env`:

```bash
AZURE_OPENAI_ENDPOINT=https://<your-resource>.openai.azure.com/
AZURE_OPENAI_DEPLOYMENT=<your chat deployment name>
AZURE_OPENAI_API_VERSION=2024-10-21
AZURE_OPENAI_TENANT_ID=<tenant that owns the Azure OpenAI resource>
```

`AZURE_OPENAI_DEPLOYMENT` has no default in this starting point, and `src/config.ts` throws at startup if it's missing.

---

> **Don't leave the tenant id out.** Without it, the credential returns a token from whichever tenant you last signed in to, which may not be the one that owns the Azure OpenAI resource, and the service answers `HTTP 400` with "Tenant provided in token does not match resource token". It looks like a code problem and isn't.

Now pick how the agent authenticates to Azure OpenAI. All three starting points support two paths and choose between them at startup.

|  | **Path A: Entra credentials** *(default, recommended)* | **Path B: API key** |
| --- | --- | --- |
| What it actually uses | `DefaultAzureCredential` (.NET) or `AzureCliCredential` (Python and Node.js) locally, and a managed identity once hosted on Azure | A resource key, sent as a bearer secret |
| Extra configuration | None; you just need to be signed in | The key, kept out of tracked files |
| What you need access to | The **Cognitive Services OpenAI User** role on the resource | The resource keys |
| Why you'd pick it | No long-lived secret, and it's the only option in tenants where key auth is disabled by policy | Environments that still depend on keys |

For **Path A**, sign in and make sure no key is set anywhere, including in user-secrets:

```bash
az login --tenant <tenant of the Azure OpenAI resource>
```

Once hosted on Azure, .NET picks up the assigned managed identity automatically; Python and Node.js each need one extra setting, `AZURE_OPENAI_USE_MANAGED_IDENTITY=true`.

For **Path B**, keep the key outside the committed files:

```bash
# .NET
dotnet user-secrets set "AzureOpenAI:ApiKey" "<key>"   # or the AzureOpenAI__ApiKey env var

# Python and Node.js, in .env, which is gitignored
AZURE_OPENAI_API_KEY=<key>
```

### Step 0-7. Run the agent and sideload it into Teams

It's time to test the agent. First, we start the agent so it's listening on the port the dev tunnel from Step 0-3 forwards to, and then we get it into Teams, which is a separate job because Teams doesn't discover bots on its own: it installs *apps*, and an app is a zip file containing a manifest plus two icons.

Starting the agent is the only part that depends on your stack.

#### .NET

```bash
dotnet run
```

#### Python

```bash
uv run python -m app.main
```

#### Node.js

```bash
npm install
npm start
```

`npm start` runs `tsx src/main.ts`, which transpiles the TypeScript as it loads it, so there's no build step and no `dist/` folder to keep in step with the sources.

---

Whichever you ran, the agent now listens on `http://localhost:3978`, and you should see a line confirming the port and the bot app id it picked up.

Now for the app package. Each starting point ships a script that fills in the manifest placeholders and builds the zip for you, and it works the same way in all three:

```powershell
./build-app-package.ps1 -BotId <bot-app-client-id>
```

The only thing you have to supply is `-BotId`, the bot app client id from Step 0-1. That's what tells Teams which bot to route your messages to.

The manifest also needs a second identifier, the **Teams app id**, which identifies the *app package* rather than the bot. It's unrelated to any Entra identity and doesn't correspond to anything in Azure, so the script generates one for you on the first build and caches it in `teams-app-id.local.json`, next to the script. Every later build reads it back from there.

That caching is the whole point, and it's worth understanding rather than treating as an implementation detail: Teams uses this id to decide whether an upload is an **update to the app you already installed** or a **completely new app**. If it changed on every build, each rebuild would leave you with yet another copy of the agent cluttering your app list. The file matches the repository's `.gitignore` pattern for `*.local.json`, so it stays on your machine and never ends up in a commit.

Because each starting point keeps its own cache file next to its own script, the three stacks get different Teams app ids automatically, which is what lets you install more than one of them in the same tenant without the second replacing the first.

If you already have a Teams app id, say you're rebuilding a package for an app that's already published, pass it explicitly and the script uses that instead:

```powershell
./build-app-package.ps1 -BotId <bot-app-client-id> -TeamsAppId <existing-teams-app-id>
```

Then sideload the resulting `appPackage.zip`:

1. Open Microsoft Teams and go to **Apps** in the left rail.
2. Click **Manage your apps** at the bottom, then **Upload an app**.
3. Choose **Upload a custom app** and select `appPackage.zip`.
4. Click **Add** on the dialog that appears.

> If **Upload a custom app** isn't there, custom app uploading is disabled for your account. That's the "Teams app upload permission" from the prerequisites, and a Teams administrator has to enable it for you.

Because the manifest declares `copilotAgents.customEngineAgents` and includes `copilot` in the bot's scopes, this same package also surfaces the agent inside Microsoft 365 Copilot.

### Step 0-8. Verify

Message the agent in Teams and ask it something it should be able to answer:

```text
What is Microsoft Entra Conditional Access?
```

You should get an answer with links to Microsoft Learn, because this agent grounds its answers in the Microsoft Learn MCP server rather than answering from the model's own knowledge.

If nothing comes back, the problem is almost always in the plumbing we just built rather than in the agent:

| What you see | Where to look |
| --- | --- |
| No reply at all, and nothing in the agent's console | The messaging endpoint is wrong, or the tunnel died; Steps 0-3 and 0-4 |
| The agent logs a request but Teams shows an error | The bot credentials don't match the app registration; Step 0-5 |
| `401` in the agent's console | `TokenValidation.Audiences` doesn't contain the bot app client id (.NET), or the connection keys aren't being read at all (Node.js); Step 0-5 |
| The console says `for appId undefined` on Node.js | The `Connections__…` keys are misspelled, or `.env` is loaded after the SDK import; Step 0-5 |
| The agent replies in the Agents Playground but not in Teams | The Teams channel isn't enabled on the bot; Step 0-2 |
| An error about the Azure OpenAI endpoint or deployment | Step 0-6 |
| `404 DeploymentNotFound` on the first question | The deployment name doesn't exist on your resource; Step 0-6 |

✅ **Checkpoint.** The agent answers in Teams. There's no Agent 365 anything yet. That starts now.

## Phase 1: Register the agent

In this phase, the agent becomes an object in your tenant rather than just a bot behind an endpoint.

Registration creates two things: a **blueprint**, which is the parent app registration holding the permissions, and an **agent identity**, a child principal of that blueprint. Note that neither of them replaces your bot app registration. As we said at the top, all three have to coexist.

### Step 1-1. Back up your bot credentials

Do this now, before anything else, for the reasons explained in the warning at the top of this guide. These are the values you set in Step 0-5: the bot app client id, secret and tenant id. The next step will overwrite them, and the secret in particular cannot be recovered afterwards.

### Step 1-2. Run the setup skill

**What you type**

```text
Set up Agent 365 for this agent. It's a custom engine agent hosted in Teams
with its own bot registration, not an AI Teammate. Use the OBO auth mode.
```

**What the skill does**

`a365-setup` verifies the prerequisites and your Azure identity, then asks the two questions that shape everything downstream:

| Question | Your answer for this scenario | Why |
| --- | --- | --- |
| Agent kind? | **Agent (Non AI Teammate)** | A human drives it, and it has its own bot registration |
| Auth mode? | **`obo`** | Attribution follows the Teams user who sent the message |

It then hands off to `make-a365-agent`, which performs the registration.

> ⚠️ **There's a genuine gap in the skills here,** `instrument-observability` only offers you two auth modes: `obo`, which means the *agentic* on-behalf-of path with its MSAL/FMI token chain, and `s2s`. Neither is exactly "custom engine agent using OBO through the Bot Framework". Answer `obo`, because it's the closer of the two, but **do not accept the token code it generates without checking it against Phase 2 below**, because the chain it writes is one you don't need on this path and that won't work here. The details are in [Known Skill Gaps](../../03-references/Known-Skill-Gaps.md).

**Behind the scenes**

```bash
a365 setup all --agent-name "my-agent" --m365 --dry-run   # preview first
a365 setup all --agent-name "my-agent" --m365             # apply
a365 setup permissions bot                                # required after --m365
```

## Phase 2: Observability

Now we make the agent report what it does. By the end of this phase, every message it handles produces telemetry attributed to the Teams user who sent it.

Here's the shape of the phase before we start. Unlike the web app scenario, we're not going to write a token chain: we're going to configure an OAuth connection on the Azure Bot resource, and let the Bot Framework Token Service do the on-behalf-of exchange for us. The code we write is small: one call to get a token, a baggage scope, and the semantic spans. The configuration around it is where the care is needed.

### Step 2-1. Create the OAuth connection

Before writing any code or using any skill, you must create the OAuth connection as following in the Azure Bot configuration:

```bash
az bot authsetting create -g <resource-group> -n <azure-bot-name> \
  -c oboConnectionProfile \
  --client-id <bot-app-client-id> --client-secret <bot-app-secret> \
  --service AadV2 \
  --provider-scope-string \
    "api://9b975845-388f-4429-889e-eab1ef63949c/Agent365.Observability.OtelWrite" \
  --parameters tenantID=<tenant-id> tokenExchangeUrl=api://botid-<bot-app-client-id>
```

That's a dense command, so let's go through the three arguments:

- **`--provider-scope-string` must be a *named* scope**, exactly as written above, otherwise leaving the default in place produces `401 InvalidAudience` when the exporter tries to use the token.
- **`tokenExchangeUrl`** is what keeps Teams SSO silent, so that the user isn't prompted to sign in again. The Teams manifest declares a single `webApplicationInfo.resource`, and this connection exchanges that SSO token for its own.
- **`--client-id` is the bot app registration, not the blueprint.** This is what makes the `azp` claim on the resulting token correct.

> The resource id `9b975845-…` and the scope name are preview-era values. Re-verify them against the current documentation before assuming they're still right.

### Step 2-3. Wire the exporter into the entry point

Now we initialise the distro when the process starts. All three stacks are doing the same two things: telling the distro to actually export rather than merely decorate spans, and handing it a callback it can use to fetch a token later. What differs is where that initialisation has to sit relative to everything else, and every stack has its own version of that problem.

#### .NET

In `Program.cs`. Pay attention to the order of registration here:

```csharp
var observabilityTokenStore = new ObservabilityTokenStore();
builder.Services.AddSingleton(observabilityTokenStore);

// Registered BEFORE UseMicrosoftOpenTelemetry so this processor sits ahead of the
// A365 export processor: OnEnd runs in registration order, and the identity has to be
// on the span before the exporter reads it.
builder.Services.AddOpenTelemetry()
    .WithTracing(t => t.AddProcessor(new BaggageBackfillProcessor()));

builder.UseMicrosoftOpenTelemetry(o =>
{
    o.Exporters = ExportTarget.Agent365;
    // Exporting to Agent 365 alone suppresses infrastructure instrumentation.
    o.Instrumentation.EnableAspNetCoreInstrumentation = true;
    o.Instrumentation.EnableHttpClientInstrumentation = true;
    o.Instrumentation.EnableAzureSdkInstrumentation = true;
});
```

> **Registration order is load-bearing in .NET.** The backfill processor has to be registered *before* `UseMicrosoftOpenTelemetry`, because `OnEnd` runs in registration order and the identity has to be attached to the span before the exporter reads it. Get the order wrong and the inference span, the prompt, the system instructions and the completion, in other words the interesting part, is dropped. The agent still answers, Defender still shows the parent span, and the LLM call is simply invisible.

#### Python

This has to run before any LangChain or Azure OpenAI import, so put it at the very top of `app/main.py`, above the agent imports:

```python
use_microsoft_opentelemetry(
    enable_a365=True,
    a365_enable_observability_exporter=True,
    a365_token_resolver=token_store.get,
    # The delegated route. Its S2S counterpart takes application tokens only and
    # refuses a delegated one; the two are not interchangeable.
    a365_use_s2s_endpoint=False,
    enable_sensitive_data=True,
    disable_metrics=True,
)
```

The distro works by patching LangChain and the Azure OpenAI SDK as they load, so if they're imported first the auto-instrumentation silently doesn't attach and you end up with no `chat` spans at all. The agent works perfectly, and the LLM calls are simply invisible.

#### Node.js

Node has the same two-switch design as Python and the same load-order sensitivity, but it's rather less forgiving about the second one, because moving a line up the file doesn't fix it. Create a small dedicated module instead, `src/observability.ts`:

```typescript
import { useMicrosoftOpenTelemetry } from "@microsoft/opentelemetry";

import { tokenStore } from "./token-store.js";

useMicrosoftOpenTelemetry({
    a365: {
        enabled: true,
        // Both flags are needed: `enabled` alone only registers the span processors.
        enableObservabilityExporter: true,
        tokenResolver: async (agentId, tenantId) => tokenStore.get(agentId, tenantId) ?? "",
        // The delegated route, same reasoning as the other two stacks.
        useS2SEndpoint: false,
    },
    instrumentationOptions: {
        langchain: {},
    },
    // Writes prompts and completions onto the spans. Useful while you're learning to read
    // the telemetry, worth reconsidering before this reaches production.
    enableSensitiveData: true,
    // Also print the spans to the terminal while developing.
    enableConsoleExporters: true,
});
```

Note that `enableSensitiveData` and `enableConsoleExporters` sit at the top level rather than inside the `a365` block, because they apply to the whole distro rather than to the Agent 365 exporter specifically. They're the Node equivalents of `EnableSensitiveData` and the `Console` export target on .NET.

Then make it the very first import in `src/main.ts`, above the one that loads `.env`:

```typescript
import "./observability.js";
import "./env.js";

import { AgentApplication, MemoryStorage, TurnContext, TurnState } from "@microsoft/agents-hosting";
```

> **Why a separate file rather than a call at the top of `main.ts`?** Because ES module imports are hoisted. Every `import` in a module is resolved and executed before any of that module's own statements run, so `import { LearnAgent } from "./agent.js"` pulls in LangChain and the Azure OpenAI SDK *before* a `useMicrosoftOpenTelemetry()` call sitting in the body of the same file ever executes. The patching then has nothing left to attach to. Putting the call in its own module and importing that module first is what guarantees it runs before LangChain loads. This is exactly the Python trap above, except that on Python you can fix it by moving a line and on Node you can't.

One good news about the Node distro: LangChain auto-instrumentation is on by default, so passing `instrumentationOptions.langchain` is really just making the intent explicit. You get `chat` spans without doing anything else. For the same reason, don't also register the LangChain instrumentation by hand, because doing both produces every span twice.

Finally, because Node processes usually exit on a signal rather than draining politely, flush on the way out:

```typescript
import { shutdownMicrosoftOpenTelemetry } from "@microsoft/opentelemetry";

for (const signal of ["SIGINT", "SIGTERM"] as const) {
    process.once(signal, () => {
        void shutdownMicrosoftOpenTelemetry().finally(() => process.exit(0));
    });
}
```

Without this, the last batch of spans is still sitting in the exporter's queue when the process dies, and the final turn of every debugging session goes missing.

### Step 2-4. Get the observability agent id right

Three separate values have to be identical:

```text
gen_ai.agent.id  ==  the token's azp  ==  the token store key
```

And for a custom engine agent, all three are the bot app registration's client id, not the agent identity and not the blueprint. If they don't match, the export fails with `HTTP 403`.

You might be tempted to use the agent identity and blueprint identifiers, but the token comes from the Bot Framework OAuth connection we created in Step 2-1, and that connection was configured with the bot app's client id, so the bot app is what the token says it is, and the service checks.

This wasn't deduced from documentation, incidentally. It was tested against the live service with one token and three candidate ids:

| Id used in the export URL | Result |
| --- | --- |
| Agent identity | `403` |
| Blueprint | `403` |
| **Bot app registration** | `415`: authorised, and merely the wrong content type for the probe |

A `415` there is a success: it means the request got past authorization.

The safest way to get it right, whatever you're on, is to read the value from the SDK's own connection settings rather than duplicating it in a second place where the two can drift apart.

#### .NET

```csharp
var observabilityAgentId = builder.Configuration["Connections:BotConnection:Settings:ClientId"];
```

#### Python

```python
@property
def observability_agent_id(self) -> str:
    return self.bot_client_id   # from CONNECTIONS__SERVICE_CONNECTION__SETTINGS__CLIENTID
```

#### Node.js

```typescript
observabilityAgentId: required("Connections__ServiceConnection__Settings__ClientId"),
```

Adding it to the settings object in `src/config.ts` this way is a little unusual, since that file otherwise keeps the SDK's own keys out of it, but it's the lesser of two evils: the alternative is a second copy of the same client id under a different name, and the day somebody updates one and not the other you get a `403` with nothing to point at.

### Step 2-5. Get the token

Here's the entire token acquisition for this scenario, and it's the same single call whatever you're on: ask the Agents SDK's authorization layer for a token from the handler backed by the OAuth connection we created in Step 2-1.

The connection is already scoped to the Observability API, so the Bot Framework Token Service performs the on-behalf-of exchange internally and hands back a finished token.

The code must be called **at the start of the turn**, before you generate the answer, so the token is already sitting in the store when the first spans flush.

#### .NET

```csharp
var tokenResponse = await authorization.GetTokenAsync(turnContext, OboAuthHandler);
observabilityTokenStore.Set(observabilityAgentId, tenantId, tokenResponse.Token);
```

#### Python

```python
token_response = await AUTHORIZATION.get_token(context, OBO_AUTH_HANDLER)
token_store.set(settings.observability_agent_id, settings.a365_tenant_id, token_response.token)
```

#### Node.js

The handler lives on the `AgentApplication` you already created, as `agentApp.authorization`:

```typescript
async function publishObservabilityToken(context: TurnContext): Promise<void> {
    try {
        const response = await agentApp.authorization.getToken(context, settings.oboAuthHandler);

        if (response.token) {
            tokenStore.set(settings.observabilityAgentId, settings.a365TenantId, response.token);
        }
    } catch (error) {
        // Losing traces is never a reason to fail the user's question.
        console.warn("Could not get an observability token for this turn.", error);
    }
}
```

The handler itself is configured from the environment rather than in code, using a naming convention of the same family as the connection keys from Step 0-5:

```bash
AgentApplication__UserAuthorization__Handlers__obo__Settings__azureBotOAuthConnectionName=oboConnectionProfile
```

`obo` in the middle of that key is the handler id, and it's the string you pass to `getToken` as the second argument. Name it whatever you like, as long as the two agree.

### Step 2-6. Open a baggage scope

Baggage is how OpenTelemetry carries contextual values alongside the execution context, and Agent 365 uses it to carry the identity dimensions it partitions telemetry on: tenant, agent, user, conversation. Spans emitted outside an active baggage scope are dropped outright.

The values are the same in all three stacks, and so is the rule that the scope has to stay open for the whole turn. What differs is how each language expresses "for the whole turn".

Two important things to keep in mind:

- **The channel name is `msteams`, not `web`.** The exporter records whatever you give it verbatim, so a wrong value doesn't fail. It just quietly misreports where the activity came from.
- **The agent id in baggage must equal the one in `AgentDetails`.** Use a single source value for both. If they disagree, the turn is split into *two* identity groups, only one of which has a token, and you end up with half your spans arriving and half disappearing.

#### .NET

```csharp
using var scope = new BaggageBuilder()
    .TenantId(settings.A365TenantId)
    .AgentId(settings.ObservabilityAgentId)
    .AgentName(agentName)
    .AgentBlueprintId(settings.A365BlueprintId)
    .ConversationId(conversationId)
    .SessionId(conversationId)
    .UserId(user.Id).UserName(user.Name).UserEmail(user.Email)
    .ChannelName("msteams")
    .Build();
```

The `using` keeps the scope open until the end of the enclosing block, so make sure the agent invocation happens inside that block.

#### Python

```python
with (
    BaggageBuilder()
    .tenant_id(settings.a365_tenant_id)
    .agent_id(settings.observability_agent_id)
    .agent_name(agent_name)
    .agent_blueprint_id(settings.a365_blueprint_id)
    .conversation_id(conversation_id)
    .session_id(conversation_id)
    .user_id(user["id"]).user_name(user["name"]).user_email(user["email"])
    .channel_name("msteams")
    .build()
):
    answer = await agent.ask(conversation_id, message)
```

#### Node.js

Node's builder is the same fluent shape, but `.build()` gives you a scope you `run()` a callback inside rather than something that closes at the end of a block:

```typescript
import { BaggageBuilder } from "@microsoft/opentelemetry";

const scope = new BaggageBuilder()
    .tenantId(settings.a365TenantId)
    .agentId(settings.observabilityAgentId)
    .agentName(agentName)
    .agentBlueprintId(settings.a365BlueprintId)
    .conversationId(conversationId)
    .sessionId(conversationId)
    .userId(user.id)
    .userName(user.name)
    .userEmail(user.email)
    .channelName("msteams")
    .build();

const answer = await scope.run(() => learnAgent.ask(conversationId, question));
```

The callback shape is doing the same job as `using` on .NET and `with` on Python: it defines the region of code the baggage is active for.

### Step 2-7. Work out who the caller is

This is simpler than in the web app scenario. There, we had a signed-in principal to inspect; here there isn't one, because the user never signs in to your app; they message it through Teams.

Instead, read the user off the incoming activity: their `id`, `name` and `email`. The channel tells you who sent the message, and that's the identity the activity gets attributed to.

The advice is to prefer the caller's **directory object id** over the channel-local id where the activity carries it, because that's what the Microsoft 365 admin center resolves to a person. On the Microsoft 365 Agents SDK that's `context.activity.from?.aadObjectId`, with `context.activity.from?.id` as the fallback for channels that don't supply it. Give the exporter the channel-local id and the export still returns `HTTP 200` and the row still arrives, it just never resolves to anybody.

### Step 2-8. Wrap the turn in the semantic scopes

Agent 365 doesn't accept arbitrary spans. It only ingests those whose `gen_ai.operation.name` is one of `invoke_agent`, `chat`, `execute_tool` or `output_messages`, and drops everything else span by span. The one that matters most is `invoke_agent`, because it becomes the root span of the turn and it's the only span the Microsoft 365 admin center ingests.

> **Session, conversation and channel have to be on the request object, not only in baggage.** This is a subtle one, because baggage *does* land on the span tags, so the information looks like it's there. But the exported `invoke_agent` payload is built from the request object you pass to the scope. Omit them and you export a span that's accepted and yet shows no run context at all.

#### .NET

```csharp
var request = new Request(
    content: message,
    sessionId: conversationId,
    conversationId: conversationId,
    channel: new Channel("msteams"));

using var invokeScope = InvokeAgentScope.Start(
    request,
    new InvokeAgentScopeDetails(endpoint),
    agentDetails,
    callerDetails);
```

#### Python

```python
with InvokeAgentScope.start(
    request=Request(
        content=message,
        session_id=conversation_id,
        conversation_id=conversation_id,
        channel=Channel(name="msteams"),
    ),
    invoke_scope_details=InvokeAgentScopeDetails(endpoint=endpoint),
    agent_details=agent_details,
    caller_details=caller_details,
):
    answer = await agent.ask(conversation_id, message)
```

If you're on Python with LangChain, there's one more thing to do here. Turn off the enrichers you aren't using:

```python
instrumentation_options={
    "openai_agents": {"enabled": False},
    "agent_framework": {"enabled": False},
    "semantic_kernel": {"enabled": False},
}
```

The reason is a registration race. The Agent Framework enrichers register first, and their presence makes the distro skip the LangChain enricher, which is the one that actually maps this agent's messages and conversation id into the shape Agent 365 expects. So you end up with spans that are technically fine and semantically empty. `openai_agents` is disabled because it isn't used here, and leaving it on makes the distro log an import traceback on every start.

#### Node.js

Two naming details to know before you write this. First, the request contract is exported as **`A365Request`** rather than `Request`, because `Request` is already a global in Node's own type definitions and importing a second one produces confusing errors. Second, the scope makes itself the active span through `withActiveSpanAsync`, which takes a callback in the same way the baggage scope does:

```typescript
import { InvokeAgentScope, type A365Request } from "@microsoft/opentelemetry";

const request: A365Request = {
    content: question,
    sessionId: conversationId,
    conversationId,
    channel: { name: "msteams" },
};

const invokeScope = InvokeAgentScope.start(
    request,
    { endpoint: { host: "teams.microsoft.com", protocol: "https" } },
    agentDetails,
    callerDetails,
);

try {
    const answer = await invokeScope.withActiveSpanAsync(() => learnAgent.ask(conversationId, question));
    invokeScope.recordResponse(answer);
    return answer;
} catch (error) {
    invokeScope.recordError(error as Error);
    throw error;
} finally {
    invokeScope.dispose();
}
```

The `try`/`catch`/`finally` is doing what `using` does on .NET. The `finally` is the important half: a scope that's never disposed is a span that's never ended, and a span that's never ended is never exported, so a turn that throws would vanish entirely rather than generating a failure. Note also that the Node scope spells failure as `recordError` and completion as `dispose`, so if you're translating from the .NET sample by eye, don't go looking for `SetError` and `End`.

The Node distro instruments LangChain by default, so `chat` spans for the model call and `execute_tool` spans for the Microsoft Learn MCP calls should appear without any further work.

### Step 2-9. Verify that telemetry is actually leaving

Before going anywhere near Defender, let's confirm from the agent's own logs that spans are being exported:

```powershell
$env:OTEL_LOG_LEVEL="INFO"
$env:A365_OBSERVABILITY_LOG_LEVEL="debug"
```

Send a message from Teams and read the output. On Node.js you'll already have the spans in front of you if you left `enableConsoleExporters` on in Step 2-3. Four things need to be true:

- `Partitioned into 1 identity groups`: **not 0, and not 2**
- there's an `invoke_agent` span, and it's a **root** span
- the export returns `HTTP 200`
- the agent id in the export URL is the **bot app client id**

Those two failure numbers mean different things. **Zero** means there was no baggage scope active around the turn. **Two** means baggage and `AgentDetails` disagree about the agent id. Go back to Step 2-6.

✅ **Checkpoint.** This is a good place to stop. The agent is registered and observable.

| What you see | Where the problem is |
| --- | --- |
| Nothing anywhere | The token, the agent id, or the baggage scope; Steps 2-4 to 2-6 |
| `403` on the export | `gen_ai.agent.id` isn't the bot app client id; Step 2-4 |
| `401 InvalidAudience` | The OAuth connection is on `/.default` instead of the named scope; Step 2-1 |
| Half the spans missing | Baggage and `AgentDetails` disagree, so you have two identity groups; Step 2-6 |
| Defender ✅, admin center ❌ | Your `invoke_agent` span, usually the caller; Step 2-7 |
| The agent stopped answering after a restart | `a365 setup all` overwrote the bot credentials; Step 1-3 |

## Troubleshooting

If something isn't working, this table covers the failures you're most likely to hit, and where each one comes from. The first group applies whatever you're writing in; the second group is stack-specific.

| Symptom | Likely cause |
| --- | --- |
| `403` on the export route | The agent id, the token's `azp` and the store key don't all match; Step 2-4 |
| `401 InvalidAudience` | The OAuth connection scope is wrong; Step 2-1 |
| `AADSTS82001` | You tried to use the blueprint as the bot. They must stay separate |
| `Partitioned into 0 identity groups` | No baggage scope around the turn; Step 2-6 |
| `Partitioned into 2 identity groups` | Baggage and `AgentDetails` disagree on the agent id; Step 2-6 |
| `HTTP 200` but nothing lands anywhere | No user in the tenant holds an Agent 365 licence |
| Teams stopped reaching the agent | The dev tunnel URL changed and the messaging endpoint wasn't updated; Step 0-4, or the bot credentials were overwritten; Step 1-3 |
| The activity arrives but resolves to nobody in the admin center | The caller id is the channel-local id rather than the directory object id; Step 2-7 |
| `404 DeploymentNotFound` on the first question | The chat deployment name doesn't exist on your Azure OpenAI resource; Step 0-6 |

And the ones that only affect one stack:

| Symptom | Stack | Likely cause |
| --- | --- | --- |
| The inference span is missing | .NET | The backfill processor was registered after `UseMicrosoftOpenTelemetry`; Step 2-3 |
| `401` in the agent's console, and it works in the Playground | .NET | `TokenValidation.Audiences` is still empty, which is what anonymous mode looks like; Step 0-5 |
| No `chat` spans | Python | The distro was initialised after LangChain was imported; Step 2-3 |
| `chat` spans exist but carry no messages | Python | The Agent Framework or Semantic Kernel enrichers won the registration race; disable them as in Step 2-8 |
| No `chat` spans | Node.js | `./observability.js` isn't the first import in `main.ts`, so LangChain was loaded before the distro could patch it; Step 2-3 |
| Every span appears twice | Node.js | The LangChain instrumentation was registered by hand as well as by the distro, which enables it by default; Step 2-3 |
| The console says `for appId undefined` and Teams gets no reply | Node.js | The `Connections__…` keys are misspelled, or `.env` is loaded after the SDK import; Step 0-5 |
| The last turn's spans never arrive | Node.js | The process exited before the exporter flushed. Add the `shutdownMicrosoftOpenTelemetry()` handler from Step 2-3 |
| Breakpoints land in the wrong file | Node.js | You're debugging compiled output. Run through `npm run dev`, which executes the TypeScript directly; Step 0-7 |

## Wrapping up

We started with a Teams agent that worked but told nobody anything, and we ended with one that's registered in the tenant, reports every turn to Defender and the admin center attributed to the Teams user who sent the message, and can reach Microsoft 365 data under that user's permissions.

Compared to the web scenario, in this case we had very little code to write on our own. The two-hop token chain we'd have written by hand in a web app was replaced by a single OAuth connection on the Azure Bot resource and one call to `get_token`. In exchange, the difficulty moved into configuration: the named scope on that connection, the `--m365` follow-up command, the agent id that has to be the bot app rather than the agent identity, and the bot credentials that setup quietly overwrites. None of those produce a compiler error. All of them produce an HTTP status code and a puzzled afternoon, which is why we walked through each one.

If you want to compare your result with a finished implementation, the [.NET agent](https://github.com/qmatteoq/agent365-demos/tree/main/dotnet-agent-teams) and the [Python agent](https://github.com/qmatteoq/agent365-demos/tree/main/python-agent-teams) both live in the demos repository. For Node.js, the [starting point in this repository](0.Resources/Starting-point/nodejs/) is the reference: it's the same agent, and its README covers the parts of the setup that are specific to that stack.
