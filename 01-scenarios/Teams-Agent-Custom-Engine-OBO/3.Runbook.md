# Step-by-Step Guide — Teams Agent with Custom Engine OBO

> **Scenario**: Onboarding a Teams-hosted custom engine agent into Microsoft Agent 365
> **Platform**: Microsoft Agent 365 · Azure Bot Service · Microsoft Entra ID · OpenTelemetry
> **Stacks**: .NET Agent Framework · Python + LangChain
> **Target Readers**: Agent developers, Azure and Entra administrators
> **Last Updated**: February 2026

## Introduction

In this guide we're going to take a **custom engine agent** that already lives in Microsoft Teams and onboard it into Microsoft Agent 365.

By custom engine agent we mean an agent you built yourself, with your own reasoning loop and your own model, hosted on your favorite platform; the agent uses an Azure Bot registration to handle the communication channel between the user and the target platform (in our case, Teams and Copilot). However, despite this agent is running inside the Microsoft 365 ecosystem, it doesn't tell the organization anything about what it's doing. There's no record of which user asked what, which tools were called, or which data was touched.

Agent 365 is what turns that black box into something governed. It gives the agent a registered identity, publishes its activity to Microsoft Defender, Microsoft Purview and the Microsoft 365 admin center, and opens a controlled path to Microsoft 365 data.

If you've already read the [web app scenario](../Web-App-Agent-User-OBO/3.Runbook.md), you'll find this one has a different approach to manage authorization and authentication. There, we hand-wrote a two-hop token exchange. Here, there's much less code and much more configuration, because the Bot Framework Token Service performs the on-behalf-of exchange for us. Almost all of the difficulty in this scenario lives in Azure Bot Service, not in your source files. 

As usual, we're going to drive most of the work with an AI coding assistant running the [Agent 365 Skills](https://github.com/microsoft/agent365-skills), and every step also shows the CLI command or code underneath, so you can do it by hand or review what the skill produced.

The work is split into phases, and each phase is a valid place to stop:

| Phase | What you get at the end of it | Rough time |
| --- | --- | --- |
| 0 — Get it working | An Azure Bot, a Teams agent that answers, and the tooling installed | 60–90 min |
| 1 — Registration | The agent exists in your tenant as a governed identity | 30 min |
| 2 — Observability | Activity in Defender, Purview and the admin center | 60–90 min |
| 3 — Work IQ | Access to Microsoft 365 data | 30 min |
| 4 — Verification | Proof that it works end to end | 30 min |

One thing that's worth knowing up front: this scenario has you moving between a lot of different portals. Here's the full list, so nothing comes as a surprise:

| Where | URL | What you'll do there |
| --- | --- | --- |
| Your terminal | — | Skills, CLI, builds, the dev tunnel |
| Azure portal | https://portal.azure.com | Creating the Azure Bot resource, its channels and its OAuth connections |
| Microsoft Entra admin center | https://entra.microsoft.com | App registrations and consent |
| Microsoft Teams | — | Sideloading the app package and testing the agent |
| Microsoft 365 admin center | https://admin.cloud.microsoft | Agent inventory and activity |
| Microsoft Defender | https://security.microsoft.com | Advanced hunting |

From Phase 1 onwards, each step follows the same structure: **what you type → what the skill does → behind the scenes → how to verify**. If you'd rather work manually, read the last two parts and skip the rest.

Let's get started — but first, there are two things you genuinely need to know before you touch anything.

---

## ⚠️ Read this before you start
### `a365 setup all` will overwrite your bot credentials

When you run the setup command in Phase 1, it rewrites the bot channel credentials in your configuration with the **blueprint's** ones, and it replaces the bot secret **in place**. The original secret is not recoverable afterwards.

So before you start Phase 1, back the credentials up somewhere outside the repository:

```powershell
# Python
Copy-Item .env "$env:USERPROFILE\bot-credentials-backup.env"

# .NET: record the ClientId and ClientSecret from user-secrets somewhere safe
```

We'll restore them in Step 1-3, and that step is not optional.

### The bot app and the blueprint have to stay separate

Once you see that you're managing two app registrations, it's tempting to simplify by letting the blueprint *be* the bot. It cannot be, for two independent reasons:

- Entra bars agentic applications from obtaining client-credentials tokens — you'll get `AADSTS82001` — so a blueprint can never sign the outbound Bot Framework replies.
- It's also the wrong audience for validating the inbound token from Teams.

Keep them as two identities. Everything in this guide depends on that separation.

## Phase 0: Get the agent answering in Teams first

Before we add anything, let's get the agent working in Teams exactly as it is.

> **A shortcut worth knowing about.** The .NET starting point runs in *anonymous mode* by default, meaning it accepts unauthenticated calls, so you can try the agent out with the [Microsoft 365 Agents Playground](https://www.npmjs.com/package/@microsoft/teams-app-test-tool) (`npm install -g @microsoft/teams-app-test-tool`, then `teamsapptester`) before creating any Azure resources at all. That's a good way to confirm the model configuration works in isolation. But Teams itself needs the real thing, so everything below still has to happen.

### Step 0-1. Create the bot's app registration

We start with the identity the agent uses to authenticate its replies back to the Bot Framework.

> ⚠️ **This is the app registration we called "the bot app" in the warning at the top.** It is *not* the Agent 365 blueprint — that doesn't exist yet, and when it does in Phase 1, the two have to stay separate. Keep a note of which is which from the very beginning; almost every confusing failure later on comes from mixing them up.

1. Go to the [Microsoft Entra admin center](https://entra.microsoft.com) and open **Identity** → **Applications** → **App registrations**.
2. Click **New registration**.
3. For **Name**, use something you'll recognise later, like `learn-agent-bot`.
4. Under **Supported account types**, choose **Accounts in this organizational directory only (Single tenant)** unless you specifically need the agent to work across tenants.
5. Leave **Redirect URI** empty — a bot doesn't use one.
6. Click **Register**.

On the **Overview** page that appears, copy two values and keep them somewhere handy — you'll need both several times:

| Value on the Overview page | What this guide calls it |
| --- | --- |
| **Application (client) ID** | The **bot app client id** |
| **Directory (tenant) ID** | Your **tenant id** |

Now create the secret the agent will authenticate with:

1. In the left menu, open **Certificates & secrets**.
2. On the **Client secrets** tab, click **New client secret**.
3. Give it a description and an expiry, then click **Add**.
4. **Copy the `Value` column immediately.** Not the `Secret ID` — the `Value`. It's only shown once, and there is no way to retrieve it afterwards; if you navigate away you'll have to delete the secret and create another.

> This is the secret that `a365 setup all` will overwrite in Phase 1, which is why we asked you to back it up before starting that phase. Now you know exactly which value that warning was about.

If you'd rather use the CLI:

```bash
az ad app create --display-name "learn-agent-bot" --sign-in-audience AzureADMyOrg
az ad app credential reset --id <bot-app-client-id> --append
```

The second command prints the secret in its output — again, the only time you'll see it.

### Step 0-2. Create the Azure Bot resource

The app registration is an identity; it doesn't know anything about Teams. The **Azure Bot** resource is what connects that identity to the messaging channels, and it's what actually holds the messaging endpoint Teams delivers to.

1. Go to the [Azure portal](https://portal.azure.com) and search the marketplace for **Azure Bot**. Click **Create**.
2. Fill in the **Basics** tab:

   | Field | What to put |
   | --- | --- |
   | **Bot handle** | A globally unique name, e.g. `learn-agent-bot-<yourname>` |
   | **Subscription** / **Resource group** | Wherever you want it; create a new resource group if in doubt |
   | **Data residency** | Global, unless your organization requires otherwise |
   | **Pricing tier** | **F0 (Free)** is plenty for this guide |
   | **Type of App** | **Single Tenant**, matching what you chose in Step 0-1 |
   | **Creation type** | **Use existing app registration** |
   | **App ID** | The **bot app client id** from Step 0-1 |
   | **App tenant ID** | Your **tenant id** from Step 0-1 |

3. Click **Review + create**, then **Create**, and wait for the deployment to finish.

> **Choose "Use existing app registration", not "Create new".** If you let Azure create one for you, you'll end up with an app registration whose secret you never saw — and you need that secret in Step 0-5. It's recoverable (you can just add a new secret to whichever app it created), but it's an avoidable detour.

The equivalent CLI command, if you prefer:

```bash
az bot create \
  --resource-group <resource-group> \
  --name <bot-handle> \
  --app-type SingleTenant \
  --appid <bot-app-client-id> \
  --tenant-id <tenant-id> \
  --sku F0
```

Finally, tell the bot it should talk to Teams:

1. In the bot resource, open **Channels** in the left menu.
2. Click **Microsoft Teams**, accept the terms, and click **Apply**.
3. Confirm that **Microsoft Teams** now appears in the list of connected channels.

Without this, everything else can be perfectly configured and Teams will still refuse to route messages to your agent.

### Step 0-3. Start a dev tunnel

The bot resource now needs somewhere to deliver messages to — and since the agent is running on your laptop, Teams can't reach it. `localhost` means nothing to a cloud service. A dev tunnel gives us a public HTTPS URL that forwards straight to your machine:

```bash
devtunnel host -p 3978 --allow-anonymous
```

The output includes a line like `Connect via browser: https://abc123-3978.euw.devtunnels.ms`. That host is what we need next.

> **Read the URL from the command output — don't construct it.** This catches people out constantly, because dev tunnel URLs look predictable and are **not** derived from the tunnel name. Copy it from the output, and keep that terminal window open for the rest of the guide: close it and the URL dies with it.

If this is your first time using dev tunnels, you'll need to sign in once first:

```bash
devtunnel user login
```

### Step 0-4. Point the bot at the tunnel

Now we tell the Azure Bot resource where to deliver messages.

1. Go back to your bot in the [Azure portal](https://portal.azure.com).
2. In the left menu, under **Settings**, click **Configuration**.
3. In the **Messaging endpoint** field, enter your tunnel host followed by `/api/messages` — so, for the example above, `https://abc123-3978.euw.devtunnels.ms/api/messages`.
4. Click **Apply** at the top of the blade, and wait for the confirmation notification.

Three things people get wrong here, all of which fail the same silent way — Teams simply never reaches your agent:

- **The `/api/messages` path is required.** The tunnel host on its own isn't an endpoint; the Agents SDK listens on that specific path.
- **It has to be `https`, not `http`.** The Bot Framework will not deliver to an unencrypted endpoint.
- **No trailing slash**, and no port number in the URL — the tunnel already maps to port 3978 on your side.

Or, from the CLI:

```bash
az bot update \
  --resource-group <resource-group> \
  --name <bot-handle> \
  --endpoint "https://<tunnel-host>/api/messages"
```

> **You'll come back to this step.** Every time you restart the dev tunnel you get a new URL, and the messaging endpoint has to be updated to match. When the agent mysteriously stops responding in Teams after a break, this is the first thing to check.

### Step 0-5. Give the agent its bot credentials

The agent needs the app registration's details so it can authenticate the replies it sends back to the channel.

On **.NET**, in `appsettings.json` — note that the client id goes in *two* places, because one validates inbound tokens from Teams and the other authenticates outbound replies:

```jsonc
"TokenValidation": {
  "Audiences": [ "<bot-app-client-id>" ]
},
"Connections": {
  "ServiceConnection": {
    "Settings": {
      "ClientId": "<bot-app-client-id>",
      "TenantId": "<tenant-id>"
    }
  }
}
```

The secret never goes in that file. Put it in user-secrets instead:

```powershell
dotnet user-secrets set "Connections:ServiceConnection:Settings:ClientSecret" "<bot-app-secret>"
```

> Leaving `TokenValidation.Audiences` empty is what puts the .NET starting point into anonymous mode. That's deliberate and useful for the Agents Playground, but it means an agent that works in the Playground and fails in Teams is often just an agent you forgot to fill this in for.

On **Python**, in `.env` (copy it from the committed `.env.example`, which is safe to commit — `.env` itself is gitignored):

```bash
CONNECTIONS__SERVICE_CONNECTION__SETTINGS__CLIENTID=<bot-app-client-id>
CONNECTIONS__SERVICE_CONNECTION__SETTINGS__CLIENTSECRET=<bot-app-secret>
CONNECTIONS__SERVICE_CONNECTION__SETTINGS__TENANTID=<tenant-id>
```

**These are the values to back up before Phase 1.** Copy them somewhere outside the repository now, while they're fresh — this is the backup the warning at the top of the guide was asking for.

### Step 0-6. Configure Azure OpenAI

Next, the agent needs to know which model to reason with.

**This part is required no matter how you authenticate.** It's worth saying explicitly, because the next paragraphs are about credentials and it's easy to assume that being signed in with the Azure CLI is enough. It isn't: signing in only decides *how the agent proves who it is*. The endpoint and deployment name tell it *where to go and what to call*, and they always have to be configured.

On **.NET**, in `appsettings.json`:

```jsonc
"AzureOpenAI": {
  "Endpoint": "https://<your-resource>.openai.azure.com/",
  "Deployment": "gpt-4.1",
  "TenantId": "<tenant that owns the Azure OpenAI resource>"
}
```

On **Python**, in `.env` (copy it from the committed `.env.example`):

```bash
AZURE_OPENAI_ENDPOINT=https://<your-resource>.openai.azure.com
AZURE_OPENAI_DEPLOYMENT=gpt-4.1
AZURE_OPENAI_API_VERSION=2024-10-21
AZURE_OPENAI_TENANT_ID=<tenant that owns the Azure OpenAI resource>
```

> **Don't leave the tenant id out.** Without it, the credential returns a token from whichever tenant you last signed in to, which may not be the one that owns the Azure OpenAI resource, and the service answers `HTTP 400 – Tenant provided in token does not match resource token`. It looks like a code problem and isn't.

Now pick how the agent authenticates to Azure OpenAI. Both starting points support two paths and choose between them at startup with a simple rule: **if an API key is configured, use key auth; if not, use Entra credentials.**

|  | **Path A — Entra credentials** *(default, recommended)* | **Path B — API key** |
| --- | --- | --- |
| What it actually uses | `DefaultAzureCredential` (.NET) or `AzureCliCredential` (Python) locally, and a managed identity once hosted on Azure | A resource key, sent as a bearer secret |
| Extra configuration | None — you just need to be signed in | The key, kept out of tracked files |
| What you need access to | The **Cognitive Services OpenAI User** role on the resource | The resource keys |
| Why you'd pick it | No long-lived secret, and it's the only option in tenants where key auth is disabled by policy | Environments that still depend on keys |

For **Path A**, sign in and make sure no key is set anywhere — including in user-secrets, which are easy to forget:

```bash
az login --tenant <tenant of the Azure OpenAI resource>
```

Once hosted on Azure, .NET picks up the assigned managed identity automatically; Python needs one extra setting, `AZURE_OPENAI_USE_MANAGED_IDENTITY=true`.

For **Path B**, keep the key outside the committed files:

```bash
# .NET
dotnet user-secrets set "AzureOpenAI:ApiKey" "<key>"   # or the AzureOpenAI__ApiKey env var

# Python — in .env, which is gitignored
AZURE_OPENAI_API_KEY=<key>
```

### Step 0-7. Run the agent and sideload it into Teams

Start the agent:

```bash
# .NET
dotnet run

# Python
uv run python -m app.main
```

It listens on `http://localhost:3978`, which is the port the dev tunnel from Step 0-3 is forwarding.

Now we need to get it into Teams. Teams doesn't discover bots on its own — it installs *apps*, and an app is a zip file containing a manifest plus two icons. The starting points ship a script that fills in the manifest placeholders and builds that zip for you:

```powershell
./build-app-package.ps1 -BotId <bot-app-client-id>
```

The only thing you have to supply is `-BotId`, the bot app client id from Step 0-1 — that's what tells Teams which bot to route your messages to.

The manifest also needs a second identifier, the **Teams app id**, which identifies the *app package* rather than the bot. It's unrelated to any Entra identity and doesn't correspond to anything in Azure, so the script generates one for you on the first build and caches it in `teams-app-id.local.json`, next to the script. Every later build reads it back from there.

That caching is the whole point, and it's worth understanding rather than treating as an implementation detail: Teams uses this id to decide whether an upload is an **update to the app you already installed** or a **completely new app**. If it changed on every build, each rebuild would leave you with yet another copy of the agent cluttering your app list. The file matches the repository's `.gitignore` pattern for `*.local.json`, so it stays on your machine and never ends up in a commit.

If you already have a Teams app id — say you're rebuilding a package for an app that's already published — pass it explicitly and the script uses that instead:

```powershell
./build-app-package.ps1 -BotId <bot-app-client-id> -TeamsAppId <existing-teams-app-id>
```

Then sideload the resulting `appPackage.zip`:

1. Open Microsoft Teams and go to **Apps** in the left rail.
2. Click **Manage your apps** at the bottom, then **Upload an app**.
3. Choose **Upload a custom app** and select `appPackage.zip`.
4. Click **Add** on the dialog that appears.

> If **Upload a custom app** isn't there, custom app uploading is disabled for your account — that's the "Teams app upload permission" from the prerequisites, and a Teams administrator has to enable it for you.

Because the manifest declares `copilotAgents.customEngineAgents` and includes `copilot` in the bot's scopes, this same package also surfaces the agent inside Microsoft 365 Copilot.

### Step 0-8. Verify

Message the agent in Teams and ask it something it should be able to answer:

```text
What is Microsoft Entra Conditional Access?
```

You should get an answer with links to Microsoft Learn, because this agent grounds its answers in the Microsoft Learn MCP server rather than answering from the model's own knowledge.

If nothing comes back, the problem is almost always in the plumbing we just built rather than in the agent:

| What you see | Where to look |
| --- | --- |
| No reply at all, and nothing in the agent's console | The messaging endpoint is wrong, or the tunnel died — Steps 0-3 and 0-4 |
| The agent logs a request but Teams shows an error | The bot credentials don't match the app registration — Step 0-5 |
| `401` in the agent's console | `TokenValidation.Audiences` doesn't contain the bot app client id — Step 0-5 |
| The agent replies in the Agents Playground but not in Teams | The Teams channel isn't enabled on the bot — Step 0-2 |
| An error about the Azure OpenAI endpoint or deployment | Step 0-6 |

✅ **Checkpoint.** The agent answers in Teams. There's no Agent 365 anything yet — that starts now.

## Phase 1: Register the agent

In this phase, the agent becomes an object in your tenant rather than just a bot behind an endpoint.

Registration creates two things: a **blueprint**, which is the parent app registration holding the permissions, and an **agent identity**, a child principal of that blueprint. Note that neither of them replaces your bot app registration — as we said at the top, all three have to coexist.

### Step 1-1. Back up your bot credentials

Do this now, before anything else, for the reasons explained in the warning at the top of this guide. These are the values you set in Step 0-5 — the bot app client id, secret and tenant id. The next step will overwrite them, and the secret in particular cannot be recovered afterwards.

### Step 1-2. Run the setup skill

**What you type**

```text
Set up Agent 365 for this agent. It's a custom engine agent hosted in Teams
with its own bot registration — not an AI Teammate. Use the OBO auth mode.
```

**What the skill does**

`a365-setup` verifies the prerequisites and your Azure identity, then asks the two questions that shape everything downstream:

| Question | Your answer for this scenario | Why |
| --- | --- | --- |
| Agent kind? | **Agent (Non AI Teammate)** | A human drives it, and it has its own bot registration |
| Auth mode? | **`obo`** | Attribution follows the Teams user who sent the message |

It then hands off to `make-a365-agent`, which performs the registration.

> ⚠️ **There's a genuine gap in the skills here,** `instrument-observability` only offers you two auth modes: `obo`, which means the *agentic* on-behalf-of path with its MSAL/FMI token chain, and `s2s`. Neither is exactly "custom engine agent using OBO through the Bot Framework". Answer `obo`, because it's the closer of the two — but **do not accept the token code it generates without checking it against Phase 2 below**, because the chain it writes is one you don't need on this path and that won't work here. The details are in [Known Skill Gaps](../../03-references/Known-Skill-Gaps.md).

**Behind the scenes**

```bash
a365 setup all --agent-name "my-agent" --m365 --dry-run   # preview first
a365 setup all --agent-name "my-agent" --m365             # apply
a365 setup permissions bot                                # required after --m365
```

Two notes on those commands. The `--m365` flag is what registers the agent for Teams and Microsoft 365 Copilot, so it's not optional in this scenario. And `a365 setup permissions bot` is a **required follow-up** to it — it's very easy to miss, because nothing fails immediately when you skip it. Things fail later, somewhere else, in a way that gives you no clue that this is the cause.

**How to verify**

```bash
cat a365.generated.config.json
```

Confirm there's an `agentBlueprintId` in there, then go to [Entra](https://entra.microsoft.com) → **App registrations** and check that the blueprint is listed.

> ⚠️ If you're not a Global Administrator, the setup summary printed a consent snippet. Until someone runs it, the permissions exist but are not granted, and Phase 2 fails with a consent error.

### Step 1-3. Restore your bot credentials

Open your configuration and compare it against the backup you took in Step 1-1. If `a365 setup all` replaced the bot client id or secret with the blueprint's, **put the originals back**:

```powershell
# Python — diff against the backup
Compare-Object (Get-Content .env) (Get-Content "$env:USERPROFILE\bot-credentials-backup.env")
```

Then **restart the agent** and message it in Teams.

The restart is the part that matters. Testing without one proves nothing, because the process still holds the old, correct values in memory — which is exactly the illusion that lets this problem hide for days. Restart the agent, message it, and only then trust that it works.

✅ **Checkpoint — and a good place to stop.** The agent is registered and governed, and it still answers in Teams.

## Phase 2: Observability

Now we make the agent report what it does. By the end of this phase, every message it handles produces telemetry attributed to the Teams user who sent it.

Here's the shape of the phase before we start. Unlike the web app scenario, we're not going to write a token chain: we're going to configure an OAuth connection on the Azure Bot resource, and let the Bot Framework Token Service do the on-behalf-of exchange for us. The code we write is small — one call to get a token, a baggage scope, and the semantic spans. The configuration around it is where the care is needed.

### Step 2-1. Create the OAuth connection

**Do this before you touch any code.** It's what makes everything afterwards simple, and it's where this scenario's real work lives.

```bash
az bot authsetting create -g <resource-group> -n <azure-bot-name> \
  -c oboConnectionProfile \
  --client-id <bot-app-client-id> --client-secret <bot-app-secret> \
  --service AadV2 \
  --provider-scope-string \
    "api://9b975845-388f-4429-889e-eab1ef63949c/Agent365.Observability.OtelWrite" \
  --parameters tenantID=<tenant-id> tokenExchangeUrl=api://botid-<bot-app-client-id>
```

That's a dense command, so let's go through the three arguments that are easy to get wrong:

- **`--provider-scope-string` must be a *named* scope**, exactly as written above. This is the one people get wrong most often, because the default is `api://botid-…/defaultScopes` and it looks harmless. It isn't: a delegated token carries *scopes*, not *roles*, so leaving the default in place produces `401 InvalidAudience` when the exporter tries to use the token.
- **`tokenExchangeUrl`** is what keeps Teams SSO silent, meaning the user isn't prompted to sign in again. The Teams manifest declares a single `webApplicationInfo.resource`, and this connection exchanges that SSO token for its own.
- **`--client-id` is the bot app registration, not the blueprint.** This is what makes the `azp` claim on the resulting token correct, which matters enormously in Step 2-4.

> The resource id `9b975845-…` and the scope name are preview-era values. Re-verify them against the current documentation before assuming they're still right.

### Step 2-2. Run the observability skill

**What you type**

```text
Instrument this agent with Agent 365 observability. It's a custom engine agent
in Teams using OBO. The observability token comes from an Azure Bot OAuth
connection called oboConnectionProfile — don't build an MSAL or FMI token chain.
```

Being this explicit is not optional. Left to its own defaults, the skill will generate a full MSAL/FMI token chain — the one from the web app scenario — which you don't need here and which will not work on this path. Telling it where the token comes from up front saves you from reviewing and deleting a lot of generated code.

**What the skill does**

It installs the distro, wires it into your entry point, adds a baggage scope, implements a token resolver, adds the semantic scopes, updates the configuration, then builds and smoke-tests the result.

Review the token code it produces against Steps 2-4 and 2-5 before accepting it.

The rest of this phase explains what those changes are. If you ran the skill you don't need to make them by hand — read on as an explanation of the code you now have, and as a checklist when something doesn't work.

### Step 2-3. Wire the exporter into the entry point

On **.NET**, in `Program.cs`. Pay attention to the order of registration here, because it's not cosmetic:

```csharp
var observabilityTokenStore = new ObservabilityTokenStore();
builder.Services.AddSingleton(observabilityTokenStore);

// Registered BEFORE UseMicrosoftOpenTelemetry so this processor sits ahead of the
// A365 export processor: OnEnd runs in registration order, and the identity has to be
// on the span before the exporter reads it.
builder.Services.AddOpenTelemetry()
    .WithTracing(t => t.AddProcessor(new BaggageBackfillProcessor()));

builder.UseMicrosoftOpenTelemetry(o =>
{
    o.Exporters = ExportTarget.Agent365;
    // Exporting to Agent 365 alone suppresses infrastructure instrumentation.
    o.Instrumentation.EnableAspNetCoreInstrumentation = true;
    o.Instrumentation.EnableHttpClientInstrumentation = true;
    o.Instrumentation.EnableAzureSdkInstrumentation = true;
});
```

> **Registration order is load-bearing in .NET.** The backfill processor has to be registered *before* `UseMicrosoftOpenTelemetry`, because `OnEnd` runs in registration order and the identity has to be attached to the span before the exporter reads it. Get the order wrong and the inference span — the prompt, the system instructions and the completion, in other words the interesting part — is dropped. The agent still answers, Defender still shows the parent span, and the LLM call is simply invisible.

On **Python**, and this has to run before any LangChain or Azure OpenAI import:

```python
use_microsoft_opentelemetry(
    enable_a365=True,
    a365_enable_observability_exporter=True,
    a365_token_resolver=token_store.get,
    # The delegated route. Its S2S counterpart takes application tokens only and
    # refuses a delegated one - the two are not interchangeable.
    a365_use_s2s_endpoint=False,
    enable_sensitive_data=True,
    disable_metrics=True,
)
```

`a365_use_s2s_endpoint=False` is written out explicitly rather than left to the default, and that's deliberate: it's a reminder that the S2S endpoint accepts application tokens *only* and will reject the delegated token we're about to obtain. The two routes are not interchangeable, and choosing the wrong one gives you an authorization error rather than anything that hints at the real cause.

### Step 2-4. Get the observability agent id right

If you read only one step of this guide, make it this one.

Three separate values have to be identical:

```text
gen_ai.agent.id  ==  the token's azp  ==  the token store key
```

And for a custom engine agent, all three are the bot app registration's client id, not the agent identity and not the blueprint. If they don't match, the export fails with `HTTP 403`.

This is counter-intuitive, which is exactly why it's worth calling out. You've just registered an agent identity and a blueprint, so those feel like the natural candidates. But the token comes from the Bot Framework OAuth connection we created in Step 2-1, and that connection was configured with the bot app's client id — so the bot app is what the token says it is, and the service checks.

The safest way to get it right is to read the value from the SDK's own connection settings rather than duplicating it in a second place where the two can drift apart:

```csharp
var observabilityAgentId = builder.Configuration["Connections:BotConnection:Settings:ClientId"];
```

```python
@property
def observability_agent_id(self) -> str:
    return self.bot_client_id   # from CONNECTIONS__SERVICE_CONNECTION__SETTINGS__CLIENTID
```

This wasn't deduced from documentation, incidentally — it was tested against the live service with one token and three candidate ids:

| Id used in the export URL | Result |
| --- | --- |
| Agent identity | `403` |
| Blueprint | `403` |
| **Bot app registration** | `415` — authorised, and merely the wrong content type for the probe |

A `415` there is a success: it means the request got past authorization.

### Step 2-5. Get the token — and it really is one call

Here's the entire token acquisition for this scenario:

```python
token_response = await AUTHORIZATION.get_token(context, OBO_AUTH_HANDLER)
token_store.set(settings.observability_agent_id, settings.a365_tenant_id, token)
```

That's it. There's no MSAL, no `fmi_path`, no blueprint secret and no two hops. The connection we created in Step 2-1 is already scoped to the Observability API, so the Bot Framework Token Service performs the on-behalf-of exchange internally and hands back a finished token. This is the payoff for all that configuration work.

Two practical details about *when* and *how* to call it.

Call it **at the start of the turn**, before you generate the answer, so the token is already sitting in the store when the first spans flush. And swallow any failure, because losing traces is never a good reason to fail the user's question:

```python
if OBSERVABILITY_ENABLED:
    await _publish_observability_token(context)
```

### Step 2-6. Open a baggage scope, and make the ids agree

Baggage is how OpenTelemetry carries contextual values alongside the execution context, and Agent 365 uses it to carry the identity dimensions it partitions telemetry on — tenant, agent, user, conversation. Spans emitted outside an active baggage scope are dropped outright.

```python
BaggageBuilder()
    .tenant_id(settings.a365_tenant_id)
    # Must match AgentDetails: auto-instrumented spans take gen_ai.agent.id from
    # baggage, and the exporter partitions on it. If the two disagree the turn splits
    # into two identity groups and only one has a token.
    .agent_id(settings.observability_agent_id)
    .agent_name(...)
    .agent_blueprint_id(settings.a365_blueprint_id)
    .conversation_id(conversation_id)
    .session_id(conversation_id)
    .user_id(user["id"]).user_name(user["name"]).user_email(user["email"])
    .channel_name("msteams")
    .build()
```

Two things here are easy to get wrong:

- **The channel name is `msteams`, not `web`.** The exporter records whatever you give it verbatim, so a wrong value doesn't fail — it just quietly misreports where the activity came from.
- **The agent id in baggage must equal the one in `AgentDetails`.** Use a single source value for both. If they disagree, the turn is split into *two* identity groups, only one of which has a token, and you end up with half your spans arriving and half disappearing. That's a genuinely confusing symptom, and Step 2-9 tells you how to spot it.

### Step 2-7. Work out who the caller is

This is simpler than in the web app scenario. There, we had a signed-in principal to inspect; here there isn't one, because the user never signs in to your app — they message it through Teams.

Instead, read the user off the incoming activity: their `id`, `name` and `email`. The channel tells you who sent the message, and that's the identity the activity gets attributed to.

### Step 2-8. Wrap the turn in the semantic scopes

Agent 365 doesn't accept arbitrary spans. It only ingests those whose `gen_ai.operation.name` is one of `invoke_agent`, `chat`, `execute_tool` or `output_messages`, and drops everything else span by span. The one that matters most is `invoke_agent`, because it becomes the root span of the turn and it's the only span the Microsoft 365 admin center ingests.

```python
InvokeAgentScope.start(
    Request(
        content=message,
        session_id=conversation_id,
        conversation_id=conversation_id,
        channel=Channel(name="msteams"),
    ),
    InvokeAgentScopeDetails(endpoint=endpoint),
    build_agent_details(settings),
    build_caller_details(user),
)
```

> **Session, conversation and channel have to be on the `Request` object, not only in baggage.** This is a subtle one, because baggage *does* land on the span tags, so the information looks like it's there. But the exported `invoke_agent` payload is built from this `Request` object — omit them and you export a span that's accepted and yet shows no run context at all.

If you're on **Python with LangChain**, there's one more thing to do. Turn off the enrichers you aren't using:

```python
instrumentation_options={
    "openai_agents": {"enabled": False},
    "agent_framework": {"enabled": False},
    "semantic_kernel": {"enabled": False},
}
```

The reason is a registration race. The Agent Framework and Semantic Kernel enrichers register first, and their presence makes the distro skip the LangChain enricher — which is the one that actually maps this agent's messages and conversation id into the shape Agent 365 expects. So you end up with spans that are technically fine and semantically empty. `openai_agents` is disabled for a less serious reason: it isn't used here, and leaving it on makes the distro log an import traceback on every start.

### Step 2-9. Verify that telemetry is actually leaving

Before going anywhere near Defender, let's confirm from the agent's own logs that spans are being exported:

```powershell
$env:OTEL_LOG_LEVEL="INFO"
$env:A365_OBSERVABILITY_LOG_LEVEL="debug"
```

Send a message from Teams and read the output. Four things need to be true:

- `Partitioned into 1 identity groups` — **not 0, and not 2**
- there's an `invoke_agent` span, and it's a **root** span
- the export returns `HTTP 200`
- the agent id in the export URL is the **bot app client id**

Those two failure numbers mean different things, and knowing which is which saves a lot of time. **Zero** means there was no baggage scope active around the turn. **Two** means baggage and `AgentDetails` disagree about the agent id — go back to Step 2-6.

✅ **Checkpoint — a good place to stop.** The agent is registered and observable.

## Phase 3: Work IQ

With observability working, we can give the agent access to Microsoft 365 data — Mail, Calendar and more — through the Work IQ MCP servers, using the permissions of the Teams user it's acting for.

**What you type**

```text
Add Work IQ tools to this agent. I want Mail and Calendar.
```

`add-workiq-tools` runs `a365 develop list-available` to show you the catalog, adds the servers you choose with `a365 develop add-mcp-servers`, writes a `ToolingManifest.json`, and wires a registration service into your agent.

> ⚠️ **A known service-side issue on this path.** While building the reference agents, this returned a **500 from `/agents/v2/{auid}/mcpServers`** for this scenario. Importantly, it failed for a completely made-up AUID too — which tells you the route itself was broken rather than your configuration. So if you hit a 500 here, try it with a nonsense AUID before you start debugging your own wiring, and treat Phase 3 as optional on this scenario.

One rule to follow: **register each tool exactly once**. A tool registered twice is called twice, with whatever real-world consequences that implies.

> That said, be careful about what looks like a duplicate. In the Agent 365 map, a single tool call can appear as **two nodes** — one keyed by the MCP server, one by the tool name — simply because Agent 365 records `ExecuteToolByMCPServer` and `ExecuteToolBySDK` as distinct action types. Before you go "fixing" a duplicate, check the real side effect: if you sent one email, you have one tool call, whatever the map shows.

## Phase 4: Verify it end to end

Everything so far proves the agent *emits* telemetry. This phase proves it *arrives*, which as we've seen is a different question entirely.

### Step 4-1. Produce some activity

Send the agent several messages — there's a set in [4.Sample-prompts.md](4.Sample-prompts.md) if you want a starting point. Include at least one that calls a tool, and if you can, send them from two different Teams users, so you can check that attribution follows the right person.

### Step 4-2. Check Microsoft Defender

Go to [Advanced hunting](https://security.microsoft.com) in the Defender portal and query the `CloudAppEvents` table. Defender accepts every operation type, so this is where you should see the fullest picture — `InvokeAgent`, `InferenceCall` and `ExecuteToolByMCPServer` rows. Here's a query to start from:

```sql
CloudAppEvents
| where ActionType in ("InvokeAgent", "InferenceCall", "ExecuteToolBySDK", "ExecuteToolByGateway", "ExecuteToolByMCPServer")
| where RawEventData.TargetAgentName == "your-agent-name" or RawEventData.AgentName == "your-agent-name"
| order by Timestamp desc
```

Defender has to index the events, so give it around five minutes before concluding something is wrong.

### Step 4-3. Check the Microsoft 365 admin center

Go to https://admin.cloud.microsoft, find your agent, and open its activity.

Remember that this surface behaves differently from Defender: it ingests `invoke_agent` rows only, and reads the caller identity from that one span. That difference is useful, because comparing the two portals tells you exactly where a problem lives:

| What you see | Where the problem is |
| --- | --- |
| Nothing anywhere | The token, the agent id, or the baggage scope — Steps 2-4 to 2-6 |
| `403` on the export | `gen_ai.agent.id` isn't the bot app client id — Step 2-4 |
| `401 InvalidAudience` | The OAuth connection is on `/.default` instead of the named scope — Step 2-1 |
| Half the spans missing | Baggage and `AgentDetails` disagree, so you have two identity groups — Step 2-6 |
| Defender ✅, admin center ❌ | Your `invoke_agent` span, usually the caller — Step 2-7 |
| The agent stopped answering after a restart | `a365 setup all` overwrote the bot credentials — Step 1-3 |

### Step 4-4. Optional — let a skill review the code

```text
Validate the Agent 365 observability code in this project.
```

`a365-code-validator` checks the instrumentation and reports problems without changing anything.

> ⚠️ **Expect one false positive on this path.** The validator flags `gen_ai.agent.id` not matching the agent identity as a blocker. On a custom engine agent that is **correct behaviour** — as we established in Step 2-4, it has to be the bot app client id. Don't let the validator talk you into "fixing" it.

## Troubleshooting

| Symptom | Likely cause |
| --- | --- |
| `403` on the export route | The agent id, the token's `azp` and the store key don't all match — Step 2-4 |
| `401 InvalidAudience` | The OAuth connection scope is wrong — Step 2-1 |
| `AADSTS82001` | You tried to use the blueprint as the bot. They must stay separate |
| `Partitioned into 0 identity groups` | No baggage scope around the turn — Step 2-6 |
| `Partitioned into 2 identity groups` | Baggage and `AgentDetails` disagree on the agent id — Step 2-6 |
| Inference span missing (.NET) | The backfill processor was registered after `UseMicrosoftOpenTelemetry` — Step 2-3 |
| No `chat` spans (Python) | The distro was initialised after LangChain was imported — Step 2-3 |
| `HTTP 200` but nothing lands anywhere | No user in the tenant holds an Agent 365 licence |
| Teams stopped reaching the agent | The dev tunnel URL changed and the messaging endpoint wasn't updated — Step 0-4 — or the bot credentials were overwritten — Step 1-3 |

## Wrapping up

We started with a Teams agent that worked but told nobody anything, and we ended with one that's registered in the tenant, reports every turn to Defender and the admin center attributed to the Teams user who sent the message, and can reach Microsoft 365 data under that user's permissions.

The thing worth remembering about this scenario is how little of the work was code. The two-hop token chain we'd have written by hand in a web app was replaced by a single OAuth connection on the Azure Bot resource and one call to `get_token`. In exchange, the difficulty moved into configuration: the named scope on that connection, the `--m365` follow-up command, the agent id that has to be the bot app rather than the agent identity, and the bot credentials that setup quietly overwrites. None of those produce a compiler error. All of them produce an HTTP status code and a puzzled afternoon — which is why we walked through each one rather than just listing the commands.

If you want to compare your result with a finished implementation, both stacks are available: the [.NET agent](https://github.com/qmatteoq/agent365-demos/tree/main/dotnet-agent-teams) and the [Python agent](https://github.com/qmatteoq/agent365-demos/tree/main/python-agent-teams).
