# Step-by-Step Guide — AI Teammate with Agent Identity

> **Scenario**: Publishing an agent as a Microsoft Agent 365 AI Teammate
> **Platform**: Microsoft Agent 365 · Microsoft Entra Agent ID · Teams · OpenTelemetry
> **Stack**: .NET Agent Framework
> **Target Readers**: Agent developers, tenant administrators
> **Last Updated**: February 2026

## Overview

This runbook publishes a Teams-hosted agent as an **AI Teammate** — an agent with its own identity
in your tenant, rather than one borrowing a user's.

It is the most advanced scenario in this repo, and the one with the most friction. Some of that
friction is deliberate (admin approval), and some is preview-era rough edges. Both are documented
here so neither surprises you.

| Phase | You get | Time |
| --- | --- | --- |
| 0 — Prerequisites | A working Teams agent and the tooling installed | 30–60 min |
| 1 — Registration and publishing | The agent published, approved, and installable | 60 min **+ admin wait** |
| 2 — Observability | Activity in Defender and the admin center | 60–90 min |
| 3 — Work IQ | Microsoft 365 data access | 30–60 min |
| 4 — Verify | Proof it works end to end | 30 min |

> ⏳ **Phase 1 contains a wait you don't control.** The agent instance request is approved by a
> human tenant admin. Line that up before you start, or you'll be blocked mid-runbook.

Where you'll be working:

| Location | URL | Task |
| --- | --- | --- |
| Your terminal | — | Skills, CLI, builds, dev tunnel |
| Teams Developer Portal | https://dev.teams.microsoft.com | Agent type and notification URL |
| Microsoft 365 admin center | https://admin.cloud.microsoft | Package upload, agent inventory |
| Admin approval queue | https://admin.cloud.microsoft/#/agents/all/requested | Approving the instance request |
| Microsoft Defender | https://security.microsoft.com | Advanced hunting |

### License Requirements

| Requirement | Notes |
| --- | --- |
| Microsoft 365 tenant | With Agent 365 enabled, and Teams |
| Agent 365 licence | **At least one user must hold one**, or telemetry is silently discarded |

### Access and Permissions

| Permission | Who | Used for |
| --- | --- | --- |
| Application Developer or higher | You | App registrations |
| **Global Administrator** | You *or* a colleague | Consent **and** approving the instance request |
| Teams app upload | You | Sideloading |

> **Identify your approving admin before Phase 1.** This is the most common place people stall.

### Naming constraint — decide now

**Your agent name must be 20 characters or fewer.**

The CLI appends `" Blueprint"` to it, and the Teams manifest's `name.short` caps at 30. A 21+
character name fails late, after several other steps have already run.

## Phase 0: Get the agent working in Teams first

### Step 0-1. Tunnel, run, sideload

```bash
devtunnel host -p 3978 --allow-anonymous
```

> Read the tunnel URL from the output. It is **not** derived from the tunnel name — never guess it.

```bash
dotnet run
```

Point the bot's messaging endpoint at `https://<tunnel-host>/api/messages`, sideload the app
package, and confirm the agent answers in Teams.

✅ **Checkpoint:** it answers in Teams. No Agent 365 anything yet.

## Phase 1: Register and publish as an AI Teammate

### Step 1-1. Run the setup skill

**What you type**

```text
Set up Agent 365 for this agent as an AI Teammate. It should act under its
own identity, not on behalf of the signed-in user.
```

**What the skill does**

`a365-setup` checks prerequisites, then — because this is an AI Teammate — hands off to
`make-ai-teammate` rather than `make-a365-agent`. That skill owns the whole flow: code generation,
`a365.config.json`, `a365 setup all`, manifest review, `a365 publish`, the Teams Developer Portal
verification, and the instance request.

> **You are not asked for an auth mode.** The AI Teammate identity model is fixed at
> `agentic-user`, so there is no `obo` / `s2s` decision. Passing `--authmode` alongside
> `--aiteammate` is **rejected**.

**Behind the scenes**

```bash
a365 setup all --agent-name "my-teammate" --aiteammate --m365
```

`--m365` is **always required** for an AI Teammate — it's what registers the agent in the
Microsoft 365 admin center.

**How to verify**

```bash
node -e "console.log(require('./a365.generated.config.json').agentBlueprintId)"
```

⚠️ If you weren't Global Admin, run the consent snippet from the setup summary before continuing.

### Step 1-2. Publish

```bash
a365 publish
```

Then upload the generated package at the Microsoft 365 admin center.

> **The CLI owns `manifest.json` and the bot endpoint registration. Do not hand-edit either.**
> Regenerate through the CLI instead — hand edits are overwritten and cause confusing mismatches.

### Step 1-3. Verify in the Teams Developer Portal

Go to
`https://dev.teams.microsoft.com/tools/agent-blueprint/<agentBlueprintId>/configuration` and check:

| Field | Expected |
| --- | --- |
| Agent Type | **API Based** |
| Notification URL | your `messagingEndpoint` |

The notification URL is auto-registered by
`a365 setup blueprint --update-endpoint --m365` on supported tenants. Set it manually **only** if
the CLI reported that automated registration wasn't available.

> When updating the endpoint later — a new dev tunnel, for instance — **remember `--m365`**.
> Without it the Teams Graph re-registration is skipped **silently**, and Teams keeps routing to
> the old URL.

### Step 1-4. Request an instance, and wait

Request an agent instance, then wait for a tenant admin to approve it at:

```text
https://admin.cloud.microsoft/#/agents/all/requested
```

⏳ **This is asynchronous and you cannot do it yourself unless you're that admin.** Nothing in
Phase 2 can be verified end to end until it completes.

Reference:
[Create an agent instance](https://learn.microsoft.com/microsoft-agent-365/developer/create-instance).

### Step 1-5. Install and verify

Install the teammate in Teams, message it, and confirm it still answers.

✅ **Checkpoint:** the agent is published, approved, and exists as its own identity.

## Phase 2: Observability

### Step 2-1. Run the observability skill

**What you type**

```text
Instrument this AI Teammate with Agent 365 observability.
```

The skill detects `agentType = ai-teammate` and **skips the auth-mode question entirely** — the
identity model is unambiguous. This is the one scenario where the skill's defaults are exactly
right, so there's less to second-guess here than in the other two.

### Step 2-2. Register the token cache yourself

**Do this first, because without it the host will not start.**

```csharp
var agenticTokenCache = new AgenticTokenCache();
builder.Services.AddSingleton<IExporterTokenCache<AgenticTokenStruct>>(agenticTokenCache);
```

> ⚠️ **The skill's reference documentation says `UseMicrosoftOpenTelemetry` registers this. It does
> not** — verified against `Microsoft.OpenTelemetry` 1.0.7. Omit it and startup fails with a
> dependency-injection error.
>
> This is a hard, immediate failure rather than a silent gap, so you'll know at once. Check whether
> it's still true in the version you're on before working around it.

### Step 2-3. Wire the exporter

```csharp
// Registered BEFORE UseMicrosoftOpenTelemetry: OnEnd runs in registration order, and the
// identity has to be on the span before the exporter reads it.
builder.Services.AddOpenTelemetry()
    .WithTracing(tracing => tracing.AddProcessor(new BaggageBackfillProcessor()));

builder.UseMicrosoftOpenTelemetry(o =>
{
    // Unconditional: traces must reach Agent 365 even during local testing, because that
    // is what makes them visible in Defender and admin center activity.
    o.Exporters = isLocalRun
        ? ExportTarget.Agent365 | ExportTarget.Console
        : ExportTarget.Agent365;

    o.Instrumentation.EnableMetrics = false;

    // Agent365-only export suppresses infrastructure instrumentation - turn back on the
    // parts that matter so outbound calls appear in the trace.
    o.Instrumentation.EnableAspNetCoreInstrumentation = true;
    o.Instrumentation.EnableHttpClientInstrumentation = true;
    o.Instrumentation.EnableAzureSdkInstrumentation = true;

    o.Agent365.TokenResolver = (agentId, tenantId) =>
        agenticTokenCache.GetObservabilityToken(agentId, tenantId);

    // The agentic-user path posts to /observability/ - leave UseS2SEndpoint at its default.
});
```

Two things worth keeping as written:

- **Export to Agent 365 unconditionally.** The console exporter is *additional* for local
  diagnosis; it never replaces the Agent 365 one. Otherwise local testing produces nothing to check.
- **Leave `UseS2SEndpoint` at its default.** The agentic-user path uses the delegated route.

### Step 2-4. Instrument the chat client

```csharp
return azureClient.GetChatClient(aoaiDeployment)
    .AsIChatClient()
    .AsBuilder()
    .UseFunctionInvocation()                                    // ExecuteToolBySDK spans
    .UseOpenTelemetry(configure: c => c.EnableSensitiveData = true)  // gen_ai.* spans
    .Build();
```

Without these, the agent span has **no LLM or tool children** in Defender — you get an invocation
record with nothing inside it.

### Step 2-5. Resolve the agent id — and handle non-agentic turns

```csharp
var isAgentic = turnContext.Activity.IsAgenticRequest();
var authHandlerName = isAgentic ? _agenticAuthHandlerName : _oboAuthHandlerName;

string? resolvedAgentId = null;
if (isAgentic)
{
    // The AI Teammate acts as itself, so the agent id is the agentic instance id from
    // the activity - not anything decoded from a user token.
    resolvedAgentId = turnContext.Activity.GetAgenticInstanceId();
}
else if (!string.IsNullOrEmpty(authHandlerName))
{
    var authToken = await UserAuthorization.GetTurnTokenAsync(turnContext, authHandlerName, ...);
    if (!string.IsNullOrEmpty(authToken))
        resolvedAgentId = Utility.ResolveAgentIdentity(turnContext, authToken);
}
```

When no identity resolves, **answer the question anyway** and skip observability for that turn.

### Step 2-6. Baggage — order matters

```csharp
using IDisposable? baggageScope = hasObservabilityIdentity
    ? new BaggageBuilder()
        .FromTurnContext(turnContext)   // user.id, user.name, channel, conversation
        .TenantId(resolvedTenantId!)
        .AgentId(resolvedAgentId!)      // chained AFTER, so it wins
        .AgentName(baggageConfig["AgentName"] ?? "LearnTeammateAgent")
        .AgentBlueprintId(baggageConfig["AgentBlueprintId"] ?? string.Empty)
        .ConversationId(conversationId)
        .SessionId(conversationId)
        .Build()
    : null;
```

> **`FromTurnContext` also writes `gen_ai.agent.id`, from `Recipient.AgenticAppId`.** Chain your
> explicit values *after* it. `BaggageBuilder` keeps one dictionary and the last `Set` wins.
> Reverse the order and the agent id silently reverts — most visibly wrong on email-triggered turns.

Blueprint id and session are **not** supplied by `FromTurnContext` — the activity carries neither.

### Step 2-7. Register the deferred token

```csharp
_tokenCache?.RegisterObservability(
    resolvedAgentId!,
    resolvedTenantId!,
    new AgenticTokenStruct(
        userAuthorization: UserAuthorization,
        turnContext: turnContext,
        authHandlerName: authHandlerName ?? string.Empty),
    EnvironmentUtils.GetObservabilityAuthenticationScope());
```

You are registering **the means to get a token**, not a token. The cache resolves it when the
exporter's resolver asks. Wrap it in a `try`/`catch` and log failures — a lost trace shouldn't
fail the turn.

### Step 2-8. Open the invoke scope

```csharp
var scope = InvokeAgentScope.Start(
    request: new Request(
        content: question,
        sessionId: conversationId,
        channel: new Channel(turnContext.Activity?.ChannelId ?? "msteams"),
        conversationId: conversationId),
    scopeDetails: new InvokeAgentScopeDetails(endpoint: endpointUri),
    agentDetails: agentDetails,
    callerDetails: callerDetails);

scope.RecordInputMessages([question]);
```

> Without this scope, Advanced Hunting shows only **orphan inference and tool rows** — and the
> admin center shows nothing at all, because `invoke_agent` is the only operation it ingests.

Build `endpointUri` from the blueprint **GUID** under the reserved `.invalid` TLD. Slugifying a
free-form display name risks `UriFormatException`.

### Step 2-9. Make local runs work

Two quirks, both from the same root cause:

```csharp
// The A365 Tooling SDK picks DevMcpTokenProvider - which demands a hand-pasted BEARER_TOKEN -
// when ASPNETCORE_ENVIRONMENT is exactly "Development". So exercising the real agentic path
// locally means running as Production, with a separate signal for "is this local?".
var isLocalRun = !string.Equals(
    Environment.GetEnvironmentVariable("A365_LOCAL_RUN"), "false", StringComparison.OrdinalIgnoreCase);

// CreateBuilder only adds user-secrets in Development, and this agent runs as Production.
// Without this the connection is built with an empty ClientSecret and every turn fails with
// "Failed to create authentication provider for connection name ''".
if (isLocalRun)
{
    builder.Configuration.AddUserSecrets(typeof(Program).Assembly, optional: true);
}
```

Keep "is this local?" and "is this Development?" as **separate signals**. They diverge here, and
collapsing them breaks either the token provider or the secrets.

### Step 2-10. Verify export

```powershell
$env:OTEL_LOG_LEVEL="INFO"
$env:A365_OBSERVABILITY_LOG_LEVEL="debug"
```

Message the teammate, then confirm:

- the host **started** (if not, see Step 2-2)
- a root `invoke_agent` span, with inference and tool spans **as children**
- the agent id is the **agentic instance id**
- `HTTP 200` on the export

✅ **Checkpoint — you can stop here.**

## Phase 3: Work IQ

```text
Add Work IQ tools to this teammate. I want Mail and Calendar.
```

`add-workiq-tools` runs `a365 develop list-available` and `a365 develop add-mcp-servers`, writes
`ToolingManifest.json`, and wires a registration service.

> ⚠️ **Possible version conflict.** In the reference agent, the SDK's
> `McpToolRegistrationService` / `McpToolServerConfigurationService` are built against
> `ModelContextProtocol.Core 0.2.0-preview.3` and throw `TypeLoadException` under the `1.3.0` the
> project needs. The workaround was to **not register them** and connect to the servers in
> `ToolingManifest.json` directly.
>
> Check your package versions before assuming you need the workaround — this may well be fixed in
> the version you have.

Register each tool **exactly once**. A tool registered twice is called twice.

> In the Agent 365 map, one tool call can appear as **two nodes** — one keyed by the MCP server,
> one by the tool name — because `ExecuteToolByMCPServer` and `ExecuteToolBySDK` are distinct
> action types. Verify the real side effect (exactly one email sent) before "fixing" it.

## Phase 4: Verify end to end

### Step 4-1. Produce activity

Work through [4.Sample-prompts.md](4.Sample-prompts.md), including a tool call.

### Step 4-2. Check Defender

[Advanced hunting](https://security.microsoft.com) → `CloudAppEvents`. Expect `InvokeAgent`,
`InferenceCall` and `ExecuteTool*` rows, with the agent as the acting identity. ~5 minutes.

### Step 4-3. Check the Microsoft 365 admin center

https://admin.cloud.microsoft → your agent → activity. Confirm activity attributes to the
**agent**, and rolls up to the blueprint.

| Symptom | Where the problem is |
| --- | --- |
| Host won't start | Token cache not registered — Step 2-2 |
| `Failed to create authentication provider for connection name ''` | User-secrets not loaded in Production — Step 2-9 |
| Prompted for a `BEARER_TOKEN` locally | Running as `Development` — Step 2-9 |
| Orphan inference/tool rows, no parent | No `InvokeAgentScope` — Step 2-8 |
| Agent span with no children | Chat client not instrumented — Step 2-4 |
| Wrong agent id, especially on email turns | Baggage chaining order — Step 2-6 |
| Inference span missing entirely | Backfill processor registered too late — Step 2-3 |
| Teams stopped reaching the agent | Endpoint updated without `--m365` — Step 1-3 |
| `HTTP 200` but nothing lands | No user in the tenant holds an Agent 365 licence |

### Step 4-4. Optional — validate the code

```text
Validate the Agent 365 observability code in this project.
```

This scenario is the validator's best fit — identity binding genuinely should be the agent's own.
Findings here are more likely to be real than in the other two scenarios.

✅ **Done.** The agent is a governed principal in your tenant, observable and attributable as
itself.
